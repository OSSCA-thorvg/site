## 이슈 요약

현재 stencil batching은 새 shape의 bounding box가 batch 안의 어떤 bounding box와도 겹치지 않을 때만 병합한다. 이는 안전하지만 concave shape, hole이 있는 ring, 떨어진 subpath, 회전 stroke처럼 실제로 그려지는 영역보다 AABB가 큰 경우 false positive를 만든다. 실제 픽셀은 겹치지 않아도 batch가 끊기므로 draw call 절감 효과가 낮아진다.

단순히 AABB 교차 검사를 path 교차 검사로 바꾸면 안 된다. 같은 bounding box가 stencil 결과를 color로 덮는 cover geometry에도 쓰이기 때문이다. shape의 실제 영역이 분리되어 있어도 큰 cover가 다른 shape의 stencil 픽셀을 통과하고 stencil operation으로 그 값을 바꾸면 잘못된 색이나 누락이 생길 수 있다.

## main 코드 조사

현재 `main`의 GL 구현에서 [`prepare()`](https://github.com/thorvg/thorvg/blob/df31fd1b59a00ffb0811837c9753d9cb5766ac6d/src/renderer/gpu_engine/gl/tvgGlStencilCoverBatch.cpp#L133-L170)는 fill/stroke bounds를 transform하고 view bounds로 잘라 `geometryBounds`를 만든다. 동시에 원래 fill/stroke `bbox`로 [두 triangle짜리 cover rectangle](https://github.com/thorvg/thorvg/blob/df31fd1b59a00ffb0811837c9753d9cb5766ac6d/src/renderer/gpu_engine/gl/tvgGlStencilCoverBatch.cpp#L54-L79)을 만든다.

[`intersects()`](https://github.com/thorvg/thorvg/blob/df31fd1b59a00ffb0811837c9753d9cb5766ac6d/src/renderer/gpu_engine/gl/tvgGlStencilCoverBatch.cpp#L173-L185)는 x 또는 y 기준으로 정렬된 기존 `RenderRegion` 목록을 훑어 새 AABB와 교차하는지 검사한다. [`mergeable()`](https://github.com/thorvg/thorvg/blob/df31fd1b59a00ffb0811837c9753d9cb5766ac6d/src/renderer/gpu_engine/gl/tvgGlStencilCoverBatch.cpp#L202-L220)는 pass, task, stencil mode, clip 상태와 geometry cap이 맞아도 `intersects(bounds)`가 true면 병합을 거절한다.

이 검사가 보수적이어야 하는 이유는 [`GlStencilCoverTask::run()`](https://github.com/thorvg/thorvg/blob/df31fd1b59a00ffb0811837c9753d9cb5766ac6d/src/renderer/gpu_engine/gl/tvgGlRenderTask.cpp#L170-L200)의 순서에 있다.

1. stencil test를 켜고 batch의 **모든 stencil geometry**를 먼저 그린다.
2. fill rule에 맞는 stencil function/op를 설정한다.
3. batch의 **모든 cover task**를 순서대로 그린다.
4. stencil test를 끈다.

한 shape의 cover rectangle이 다른 shape의 stencil 영역에 닿으면, 해당 cover draw가 다른 shape의 stencil 결과까지 통과시키거나 replace할 수 있다. 따라서 현재 AABB 비중첩 조건은 단순 성능 heuristic이 아니라 공유 stencil buffer의 correctness invariant이기도 하다.

cover rectangle은 shape의 local fill/stroke bounds 전체를 덮는다. ring의 빈 중심, C자 concave 영역, 서로 떨어진 compound subpath에도 rectangle 픽셀은 존재한다. 이런 shape들을 중첩 배치하면 실제 path끼리는 떨어져 있어도 cover region끼리는 겹칠 수 있다.

현재 `main`에는 `WgStencilBatch` 파일이 없다. 다만 관련 [열린 PR #4594](https://github.com/thorvg/thorvg/pull/4594)는 WebGPU에 stencil batch를 추가하면서 `renderData->aabb`를 viewport로 자른 region 목록과 동일한 AABB `intersects()` 조건을 사용한다. 이슈의 `webgpu` label은 해당 진행 중인 설계에도 같은 제한이 있음을 가리키는 것으로 보인다.

이 문제는 기존 [Issue #4260](https://github.com/thorvg/thorvg/issues/4260)에서 도입된 complex shape batching의 다음 최적화 단계다. 현재 결과는 올바르고 이슈의 목적은 성능 개선이다.

## 원인 분석

### 확인된 사실

- GL batch는 실제 path 교차가 아니라 transform·clip된 `RenderRegion` 교차로 병합 가능성을 판정한다.
- cover geometry는 shape bounds 전체를 덮는 rectangle 두 개 triangle이다.
- 하나의 batch는 모든 stencil geometry를 그린 뒤 모든 cover task를 실행한다.
- cover 단계의 stencil operation은 공유 buffer 값을 검사하고 변경하므로 cover 영역 교차는 다른 shape 결과에 영향을 줄 수 있다.
- concave/hole/compound/rotated stroke의 AABB는 실제 그려지는 영역보다 클 수 있다.
- WebGPU stencil batching은 현재 main에 없고, 열린 PR #4594가 비슷한 AABB 정책을 제안한다.

### 추론과 판단

- AABB false positive만 제거하고 cover rectangle을 유지하면 실제 shape 비중첩 여부와 무관하게 stencil contamination이 발생할 수 있다.
- 안전하게 더 많이 병합하려면 “overlap 판정에 쓰는 영역”과 “cover가 실제로 접근하는 영역”을 같은 더 촘촘한 표현으로 바꾸거나, shape별 stencil 값이 서로 간섭하지 않는 별도 격리 방법이 필요하다.
- 정확한 path boolean intersection은 CPU 비용과 수치 안정성 부담이 크고, cover가 그대로라면 correctness 문제도 해결하지 못한다.
- 여러 작은 rectangle/tile 또는 기존 tessellation에서 얻은 conservative cover mesh는 AABB보다 촘촘할 수 있지만 vertex/index·task 비용이 draw call 절감보다 커지는 임계점을 측정해야 한다.
- stencil bit/reference를 shape별로 나누는 방식은 non-zero winding count, bit 수, fill rule, batch 크기와 충돌하므로 일반 해법으로 단정하기 어렵다.

## 구현 방향

1. 먼저 계측 가능한 목표를 고정한다.
   - 중첩된 비접촉 ring N개의 stencil/cover draw 수
   - 기존 대비 CPU batch 시간, vertex/index byte, GPU 시간
   - GL/WebGL의 pixel-identical 결과
2. overlap key와 cover geometry를 하나의 `CoverageRegion` 추상으로 묶는 prototype을 만든다. 판정과 실제 cover가 서로 다른 공간을 사용하지 못하게 API로 강제한다.
3. 후보 표현을 비교한다.
   - 기존 AABB
   - scan/tile 기반 conservative region 집합
   - tessellation에서 파생한 여러 convex/rect cover
   - shape별 stencil 격리 또는 제한된 reference 분할
4. 새 region은 실제 fill/stroke를 **빠뜨리지 않는 conservative superset**이어야 하며, 같은 batch의 다른 region과 겹치지 않을 때만 병합한다.
5. region 생성 비용과 복잡도에 cap을 둔다. cap을 넘거나 수치가 불안정하면 기존 AABB와 batch split으로 안전하게 fallback한다.
6. GL에서 correctness와 성능을 먼저 증명한다. WebGPU에는 PR #4594가 main에 반영된 뒤 같은 invariant를 backend 공통 테스트와 함께 이식한다.
7. 관련 #4610의 physical stencil geometry 병합과 결합될 수 있으므로, draw counter에서 “outer batch”, “physical stencil draw”, “cover draw”를 따로 측정한다.

## 초심자 시작 가이드

전체 알고리즘 변경은 초심자에게 권하지 않는다. 안전한 하위 작업은 재현/계측 fixture다.

1. 같은 중심을 가진 두 개 이상의 얇은 ring을 만들되 실제 ring 영역은 서로 닿지 않게 한다.
2. 각 ring의 AABB와 실제 pixel mask를 출력해 “AABB overlap, pixel non-overlap”을 수치로 확인한다.
3. 현재 `GlStencilCoverBatch::intersects()`가 batch를 끊는 횟수와 `glDrawElements` 호출 수를 기록한다.
4. 한쪽 ring을 조금 이동해 실제 영역도 겹치는 대조 사례를 만든다.
5. baseline 이미지를 GL과 WebGL에서 저장하고, 이후 prototype은 draw 수와 pixel diff를 모두 통과해야 한다.

성능만 좋아 보이는 patch라도 cover rectangle을 그대로 둔 채 AABB guard를 약화하지 않는다.

## 위험/검증

- 동심 ring, C자 concave path, hole, 떨어진 compound subpath, 회전/diagonal stroke를 각각 테스트한다.
- AABB만 겹치는 사례와 실제 fill pixel도 겹치는 대조 사례를 함께 둔다.
- NonZero와 EvenOdd fill rule에서 stencil count/wrap과 최종 pixel이 유지되는지 확인한다.
- solid·linear·radial cover, opacity/blend, clip chain과 pass/viewport 경계를 검사한다.
- 새 conservative region이 path의 모든 covered pixel을 포함하는지 CPU mask 또는 reference rasterizer와 비교한다.
- region 수/vertex/index cap 초과와 allocation 실패에서 기존 안전한 batch split으로 fallback하는지 확인한다.
- native GL, WebGL의 작은 memory cap, 향후 WebGPU 경로를 별도 실행한다.
- outer task 수, physical stencil draw 수, cover draw 수, buffer upload 수를 분리해 측정한다.
- region 생성 CPU 시간과 staging memory 증가를 포함한 end-to-end benchmark를 shape 수별로 기록한다.
- pixel diff, GL debug output과 sanitizer를 함께 실행해 잘못된 index/viewport 및 state leak를 검사한다.
