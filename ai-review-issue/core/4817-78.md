## 이슈 요약

이슈는 Lottie shape 안의 개별 fill에 기록된 `bm`(blend mode)이 적용되지 않고 group에 지정된 blend만 반영된다고 보고한다. 현재 구현은 layer와 shape group의 `bm`을 읽어 `Scene`에 적용하지만, solid fill(`fl`)과 gradient fill(`gf`) parser는 같은 필드를 읽지 않는다. 따라서 파일을 정상적으로 load하고 frame을 생성해도 해당 fill은 항상 `Normal`로 렌더링된다.

표면적인 수정은 fill model에 `BlendMethod`를 저장하고 builder에서 `ctx->propagator->blend()`를 호출하는 것이다. 실제로 열린 구현 초안도 이 방향을 보여 준다. 그러나 ThorVG의 propagator는 하나의 Lottie style만 나타내지 않는다. 같은 내부 `Shape`에 fill과 stroke가 함께 들어갈 수 있고, 여러 fill을 처리할 때 context를 복제하는 기존 fragment 규칙도 blend mode를 고려하지 않는다. 따라서 단순 속성 전달은 다른 style까지 blend하거나 일부 non-Normal fill을 건너뛸 수 있다.

## main 코드 조사

공식 Lottie schema에서 [solid fill](https://github.com/LottieFiles/lottie-docs/blob/960b404c2e1147e1d4024caa417eadddc9145319/schema/shapes/fill.json#L1-L31)과 [gradient fill](https://github.com/LottieFiles/lottie-docs/blob/960b404c2e1147e1d4024caa417eadddc9145319/schema/shapes/gradient-fill.json#L1-L32)은 모두 `shape-style`을 상속한다. `shape-style`은 다시 [graphic element](https://github.com/LottieFiles/lottie-docs/blob/960b404c2e1147e1d4024caa417eadddc9145319/schema/shapes/shape-style.json#L1-L24)를 상속하고, graphic element에는 [`bm`이 Blend Mode로 정의](https://github.com/LottieFiles/lottie-docs/blob/960b404c2e1147e1d4024caa417eadddc9145319/schema/shapes/graphic-element.json#L20-L35)되어 있다. 즉 `bm`은 layer/group에만 한정된 필드가 아니라 fill 같은 shape style에도 유효하다.

공식 schema의 [blend mode 값](https://github.com/LottieFiles/lottie-docs/blob/960b404c2e1147e1d4024caa417eadddc9145319/schema/constants/blend-mode.json#L1-L79)은 0 Normal, 1 Multiply, 2 Screen, 3 Overlay, 4 Darken, 5 Lighten 순으로 정의된다. 참조 구현인 lottie-web도 [동일한 숫자를 CSS blend mode로 변환](https://github.com/airbnb/lottie-web/blob/bede03d25d232826e0c9dca1733d542d8a7754fb/player/js/utils/helpers/blendModes.js#L1-L23)하고 [SVG shape style의 `data.bm`을 `mix-blend-mode`에 적용](https://github.com/airbnb/lottie-web/blob/bede03d25d232826e0c9dca1733d542d8a7754fb/player/js/elements/svgElements/SVGShapeElement.js#L143-L165)한다. 현재 ThorVG의 [`BlendMethod` 열거 순서](https://github.com/thorvg/thorvg/blob/571d539d810138f3dc15e88d275ba6d6b79fc480/inc/thorvg.h#L238-L264)도 0~16 범위에서 이 순서와 맞는다. 다만 공식 schema에는 17 Hard Mix도 있는데 ThorVG enum에는 대응 값이 없으므로, parser가 정수 전체를 무검증 cast하기보다 지원 범위와 fallback을 명시해야 한다.

현재 [solid fill parser](https://github.com/thorvg/thorvg/blob/571d539d810138f3dc15e88d275ba6d6b79fc480/src/loaders/lottie/tvgLottieParser.cpp#L608-L623)는 색, opacity, 활성 여부와 fill rule만 읽고 나머지 키를 버린다. [gradient fill parser](https://github.com/thorvg/thorvg/blob/571d539d810138f3dc15e88d275ba6d6b79fc480/src/loaders/lottie/tvgLottieParser.cpp#L761-L775)도 fill rule과 gradient 속성만 처리한다. 반면 [group parser](https://github.com/thorvg/thorvg/blob/571d539d810138f3dc15e88d275ba6d6b79fc480/src/loaders/lottie/tvgLottieParser.cpp#L1195-L1210)와 [layer parser](https://github.com/thorvg/thorvg/blob/571d539d810138f3dc15e88d275ba6d6b79fc480/src/loaders/lottie/tvgLottieParser.cpp#L1564-L1600)는 `bm`을 읽어 `blendMethod`에 저장한다.

[fill model](https://github.com/thorvg/thorvg/blob/571d539d810138f3dc15e88d275ba6d6b79fc480/src/loaders/lottie/tvgLottieModel.h#L757-L862)은 solid와 gradient의 색·opacity·fill rule·gradient 좌표를 보관하지만 blend mode 필드는 없다. group에는 별도 `blendMethod`가 있으므로 parser에서 읽은 group 값은 유지되지만 fill 값은 저장할 자리도 없는 상태다.

[group builder](https://github.com/thorvg/thorvg/blob/571d539d810138f3dc15e88d275ba6d6b79fc480/src/loaders/lottie/tvgLottieBuilder.cpp#L247-L278)는 group mode가 parent와 호환되면 같은 `Scene`을 재사용하고, 단일 child이면 parent scene에 mode를 전파하며, 그 외에는 새 `Scene`을 만들어 blend를 적용한다. [layer builder](https://github.com/thorvg/thorvg/blob/571d539d810138f3dc15e88d275ba6d6b79fc480/src/loaders/lottie/tvgLottieBuilder.cpp#L1555-L1580)도 layer 전체의 `Scene`에 blend를 설정한다. 현재 blend 구현이 group/layer에만 보이는 이유는 이 두 경로만 mode를 model에 보존하고 render object에 적용하기 때문이다.

[solid·gradient fill builder](https://github.com/thorvg/thorvg/blob/571d539d810138f3dc15e88d275ba6d6b79fc480/src/loaders/lottie/tvgLottieBuilder.cpp#L345-L385)는 opacity가 충분한 fill을 만나면 이전 fill 처리를 중단하고, color/gradient와 fill rule을 propagator에 설정한다. 여기에는 blend 적용이 없다. 특히 fully opaque fill의 조기 종료는 Normal source-over라면 아래 fill을 완전히 가린다는 전제에 의존한다. Multiply나 Screen처럼 destination 색을 사용하는 mode에는 같은 전제를 적용할 수 없다.

[현재 fragment helper](https://github.com/thorvg/thorvg/blob/571d539d810138f3dc15e88d275ba6d6b79fc480/src/loaders/lottie/tvgLottieBuilder.cpp#L298-L309)는 이미 `ctx->fragment`가 설정돼 있으면 `true`를 반환하고 더 이상 context를 만들지 않는다. [group의 사전 분석](https://github.com/thorvg/thorvg/blob/571d539d810138f3dc15e88d275ba6d6b79fc480/src/loaders/lottie/tvgLottieModel.cpp#L522-L570)은 fill이 둘 이상이거나 stroke가 둘 이상인 경우 fragmentation을 요구하지만, fill 하나와 stroke 하나가 함께 있는 경우는 분리하지 않는다. [`RenderContext`](https://github.com/thorvg/thorvg/blob/571d539d810138f3dc15e88d275ba6d6b79fc480/src/loaders/lottie/tvgLottieBuilder.h#L76-L109)도 하나의 `Shape* propagator`에 fill·stroke 속성을 전파한다.

공개 [`Paint::blend()`](https://github.com/thorvg/thorvg/blob/571d539d810138f3dc15e88d275ba6d6b79fc480/inc/thorvg.h#L542-L559)는 paint object 전체의 합성 방법을 정한다. 실제 [shape render 경로](https://github.com/thorvg/thorvg/blob/571d539d810138f3dc15e88d275ba6d6b79fc480/src/renderer/tvgShape.h#L43-L54)도 `Shape`의 한 `blendMethod`를 renderer에 설정한 뒤 fill과 stroke를 그린다. 그러므로 fill의 `bm`을 공유 propagator에 바로 설정하면 같은 `Shape`의 stroke에도 적용된다. 포맷의 style 단위와 renderer의 paint 단위가 다르다는 것이 핵심 구조 문제다.

열린 [구현 초안 PR #4804](https://github.com/thorvg/thorvg/pull/4804)은 model/parser에 fill mode를 추가하고, 불투명 조기 종료를 Normal일 때만 수행하며, propagator에 blend를 설정하는 3개 파일의 작은 변경을 제시한다. 하지만 현재 patch에서는 fragment가 이미 `ByFill`인 non-Normal fill이 `fragmented()`에서 즉시 반환되어 적용되지 않을 수 있고, fill+stroke가 같은 propagator를 공유하면 fill mode가 stroke로 번질 수 있다. 이는 [fragment 누락 지적](https://github.com/thorvg/thorvg/pull/4804#discussion_r4011059699)과 [공유 Shape 오염 지적](https://github.com/thorvg/thorvg/pull/4804#discussion_r4022684674)에도 구체적으로 드러난다.

renderer 선행 조건도 남아 있다. current main의 CPU [gradient blend 경로](https://github.com/thorvg/thorvg/blob/571d539d810138f3dc15e88d275ba6d6b79fc480/src/renderer/cpu_engine/tvgSwRaster.cpp#L1161-L1216)는 translucent gradient에 `opBlendPreNormal`을 먼저 적용한 뒤 blend 함수를 호출한다. GL shader도 [같은 순서를 parity 동작으로 명시](https://github.com/thorvg/thorvg/blob/571d539d810138f3dc15e88d275ba6d6b79fc480/src/renderer/gpu_engine/gl/tvgGlShaderSrc.cpp#L573-L665)한다. 이 순서는 raw source에 blend를 적용한 뒤 source-over로 합성하는 기대와 다를 수 있으며, 관련 GPU 수정은 [PR #4812](https://github.com/thorvg/thorvg/pull/4812)에서 아직 논의 중이다.

8-bit gradient buffer overflow를 막는 변경은 [PR #4813](https://github.com/thorvg/thorvg/pull/4813)으로 main에 들어왔다. 다만 current main의 [matted grayscale gradient 경로](https://github.com/thorvg/thorvg/blob/571d539d810138f3dc15e88d275ba6d6b79fc480/src/renderer/cpu_engine/tvgSwRaster.cpp#L1129-L1160)는 여전히 지원하지 않는 경우 `false`를 반환한다. 즉 과거 crash 위험은 완화됐지만 blend fill이 matte source 안에 있을 때 빈 결과나 backend 차이를 만들 가능성은 별도로 검증해야 한다.

현재 [Lottie coverage test](https://github.com/thorvg/thorvg/blob/571d539d810138f3dc15e88d275ba6d6b79fc480/test/testLottie.cpp#L37-L73)는 여러 파일의 load와 frame 성공 여부를 확인할 뿐 결과 pixel이나 fill의 mode를 검사하지 않는다. [software renderer test](https://github.com/thorvg/thorvg/blob/571d539d810138f3dc15e88d275ba6d6b79fc480/test/testSwEngine.cpp#L45-L115)는 여러 `BlendMethod`를 직접 `Shape`에 설정해 API 경로를 통과시키지만, Lottie fill parsing·fragmentation·style isolation은 다루지 않는다.

## 원인 분석

### 확인된 사실

- 공식 schema상 solid fill과 gradient fill은 `bm`을 가질 수 있고, 17 Hard Mix는 현재 ThorVG `BlendMethod`에 직접 대응하지 않는다.
- current main은 layer와 group의 `bm`은 parsing·적용하지만 두 fill parser에서는 `bm`을 버린다.
- fill model에는 blend mode 저장 필드가 없고 fill builder도 blend를 적용하지 않는다.
- Normal fully opaque fill은 현재 이전 fill 처리를 중단하며, non-Normal mode는 destination 색을 필요로 한다.
- 하나의 `RenderContext`와 `Shape`가 fill과 stroke를 함께 보유할 수 있다.
- `Paint::blend()`와 renderer의 blend state는 fill 전용이 아니라 전체 paint에 적용된다.
- 기존 fragmentation은 fill 개수와 stroke 개수를 각각 세지만 “non-Normal style을 별도 paint로 격리”하는 규칙은 없다.
- current main의 CPU·GL gradient blending은 translucent gradient를 먼저 destination과 섞은 뒤 blend 함수에 전달하는 경로를 공유한다.
- Lottie unit test에는 개별 fill `bm`의 parsing과 pixel 결과를 고정하는 회귀가 없다.

### 추론과 판단

- **직접 원인:** fill parser-model-builder 데이터 흐름에 `bm`이 완전히 빠져 있어 파일의 style 정보가 renderer까지 도달하지 않는다.
- **구조적 원인:** Lottie는 fill/stroke 각각을 style object로 다루지만 builder는 호환 가능한 style을 하나의 ThorVG `Shape`로 병합한다. paint 전체 속성인 blend를 style 한 개에만 적용할 표현 경계가 없다.
- **조기 종료 문제:** opaque Normal fill은 아래 색을 가리므로 이전 fragment를 버려도 되지만, non-Normal fill은 아래 색이 blend destination이다. 같은 최적화를 유지하면 올바른 입력을 제거하게 된다.
- **단순 patch의 누락 가능성:** 기존 `fragmented()`는 이미 fragment 상태인 context를 완료된 것으로 간주한다. 조기 종료 조건만 완화하면 non-Normal fill이 그 helper에서 반환되어 실제 color와 blend를 설정하지 못할 수 있다.
- **공유 propagator 위험:** fill 하나+stroke 하나는 현재 fragment를 요구하지 않는다. 여기에 fill mode를 설정하면 의도와 달리 stroke도 같은 mode로 합성된다는 판단이 renderer의 paint 단위 동작과 일치한다.
- **backend 독립성:** loader가 style isolation을 올바르게 구현해도 gradient source/destination 순서나 grayscale matte 지원이 backend마다 다르면 compliance 결과는 완성되지 않는다. loader 수정과 engine 수정은 책임을 나눌 수 있지만 최종 검증은 함께 해야 한다.
- **범위 판단:** 이슈 본문은 fill을 지목한다. schema 상 stroke도 같은 `shape-style`을 상속하므로 후속 지원 여부는 점검해야 하지만, 재현과 합의 없이 첫 PR의 필수 범위를 stroke까지 확대하지 않는 편이 안전하다.

## 구현 방향

1. solid fill과 gradient fill에 기본값 `BlendMethod::Normal`인 필드를 추가하고 각 parser가 `bm`을 읽도록 한다. 표준 0~16 값은 현재 열거 순서와 일치하지만, Hard Mix(17)와 범위를 벗어난 값은 Normal로 fallback할지 별도 지원할지 명시한다.
2. mode 저장과 실제 render isolation을 별도 단계로 나눈다. parser/model 변경만으로 지원 완료로 간주하지 말고, builder가 non-Normal style마다 독립된 `Shape` 또는 중간 `Scene`을 생성하도록 설계한다.
3. fill+stroke 또는 여러 fill이 한 propagator를 공유하지 않게 한다. 가장 작은 안전한 규칙은 non-Normal fill 진입 시 현재 path와 필요한 transform/modifier 상태를 복제한 전용 context를 만들고, 해당 fill의 paint만 그 context에 적용하는 것이다.
4. 기존 `fragmented()`의 `ctx->fragment` 조기 반환을 그대로 재사용하지 않는다. Normal multi-fill, non-Normal multi-fill, fill 뒤 stroke의 순서를 상태 전이 표로 작성하고, 각 style이 어느 context에서 시작·종료되는지 명시한다.
5. opaque early-out은 `blendMethod == Normal`일 때만 허용한다. non-Normal fill 아래의 destination fragment는 보존하고, 결과 scene의 추가 순서가 Lottie style stack 순서와 같은지 확인한다.
6. solid fill의 opacity가 0이면 blend state를 바꾸지 않는다. gradient는 `fill()`이 실제 `Fill*`을 반환한 경우에만 mode를 설정해, 투명 gradient가 공유 state를 오염하지 않게 한다.
7. loader PR과 engine 선행 수정의 경계를 문서화한다. CPU·GL·WG의 translucent gradient 순서를 먼저 또는 같은 릴리스에서 고치고, grayscale matte에서 blend를 무시할지 alpha 결과를 별도 계산할지도 결정한다.
8. 이슈 첨부 파일을 최소 fixture로 축소한다. 두 겹의 shape, `fl`/`gf`, 한두 mode와 기대 pixel만 남겨 parser와 compositing 회귀 원인을 명확히 고정한다.
9. stroke의 `bm`은 별도 fixture로 현재 동작을 기록한다. fill 수정과 동일한 style isolation 기반을 재사용할 수 있을 때 후속 PR로 확장하고, 지원하지 않는 동안에는 model의 공통 base field가 stroke 지원을 암시하지 않게 둔다.

## 초심자 시작 가이드

이 이슈는 첫 구현 과제로는 권하지 않지만, 조사와 테스트 fixture 작업으로 기여할 수 있다.

1. 64×64 canvas에 아래 사각형 하나와 위 사각형 하나만 둔 Lottie JSON을 만든다. 위 사각형의 solid fill에 `bm: 1`(Multiply)을 넣고 Normal 결과와 pixel을 비교한다.
2. 같은 fixture의 `fl`을 `gf`로 바꿔 solid/gradient 두 parser 경로를 분리한다.
3. 위 shape에 stroke를 추가해 fill만 Multiply이고 stroke는 Normal인 기대 이미지를 만든다. 이 fixture가 style isolation의 핵심 회귀다.
4. fill 두 개를 한 group에 넣고 두 번째 fill만 non-Normal로 설정한다. `fragmented()` 전후 context 수와 각 `Shape`의 blend mode를 debugger로 확인한다.
5. opacity 0, 128, 255와 Normal/Multiply/Screen 조합을 표로 만들고, 조기 종료가 가능한 행과 destination을 보존해야 하는 행을 표시한다.
6. 먼저 CPU golden image를 고정한 뒤 같은 fixture를 GL·WG에서 비교한다. backend 차이가 나면 loader와 engine 문제를 한 commit에서 섞지 말고 최소 재현을 각각 남긴다.

## 위험/검증

- solid fill과 linear/radial gradient fill 각각에서 `bm` 없음, 0, 1, 2 및 지원 상한 값을 parsing하고 model 기본값이 Normal인지 확인한다.
- 범위를 벗어난 음수·큰 `bm`이 renderer 배열 index나 enum UB로 이어지지 않도록 입력 검증을 추가한다.
- 한 path에 fill만, stroke만, fill+stroke, gradient fill+gradient stroke를 두고 각 style의 blend가 다른 style에 전파되지 않는지 검사한다.
- 한 group에 Normal fill 두 개, Normal+non-Normal, non-Normal 두 개, fill+중첩 group을 두어 누락·중복 draw와 순서를 확인한다.
- opaque non-Normal fill 아래의 destination이 보존되는지, opaque Normal fill의 기존 early-out과 성능 최적화는 유지되는지 비교한다.
- opacity 0 gradient가 `Fill*`을 만들지 않을 때 이전 fill/stroke의 blend state를 변경하지 않는지 확인한다.
- transform, trim path, roundness, repeater와 merge 가능한 path에서 context 복제 뒤 geometry·gradient transform이 달라지지 않는지 검사한다.
- alpha/luma matte와 add/subtract/intersect mask 안팎에서 solid·gradient blend 결과와 빈 mask 회귀를 확인한다.
- CPU rectangle/RLE, GL, WG backend에서 premultiplied alpha와 translucent gradient 결과를 공식 참조 renderer의 pixel 또는 허용 오차 내 golden image와 비교한다.
- Multiply뿐 아니라 Screen, Overlay, Darken/Lighten, Hard/Soft Light처럼 서로 다른 공식을 대표하는 mode를 포함한다.
- Lottie load/frame 성공 assertion에 더해 특정 좌표 RGBA, 전체 image hash 또는 Pixel Inspector fixture를 추가해 시각 결과를 고정한다.
- fragmentation 증가에 따른 paint 수, intermediate surface와 frame time을 측정해 Normal-only animation의 기존 merge 성능이 유지되는지 확인한다.
- sanitizers로 matte·mask 조합의 8-bit/32-bit buffer 접근을 검사하고, unsupported 경로가 crash 대신 명시적인 결과를 내는지 확인한다.
