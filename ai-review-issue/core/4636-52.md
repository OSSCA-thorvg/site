## 이슈 요약

동일한 embedded font 이름을 가진 Lottie composition 두 개를 동시에 열고 첫 번째 composition을 파괴하면, 두 번째 composition의 새 glyph가 사라지거나 ASAN use-after-free가 발생한다. 첫 composition의 base64 decode buffer를 공유 font loader가 복사 없이 참조하는데, 첫 composition destructor가 그 buffer를 해제한 뒤에도 두 번째 composition이 같은 loader를 사용하기 때문이다.

이슈가 제공한 재현은 “첫 composition에서 아직 사용하지 않은 glyph를 두 번째에서 나중에 요청”하는 조건을 포함한다. 이미 cache된 glyph는 원본 font table을 다시 읽지 않을 수 있어 정상처럼 보이지만, 새 glyph의 lazy 변환 시 해제된 reader data를 접근하면서 문제가 드러난다.

## main 코드 조사

Lottie parser는 [`parseFontData()`](https://github.com/thorvg/thorvg/blob/f38fc532fc36be7700508d6cc60a4f4c392fbecc/src/loaders/lottie/tvgLottieParser.cpp#L1113-L1140)에서 `data:font/ttf` 또는 `data:font/otf` base64를 각 `LottieFont::b64src`에 decode한다. [`parseFont()`](https://github.com/thorvg/thorvg/blob/f38fc532fc36be7700508d6cc60a4f4c392fbecc/src/loaders/lottie/tvgLottieParser.cpp#L1144-L1161)는 이름과 경로를 읽은 뒤 즉시 `font->prepare()`를 호출한다.

현재 [`LottieFont::prepare()`](https://github.com/thorvg/thorvg/blob/f38fc532fc36be7700508d6cc60a4f4c392fbecc/src/loaders/lottie/tvgLottieModel.cpp#L292-L295)는 `Text::load(name, b64src, size, mime, false)`를 호출한다. 마지막 `false`는 font loader가 입력 data를 복사하지 않는다는 뜻이다.

[`SfntLoader::open()`](https://github.com/thorvg/thorvg/blob/f38fc532fc36be7700508d6cc60a4f4c392fbecc/src/loaders/sfnt/tvgSfntLoader.cpp#L542-L555)은 우선 reader가 caller buffer를 가리키게 하고, `copy`가 true일 때만 별도 memory를 할당해 `freeData`를 설정한다. `copy=false`이면 loader는 LottieFont 소유 buffer를 빌린다. [`SfntLoader::request()`](https://github.com/thorvg/thorvg/blob/f38fc532fc36be7700508d6cc60a4f4c392fbecc/src/loaders/sfnt/tvgSfntLoader.cpp#L263-L273)는 cache miss glyph를 요청할 때 reader에서 outline을 변환하므로 load 시점 이후에도 font data를 읽을 수 있다.

named memory font는 [`LoaderMgr::loader(name, data, ...)`](https://github.com/thorvg/thorvg/blob/f38fc532fc36be7700508d6cc60a4f4c392fbecc/src/renderer/tvgLoaderMgr.cpp#L323-L344)에서 전역 cache에 들어간다. 이 함수는 새 loader를 만들기 전에 [`font(name)`](https://github.com/thorvg/thorvg/blob/f38fc532fc36be7700508d6cc60a4f4c392fbecc/src/renderer/tvgLoaderMgr.cpp#L346-L357)을 호출한다. 동일한 `name`이 있으면 data pointer나 content를 비교하지 않고 기존 loader의 `sharing`을 증가시켜 반환한다. 따라서 두 번째 composition의 별도 `b64src`는 loader에 연결되지 않고 첫 번째 loader가 계속 공유된다.

[`LottieFont` destructor](https://github.com/thorvg/thorvg/blob/f38fc532fc36be7700508d6cc60a4f4c392fbecc/src/loaders/lottie/tvgLottieModel.h#L449-L478)는 embedded font이면 `Text::unload(name)`을 호출한 뒤 `name`과 `b64src`를 해제한다. 그러나 [`Text::unload()`](https://github.com/thorvg/thorvg/blob/f38fc532fc36be7700508d6cc60a4f4c392fbecc/src/renderer/tvgText.cpp#L80-L89)은 file path cache를 대상으로 하는 API이며 file I/O가 꺼진 build에서는 `NonSupport`를 반환한다. file cache 조회는 [`hashpath`를 비교](https://github.com/thorvg/thorvg/blob/f38fc532fc36be7700508d6cc60a4f4c392fbecc/src/renderer/tvgLoaderMgr.cpp#L163-L172)하지만 named memory font는 `name` field로 cache된다. 따라서 이 호출은 named embedded font loader를 해제하는 정확한 대칭 연산이 아니다.

기존 [`testText.cpp` memory font test](https://github.com/thorvg/thorvg/blob/f38fc532fc36be7700508d6cc60a4f4c392fbecc/test/testText.cpp#L67-L105)는 named data load와 `Text::load(name, nullptr, 0)` 경로를 검사하지만, 복사한 입력 하나만 사용하고 두 Lottie composition의 파괴 순서나 lazy glyph 접근은 다루지 않는다. `testLottie.cpp`에도 embedded font를 공유하는 수명 회귀 fixture는 없다.

최근 [`f6e9c13d`](https://github.com/thorvg/thorvg/commit/f6e9c13d2095cb45611baef52444324e129325f0)는 동일 이름의 cached data loading에서 sharing count가 남는 문제를 기록하고 종료 시 font loader를 강제 정리하도록 변경했다. 이는 종료 leak을 완화하지만, 실행 중 첫 composition이 borrowed buffer를 해제하는 현재 UAF 조건과는 별개다.

## 원인 분석

### 확인된 사실

- 각 Lottie composition은 embedded font를 자신의 `b64src`에 decode한다.
- 첫 named font load는 `copy=false`이므로 `SfntLoader`가 첫 composition의 buffer를 빌린다.
- 같은 font 이름의 다음 load는 data identity를 확인하지 않고 기존 named loader를 공유한다.
- 첫 `LottieFont` destructor는 loader가 공유 중인지와 무관하게 자신의 `b64src`를 해제한다.
- `SfntLoader`는 아직 cache되지 않은 glyph를 요청할 때 reader data를 다시 읽는다.
- destructor의 `Text::unload(name)`은 named memory cache가 아니라 file path cache를 대상으로 한다.

### 추론과 판단

- ASAN UAF의 직접 원인은 loader의 borrowed pointer lifetime이 첫 `LottieFont` lifetime보다 길어진다는 계약 위반이다.
- `prepare()`를 `copy=true`로 바꾸면 첫 loader가 data를 소유하므로 첫 composition의 `b64src` 해제와 분리되어 직접 UAF를 막을 수 있다.
- 그러나 동일 이름 hit 때 두 번째 data가 무시되는 정책, acquire마다 증가하는 sharing count와 정확한 release 방법은 별도 검토가 필요하다. copy만 바꾸고 lifecycle API를 그대로 두면 실행 중 loader retention 또는 종료 시 강제 정리에 의존할 수 있다.
- 동일 이름에 실제로 다른 font binary가 들어오면 현재 cache key 정책은 수명뿐 아니라 잘못된 glyph를 선택하는 의미 오류도 만들 수 있다.
- 가장 안전한 장기 해법은 Lottie가 raw buffer와 이름으로 전역 cache를 간접 제어하지 않고, loader 소유 registration handle을 받아 RAII로 release하는 것이다.

## 구현 방향

1. 이슈 첨부 재현을 최소 test fixture로 만든다.
   - 같은 font 이름과 data를 넣은 composition A/B
   - A에서 일부 glyph만 사용
   - B를 유지한 채 A 파괴
   - B에서 이전에 요청하지 않은 glyph render
2. 즉시 안전성 수정은 embedded font registration에 owned copy를 사용한다. loader가 살아 있는 동안 font bytes도 반드시 살아 있게 만든다.
3. named font API의 acquire/release를 명시한다.
   - registration이 증가시키는 reference
   - 각 `Text` instance가 증가시키는 reference
   - composition 파괴와 Text 파괴가 각각 감소시키는 reference
   - 마지막 reference에서 cache와 owned data가 제거되는 시점
4. `Text::unload(filename)`을 named resource 해제에 재사용하지 않는다. named memory font 전용 release API나 opaque handle/token을 사용해 cache key 종류를 구분한다.
5. cache key 정책을 결정한다.
   - 이름이 전역 identity라면 같은 이름·다른 data를 명시적으로 reject
   - 여러 binary를 허용한다면 content hash/namespace를 key에 포함
6. `SfntLoader`의 data ownership을 enum 또는 owning buffer type으로 표현해 `copy` bool과 `freeData` 조합의 잘못된 상태를 줄인다.
7. 정상 실행 중 마지막 reference 해제와 `Initializer::term()` 강제 정리를 모두 sanitizer에서 검증한다.

## 초심자 시작 가이드

첫 작업은 수정이 아니라 ASAN 회귀 테스트로 제한하는 것이 좋다.

1. 이슈의 두 composition 구조를 작은 fixture로 줄이고 embedded font 이름은 동일하게 둔다.
2. composition A에서 사용하지 않은 문자 하나를 B에서 A 파괴 후 처음 render한다.
3. ASAN build에서 기존 main이 실패하는 stack trace를 저장한다.
4. A/B 파괴 순서를 바꾼 대조 사례와 세 composition 반복 사례를 추가한다.
5. `copy=true` 실험 patch에서 UAF가 사라지는지 확인하되, 종료 leak과 sharing count도 함께 기록한다.

loader cache와 공개 font API를 바꾸는 patch는 해당 계층의 maintainer와 reference invariant를 합의한 뒤 진행한다.

## 위험/검증

- 같은 이름·같은 data와 같은 이름·다른 data를 분리해 기대 동작을 명시한다.
- A 먼저 파괴, B 먼저 파괴, 동시에 파괴, 반복 load/unload와 `Initializer::term()` 순서를 검사한다.
- 첫 composition에서 cache된 glyph뿐 아니라 파괴 후 처음 요청되는 glyph를 반드시 포함한다.
- ASAN으로 UAF/double-free, LSan으로 loader/data leak, ThreadSanitizer로 전역 cache 경쟁을 검사한다.
- file font, application이 직접 등록한 memory font와 embedded Lottie font가 같은 이름일 때의 충돌을 검증한다.
- `THORVG_FILE_IO_SUPPORT` on/off에서 release 결과가 달라지지 않도록 한다.
- invalid base64, 잘린 SFNT, zero size와 loader open 실패에서 buffer와 cache entry가 남지 않는지 확인한다.
- 다수 composition과 여러 font를 반복 생성해 `_activeLoaders`, sharing count와 총 owned bytes가 기준선으로 돌아오는지 계측한다.
- 기존 `testText`, `testLottie`와 renderer별 text output pixel regression을 실행한다.
