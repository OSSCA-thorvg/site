## 이슈 요약

제보자는 같은 Lottie asset을 GL, WGPU, CPU backend로 렌더한 캡처 세 장을 제시했다. asset은 빨간 사각형, 초록 타원, 파란 비정형 path에 흰색 28px stroke를 적용하고 각 shape에 소수점 translation·size를 사용한다. 캡처에서 특히 검은 배경과 맞닿는 흰색 stroke의 원·대각선 경계가 GL에서 WGPU·CPU보다 계단져 보인다.

이 문제는 Lottie parser가 shape를 잘못 만드는 현상으로 단정하기 어렵다. 같은 asset의 큰 geometry와 색·겹침은 세 backend에서 대체로 일치하고, 차이는 경계 coverage 품질에 집중되어 있다. current GL은 CPU식 coverage fringe를 geometry에 추가하지 않고 4x multisample framebuffer와 stencil-and-cover 결과에 의존한다. 따라서 먼저 실제 draw 시 multisampling이 활성인지, stroke stencil이 sample별 coverage를 보존하는지, resolve 뒤 값이 유지되는지를 단계별로 확인해야 한다.

## main 코드 조사

GL target은 [`GlRenderTarget::init()`](https://github.com/thorvg/thorvg/blob/6c76afd1b25efb9f1717c4f0355cd6fe94d43e63/src/renderer/gpu_engine/gl/tvgGlRenderTarget.cpp#L33-L79)에서 color와 depth-stencil renderbuffer를 모두 고정 4 samples로 만든다. color 결과는 single-sample texture가 붙은 별도 resolved framebuffer로 옮겨진다. 즉 설계상 GL antialias의 첫 번째 기반은 4x MSAA다. 다만 같은 함수는 `glCheckFramebufferStatus()`나 지원 sample 수 확인 결과를 검사하지 않는다.

root target도 별도 예외가 아니다. [`GlRenderer::target()`](https://github.com/thorvg/thorvg/blob/6c76afd1b25efb9f1717c4f0355cd6fe94d43e63/src/renderer/gpu_engine/gl/tvgGlRenderer.cpp#L928-L963)은 외부 context와 최종 FBO id를 받은 뒤 전체 surface 크기의 `mRootTarget`을 위 multisample 방식으로 초기화한다. [`preRender()`](https://github.com/thorvg/thorvg/blob/6c76afd1b25efb9f1717c4f0355cd6fe94d43e63/src/renderer/gpu_engine/gl/tvgGlRenderer.cpp#L1052-L1061)는 이 root target으로 render pass를 시작한다.

GL의 동기화 단계는 [`GlRenderer::sync()`](https://github.com/thorvg/thorvg/blob/6c76afd1b25efb9f1717c4f0355cd6fe94d43e63/src/renderer/gpu_engine/gl/tvgGlRenderer.cpp#L967-L1016)에서 blend, scissor, cull/front-face, depth 상태를 명시적으로 설정하고 최종 blit task를 실행한다. 이 구간에는 `GL_MULTISAMPLE`을 명시적으로 활성화하거나 `GL_SAMPLES`를 확인하는 코드가 없다. OpenGL 상태를 공유하는 application이 이를 끈 경우를 current renderer가 방어하는지는 실행 실험이 필요하다.

재현 asset의 흰색 테두리는 공통 GPU stroker를 거친다. [`GlGeometry::prepare()`](https://github.com/thorvg/thorvg/blob/6c76afd1b25efb9f1717c4f0355cd6fe94d43e63/src/renderer/gpu_engine/gl/tvgGlGeometry.cpp#L121-L144)는 path를 GPU 최적화하고, [`tesselateStroke()`](https://github.com/thorvg/thorvg/blob/6c76afd1b25efb9f1717c4f0355cd6fe94d43e63/src/renderer/gpu_engine/gl/tvgGlGeometry.cpp#L195-L219)는 transform scale을 품질 값으로 사용해 cap/join이 포함된 triangle mesh를 만든다. 별도의 alpha fringe vertex나 shader coverage 값은 이 경로에서 생성되지 않는다.

stroke draw는 [`getStencilMode()`](https://github.com/thorvg/thorvg/blob/6c76afd1b25efb9f1717c4f0355cd6fe94d43e63/src/renderer/gpu_engine/gl/tvgGlGeometry.cpp#L285-L297)에 의해 항상 `GlStencilMode::Stroke`를 선택한다. [`GlStencilCoverTask::run()`](https://github.com/thorvg/thorvg/blob/6c76afd1b25efb9f1717c4f0355cd6fe94d43e63/src/renderer/gpu_engine/gl/tvgGlRenderTask.cpp#L139-L186)은 먼저 color write를 끄고 stroke mesh를 stencil에 쓴 다음, bbox cover geometry를 stencil test로 칠한다. 이 구조에서는 multisample rasterization과 sample별 stencil 값이 경계 coverage를 보존해야 한다.

render pass의 마지막은 [`GlComposeTask::onResolve()`](https://github.com/thorvg/thorvg/blob/6c76afd1b25efb9f1717c4f0355cd6fe94d43e63/src/renderer/gpu_engine/gl/tvgGlRenderTask.cpp#L243-L248)에서 multisample FBO를 resolved FBO로 `glBlitFramebuffer(..., GL_NEAREST)`한다. multisample resolve에서 filter는 `GL_NEAREST`여야 하므로 이 호출 자체만으로 결함이라 할 수 없다. 중요한 것은 resolve 전 sample별 color가 실제로 달랐는지와 resolve 후 중간 coverage 값이 유지되는지다.

비교 backend인 WGPU도 [`WgPipelines::initialize()`](https://github.com/thorvg/thorvg/blob/6c76afd1b25efb9f1717c4f0355cd6fe94d43e63/src/renderer/gpu_engine/wg/tvgWgPipelines.cpp#L153-L173)에서 일반 shape pipeline에 sample count 4를 사용한다. 따라서 “GL은 4 samples라서 WGPU보다 나쁘다”는 설명은 충분하지 않다. sample 위치, stencil pipeline과 resolve/target 상태 중 어디에서 구현 차이가 생기는지 비교해야 한다.

CPU 쪽은 MSAA가 아니라 coverage rasterizer를 사용한다. 공통 GPU 최적화 코드에도 [SW coverage 정밀도를 8-bit로 설명한 상수](https://github.com/thorvg/thorvg/blob/6c76afd1b25efb9f1717c4f0355cd6fe94d43e63/src/renderer/gpu_engine/tvgGpuCommon.cpp#L32-L38)가 있고, CPU 캡처가 GPU의 4단계 sample coverage보다 더 부드러운 색 단계를 보이는 것은 구조상 자연스럽다. CPU를 pixel-identical 목표로 삼기보다 허용 오차와 최소 품질 계약을 먼저 정해야 한다.

현재 GL test는 [`GL Basic draw`](https://github.com/thorvg/thorvg/blob/6c76afd1b25efb9f1717c4f0355cd6fe94d43e63/test/testGlEngine.cpp#L36-L114)에서 여러 fill·stroke·mask·blend를 draw/sync하지만 결과 pixel의 edge coverage를 읽어 검증하지 않는다. [`GL Synchronized Drawing`](https://github.com/thorvg/thorvg/blob/6c76afd1b25efb9f1717c4f0355cd6fe94d43e63/test/testGlCanvas.cpp#L112-L142)도 API 성공을 확인할 뿐이다. 따라서 multisample이 조용히 비활성화되거나 resolve 품질이 바뀌어도 기존 test는 통과할 수 있다.

## 원인 분석

### 확인된 사실

- issue는 동일 asset의 GL, WGPU, CPU 결과를 제공하며 GL 경계가 상대적으로 거칠게 보인다.
- 재현 asset은 세 shape 모두 28px 흰색 stroke와 소수점 size/translation을 사용한다.
- current GL root와 중간 render target은 color와 depth-stencil을 고정 4 samples로 생성한다.
- GL stroke는 alpha fringe 없이 triangle mesh를 stencil에 쓴 뒤 cover pass로 색을 채운다.
- GL sync는 여러 공유-context 상태를 명시적으로 설정하지만 `GL_MULTISAMPLE`은 설정·확인하지 않는다.
- GL target 생성부는 framebuffer completeness와 실제 sample 수를 검사하지 않는다.
- WGPU 일반 shape pipeline도 4 samples를 사용한다.
- current GL test는 draw/sync 성공 위주이고 edge pixel coverage를 검증하지 않는다.

### 추론과 판단

- **가장 먼저 검증할 가설:** 실제 제보 환경에서 GL multisample rasterization이 비활성화됐거나 4-sample attachment가 기대대로 구성되지 않아 stroke stencil이 binary coverage만 남겼을 수 있다. `GL_MULTISAMPLE`, `GL_SAMPLE_BUFFERS`, `GL_SAMPLES`와 FBO status를 캡처해야 확정할 수 있다.
- **두 번째 가설:** MSAA는 활성이나 stroke stencil-and-cover 또는 resolve 단계가 일부 sample의 coverage를 잃을 수 있다. 동일 mesh를 stencil 없이 직접 색칠한 결과와 비교하면 geometry와 stencil 책임을 분리할 수 있다.
- **Lottie 범위 판단:** parser 문제 가능성은 낮지만 확정적으로 배제되지는 않았다. 첨부 JSON을 public Shape API로 축소한 circle, fractional rectangle, diagonal path에서 같은 차이가 나오는지 확인해야 renderer 공통 문제로 확정된다.
- **sample 수 판단:** WGPU도 4 samples이므로 GL sample count를 8이나 16으로 올리는 것만으로 근본 원인을 해결했다고 보기 어렵다. 고정 4를 지원하지 않는 장치도 고려하면 capability negotiation 없는 증가는 오히려 실패 범위를 넓힌다.
- **CPU 비교 판단:** CPU의 8-bit coverage와 4x MSAA는 동일한 alpha 단계 계약이 아니다. 허용 오차는 경계 연속성, intermediate coverage 존재, 대칭성 같은 지표로 정의하는 편이 적합하다.
- **공유 context 위험:** GL state를 강제로 켜는 수정은 호출자 상태와 충돌할 수 있다. ThorVG가 render 동안 필요한 상태를 보장하고 종료 후 무엇을 복구하는지 기존 state-cache 계약과 함께 정해야 한다.

## 구현 방향

1. 첨부 JSON과 동일한 geometry를 public Shape API로 축소한다. 흰색 stroke가 있는 원, 소수점 이동 rectangle, 대각선 path를 각각 독립 buffer에 그려 어느 primitive부터 차이가 나는지 분리한다.
2. root와 composite FBO 생성 직후 `glCheckFramebufferStatus`, `GL_SAMPLE_BUFFERS`, `GL_SAMPLES`, 최대 지원 sample 수를 임시 기록한다. draw 직전 `GL_MULTISAMPLE` 활성 상태도 기록하고 캡처 환경의 실제 전제를 확정한다.
3. 같은 stroke mesh를 기존 stencil-and-cover와 진단용 direct color draw로 렌더해 경계 pixel을 비교한다. direct draw만 intermediate coverage를 가지면 stencil pass나 cover 상태가 원인이다.
4. stencil pass 직후, cover pass 직후, resolve 직후의 작은 영역을 readback해 coverage가 사라지는 정확한 단계를 찾는다. 진단 코드는 최종 PR에서 제거하거나 test helper로 한정한다.
5. multisample 상태 누락이 원인이면 GL render pass 시작 시 필요한 state를 state cache를 통해 명시적으로 설정한다. 외부 context와 공유하는 상태의 복구 정책도 기존 API 계약에 맞춘다.
6. sample attachment 구성이 원인이면 요청 sample 수를 장치 capability로 제한하고 FBO completeness 실패를 조용히 진행하지 않도록 한다. 지원 불가 시 명시적 fallback이나 target 실패를 결정한다.
7. stencil/resolve 문제라면 fill, even-odd, stroke, clip에서 sample별 stencil 보존을 함께 고정한다. 특정 Lottie asset만 위한 geometry 보정은 피한다.
8. GL test harness에 작은 offscreen pixel readback을 추가해 diagonal·circle stroke의 외부 경계에 0과 255 사이 coverage가 존재하는지 검사한다. sample 위치 차이를 허용하도록 exact image가 아닌 invariant와 제한된 오차를 사용한다.

첫 수정 PR은 재현 가능한 최소 GL test와 확정된 한 단계의 수정에 집중하는 편이 좋다. configurable MSAA나 analytical fringe는 측정 결과가 별도 설계를 요구할 때 후속 작업으로 분리할 수 있다.

## 초심자 시작 가이드

이 issue의 최종 수정은 GPU 상태 계약 때문에 초심자에게 권하지 않지만, 원인 분리용 실험은 기여할 수 있다.

1. 첨부 JSON에서 원 하나만 남기고 fill을 끈 28px 흰색 stroke asset을 만든다. GL, WGPU, CPU를 같은 canvas 크기와 transform으로 캡처한다.
2. GL 결과에서 검은 배경과 맞닿은 한 scanline의 RGBA 값을 출력한다. 0/255만 있는지, 중간 alpha 또는 회색 값이 있는지 기록한다.
3. draw 직전 `GL_MULTISAMPLE`과 `GL_SAMPLES`를 출력한다. 로그를 추가한 build와 기존 build의 출력이 같은지 확인한 뒤 임시 로그는 제거한다.
4. circle을 stroke가 아닌 두 개의 원을 겹친 ring fill로 바꿔 비교한다. ring fill은 부드럽고 stroke만 거칠면 stroke stencil 경로로 범위를 줄일 수 있다.
5. 같은 scene을 normal, clip, mask 안에서 각각 렌더해 중간 FBO에서도 현상이 유지되는지 비교한다.
6. 최소 test는 전체 스크린샷 비교보다 경계에 intermediate coverage가 존재하고 좌우 대칭 오차가 제한되는지를 먼저 검사한다.

## 위험/검증

- issue asset을 동일 viewport·배경·scale로 GL, GLES/WebGL, WGPU, CPU에서 캡처한다.
- circle, axis-aligned fractional rectangle, diagonal path의 fill-only·stroke-only·fill+stroke를 각각 검사한다.
- butt/round/square cap과 miter/round/bevel join, 얇은 1px 이하와 28px stroke를 비교한다.
- 정수·0.25·0.5·0.75 translation과 확대·축소·회전에서 edge coverage가 끊기지 않는지 확인한다.
- convex direct fill, non-zero/even-odd stencil fill, stroke stencil을 분리해 회귀 지점을 확인한다.
- root FBO, scene composition, clip, mask, blend, effect의 중간 FBO에서 sample 수와 resolve 결과를 확인한다.
- desktop GL과 GLES/WebGL에서 framebuffer completeness, 실제 sample 수와 지원 최대값을 검사한다.
- 호출자가 `GL_MULTISAMPLE`을 끈 상태, 다른 FBO를 바인딩한 상태 등 공유 context 시나리오를 테스트한다.
- transparent target에서 premultiplied alpha가 edge color와 올바르게 resolve되는지 확인한다.
- pixel test는 GPU별 sample 위치 차이를 허용하되 intermediate coverage 존재, 경계 폭, 대칭성의 범위를 고정한다.
- 전체 GL/WGPU/CPU test와 sanitizer 가능한 build를 실행한다.
- sample 수·추가 state query·readback이 production path에 남지 않는지 확인하고 representative Lottie의 frame time과 memory를 비교한다.
