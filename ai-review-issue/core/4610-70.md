- 실현 가능성: **중간 이상** — 현재 batch 객체가 한 논리 작업 안에 여러 stencil task를 보관할 수 있어 구조적 기반은 있다. 다만 uniform gap을 안전하게 건너뛰는 index/layout 설계와 성능 회귀 테스트가 선행되어야 한다.

## 이슈 요약

겹치지 않고 stencil 상태도 호환되는 gradient shape는 하나의 stencil draw로 합칠 수 있지만 현재는 각각 별도 draw가 된다. gradient 한 개의 stencil vertex가 기록된 뒤 같은 staging buffer에 transform/gradient uniform 데이터가 들어가고, 다음 shape의 vertex가 그 뒤에 기록된다. 기존 merge는 두 vertex 구간이 byte 단위로 바로 이어져야 한다고 가정하므로 이 uniform gap에서 실패한다.

또한 현재 batch의 전체 호환성 검사에 물리 vertex/index 한도까지 포함되어 있다. 한도를 넘으면 현재 stencil draw만 닫고 같은 논리 stencil-cover batch 안에서 새 draw를 시작할 수 있는데도, 외부 batch 전체를 닫는다. 목표는 렌더링 순서와 기존 세 개 GPU buffer upload를 보존하면서 이 두 경계를 분리하는 것이다.

## main 코드 조사

[`GlStencilCoverBatch`의 한도](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/renderer/gpu_engine/gl/tvgGlStencilCoverBatch.cpp#L31-L43)는 native GL과 WebGL에 서로 다른 최대 region/vertex/index 수를 둔다. 따라서 새 병합도 작은 WebGL 한도를 독립적으로 지켜야 한다.

현재 [`mergeable()`](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/renderer/gpu_engine/gl/tvgGlStencilCoverBatch.cpp#L202-L219)는 같은 pass와 마지막 task, stencil mode, clipped 상태, 유효 bounds, region 수, 비겹침을 검사한다. 여기에 현재 물리 stencil task의 vertex/index 한도까지 함께 검사한다. 한도를 넘으면 `draw()`가 [`emitSingle()`로 새 외부 `GlStencilCoverTask`](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/renderer/gpu_engine/gl/tvgGlStencilCoverBatch.cpp#L223-L252)를 만들어 논리 batch도 끊어진다.

반면 기존 [`append()`](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/renderer/gpu_engine/gl/tvgGlStencilCoverBatch.cpp#L255-L276)는 물리 stencil merge가 실패하면 같은 `GlStencilCoverTask`의 `mStencilTasks`에 새 task를 추가하고 다음 merge target으로 설정할 수 있다. 즉, 물리 한도 도달만으로 외부 batch를 닫을 필요는 없는 구조다.

물리 [`merge()`](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/renderer/gpu_engine/gl/tvgGlStencilCoverBatch.cpp#L279-L311)는 program, view matrix, layout 속성, array buffer와 연속된 index 구간을 확인한다. 핵심 조건은 기존 `layout.offset + vertexCount * stride`가 다음 `appendLayout.offset`과 정확히 같아야 한다는 것이다. 성공하면 [`buildIndices()`](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/renderer/gpu_engine/gl/tvgGlStencilCoverBatch.cpp#L81-L91)와 누적 `vertexCount`로 다음 index를 재작성한다.

gradient 그리기에서는 [`drawPrimitiveGeometry()`가 먼저 stencil geometry를 staging buffer에 기록](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/renderer/gpu_engine/gl/tvgGlRenderer.cpp#L376-L391)한다. 그 뒤 같은 `mGpuBuffer`에 [`TransformInfo`](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/renderer/gpu_engine/gl/tvgGlRenderer.cpp#L393-L416)와 [linear/radial `GradientInfo`](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/renderer/gpu_engine/gl/tvgGlRenderer.cpp#L427-L501)를 push한다. 다음 gradient의 vertex offset은 이전 vertex 끝이 아니라 이 uniform block들 뒤에 있으므로 현재의 인접 조건을 만족하지 못한다.

cover task는 gradient마다 다른 uniform binding을 가지며, [`mergeCover()`는 binding resource가 있으면 병합하지 않는다](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/renderer/gpu_engine/gl/tvgGlStencilCoverBatch.cpp#L315-L345). 따라서 이번 목표는 gradient cover draw까지 하나로 만드는 것이 아니라, 호환되는 stencil geometry draw를 줄이는 것으로 읽는 것이 안전하다.

[`GlStageBuffer::flushToGPU()`](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/renderer/gpu_engine/gl/tvgGlGpuBuffer.cpp#L163-L192)는 main, auxiliary, index buffer를 각각 업로드한다. 별도 stencil buffer를 새로 만들면 기존 세 번 업로드라는 제약을 깨뜨릴 수 있으므로, 기존 buffer 안에서 gap을 표현하거나 기존 업로드 구조 안에서 geometry를 compact해야 한다.

Khronos의 [`glDrawElements` 참조](https://registry.khronos.org/OpenGL-Refpages/gl4/html/glDrawElements.xhtml)는 index 배열의 요소로 primitive를 구성하는 indexed draw를 정의한다. [`glVertexAttribPointer` 참조](https://registry.khronos.org/OpenGL-Refpages/gl4/html/glVertexAttribPointer.xhtml)는 vertex attribute의 시작 pointer와 stride가 배열 해석을 결정한다고 설명한다. 따라서 gap을 허용하려면 단순 정점 개수가 아니라 실제 attribute byte offset에 대응하는 index/base 계산이 필요하다.

## 원인 분석

### 확인된 사실

- gradient stencil geometry를 기록한 뒤 다음 gradient geometry 전에 transform/gradient uniform bytes가 같은 main staging buffer에 기록된다.
- 현재 stencil merge는 두 vertex layout이 byte 단위로 연속일 때만 성공한다.
- index 병합은 누적 `vertexCount`를 base로 incoming index를 다시 쓴다.
- outer `mergeable()`은 논리 호환성과 물리 vertex/index 한도를 함께 검사한다.
- `append()`는 물리 merge 실패 시 같은 outer task 안에서 새 stencil task를 시작할 수 있다.
- gradient cover는 binding resource가 있어 현재 cover merge 대상이 아니다.
- 현재 GPU flush는 main, auxiliary, index의 세 buffer upload를 수행한다.

### 추론과 판단

- gradient uniform gap이 현재 이슈에서 stencil draw 병합을 막는 직접적인 이유다. program이나 stencil mode가 같아도 연속 layout 조건에서 거절된다.
- gap을 포함한 실제 vertex span이 stride로 정확히 나누어지고 같은 array buffer를 참조한다면, 다음 geometry의 base를 byte offset 차이에서 계산해 index를 재작성할 수 있다. 이 경우 gap 구간은 index가 참조하지 않으므로 draw 대상 vertex가 되지 않는다.
- 다만 gap bytes가 vertex stride에 정렬되지 않거나 base/index 범위를 넘으면 병합하면 안 된다. 이 판단은 구현 전에 실제 정렬 결과와 buffer allocator 계약으로 확인해야 한다.
- 물리 cap은 `merge()`의 실패 사유로 처리하고 outer batch는 유지하는 편이 현재 `append()` 구조와 맞는다. 새 stencil task가 다음 물리 merge target이 되어야 한다.
- 별도 네 번째 GPU buffer를 추가하는 것보다 기존 main buffer offset을 안전하게 활용하거나 기존 세 buffer 중 하나에서 stencil geometry를 compact하는 방향이 요구사항에 부합한다.

## 구현 방향

1. outer batch 호환성에서 다음만 유지한다: pass/task 연속성, stencil mode, clipped 상태, 유효/비중첩 bounds와 region cap.
2. 물리 vertex/index 한도는 `merge()`에서 검사한다. 한도를 넘으면 false를 반환하고 `append()`가 같은 outer task 안에 새 stencil task를 추가하도록 한다.
3. 현재 merge target의 첫 vertex offset과 incoming vertex offset 차이로 실제 base vertex를 계산하는 방안을 검토한다.
   - 같은 array buffer와 동일한 layout type/size/stride/normalization인지 확인
   - byte 차이가 stride로 나누어떨어지는지 확인
   - gap을 포함한 vertex span과 새 index가 native/WebGL 한도 안인지 확인
   - incoming index에는 단순 누적 vertex 수가 아니라 계산된 base를 더함
4. 병합 성공 후 저장하는 값도 “실제 참조 정점 수”와 “layout에서 차지한 span”을 구분한다. cap 계산이 어느 값을 제한하는지 명시한다.
5. alignment를 보장할 수 없다면 기존 세 upload 구조 안에서 stencil vertex만 연속 영역으로 compact하는 대안을 사용한다. 별도 upload 추가는 성능 목표와 함께 별도 승인을 받아야 한다.
6. gradient cover task는 각 uniform binding을 유지하고 stencil task만 병합한다.
7. draw 호출과 upload 호출을 계측하는 GL 회귀 테스트/디버그 훅을 추가해 최적화의 효과를 수치로 고정한다.

## 초심자 시작 가이드

이 이슈는 첫 GL 최적화 작업으로는 권하지 않는다. 학습 목적이라면 구현보다 아래 계측부터 독립적으로 맡는 것이 안전하다.

1. 겹치지 않는 동일 모드 linear gradient 두 개의 fixture를 만든다.
2. `glDrawElements` 호출 수와 세 buffer의 upload 호출 수를 기록한다.
3. 두 shape 사이 main buffer offset을 출력해 vertex 구간 사이에 uniform bytes가 있는지 확인한다.
4. solid fill 두 개와 비교해 기존 병합 경로가 어떤 offset/index를 만드는지 정리한다.
5. 픽셀 결과를 기준 이미지로 고정한 뒤에만 batching 코드를 변경한다.

포인터 offset, stride, base index의 단위를 모두 byte/vertex/index 중 하나로 주석에 표시한다. 단위가 섞인 산술은 화면 깨짐을 넘어 out-of-bounds GPU 접근을 만들 수 있다.

## 위험/검증

- 호환되는 비중첩 linear/radial gradient들의 stencil `glDrawElements` 수가 목표대로 줄어드는지 계측한다.
- gradient cover draw 수는 uniform binding 때문에 유지될 수 있음을 테스트 기대값에 분리해 기록한다.
- 겹치는 bounds, 다른 pass, 다른 stencil mode, clip 경계, view matrix 차이는 병합되지 않는지 확인한다.
- uniform gap이 stride 정렬된 경우와 정렬되지 않은 경우를 각각 검사하고 후자는 안전하게 새 물리 task로 분리한다.
- vertex/index cap 직전, 정확한 한도, 한도 초과를 테스트해 초과 시 outer batch가 아니라 physical stencil task만 바뀌는지 확인한다.
- native GL과 더 작은 WebGL 한도를 각각 사용해 index overflow와 제한 초과가 없는지 확인한다.
- 병합 전후 픽셀 비교를 linear/radial, fill/stroke, opacity, blend, clip 조합에서 수행한다.
- main/aux/index의 GPU upload 횟수가 기존 세 번으로 유지되는지 계측한다.
- ASan/UBSan과 GL debug output으로 CPU index rewrite 범위 및 GPU invalid operation을 확인한다.
- 최적화 전후 CPU batch 시간과 GPU draw 수를 함께 측정해 draw 감소가 buffer 처리 비용 증가를 상쇄하는지 확인한다.
