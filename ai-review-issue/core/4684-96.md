## 이슈 요약

이 이슈는 current WebGPU backend가 path를 CPU에서 triangle mesh로 tessellate하고 GPU stencil·cover pass와 4× MSAA로 채우는 대신, compute shader에서 scanline coverage를 계산할 수 있는지 탐색하자는 제안이다. 특히 매 frame geometry가 바뀌는 animated path에서는 tessellation, staging upload, stencil pass와 multisampling 비용이 반복될 수 있다는 문제의식이 있다.

제안은 기존 경로가 잘못되었거나 compute 방식이 반드시 더 빠르다고 주장하지 않는다. 이슈 자체가 초기 토론 초안이며, CPU scanline renderer와 외부 알고리즘 자료를 출발점으로 GPU에 맞는 자료구조·병렬화 방법과 실제 trade-off를 조사하는 범위다. 따라서 완료 조건도 곧바로 renderer를 교체하는 것이 아니라 대표 workload에서 정확성과 end-to-end 비용을 비교할 수 있는 prototype, benchmark와 채택 기준을 마련하는 것으로 잡는 편이 안전하다.

## main 코드 조사

WebGPU shape 준비 단계의 [`WgRenderDataShape::updateMeshes()`](https://github.com/thorvg/thorvg/blob/c4f274fe38da46a1ddaa111d287675d85c7fc252/src/renderer/gpu_engine/wg/tvgWgRenderData.cpp#L144-L203)는 먼저 기존 mesh를 해제한 뒤 path를 GPU 친화적인 outline으로 변환하고, 일반 fill에는 `WgBWTessellator`, thin fill·stroke에는 `WgStroker`를 사용한다. 함수에는 path가 바뀌지 않았을 때 mesh를 재사용해야 한다는 주석도 있어, scanline 전환과 별개로 cache가 반복 준비 비용을 줄일 가능성도 함께 측정해야 한다.

[`WgBWTessellator::tessellate()`](https://github.com/thorvg/thorvg/blob/c4f274fe38da46a1ddaa111d287675d85c7fc252/src/renderer/gpu_engine/wg/tvgWgTessellator.cpp#L417-L498)는 CPU에서 contour를 읽고 cubic을 여러 line segment로 flatten한 뒤 첫 contour vertex를 기준으로 triangle을 만든다. 이 단계는 convex 여부도 함께 조사한다. 즉 current main에서 GPU에 전달되는 핵심 입력은 original curve나 edge list가 아니라 이미 CPU에서 생성된 vertex/index mesh다.

생성된 geometry는 [`WgRenderDataShape::updateBuffer()`](https://github.com/thorvg/thorvg/blob/c4f274fe38da46a1ddaa111d287675d85c7fc252/src/renderer/gpu_engine/wg/tvgWgRenderData.cpp#L505-L512)에서 shape mesh, bounding box와 stroke mesh별 staging buffer에 추가되고, [`WgRenderData::flush()`](https://github.com/thorvg/thorvg/blob/c4f274fe38da46a1ddaa111d287675d85c7fc252/src/renderer/gpu_engine/wg/tvgWgRenderData.cpp#L599-L603)가 vertex/index data를 GPU buffer에 업로드한다. compute prototype은 이 mesh upload를 줄이는 대신 curve 또는 edge data와 scanline bin을 위한 새로운 buffer·upload·lifetime 비용을 도입한다.

current fill pipeline은 [`WgPipelines`의 multisample 설정](https://github.com/thorvg/thorvg/blob/c4f274fe38da46a1ddaa111d287675d85c7fc252/src/renderer/gpu_engine/wg/tvgWgPipelines.cpp#L158-L170)에서 4× MSAA와 1× 상태를 만들고, [fill rule별 stencil operation](https://github.com/thorvg/thorvg/blob/c4f274fe38da46a1ddaa111d287675d85c7fc252/src/renderer/gpu_engine/wg/tvgWgPipelines.cpp#L201-L213)은 NonZero에 증가·감소 wrap, EvenOdd에 invert를 사용한다. 이어서 [stencil, depth 복사·병합과 fill cover pipeline](https://github.com/thorvg/thorvg/blob/c4f274fe38da46a1ddaa111d287675d85c7fc252/src/renderer/gpu_engine/wg/tvgWgPipelines.cpp#L259-L358)이 별도로 구성된다. 새 coverage 경로는 이 두 fill rule의 결과를 동일하게 보존해야 한다.

[`WgCompositor::drawShape()`](https://github.com/thorvg/thorvg/blob/c4f274fe38da46a1ddaa111d287675d85c7fc252/src/renderer/gpu_engine/wg/tvgWgCompositor.cpp#L567-L606)는 convex path는 mesh를 곧바로 그리지만 complex path는 mesh로 stencil 값을 만든 뒤 bounding-box cover를 paint로 채운다. [custom blend 경로](https://github.com/thorvg/thorvg/blob/c4f274fe38da46a1ddaa111d287675d85c7fc252/src/renderer/gpu_engine/wg/tvgWgCompositor.cpp#L609-L650)는 target을 복사하고 render pass를 다시 연 뒤 같은 stencil·cover 순서를 사용하며, [clip 경로](https://github.com/thorvg/thorvg/blob/c4f274fe38da46a1ddaa111d287675d85c7fc252/src/renderer/gpu_engine/wg/tvgWgCompositor.cpp#L653-L688)는 stencil과 depth/stencil merge를 결합한다. coverage texture를 추가하면 solid fill만 바꾸는 것으로 끝나지 않고 이 pass ordering과 clip·blend 계약에 연결해야 한다.

render target은 [`WgRenderTarget::initialize()`](https://github.com/thorvg/thorvg/blob/c4f274fe38da46a1ddaa111d287675d85c7fc252/src/renderer/gpu_engine/wg/tvgWgRenderTarget.cpp#L25-L36)에서 1× storage texture와 4× MSAA attachment를 모두 만들고, compositor는 [4× color/depth-stencil attachment에서 1× texture로 resolve하는 pass](https://github.com/thorvg/thorvg/blob/c4f274fe38da46a1ddaa111d287675d85c7fc252/src/renderer/gpu_engine/wg/tvgWgCompositor.cpp#L168-L197)를 구성한다. compute coverage가 MSAA를 완전히 대체할지, edge mask에만 쓰고 이후 pass는 유지할지에 따라 memory와 bandwidth 모델이 크게 달라진다.

backend에는 [generic compute pipeline 생성 helper](https://github.com/thorvg/thorvg/blob/c4f274fe38da46a1ddaa111d287675d85c7fc252/src/renderer/gpu_engine/wg/tvgWgPipelines.h#L123-L128)와 [구현](https://github.com/thorvg/thorvg/blob/c4f274fe38da46a1ddaa111d287675d85c7fc252/src/renderer/gpu_engine/wg/tvgWgPipelines.cpp#L75-L88)이 이미 있다. 그러나 current main에는 path edge, scanline bin, coverage accumulation 또는 scanline resolve를 위한 전용 compute shader·buffer·dispatch 경로가 없다. 기반 API helper가 있다는 사실과 새 rasterizer의 구현 비용은 구분해야 한다.

CPU renderer는 정확성 reference로 활용할 수 있다. [`_horizLine()`](https://github.com/thorvg/thorvg/blob/c4f274fe38da46a1ddaa111d287675d85c7fc252/src/renderer/cpu_engine/tvgSwRle.cpp#L314-L367)은 누적 cover와 area를 EvenOdd·NonZero 규칙에 맞게 0–255 coverage로 바꾸고 span을 기록하며, [`_sweep()`](https://github.com/thorvg/thorvg/blob/c4f274fe38da46a1ddaa111d287675d85c7fc252/src/renderer/cpu_engine/tvgSwRle.cpp#L370-L390)은 한 row의 cell을 왼쪽부터 순회해 coverage를 resolve한다. [edge traversal](https://github.com/thorvg/thorvg/blob/c4f274fe38da46a1ddaa111d287675d85c7fc252/src/renderer/cpu_engine/tvgSwRle.cpp#L520-L620)은 cell별 cover와 area를 누적한다. 이 순차적 구현은 expected pixel을 제공하지만 그대로 GPU에 옮기면 row dependency와 불규칙 memory access가 병렬성을 제한하므로 algorithm specification과 구현 구조를 분리해야 한다.

현재 WebGPU test fixture는 [`TestWgEngine`](https://github.com/thorvg/thorvg/blob/c4f274fe38da46a1ddaa111d287675d85c7fc252/test/testWgEngine.h#L35-L108)에서 compatibility-level adapter/device와 render texture를 만들고, [engine test](https://github.com/thorvg/thorvg/blob/c4f274fe38da46a1ddaa111d287675d85c7fc252/test/testWgEngine.cpp#L33-L138)는 여러 mask·blend 조합의 API 성공을 검사한다. gradient·mask·blend를 추가로 다루는 [후반 test](https://github.com/thorvg/thorvg/blob/c4f274fe38da46a1ddaa111d287675d85c7fc252/test/testWgEngine.cpp#L248-L337)도 draw·sync 성공이 중심이며 pixel readback이나 reference image 비교 helper는 보이지 않는다. coverage backend를 평가하려면 submission 성공보다 강한 pixel oracle부터 추가해야 한다.

## 원인 분석

### 확인된 사실

- 이 이슈는 렌더링 오류의 root cause를 보고한 bug가 아니라 alternative rasterization의 성능·구조적 타당성을 묻는 초기 제안이다.
- current WebGPU path는 CPU에서 curve flattening과 triangle mesh 생성을 수행하고, staging vertex/index buffer를 GPU에 업로드한다.
- complex fill은 stencil mesh pass 뒤 bounding-box cover pass를 사용하며 NonZero와 EvenOdd는 서로 다른 stencil operation으로 구현된다.
- color와 depth/stencil render target은 4× MSAA로 그린 뒤 1× texture로 resolve된다.
- generic compute pipeline helper는 있지만 scanline edge·bin·coverage용 shader, storage buffer와 pass scheduling은 없다.
- CPU scanline 구현에는 cover·area 누적과 두 fill rule을 coverage span으로 바꾸는 reference logic이 있다.
- current WebGPU tests는 다양한 API 경로의 성공을 다루지만 pixel readback 기반의 rasterization 정확성 비교 체계는 제공하지 않는다.

### 추론과 판단

- **성능 가설:** animated path에서 CPU tessellation, mesh upload, stencil과 MSAA 비용이 반복될 수 있다는 주장은 구조상 타당하다. 다만 각 단계가 실제 frame time에서 차지하는 비중은 workload와 platform별 계측 전에는 확정할 수 없다.
- **대안 가설:** compute scanline은 triangle·stencil 비용을 줄일 수 있지만 edge binning, atomic accumulation, prefix scan, coverage texture write/read와 additional dispatch 비용을 새로 만든다. small·convex·static path에서는 current path보다 느릴 가능성도 있다.
- **단순 이식 불가:** CPU RLE의 left-to-right sweep는 row 내 순서가 있다. GPU에서는 edge를 tile/scanline에 binning하고 boundary contribution을 병렬로 만든 뒤 prefix sum 또는 동등한 resolve 단계를 두는 별도 설계가 필요하다.
- **경쟁하는 작은 최적화:** `updateMeshes()`의 unconditional release와 cache TODO를 먼저 개선하면 static 또는 unchanged path의 반복 비용을 훨씬 작은 변경으로 줄일 수 있다. scanline benchmark는 mesh cache가 적용된 baseline도 포함해야 한다.
- **메모리 동기화:** WGSL atomic은 단일 위치의 read-modify-write를 제공하지만 서로 다른 workgroup 사이에 일반적인 barrier를 제공하지 않는다. global scan을 한 dispatch 안의 암묵적 순서에 의존시키지 말고 stage별 dispatch와 명시적인 resource usage transition으로 설계해야 한다.
- **portability 판단:** compatibility-level adapter에서도 동작해야 하므로 optional subgroup 기능이나 특정 vendor의 wave size를 필수 전제로 삼지 않는 편이 안전하다. device limit와 buffer 크기를 넘으면 current render path로 fallback해야 한다.
- **채택 판단:** prototype이 일부 benchmark에서 빠른 것만으로 기본 경로를 바꾸면 안 된다. pixel equivalence, worst-case memory, multiple backend의 latency와 representative frame 전체 비용을 통과한 shape class에만 선택적으로 적용하는 것이 현실적이다.

## 구현 방향

1. 먼저 기존 pipeline을 구간별로 계측한다.
   - path flattening·tessellation CPU 시간과 생성 vertex/index 수
   - staging upload byte와 queue submission 시간
   - stencil, cover와 MSAA resolve GPU 시간
   - static, transform-only, 매 frame path mutation을 분리한 end-to-end frame time
2. 첫 prototype의 범위를 solid fill, transform된 non-stroke path와 제한된 target 크기로 고정한다. current path는 항상 fallback으로 유지하고 runtime flag나 개발용 switch로 A/B 비교한다.
3. CPU에서 curve를 flatten한 edge list를 만드는 단계는 우선 유지해 알고리즘 위험을 줄인다. CPU tessellation mesh와 edge-list upload의 비용을 같은 입력에서 비교한 뒤 curve flattening의 GPU 이전은 후속 단계로 분리한다.
4. GPU 자료 흐름을 여러 dispatch로 명시한다.
   - edge를 screen-space tile 또는 scanline에 count·binning
   - boundary cell의 signed cover·area contribution 생성
   - row별 prefix scan으로 winding과 span resolve
   - 0–255 coverage texture 또는 compact span buffer 출력
   - existing paint shader가 coverage를 곱해 solid·gradient·image fill 수행
5. atomic contention과 memory 상한을 통제한다. per-tile local accumulation, prefix offsets와 bounded list를 사용하고 edge·tile 수, coordinate 범위 또는 allocation이 cap을 넘으면 current tessellation path로 되돌린다.
6. EvenOdd와 NonZero를 algorithm input으로 만들고 CPU RLE가 내는 coverage와 비교한다. fill rule을 paint 단계에서 근사하지 않고 winding resolve 단계에서 정확히 반영한다.
7. coverage texture가 기존 clip, mask, custom blend와 depth/stencil merge 중 어느 단계에 들어가는지 resource-state diagram과 pass contract로 먼저 고정한다. 첫 PR에서 모든 composition을 동시에 지원하지 말고 미지원 조합은 명시적으로 fallback한다.
8. pixel readback fixture와 benchmark harness를 prototype보다 먼저 또는 같은 실험 branch에 둔다. correctness failure, unsupported device limit와 성능 threshold에서 자동으로 기존 경로를 선택하도록 한다.

production patch 하나로 전체 renderer를 교체하기보다 “계측 → 제한된 compute prototype → correctness 범위 확대 → 선택 정책”의 네 단계로 나누는 편이 review와 rollback에 유리하다.

## 초심자 시작 가이드

전체 구현은 초심자에게 적합하지 않지만, 재현·계측 기반의 하위 작업은 기여할 수 있다.

1. WebGPU test target에 작은 non-convex path, hole과 self-intersection을 추가하고 현재 renderer의 RGBA texture를 CPU로 readback하는 helper를 만든다.
2. 같은 geometry를 Software backend로 render해 pixel buffer를 기준값으로 저장하고, alpha 차이의 최대값·평균값·불일치 pixel 수를 출력한다.
3. static path, transform만 바뀌는 path, path command가 매 frame 바뀌는 세 workload를 만들어 update·draw·sync 시간을 별도로 기록한다.
4. `updateMeshes()`, buffer flush, stencil/cover pass와 MSAA resolve에 debug marker 또는 timestamp를 붙여 “느릴 것”이라는 가설을 단계별 수치로 바꾼다.
5. 첫 compute 연습은 path 대신 몇 개의 synthetic edge를 storage buffer에 넣고 tile별 edge count를 계산하는 shader로 제한한다. overflow, empty tile과 device limit fallback test를 함께 둔다.
6. CPU RLE의 한 scanline에서 만들어지는 cover·area와 synthetic compute 결과를 dump해 같은 winding·coverage를 내는지 확인한 뒤 여러 row로 확장한다.

이 하위 작업만으로도 알고리즘 선택에 필요한 evidence와 test infrastructure를 제공하며, renderer 기본 경로를 건드리지 않아 검토 범위가 명확하다.

## 위험/검증

- convex·concave·hole·multiple contour·self-intersection을 EvenOdd와 NonZero 각각에서 CPU renderer의 pixel 결과와 비교한다.
- 수평·수직 edge, coincident edge, zero-length segment, very thin geometry와 scanline 경계에 정확히 놓인 vertex의 double count 규칙을 고정한다.
- cubic flattening tolerance, 큰 scale·translation, 음수·매우 큰 좌표와 target 밖 geometry가 overflow나 out-of-bounds write를 만들지 않는지 검사한다.
- coverage가 0, 1–254, 255인 edge·interior pixel을 직접 검증하고 4× MSAA baseline과 허용 가능한 차이 범위를 문서화한다.
- solid, opacity, linear/radial gradient와 image fill에서 coverage가 paint alpha에 한 번만 적용되는지 확인한다.
- clip chain, alpha/luma mask, custom blend, group opacity와 viewport scissor 조합은 지원 여부를 명시하고 미지원이면 current path로 fallback하는지 검사한다.
- stroke join·cap·dash와 thin stroke는 fill prototype에 암묵적으로 포함하지 말고 current stroker 경로를 유지한 뒤 별도 milestone로 검증한다.
- edge-per-tile가 몰리는 pathological path에서 atomic contention, list overflow와 temporary buffer peak를 기록한다.
- empty path, allocation 실패, device lost, 낮은 storage-buffer limit와 target resize에서 resource lifetime과 fallback을 검사한다.
- native Vulkan·Metal·D3D 계열과 Wasm 환경의 representative adapter에서 correctness와 성능을 따로 기록한다. optional GPU 기능이 없을 때도 기존 경로가 유지되어야 한다.
- static, transform-only, animated path를 small/medium/large geometry로 나누고 CPU time, upload byte, dispatch 수, GPU time, peak memory와 total frame time을 비교한다.
- current mesh cache 가능성을 반영한 baseline, current 4× MSAA path와 compute prototype을 동일한 scene·warm-up·반복 횟수로 측정한다.
- WebGPU validation error, shader compilation warning, sanitizer와 전체 engine test를 실행하고 pixel suite가 없는 단순 `sync()` 성공을 정확성 통과로 간주하지 않는다.
