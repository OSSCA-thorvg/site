- 초심자 추천: 비추천 (공개 C++/C ABI, 일곱 객체 계층, 비소유 pointer의 수명·복제·동시성 계약을 함께 설계해야 함)

- 실현 가능성: **중간 이상** — 대부분의 대상은 이미 내부 `Impl`을 가지며 C API도 opaque handle이라 pointer 한 칸과 새 symbol을 추가할 수 있다. 다만 API 이름보다 먼저 “library가 pointer를 소유하지 않는다”, “duplicate에는 무엇이 들어간다”, “동시 접근을 보장하는가”를 확정하지 않으면 language binding에서 use-after-free를 만들 수 있다.

## 이슈 요약

언어별 wrapper object와 native instance를 연결할 수 있도록 `Accessor`, `Animation`, `Canvas`, `Fill`, `Paint`, `Saver`, `Video` 각각에 임의의 user-data pointer를 저장하고 되찾는 API를 추가해 달라는 제안이다. 같은 기능을 flat C API에도 노출해야 한다.

요청은 렌더링 결과를 바꾸는 기능이 아니라 객체 identity를 binding runtime과 연결하는 기반 API다. 구현의 핵심은 `void*` 필드 한 개보다 그 pointer의 소유자, 유효 기간, 복제와 해제 시 의미를 공개 계약으로 만드는 데 있다.

분석한 current `main`에는 객체에 붙는 범용 user-data slot이 없고 이 이슈를 구현한다고 표시한 열린 source PR도 확인되지 않았다. `void* data`라는 이름의 기존 API는 있지만 callback 호출 때 전달되는 context이므로 이 요청을 충족하지 않는다.

## main 코드 조사

공개 C++ API의 대상은 [Paint와 Fill](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/inc/thorvg.h#L398-L885), [Canvas](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/inc/thorvg.h#L890-L915), [Animation·Saver·Accessor](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/inc/thorvg.h#L2588-L2885), extra media header의 [Video](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/src/loaders/media/thorvg_media.h#L8-L168)다. `Paint`를 상속하는 Shape/Scene/Picture/Text와 `Fill`을 상속하는 두 gradient는 base method 하나로 함께 지원할 수 있다.

공통 macro는 [copy를 금지하고 public `Impl* pImpl`을 배치](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/inc/thorvg.h#L45-L64)한다. 그러나 구현 형태는 완전히 같지 않다. `Canvas`, `Animation`, `Saver`, `Video`는 heap-allocated Impl을 소유하고, [Canvas destructor](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/src/renderer/tvgCanvas.cpp#L40-L52)와 [Video destructor](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/src/loaders/media/tvgVideo.cpp#L35-L62)에서 삭제한다.

`Paint`의 concrete implementation은 [각 derived object 안에 `Paint::Impl`을 포함](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/src/renderer/tvgPaint.h#L44-L78)하고 public `pImpl`이 이를 가리킨다. `Fill`도 [gradient 구현 안에 `Fill::Impl`을 포함하고 그 주소를 연결](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/src/renderer/tvgFill.h#L81-L101)한다. 따라서 public base object에 새 data member를 직접 추가할 필요 없이 각 Impl에 동일한 초기값 `nullptr`을 둘 수 있다.

`Accessor`는 예외다. current factory는 [`AccessorImpl : Accessor`를 직접 생성](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/src/renderer/tvgAccessor.cpp#L31-L48)하고 public macro가 선언한 `pImpl`을 초기화하거나 사용하지 않는다. accessor method는 `this`를 `AccessorImpl*`로 cast한다. user data를 공통 Impl 접근 방식으로 구현하려면 이 특수 구조를 그대로 지원하거나 Accessor 내부 구조를 먼저 정리해야 한다.

flat C header는 [일곱 대상을 모두 opaque pointer typedef](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/src/bindings/capi/thorvg_capi.h#L59-L98)로 노출한다. implementation은 이 handle을 C++ object로 cast한다. 예를 들어 [`tvg_paint_get_id`와 `set_id`](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/src/bindings/capi/tvgCapi.cpp#L198-L217)는 direct getter와 `Tvg_Result` setter를 사용하고 null handle을 0 또는 `INVALID_ARGUMENT`으로 처리한다. user-data API도 모든 handle에서 같은 null 정책과 naming을 유지해야 한다.

현재 C++의 [Accessor callback](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/inc/thorvg.h#L2825-L2836)과 C API의 [`tvg_accessor_set`](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/src/bindings/capi/tvgCapi.cpp#L1181-L1185)은 `void* data`를 callback argument로 전달한다. Picture asset resolver도 같은 context pattern을 쓴다. 이 값들은 등록된 callback 호출에 종속되며 “객체에서 언제든 조회하는 metadata slot”은 아니다.

복제 계약이 가장 중요한 열린 결정이다. [`Paint::Impl::duplicate()`](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/src/renderer/tvgPaint.cpp#L145-L160)은 concrete 속성을 복제한 뒤 transform, blend, opacity, visibility를 복사한다. [`Fill`의 두 duplicate 경로](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/src/renderer/tvgFill.h#L81-L101)도 Impl의 gradient 속성을 복사한다. 새 user-data slot을 기계적으로 Impl 전체와 함께 복사하면 원본 wrapper pointer가 별도 native object 두 개를 가리키는 모순이 생긴다.

Paint는 [reference count와 Canvas 소유권 이전](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/inc/thorvg.h#L719-L780)을 지원하고, Animation과 Video는 각각 내부 Picture를 소유한다. Saver는 비동기로 동작할 수 있고 Canvas update도 thread를 사용할 수 있다. 따라서 pointer를 저장한다는 사실이 대상 wrapper의 수명을 연장하거나 worker thread에서 안전한 접근을 보장한다고 해석되어서는 안 된다.

현재 C API 생성·해제도 객체마다 다르다. [Canvas는 engine별 create와 destroy](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/src/bindings/capi/tvgCapi.cpp#L64-L93)를 사용하고, [Animation과 Accessor](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/src/bindings/capi/tvgCapi.cpp#L1083-L1185)는 `new/del`, Video는 media feature guard 안의 `new/del`을 사용한다. 한 종류만 test하면 나머지 handle의 cast나 feature guard 누락을 잡을 수 없다.

## 원인 분석

### 확인된 사실

- 요청된 일곱 C++ class와 대응 opaque C handle이 모두 존재한다.
- current API에는 객체에 저장·조회하는 공통 user-data slot이 없다.
- 기존 `void* data`는 Accessor/asset resolver callback context이며 object metadata가 아니다.
- Paint 하나의 API로 Shape, Scene, Picture, Text concrete type을 포괄하고 Fill 하나로 두 gradient를 포괄할 수 있다.
- 대부분 대상은 Impl 저장소가 있지만 Accessor는 derived implementation을 직접 cast하는 특수 구조다.
- Paint와 Fill에는 새 native instance를 만드는 duplicate API가 있다.
- Paint는 reference count와 소유권 이전을 지원하고 Canvas/Saver 작업은 비동기일 수 있다.
- Video API와 구현은 media feature 조건부다.

### 추론과 판단

- **요청의 직접 원인:** binding은 native handle만으로 대응 language wrapper를 역조회할 공통 위치가 없어 별도 전역 map을 유지해야 한다. 객체 slot은 이 identity lookup 비용과 관리 복잡도를 줄일 수 있다.
- **권장 소유권:** 단순 `void*` API라면 library가 값을 delete/free하지 않는 non-owning pointer로 문서화하는 것이 가장 예측 가능하다. destroy callback까지 호출하려면 callback thread, 교체 시 호출 순서, 재진입과 예외 경계를 별도 설계해야 하므로 이번 최소 범위와 분리하는 편이 안전하다.
- **권장 복제 의미:** duplicate 결과의 user data는 `nullptr`로 초기화해야 한다. user data는 native rendering property가 아니라 특정 wrapper instance와의 association이므로 같은 pointer를 복사하면 alias와 double-finalization 위험이 생긴다. 다른 정책이 필요하다면 반드시 명시적 test와 문서가 있어야 한다.
- **동시성 판단:** raw pointer set/get을 atomic으로 만들더라도 pointee 수명까지 안전해지지는 않는다. 기본 계약은 외부 동기화가 필요한 control-plane metadata로 두고 render/update/save 진행 중 mutation을 허용하지 않는 편이 명확하다.
- **ABI 판단:** 값을 Impl에 넣으면 공개 object 크기를 바꾸지 않을 수 있고 C opaque handle layout도 노출되지 않는다. 하지만 새 exported symbol과 모든 build configuration의 link 검증은 여전히 필요하다.

## 구현 방향

1. 먼저 공통 계약을 API 문서로 확정한다.
   - 초기값과 `set(nullptr)` 결과는 `nullptr`
   - library는 pointee를 소유·해제하지 않음
   - object 파괴 시 pointer 값만 사라지고 callback은 호출하지 않음
   - 호출자가 pointee를 native object보다 오래 살게 함
   - concurrent set/get 및 render 중 mutation은 외부 동기화 대상
   - duplicate 결과는 `nullptr`
2. C++에는 각 base class에 `Result userData(void* data) noexcept`와 `void* userData() const noexcept`처럼 setter/getter를 추가한다. 기존 overload naming 관례를 따르되 `data()`처럼 의미가 넓은 이름은 피한다.
3. `Paint::Impl`, `Fill::Impl`, `Canvas::Impl`, `Animation::Impl`, `Saver::Impl`, `Video::Impl`에 `void* userData = nullptr`를 추가하고 얇은 public forwarding method를 구현한다.
4. Accessor는 `AccessorImpl` field를 직접 읽는 최소 변경 또는 정상적인 pImpl 초기화 중 하나를 선택한다. 후자는 구조 정리 범위가 커지므로 별도 refactor 없이 일관된 public 동작을 먼저 제공하는 방안이 작다.
5. flat C API에는 각 opaque handle별 set/get symbol을 제공한다. setter는 null handle에서 `TVG_RESULT_INVALID_ARGUMENT`, getter는 null handle에서 `NULL`을 반환하는 기존 direct getter 관례를 따른다.
6. Paint/Fill duplicate helper가 user data를 복사하지 않는지 명시적으로 유지한다. Impl `copy`나 assignment를 넓힐 때 pointer가 우연히 포함되지 않도록 test를 둔다.
7. `Video` 선언은 media header/C header의 feature 정책과 implementation guard를 함께 맞춘다. media-off build에서도 header symbol 계약과 link 결과가 기존 정책대로인지 확인한다.
8. ABI checker가 있다면 공개 class size와 exported symbol 차이를 기록한다. 새 API version tag와 `@since` 값을 release 정책에 맞춰 추가한다.

## 초심자 시작 가이드

전체 API 구현은 초심자 첫 작업으로 권하지 않지만, test matrix 작성은 분리해서 시작할 수 있다.

1. 각 base class로 생성 가능한 최소 concrete object를 표로 만든다: Shape, LinearGradient, SwCanvas, Animation, Saver, Accessor, Video.
2. stack의 작은 정수 주소를 쓰지 말고 수명이 test 끝까지 유지되는 dummy object의 주소를 저장한다.
3. 초기 `nullptr` → pointer 설정 → 동일 pointer 조회 → `nullptr`로 clear 순서를 C++에서 먼저 고정한다.
4. 같은 순서를 C opaque handle마다 반복하고 null handle의 setter/getter 결과를 확인한다.
5. Paint와 Fill은 duplicate 뒤 원본 pointer는 유지되고 복제본은 `nullptr`인지 별도 case로 만든다.
6. Canvas에 Paint를 넘긴 뒤와 Paint ref/unref 전후에도 wrapper가 기대한 소유권 규칙을 지키는지 sanitizer로 확인한다.

## 위험/검증

- 일곱 C++ base class와 일곱 C handle에서 초기값, set/get, overwrite, clear가 동일하게 동작해야 한다.
- null C handle은 crash 없이 문서화된 sentinel 또는 `INVALID_ARGUMENT`을 반환해야 한다.
- Shape/Scene/Picture/Text가 Paint base slot 하나를 공유하고 Linear/RadialGradient가 Fill base slot을 공유하는지 확인한다.
- Paint와 Fill duplicate는 원본의 user data를 복사하지 않으며 원본 값도 바꾸지 않아야 한다.
- Canvas 소유권 이전, Paint ref/unref와 `rel`, C destroy/del 이후 binding map이 stale handle을 사용하지 않도록 integration test를 둔다.
- Animation/Video가 소유한 Picture의 user data와 controller 자체의 user data는 서로 독립이어야 한다.
- Saver의 async save와 Canvas update/draw 중에는 user data를 rendering worker가 참조하지 않는지 확인하고, concurrent access 비보장을 문서화한다.
- media on/off, 모든 renderer 조합, static/shared library, C와 C++ compiler에서 header와 link test를 실행한다.
- exported symbol 목록과 public C++ object size를 기존 release와 비교해 의도하지 않은 ABI 변화가 없는지 확인한다.
- ASan/TSan integration으로 wrapper가 먼저 해제되는 음성 case를 점검하되, non-owning 계약 밖의 stale dereference를 library가 자동 방지한다고 기대하지 않는다.
- 향후 destroy callback을 추가한다면 pointer 교체·clear·object 파괴에서 정확히 한 번 호출되는지와 callback 재진입을 별도 설계한다.
