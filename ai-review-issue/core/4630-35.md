## 이슈 요약

`Shape::trimpath(begin, end)`는 0–1 밖의 값을 원형 범위처럼 감싼다고 문서화되어 있다. 그러나 현재 정규화 함수는 1보다 크면 1을 한 번 빼고, 0보다 작으면 1을 한 번 더할 뿐이다. 따라서 `(2.06, 2.26)`처럼 두 주기 이상 이동한 구간은 여전히 0–1 밖에 남는다.

정규화되지 않은 값은 path 전체 길이에 그대로 곱해진다. 시작 길이가 실제 path 끝보다 커지면 순회 중 어느 segment도 출력 조건을 만족하지 않아 trimmed path가 비고, 각 backend는 해당 shape를 그리지 않는다. 공개 API는 입력을 받아 `Success`를 반환하므로 사용자는 오류 대신 도형이 조용히 사라지는 현상을 보게 된다.

## main 코드 조사

C++ [`Shape::trimpath()` 문서](https://github.com/thorvg/thorvg/blob/eaa65c8c221937d882b2556a961a3449fbd322fa/inc/thorvg.h#L1405-L1420)와 [C API 문서](https://github.com/thorvg/thorvg/blob/eaa65c8c221937d882b2556a961a3449fbd322fa/src/bindings/capi/thorvg_capi.h#L1635-L1648)는 `begin`과 `end`가 0–1을 넘으면 angle wrapping과 비슷하게 원형으로 처리된다고 같은 계약을 명시한다.

공개 C++ 구현은 [`Shape::trimpath()`에서 값을 그대로 내부 상태에 저장하고 항상 `Result::Success`를 반환](https://github.com/thorvg/thorvg/blob/eaa65c8c221937d882b2556a961a3449fbd322fa/src/renderer/tvgShape.cpp#L235-L239)한다. [`ShapeImpl::trimpath()`](https://github.com/thorvg/thorvg/blob/eaa65c8c221937d882b2556a961a3449fbd322fa/src/renderer/tvgShape.h#L191-L205)도 값이 달라지면 raw `begin`, `end`, `simultaneous`를 보존하고 path update만 표시한다. 즉 API 입구에는 범위 제한이나 반복 정규화가 없다.

실제 보정은 공통 renderer의 [`_get()`](https://github.com/thorvg/thorvg/blob/eaa65c8c221937d882b2556a961a3449fbd322fa/src/renderer/tvgRender.cpp#L635-L648)에서 일어난다. 각 값에 대해 `> 1`이면 `- 1`, `< 0`이면 `+ 1`을 한 번만 적용한다. `(2.06, 2.26)`은 `(1.06, 1.26)`에 머물고, `(-2.8, -2.6)`도 `(-1.8, -1.6)`에 머문다.

이어지는 [`_trim()`](https://github.com/thorvg/thorvg/blob/eaa65c8c221937d882b2556a961a3449fbd322fa/src/renderer/tvgRender.cpp#L615-L631)은 두 값을 전체 path 길이에 곱한다. [`_trimPath()`의 segment 순회](https://github.com/thorvg/thorvg/blob/eaa65c8c221937d882b2556a961a3449fbd322fa/src/renderer/tvgRender.cpp#L548-L613)는 누적 길이가 `trimStart`와 `trimEnd`에 도달할 때만 `_trimAt()` 또는 `_add()`를 호출한다. 두 경계가 path 끝보다 크면 출력 point가 생기지 않는다.

[`RenderTrimPath::trim()`](https://github.com/thorvg/thorvg/blob/eaa65c8c221937d882b2556a961a3449fbd322fa/src/renderer/tvgRender.cpp#L652-L700)은 입력 point가 부족하거나 원래 `begin == end`인 경우에만 일찍 실패하고, `_get()` 뒤 결과가 비었는지는 마지막 `out.pts.count >= 2`로 판정한다. 따라서 큰 offset은 API 오류가 아니라 빈 outline으로 전파된다.

이 helper는 backend 공통이다. SW는 [fill/stroke outline 생성 전에 `trim()`](https://github.com/thorvg/thorvg/blob/eaa65c8c221937d882b2556a961a3449fbd322fa/src/renderer/cpu_engine/tvgSwShape.cpp#L238-L248)을 호출하고, GPU 공통 stroke path도 [`RenderTrimPath::trim()` 결과를 사용](https://github.com/thorvg/thorvg/blob/eaa65c8c221937d882b2556a961a3449fbd322fa/src/renderer/gpu_engine/tvgGpuCommon.cpp#L818-L828)한다. GL과 WG의 fill geometry 역시 각각 [동일한 공통 trim](https://github.com/thorvg/thorvg/blob/eaa65c8c221937d882b2556a961a3449fbd322fa/src/renderer/gpu_engine/gl/tvgGlGeometry.cpp#L133-L144), [공통 trim 후 optimize](https://github.com/thorvg/thorvg/blob/eaa65c8c221937d882b2556a961a3449fbd322fa/src/renderer/gpu_engine/wg/tvgWgRenderData.cpp#L178-L190) 순서를 따른다.

Lottie 경로도 [`updateTrimpath()`에서 계산한 animation 값을 같은 API로 전달](https://github.com/thorvg/thorvg/blob/eaa65c8c221937d882b2556a961a3449fbd322fa/src/loaders/lottie/tvgLottieBuilder.cpp#L822-L837)한다. offset이 여러 회전 누적되는 animation은 직접 API를 호출하는 예제와 같은 결함을 만날 수 있다.

현재 [`testShape.cpp`](https://github.com/thorvg/thorvg/blob/eaa65c8c221937d882b2556a961a3449fbd322fa/test/testShape.cpp#L208-L220)는 `(0.3, 0.88)` 호출이 `Success`인지 한 번 확인할 뿐, 생성된 path나 0–1 밖 값의 주기 동치를 검증하지 않는다.

과거 [`7c87d8e` 변경](https://github.com/thorvg/thorvg/commit/7c87d8e632eebbed0a67b1a2754a837168b0f133)은 문서를 현재 원형 범위 계약으로 바꾸면서 시작·끝의 거리가 한 바퀴 이상이면 전체 stroke를 그려야 한다고 명시했다. 이후 trim을 backend 공통 `RenderTrimPath`로 옮긴 [`eb4b286` 변경](https://github.com/thorvg/thorvg/commit/eb4b286da5f1b990feffa1af3f103d6ad1d7d97f)에는 한 번짜리 wrapping 로직은 들어왔지만 기존 full-span 판정은 함께 옮겨지지 않았다.

## 원인 분석

### 확인된 사실

- C와 C++ 공개 문서는 0–1 밖의 두 인자를 원형 범위로 wrapping한다고 명시한다.
- API와 `ShapeImpl`은 raw 값을 저장하며, 실제 정규화는 렌더 시점의 `_get()` 한 곳에서 수행한다.
- `_get()`은 각 값에 ±1을 최대 한 번만 적용하므로 두 주기 이상 떨어진 값은 정규 범위에 들어오지 않는다.
- `_trim()`은 보정 결과를 전체 길이에 곱하고, path 끝보다 큰 시작점은 빈 출력으로 이어질 수 있다.
- SW, GL, WG와 GPU 공통 stroke 생성은 모두 같은 `RenderTrimPath::trim()`을 사용한다.
- 테스트에는 정상 범위 API 반환값만 있고, 큰 양수·음수 offset이나 렌더 결과의 주기 동치 검증이 없다.
- 과거 변경 설명은 `|end - begin|`이 한 바퀴 이상이면 전체 stroke가 되어야 한다는 의도를 기록했지만, 현재 공통 구현에는 그 판정이 없다.

### 추론과 판단

- #4630의 사라짐은 backend별 rasterizer 결함보다 `_get()`의 불완전한 정규화로 설명된다. 동일한 공통 trimmed path가 비기 때문에 모든 backend가 영향을 받을 가능성이 높다.
- 단순히 `begin`과 `end`를 각각 `[0, 1)`로 modulo 처리하면 두 값 사이의 원래 길이 정보가 사라진다. 예를 들어 정확히 한 바퀴 떨어진 두 값이 같은 점으로 축약되어 빈 구간으로 오인될 수 있다.
- `begin`을 기준으로 공통 정수 offset을 두 값에서 함께 빼면 상대 길이와 방향을 보존하면서 큰 절대 offset을 제거할 수 있다.
- full-span을 `_get()`에서만 `(0, 1)`로 바꾸면 화면은 고쳐져도 `RenderTrimPath::valid()`가 raw non-default 값을 계속 “trim 활성”으로 판단해 rectangle fast path나 antialiasing 선택에 불필요한 차이를 남길 수 있다. 정규화와 활성 판정이 같은 계약을 공유하는 편이 안전하다.
- `NaN`과 무한대는 이슈 범위 밖이지만 `floorf`/modulo를 도입할 때 별도 정책 없이 통과시키면 비교와 길이 계산이 다시 빈 path를 만들 수 있으므로 명시적으로 결정해야 한다.

## 구현 방향

1. 먼저 원형 구간 계약을 테스트 표로 고정한다.
   - `begin == end`: 빈 구간
   - `|end - begin| >= 1`: 전체 path
   - 그 외: 상대 방향과 길이를 보존한 한 주기 이내 구간
2. `span = end - begin`을 정규화 전에 계산한다. full-span과 empty 판정을 raw pair에서 먼저 끝내야 modulo로 두 점이 같아지는 경우를 구분할 수 있다.
3. 부분 구간은 `shift = floorf(begin)` 같은 공통 정수 offset을 두 값에서 함께 빼 절대 회전 수만 제거한다. 이후 기존 seam 방향 판정은 정규화된 pair에 적용한다.
4. normalization 결과를 표현하는 작은 공통 helper를 두고 `RenderTrimPath::trim()`과 `valid()`/fast-path 판정이 같은 결과를 사용하게 한다. 렌더 결과와 최적화 상태가 서로 다른 계약을 갖지 않게 한다.
5. `Shape::trimpath()`가 raw 값을 보존하는 API 동작은 호환성을 위해 유지하되, finite하지 않은 입력을 허용할지 `InvalidArguments`로 거부할지 별도 정책과 테스트를 추가한다.
6. 구현 PR은 공통 renderer와 직접 회귀 테스트에 집중하고 backend별 코드를 개별 보정하지 않는다.

## 초심자 시작 가이드

1. `_get()`의 현재 로직을 작은 table test로 옮겨 `(0.06, 0.26)`, `(2.06, 2.26)`, `(-2.94, -2.74)`가 같은 정규 결과를 가져야 한다는 실패 테스트를 만든다.
2. `(0.2, 1.2)`, `(2.2, 3.2)`, `(0.8, -0.2)`처럼 정확히 한 바퀴 차이 나는 pair를 별도로 두고 전체 path 기대값을 고정한다.
3. `(0.8, 1.1)`과 `(-0.2, 0.1)`처럼 seam을 지나는 동치 pair에서 방향과 길이가 같은지 확인한다.
4. helper 테스트를 통과시킨 뒤 단순 line/rectangle에 실제 `RenderTrimPath::trim()`을 적용해 command/point 수와 끝점을 비교한다.
5. 마지막에 공개 `Shape::trimpath()`로 SW 렌더를 수행해 큰 offset에서도 기준 이미지와 pixel 결과가 같은지 확인한다.

정상 범위 한 사례만 보고 완료하지 말고, 모든 정수 `k`에 대해 부분 구간 `trim(begin + k, end + k)`가 `trim(begin, end)`와 같다는 주기 동치를 핵심 invariant로 사용한다.

## 위험/검증

- 큰 양수와 음수 공통 offset에서 기준 구간과 command/point 및 pixel 결과가 같은지 확인한다.
- `begin < end`, `begin > end`, seam 통과와 역방향 구간을 각각 검증한다.
- `begin == end`, 차이가 정확히 1, 1보다 약간 작거나 큰 값을 EPSILON 경계와 함께 검사한다.
- open/closed path, line/cubic, fill/stroke, dash가 있는 stroke를 분리해 검사한다.
- 여러 subpath에서 `simultaneous=true/false`의 길이 분배가 유지되는지 확인한다.
- SW, GL, WG가 가능한 환경에서 같은 reference image를 만들고 빈 geometry나 backend 차이가 없는지 확인한다.
- full-span non-default pair가 원본 path와 같은 결과를 내고, clip/rectangle fast path 및 antialiasing 선택에 불필요한 회귀가 없는지 확인한다.
- Lottie trim animation의 offset이 여러 회전 누적되어도 특정 frame부터 사라지지 않는지 검사한다.
- C와 C++ API가 동일한 pair에서 같은 결과를 내며 기존 정상 범위 입력의 방향과 seam 동작이 변하지 않는지 확인한다.
- `NaN`, `+Inf`, `-Inf` 정책을 정하고 sanitizer와 debug build에서 비정상 길이 계산이 전파되지 않는지 확인한다.
