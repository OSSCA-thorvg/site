## 이슈 요약

이슈는 단순 build job이 unit-test job과 사실상 같은 build configuration을 다시 컴파일해 CI 시간과 자원을 소비한다고 지적한다. 제안은 동일한 configuration이 다른 CI test에서 이미 검증되면 해당 build를 제거하고, 남은 build는 기본값의 반대 조합을 검증하도록 재구성하는 것이다.

후속 논의에서 maintainer는 기존 `build`를 제거하고 `compact_test`를 일반 `build` 역할로 바꾸며, `log=true`, 모든 loader/saver, 내장 codec, single-thread, partial rendering 비활성화, SIMD 활성화 조합을 사용하자는 구체적인 방향을 제시했다. 별도 의견으로 Ubuntu unit-test 안에서 CPU·WebGPU·OpenGL 관련 Valgrind 검증을 병렬화하는 방안이 제안됐고 maintainer도 긍정적으로 답했다.

따라서 이 작업의 성공 기준은 단순히 job 수를 줄이는 것이 아니다. 기본 configuration은 unit test가 계속 compile·install·execute해야 하고, 남기는 build는 unit test와 다른 compile-time branch를 실제로 지나야 하며, 삭제 전후 CI 소요 시간과 필수 check·artifact 계약도 보존 또는 의도적으로 갱신돼야 한다.

## main 코드 조사

현재 [Ubuntu workflow](https://github.com/thorvg/thorvg/blob/4675894a6b3acd5c4088a28b312e4bd406bfc045/.github/workflows/build_ubuntu.yml#L17-L76)는 `build`, `compact_test`, `unit_test` 세 job을 서로 독립적으로 실행한다. 기본 `build`는 CPU·GL engine, 모든 loader/saver, C binding과 추가 기능을 compile·install한다. `unit_test`는 여기에 `tests=true`를 더하고 engine을 `all`로 넓혀 같은 library를 install한 뒤 software GL 환경에서 test를 실행한다. Ubuntu에서는 engine 범위와 test 실행 면에서 `unit_test`가 기본 `build`보다 넓지만, 기본 `build`만 `log=true`를 명시하므로 두 configuration이 문자 그대로 동일하지는 않다.

[macOS workflow](https://github.com/thorvg/thorvg/blob/4675894a6b3acd5c4088a28b312e4bd406bfc045/.github/workflows/build_macos.yml#L15-L83)와 [Windows workflow](https://github.com/thorvg/thorvg/blob/4675894a6b3acd5c4088a28b312e4bd406bfc045/.github/workflows/build_windows.yml#L15-L71)도 같은 세-job 구조다. 각 `unit_test`는 기본 `build`와 같은 loader/saver·C binding·추가 기능을 compile하고 `install test`를 실행한다. 여기서도 고유한 기본-build 차이는 `log=true`이며, 이를 남는 alternative build로 옮기면 기본 build의 compile-time log branch를 잃지 않고 중복 job을 제거할 수 있다.

현재 `compact_test`는 세 OS 모두 `static=true`와 `threads=false`를 사용한다. 그러나 [`meson_options.txt`](https://github.com/thorvg/thorvg/blob/4675894a6b3acd5c4088a28b312e4bd406bfc045/meson_options.txt#L24-L53)에 따르면 `threads` 기본값은 `true`, `partial` 기본값은 `true`, `simd` 기본값은 `false`다. 후속 댓글의 `partial=false`, `simd=true`를 추가하면 남는 job 하나가 기본 unit-test와 반대 compile-time branch 네 가지(`threads`, `partial`, `simd`, 내장 codec 선택)를 함께 검증한다.

[`meson.build`](https://github.com/thorvg/thorvg/blob/4675894a6b3acd5c4088a28b312e4bd406bfc045/meson.build#L18-L47)는 `threads`와 `partial`에 따라 각각 compile-time configuration macro를 설정하고, [SIMD 선택](https://github.com/thorvg/thorvg/blob/4675894a6b3acd5c4088a28b312e4bd406bfc045/meson.build#L108-L122)은 host CPU family에 따라 AVX 또는 NEON macro와 compiler flag로 이어진다. 따라서 이 옵션들은 이름만 다른 동일 build가 아니라 서로 다른 전처리·compiler 경로를 실제로 검증한다.

주의할 점은 project option `static=true`가 ThorVG library 자체를 static library로 만드는 옵션은 아니라는 것이다. [loader build](https://github.com/thorvg/thorvg/blob/4675894a6b3acd5c4088a28b312e4bd406bfc045/src/loaders/meson.build#L15-L45)는 이 값을 PNG/JPG/WebP의 내장 구현과 외부 dependency 중 무엇을 쓸지 결정하는 데 사용한다. 반면 [`src/meson.build`](https://github.com/thorvg/thorvg/blob/4675894a6b3acd5c4088a28b312e4bd406bfc045/src/meson.build#L1-L10)는 library 종류를 Meson built-in `default_library`에서 읽는다. 즉 Windows의 `result_windows_static` artifact 이름만 보고 static library coverage라고 단정하면 안 되며, 정말 library linkage까지 검증하려면 `-Ddefault_library=static`을 별도로 논의해야 한다.

각 unit-test build는 [`tests=true`일 때 test subdirectory를 포함](https://github.com/thorvg/thorvg/blob/4675894a6b3acd5c4088a28b312e4bd406bfc045/meson.build#L173-L180)한다. [test target](https://github.com/thorvg/thorvg/blob/4675894a6b3acd5c4088a28b312e4bd406bfc045/test/meson.build#L12-L70)은 공통 library에 link되고, enabled engine과 dependency가 있으면 GL·WebGPU test source도 포함한다. 그러므로 unit-test job은 source compile만 하는 별도 도구가 아니라 기본 library build까지 포함하는 직접적인 중복 근거다.

Windows의 두 build job은 각각 [`result_windows`와 `result_windows_static` artifact를 업로드](https://github.com/thorvg/thorvg/blob/4675894a6b3acd5c4088a28b312e4bd406bfc045/.github/workflows/build_windows.yml#L25-L55)한다. current main 검색에서는 이 이름을 다운로드하는 다른 workflow가 없지만, 사용자가 수동으로 내려받거나 외부 자동화가 소비하는지는 저장소만으로 확인할 수 없다. 제거 PR에서는 artifact를 없애는 것이 의도인지, alternative build 산출물 하나만 유지할지 maintainer 확인이 필요하다.

Ubuntu `unit_test`는 test 뒤에 [Valgrind와 ASan 단계를 순차 실행](https://github.com/thorvg/thorvg/blob/4675894a6b3acd5c4088a28b312e4bd406bfc045/.github/workflows/build_ubuntu.yml#L72-L100)한다. current [Valgrind script](https://github.com/thorvg/thorvg/blob/4675894a6b3acd5c4088a28b312e4bd406bfc045/.github/workflows/memcheck_valgrind.sh#L8-L27)는 하나의 `tvgUnitTests` process 전체를 Valgrind 아래에서 실행한다. CPU·GL·WebGPU를 병렬화하려면 단순 shell background 실행이 아니라 test filter가 각 backend group을 완전히 분할하는지, 공통 test가 누락·중복되지 않는지, 여러 process의 report와 실패 status가 정확히 합쳐지는지 먼저 설계해야 한다.

## 원인 분석

### 확인된 사실

- 세 desktop OS workflow는 모두 기본 build, alternative build, unit-test의 세 독립 job을 실행한다.
- 각 unit-test job은 library를 compile·install한 뒤 test까지 실행하며, 기본 build와 loader/saver·binding·추가 기능 옵션이 대부분 겹친다.
- Ubuntu unit-test는 `engines=all`을 사용해 기본 build의 CPU·GL 범위를 포함하고 WebGPU까지 넓힌다.
- 기본 build만 `log=true`를 명시하고 unit-test는 log 기본값 `false`를 사용하므로 완전히 같은 configuration은 아니다.
- 현재 alternative build는 `threads=false`, `static=true`지만 `partial`과 `simd`는 각각 기본값 `true`, `false`를 유지한다.
- `static=true`는 내장 image loader 선택에 쓰이고, library 종류는 별도의 Meson `default_library` built-in option으로 결정된다.
- Windows의 기본·alternative build는 binary artifact를 올리며, current repository 안에서는 그 artifact 이름을 내려받는 workflow가 검색되지 않는다.
- Valgrind script는 현재 전체 unit-test executable을 한 process로 실행한다.

### 추론과 판단

- **중복의 핵심:** 기본 build의 compile·install 성공 신호는 같은 OS의 unit-test build가 대부분 포함한다. `log=true`만 alternative build로 이동하면 basic build를 제거해도 current main에서 확인되는 고유 compile branch를 보존할 수 있다.
- **남기는 job의 가치:** `threads=false`, `partial=false`, `simd=true`, 내장 loader 조합은 unit-test 기본값과 의도적으로 반대라서, 삭제한 job 수보다 높은 compile-option diversity를 한 job에 모을 수 있다.
- **static 명칭 위험:** maintainer가 말한 `static=true`의 의도가 “내장 codec”인지 “ThorVG static library”인지 구분해야 한다. 후자라면 current command는 목표를 충족하지 않으며 `default_library=static`과 소비자 link test가 필요하다.
- **artifact 소비 가능성:** 저장소 내부 참조가 없으므로 build artifact가 CI dependency일 가능성은 낮아 보이지만, 수동 release/debug 사용과 외부 소비는 검색만으로 배제할 수 없다.
- **Valgrind 병렬화는 별도 최적화:** build job 제거와 달리 test partition·report aggregation·runner memory pressure가 추가된다. 같은 PR에서 처리할 수는 있지만, 전후 시간과 오류 검출 동등성을 따로 측정하지 않으면 원인 추적이 어려워진다.
- **필수 check 변경 위험:** GitHub의 required status check는 job name을 기준으로 지정될 수 있다. `compact_test`를 `build`로 rename하거나 기존 `build` job을 삭제하면 repository ruleset/branch protection도 함께 확인해야 한다.

## 구현 방향

1. 세 workflow에서 현재 job별 OS, package, Meson option, build/install/test, artifact를 표로 만든다. “다른 job과 동일”이 아니라 고유 열이 하나라도 있는지 기준으로 삭제 대상을 확정한다.
2. 기본 `build` job을 제거하되, 그 job만 갖던 `log=true`는 남기는 alternative configuration에 옮긴다. `unit_test`는 기본값 configuration의 build·install·실행 담당으로 유지한다.
3. `compact_test`를 목적이 드러나는 `build` 또는 `alternative_build`로 바꾸고, 합의된 `log=true`, `loaders=all`, `savers=all`, `static=true`, `threads=false`, `partial=false`, `simd=true`를 명시한다. OS별로 기존 `engines`, `extra`, media loader가 빠지지 않는지도 diff에서 따로 확인한다.
4. `static=true`의 목표를 문서화한다. 내장 PNG/JPG/WebP implementation compile이 목표면 현 option을 유지하고 job/artifact 이름에서 library-static 오해를 없앤다. ThorVG static library가 목표면 `default_library=static`을 추가하고 C/C++ consumer link smoke test를 검토한다.
5. Windows artifact 정책을 결정한다. 더 이상 필요 없으면 PR 설명에 제거를 명시하고, 필요하면 남는 alternative job 또는 unit-test job에서 의미가 정확한 이름으로 업로드한다.
6. branch protection/ruleset의 required check 목록에서 삭제·rename되는 job 이름을 확인한다. workflow change를 merge하기 전에 새 check가 한 번 성공해 선택 가능해지는 순서까지 고려한다.
7. Valgrind 병렬화는 backend별 test filter 목록과 공통 test 처리 규칙을 먼저 만든다. 각 process의 exit code와 log를 수집하고 하나라도 실패하면 job을 실패시키며, 기존 단일 실행과 test case 수·오류 수가 같음을 검증한다.
8. 변경 전 최근 여러 PR의 OS별 job duration과 변경 PR의 duration을 비교한다. checkout/package install이 job 단위로 사라지는 효과, total billed time, wall-clock critical path를 구분해 기록한다.

첫 PR은 세 OS의 중복 build 제거와 alternative option 보존에 집중하고, Valgrind 병렬화는 측정 가능한 별도 commit 또는 후속 PR로 분리하는 편이 안전하다. 이렇게 하면 CI 절감 효과와 memory-test partition 변경의 영향을 각각 되돌리고 비교할 수 있다.

## 초심자 시작 가이드

1. 세 workflow의 `build`, `compact_test`, `unit_test` command를 spreadsheet나 Markdown 표로 옮기고 옵션이 생략된 경우 `meson_options.txt`의 기본값을 채운다.
2. 각 행에 “compile”, “install”, “test”, “artifact”를 표시한다. unit-test가 compile과 install도 수행한다는 점을 놓치지 않는다.
3. `meson setup`을 clean directory 세 개에 실행한 뒤 `meson configure <dir>` 결과를 저장한다. 기본 unit-test와 alternative build의 최종 option 값을 diff한다.
4. 먼저 한 OS workflow에서만 local YAML diff를 만들고, 제거된 option과 artifact 이름을 checklist로 검토한다. 동일한 원칙을 나머지 두 OS에 적용한다.
5. draft PR의 Actions에서 세 OS의 unit-test와 alternative build가 모두 시작되는지, job 이름이 예상대로 표시되는지 확인한다.
6. 성공 후 각 job의 setup·compile·test 시간과 전체 workflow 종료 시간을 변경 전 run과 비교해, 실제 절감 수치를 PR에 남긴다.

## 위험/검증

- Ubuntu, macOS, Windows에서 clean checkout 후 unit-test job의 configure·compile·install·test가 모두 성공하는지 확인한다.
- 남는 alternative build가 `threads=false`, `partial=false`, `simd=true`, `log=true`, 내장 image loader configuration을 Meson summary에 출력하는지 확인한다.
- x86 runner에서는 SIMD가 AVX로, ARM runner를 사용한다면 NEON으로 선택되는지 확인하고 unsupported family에서 조용히 `none`이 되는 정책이 의도인지 확인한다.
- Ubuntu의 CPU·GL·WebGPU unit test source가 필요한 dependency 발견 조건에 따라 실제 executable에 포함되는지 test log에서 확인한다.
- macOS의 media loader와 Ubuntu/Windows의 extra option이 workflow 정리 중 빠지지 않았는지 최종 command를 비교한다.
- Windows에서 dynamic/static이라는 artifact 이름과 실제 `default_library` 값이 일치하는지 확인하고, 필요한 binary artifact가 계속 제공되는지 검증한다.
- required status check 목록에 삭제된 job 이름이 남아 merge를 영구 대기시키지 않는지 확인한다.
- pull request와 main push event 모두 같은 job 집합을 실행하는지 확인한다.
- Valgrind를 병렬화한다면 기존 단일 실행과 총 test case 수, backend coverage, suppression 적용, 오류 판정, log artifact를 비교한다.
- ASan/UBSan 단계가 build directory 재생성 후 계속 실행되고, Valgrind 병렬화의 임시 파일이나 report와 충돌하지 않는지 확인한다.
- 변경 전후 최소 3회 run의 wall-clock duration과 각 OS별 billed time을 비교해 일시적 runner 편차를 줄인다.
- workflow YAML syntax와 Meson configure를 local에서 검사하고, 실제 hosted runner 세 종류의 결과가 모두 성공하기 전에는 merge하지 않는다.
