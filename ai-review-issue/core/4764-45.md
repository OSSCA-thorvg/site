## 이슈 요약

이슈는 새 pull request가 열리거나 draft에서 ready로 전환될 때 Codex 리뷰를 자동으로 시작하고, draft에는 불필요한 리뷰를 요청하지 않으며, 현재 maintainer 승인 흐름을 그대로 유지하자는 요청이다. 추가 commit 이후 재리뷰 동작도 확인하고, Codex와 Copilot을 동시에 유지할지 비용 대비 효과를 기준으로 판단하자는 질문이 포함돼 있다.

여기서 “자동 assign”을 일반 GitHub reviewer API 호출로 바로 해석하면 구현을 불필요하게 복잡하게 만들 수 있다. 현재 공식 Codex 문서는 연결된 repository에서 Code review와 Automatic reviews를 켜는 설정형 경로를 안내하며, 새 PR이 review 대상으로 열리면 표준 GitHub review를 게시한다고 설명한다. 따라서 첫 구현 후보는 workflow YAML이 아니라 integration 설정이다.

성공 기준은 Codex 댓글이 한 번 달리는 데 그치지 않는다. ready 상태에서만 첫 리뷰가 시작되고, 사람 CODEOWNER 요청과 required approval이 보존되며, 추가 push와 재요청 정책이 예측 가능하고, 두 AI reviewer를 병행할 경우 중복 지적과 비용을 측정할 수 있어야 한다.

## main 코드 조사

현재 [`CODEOWNERS`](https://github.com/thorvg/thorvg/blob/fecc36e041e458a25c579017f840334689ea13f0/CODEOWNERS#L1-L13)는 모든 변경에 기본 maintainer를 지정하고 renderer, loader, test, workflow 경로에는 추가 owner를 둔다. [`CONTRIBUTING.md`](https://github.com/thorvg/thorvg/blob/fecc36e041e458a25c579017f840334689ea13f0/CONTRIBUTING.md#L32-L40)는 GitHub infrastructure가 reviewer를 자동 요청한다고 설명하고, [PR checklist](https://github.com/thorvg/thorvg/blob/fecc36e041e458a25c579017f840334689ea13f0/CONTRIBUTING.md#L106-L112)는 reviewer 자동 할당과 integration test 통과를 요구한다. 즉 AI 리뷰는 이미 존재하는 사람 reviewer 흐름에 추가돼야 하며 이를 대체하는 새 승인 체계로 만들면 안 된다.

GitHub 공식 문서에 따르면 CODEOWNER는 일반 PR이 열릴 때 자동 요청되지만 draft PR에는 요청되지 않고, draft가 ready로 바뀌면 통지된다. 현재 저장소의 인간 reviewer 흐름은 이슈가 원하는 “draft는 건너뛰고 ready에서 시작” 의미와 이미 맞는다. Codex도 동일한 상태 전이를 따르는지 별도 시험하면 두 요청 시점을 나란히 검증할 수 있다.

current main의 [PR Labeler workflow](https://github.com/thorvg/thorvg/blob/fecc36e041e458a25c579017f840334689ea13f0/.github/workflows/pr_labeler.yml#L1-L12)는 `pull_request_target`에서 `actions/labeler@v4`와 `GITHUB_TOKEN`을 사용한다. 하지만 역할은 changed path에 따른 label 동기화뿐이며 reviewer나 외부 AI 호출은 하지 않는다. current tree에는 `AGENTS.md`, Codex 설정 파일, Copilot review 설정 파일이 없다. repository 밖의 integration 설정은 Git tree에 나타나지 않으므로 “파일이 없다”는 사실만으로 기능이 비활성이라고 단정할 수는 없다.

[Codex 공식 설정 문서](https://learn.chatgpt.com/docs/third-party/github)는 repository에 Codex cloud를 설정하고, GitHub push 또는 admin 권한을 가진 사용자가 Codex settings에서 Code review를 켜도록 안내한다. Automatic reviews를 켜면 누군가 새 PR을 review 대상으로 열 때 `@codex review` 댓글 없이 review를 게시한다. 수동 경로는 PR 댓글의 `@codex review`이며, repository별 지침이 필요하면 `AGENTS.md`의 `## Code Review Rules`를 사용한다.

공식 문서가 표현한 trigger는 “새 PR을 review 대상으로 열 때”다. 이는 ready 상태로 여는 PR에는 직접 대응하지만, draft→ready 전환과 이후 `synchronize`마다 자동 재리뷰되는지는 문서 문구만으로 완전히 확정되지 않는다. 특히 Copilot은 [자동 리뷰 trigger](https://docs.github.com/en/copilot/concepts/agents/code-review#triggering-an-automatic-pull-request-review)를 별도로 문서화해 기본 open/draft→open, 선택적 모든 new push, 선택적 draft 리뷰를 구분한다. Codex에도 동일 옵션이 있다고 추정하지 말고 실제 Codex settings와 시험 결과를 기준으로 해야 한다.

Codex의 [review rule 지침](https://learn.chatgpt.com/docs/third-party/github#customize-what-codex-reviews)은 중요한 repository 고유 제약만 짧고 지속 가능한 규칙으로 남기고, format·lint 같은 결정론적 검사는 CI에 두라고 권한다. 현재 `CONTRIBUTING.md`의 formatting과 test 명령을 전부 복사하기보다, maintainer가 반복해서 설명하는 ABI/API 호환성이나 backend 교차 영향처럼 diff만으로 알기 어려운 규칙 2~3개를 먼저 찾는 편이 적합하다.

[Codex for Open Source 신청 페이지](https://openai.com/form/codex-for-oss/)는 active open-source project maintainer의 상시 신청을 받고, 선정된 maintainer에게 PR review 등 핵심 OSS 작업을 위한 API credits와 일정 기간의 ChatGPT Pro가 제공될 수 있다고 안내한다. 이것은 신청·선정 절차이지 자동 무상 제공 보장은 아니므로, 비용 계획에서는 승인 전 사용량과 승인 후 지원을 분리해야 한다.

Copilot은 review당 AI credits와 agentic 기능의 Actions minutes가 소비될 수 있고, 공식 문서에는 effort별 추정 범위와 자동 리뷰 시 귀속 주체가 명시돼 있다. 따라서 두 reviewer를 “둘 다 좋으므로 유지” 또는 “하나가 비싸므로 제거”로 선결정하지 말고 동일 PR 표본에서 검출 품질, 중복률, 지연, 실제 청구를 측정할 수 있다.

## 원인 분석

### 확인된 사실

- current main은 CODEOWNERS로 사람 reviewer를 경로별 자동 요청하며, contribution 문서도 reviewer 자동 할당을 기존 PR 절차로 명시한다.
- current main의 repository 파일에는 Codex/Copilot reviewer 자동화나 `AGENTS.md`가 없고, 기존 `pull_request_target` workflow는 label만 동기화한다.
- Codex 공식 integration은 connected repository, Codex cloud, 적절한 GitHub 권한을 전제로 Codex settings에서 Code review와 Automatic reviews를 켜는 경로를 제공한다.
- Codex는 수동 `@codex review`를 지원하고 표준 GitHub review를 게시하며, 자동 리뷰는 새 PR이 review 대상으로 열릴 때 실행된다고 공식 문서에 명시돼 있다.
- Codex review rule은 `AGENTS.md`에 둘 수 있지만 tests, branch protections, required approvals를 대체하지 않는다.
- GitHub CODEOWNERS는 draft PR에는 자동 요청되지 않고 draft→ready 시 요청된다.
- Copilot 자동 리뷰는 기본 open/draft→open, 선택적 new push, 선택적 draft review를 구분하며, review마다 AI credits가 소비될 수 있다.
- Codex for Open Source는 rolling application과 선정 절차가 있으며, 선정된 maintainer에게 credits 등이 제공될 수 있다.

### 추론과 판단

- **설정 우선:** 기본 요구는 Codex의 native Automatic reviews 설정만으로 충족될 가능성이 높다. 별도 Actions workflow와 secret을 먼저 추가하면 같은 trigger를 중복 실행하고 운영 표면만 넓힐 수 있다.
- **draft 동작은 시험 필요:** “review 대상으로 열린다”는 문구는 draft가 ready가 되는 시점을 포함한다고 읽을 수 있지만, 공개 문서가 event matrix를 명시하지 않았으므로 확인 전에는 확정 사실이 아니다.
- **재리뷰는 별도 정책:** 첫 자동 review와 추가 push마다 재review하는 것은 다른 요구다. native 설정에서 자동 new-push trigger가 확인되지 않으면, 당장은 `@codex review` 수동 재요청을 문서화하고 무조건적인 workflow 보완은 미루는 편이 안전하다.
- **CODEOWNERS와 공존 가능:** Codex review는 추가 신호로 쓰고 required approval은 기존 사람 reviewer에게 남기면 충돌 가능성이 낮다. AI가 review를 게시했다는 사실을 merge 승인과 동일하게 취급하지 않아야 한다.
- **두 AI의 병행은 실험 문제:** 서로 다른 심각도 기준과 coverage가 있을 수 있으므로 소수의 대표 PR에서 먼저 병행하고, 유효한 고유 finding과 중복 finding을 구분한 뒤 비용 정책을 정하는 것이 합리적이다.
- **repository diff가 없을 수 있음:** integration 활성화가 settings-only라면 이슈 해결 PR이 꼭 필요하지 않다. 감사 가능성이 필요하면 최소 운영 문서나 `AGENTS.md`만 별도 PR로 남기고, 실제 설정 변경과 검증 결과는 이슈에 기록할 수 있다.

## 구현 방향

1. repository owner가 Codex cloud 연결 상태, GitHub App의 repository access, Code review settings에 접근 가능한 계정을 확인한다. 조직 정책과 데이터 처리 기준도 activation 전에 확인한다.
2. Codex settings에서 해당 repository의 Code review와 Automatic reviews를 켠다. native integration이 제공하는 기능을 확인하기 전에는 `pull_request_target` workflow, personal access token, reviewer REST 호출을 추가하지 않는다.
3. 사람 CODEOWNERS와 required approval 설정은 그대로 둔다. contribution 문서에는 Codex가 보조 reviewer이며 maintainer 승인과 CI를 대체하지 않는다는 한 문장을 필요할 때만 추가한다.
4. 대표적인 작은 PR로 event matrix를 실행한다: 처음부터 ready로 생성, draft 생성 후 push, draft→ready, 첫 review 후 추가 push, 수동 `@codex review`, fork PR, bot PR. 각 경우 review 요청·게시 시점과 중복 실행 여부를 기록한다.
5. 추가 push 자동 재리뷰가 native 설정에 없다면 기본 운영은 수동 `@codex review`로 둔다. 자동화가 꼭 필요해진 뒤에만 공식 지원 API/event와 최소 권한을 확인해 별도 설계한다.
6. repository 고유 review 지침은 반복되는 실제 maintainer feedback을 2~3개 수집한 뒤 root 또는 해당 경로의 `AGENTS.md` `## Code Review Rules`에 추가한다. format, build, test는 기존 CI와 문서에 남긴다.
7. Codex와 Copilot을 10~20개의 크기·영역이 다른 PR에서 제한적으로 함께 실행한다. reviewer별 고유 actionable finding, 중복, false positive, 응답 시간, maintainer 확인 시간, credit/Actions 비용을 표로 기록한다.
8. 실험 종료 후 “둘 다”, “Codex만”, “Copilot만”, “고위험 PR에서만 둘 다” 중 정책을 결정하고 1~2개월 뒤 다시 평가한다. OSS 지원은 신청 가능하지만 선정 전 비용을 0으로 가정하지 않는다.

첫 단계는 settings activation과 event matrix 검증으로 제한하는 편이 좋다. 이 단계가 통과하면 repository 파일 변경 없이 이슈의 핵심 목표를 달성할 수 있고, 이후 `AGENTS.md`나 운영 문서는 관찰된 부족한 점만 반영할 수 있다.

## 초심자 시작 가이드

1. 작은 문서 수정 branch로 draft PR을 만들고, draft 상태에서 CODEOWNER와 Codex가 요청되는지 시각과 함께 기록한다.
2. 같은 PR을 ready로 바꾼 뒤 사람 reviewer 요청과 Codex review가 각각 언제 나타나는지 확인한다.
3. Codex가 review를 게시한 뒤 작은 추가 commit을 push한다. 자동 재리뷰가 없으면 `@codex review`로 수동 요청하고 두 번째 review가 latest diff를 보는지 확인한다.
4. PR의 Reviews, checks, timeline을 캡처하거나 링크로 남겨 expected/actual 표를 만든다. settings 변경 전후를 같은 형식으로 비교한다.
5. 첫 주에는 `AGENTS.md`를 길게 작성하지 않는다. maintainer가 실제로 중요하다고 판정한 누락 사례만 규칙 후보로 모은다.
6. 두 AI를 함께 시험한다면 “댓글 수”보다 실제 bug 발견, 수정 수용 여부, 중복 여부, review당 비용을 한 행씩 기록한다.

## 위험/검증

- 처음부터 ready인 PR에서 manual mention 없이 Codex review가 정확히 한 번 게시되는지 확인한다.
- draft PR에는 review가 실행되지 않고, ready 전환 후 처음 실행되는지 확인한다. 공식 문서와 실제 결과가 다르면 actual behavior를 운영 문서에 남긴다.
- 추가 commit push 후 자동 재리뷰 여부와 수동 `@codex review` fallback을 확인하고, old diff에 대한 중복 comment가 생기지 않는지 본다.
- CODEOWNERS의 사람 reviewer 요청과 기존 required approval이 유지되며 Codex review만으로 merge 가능해지지 않는지 확인한다.
- fork와 bot이 만든 PR에서도 권한 오류, secret 노출, 무한 comment/review loop가 없는지 확인한다.
- Codex GitHub App에는 필요한 repository만 허용하고, organization audit log와 설치 권한을 검토한다.
- 설정을 끄거나 App access를 제거했을 때 안전하게 rollback되고 기존 PR review 흐름이 계속 동작하는지 확인한다.
- `AGENTS.md`를 추가한다면 대표 PR의 finding을 변경 전후 비교하고, 결정론적 CI 규칙 복제로 noise가 늘지 않는지 확인한다.
- Codex와 Copilot 병행 기간에는 PR별 호출 횟수, credit/Actions 사용량, unique actionable finding, duplicate·false positive를 기록한다.
- 대형 generated file, dependency metadata, 문서-only, renderer·loader·workflow 변경을 표본에 포함해 reviewer별 coverage 차이를 확인한다.
- 최소 한 명의 maintainer가 AI finding을 재현·판정하고, 보안·호환성 관련 결론은 인간 승인을 거치게 한다.
