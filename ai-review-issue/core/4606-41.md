## 이슈 요약

Lottie를 처음 로드할 때 외부 이미지 resolver는 호출되지만, 이미지 슬롯으로 새 경로 또는 URL을 적용하면 resolver가 호출되지 않고 그림이 비어 보인다. 슬롯 교체는 이미지의 source와 picture를 바꾸지만, 기존 자산에서 남은 `resolved` 상태를 무효화하지 않는다. 더 나아가 현재 bitmap copy는 새 source path 자체를 복사하지 않으므로 플래그만 초기화해도 콜백에 유효한 경로가 전달되지 않을 수 있다.

2026-07-28 현재 [수정 PR #4608](https://github.com/thorvg/thorvg/pull/4608)이 열려 있다. 이 변경은 복사된 picture가 실제로 로드된 경우에만 `resolved`를 true로 다시 계산하고, bitmap의 data/path·mime type·size를 shallow/deep copy 정책에 맞춰 옮긴다. 아직 `main`에는 병합되지 않았다.

## main 코드 조사

parser의 [`parseImage()`](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/loaders/lottie/tvgLottieParser.cpp#L1025-L1060)는 embedded byte data, URL, 로컬 경로를 구분해 `LottieBitmap`에 저장하고 `prepare()`를 호출한다. 이미지 asset에 slot id가 있으면 parser는 [해당 bitmap을 slot 속성으로 등록](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/loaders/lottie/tvgLottieParser.cpp#L1096-L1101)한다.

[`LottieImage::prepare()`](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/loaders/lottie/tvgLottieModel.cpp#L298-L311)는 byte data 또는 외부 로컬 파일을 picture에 로드하고 성공하면 `resolved = true`로 설정한다. 반면 URL처럼 외부 resolver가 필요한 자산은 빌더 단계까지 미해결 상태로 남아야 한다.

빌더의 [`updateImage()`](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/loaders/lottie/tvgLottieBuilder.cpp#L964-L985)는 picture가 있고 `!image->resolved`일 때만 resolver를 `bitmap.path`와 함께 호출한다. 호출 뒤에는 결과와 관계없이 크기를 적용하고 `resolved = true`로 바꾼다. 따라서 슬롯 교체 후 상태가 true로 남으면 새 source는 resolver 경로에 들어가지 않는다.

[`LottieImage::override()`](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/loaders/lottie/tvgLottieModel.h#L947-L959)는 기존 bitmap을 해제하거나 backup한 뒤 슬롯의 bitmap을 `copy(..., false)`로 복사한다. 그러나 여기에는 `resolved`를 새 bitmap의 실제 상태에 맞게 갱신하는 코드가 없다.

현재 [`LottieBitmap::copy()`](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/loaders/lottie/tvgLottieProperty.h#L942-L998)는 기존 데이터를 release한 뒤 `picture`, `width`, `height`만 복사한다. union에 든 `data/path`, `mimeType`, `size`는 복사하지 않는다. `release()`도 포인터는 null로 만들지만 `size`를 0으로 되돌리지 않는다.

열린 [PR #4608의 패치](https://github.com/thorvg/thorvg/pull/4608/files)는 이 두 문제를 함께 다룬다. shallow copy에서는 data/path 관련 필드를 이동하고, deep copy에서 path를 복제하며, release 시 size를 초기화한다. override 뒤에는 복사된 picture가 유효한 크기를 보고하는지에 따라 `resolved`를 다시 계산한다.

Lottie 공식 [Image Asset 사양](https://lottie.github.io/lottie-spec/dev/specs/assets/#image-asset)은 `p`를 파일명 또는 data URL, `u`를 파일 경로, `e`를 embedded 표시로 정의한다. [Composition Slots 사양](https://lottie.github.io/lottie-spec/latest/specs/composition/#slots)은 slot dictionary의 값이 일치하는 속성을 교체한다고 정의한다. 새 슬롯 값의 source와 해결 상태가 함께 교체되어야 한다는 방향과 맞는다.

## 원인 분석

### 확인된 사실

- resolver 호출은 `image->resolved == false`이고 picture가 있을 때만 실행된다.
- `LottieImage::override()`는 bitmap을 교체하지만 `resolved`를 갱신하지 않는다.
- `LottieBitmap::copy()`는 현재 picture와 크기만 복사하고 path/data, mime type, size를 복사하지 않는다.
- 슬롯으로 URL/path 자산을 적용하면 resolver가 필요하지만 기존 true 상태가 호출을 차단할 수 있다.
- 열린 PR #4608은 `resolved` 재계산과 bitmap source copy/release를 함께 수정하며 아직 `main`에 없다.

### 추론과 판단

- `resolved = false` 한 줄만 추가하면 호출 차단은 풀리지만, 현재 copy가 path를 버리므로 resolver에 `nullptr` 또는 잘못된 source가 전달될 수 있다. 두 불변식을 함께 고쳐야 한다.
- `resolved`는 “picture 포인터가 존재함”이 아니라 “현재 slot source가 사용 가능한 picture로 해결됨”을 나타내야 한다.
- shallow copy에서 소유권을 이동하고 deep copy에서 문자열을 복제하는 기존 property 관례를 지키지 않으면 slot reset 또는 destructor에서 double-free/leak가 생길 수 있다.
- resolver가 false를 반환해도 현재 빌더가 즉시 `resolved = true`로 바꾸는 동작은 재시도 정책과 관련된 별도 논점이다. 이번 회귀 테스트가 현재 정책을 무심코 바꾸지 않도록 명시해야 한다.

## 구현 방향

1. `LottieBitmap::copy()`가 이미지 source 상태 전체를 복사하도록 한다.
   - shallow copy: picture ref와 함께 union 값, mime type, size를 기존 ownership 규칙대로 이전
   - deep copy: 외부 path 문자열을 새로 할당해 독립 수명 보장
2. `release()`가 해제한 포인터뿐 아니라 `size` 등 union 해석에 영향을 주는 상태도 초기화하도록 한다.
3. `LottieImage::override()` 후 `resolved`를 새 picture의 실제 로드 상태에서 다시 계산한다. URL/path로 resolver가 필요한 빈 picture는 false여야 한다.
4. 최초 asset과 slot asset의 source가 다른 fixture를 만들고, slot 적용 뒤 resolver가 새 경로로 정확히 한 번 호출되는지 검사한다.
5. 슬롯 복원/해제 시 backup bitmap과 원래 `resolved` 상태가 일관되게 돌아오는지 점검한다.
6. PR #4608의 패치를 기준으로 ref count와 union ownership을 집중 검토한다.

## 초심자 시작 가이드

다음 상태표를 먼저 만들면 플래그를 임의로 바꾸는 실수를 줄일 수 있다.

| 자산 | picture | source path | 기대 `resolved` | resolver |
|---|---|---|---:|---|
| 이미 decode된 embedded 이미지 | 유효 | 없음 | true | 호출 안 함 |
| 아직 받지 않은 URL 이미지 | 빈 picture | 있음 | false | 호출 |
| slot으로 교체된 URL 이미지 | 빈 picture | 새 경로 | false | 호출 |
| resolver가 채운 이미지 | 유효 | 있음 | true | 반복 호출 안 함 |

테스트 콜백에는 호출 횟수와 받은 `src`를 기록한다. apply 후 화면만 보는 것보다 먼저 이 두 값을 단언하고, reset 후 원래 자산으로 돌아오는지 확인한다. ASan을 켠 상태에서 같은 slot을 여러 번 apply/reset해 소유권 오류를 찾는다.

## 위험/검증

- 초기 URL/path 자산과 slot으로 적용한 URL/path 자산 모두에서 resolver가 정확한 source를 받는지 검사한다.
- 이미 decode된 embedded 이미지 slot은 불필요하게 resolver를 호출하지 않는지 확인한다.
- 같은 slot을 반복 적용할 때 호출 횟수와 `resolved` 상태가 안정적인지 확인한다.
- slot reset/delete 후 원래 이미지와 상태가 복원되는지 확인한다.
- shallow copy와 backup용 deep copy에서 path/data/mimeType/size의 소유자가 명확한지 검토한다.
- ASan/LSan으로 use-after-free, double-free, leak를 검사하고 picture ref count가 균형을 이루는지 확인한다.
- 로드된 picture가 크기 조회에 실패하는 경우 `resolved` 판정이 안전한지 검사한다.
- resolver 실패와 성공, 로컬 파일 prepare 성공 경로가 기존 정책대로 동작하는지 확인한다.
