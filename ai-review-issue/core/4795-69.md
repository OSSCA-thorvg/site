## 이슈 요약

이 이슈는 CPU 엔진이 큰 shape의 outline을 scanline RLE로 바꿀 때 발생하는 cell buffer 할당과 재처리 비용을 줄이는 작업이다. 첨부된 `test_20p.json`, `test_40p.json`이 stress asset이고, 선행 draft PR #4775의 실험이 배경 자료다.

현재 코드는 bounding box의 긴 변을 이용한 경험식으로 thread별 cell pool을 미리 키운다. 그 buffer로 한 band를 처리할 수 없으면 즉시 세로 구간을 반으로 나누고, 두 하위 band 각각에 대해 전체 outline decomposition을 다시 실행한다. 복잡도가 큰 outline은 작은 band가 많이 생겨 같은 geometry를 반복 순회하므로 allocation을 아낀 대신 CPU 시간이 급증할 수 있다.

선행안은 overflow 시 buffer를 두 배씩 키워 같은 band를 재시도하고, 정한 상한 또는 allocation 실패에서만 기존 band 분할로 돌아가는 방식이다. 특정 stress asset에서는 큰 개선이 보고됐지만 다른 일반 자산에서는 회귀도 측정됐고, maintainer는 resource-constrained device에서 상한 메모리가 과도할 수 있다고 지적했다. 따라서 단순히 선행 패치를 옮기는 문제가 아니라 입력 특성에 맞는 성장 조건과 budget을 결정하는 문제다.

## main 코드 조사

[`SwCellPool`](https://github.com/thorvg/thorvg/blob/18151add07ff7e16e5c931a4d0c0e558937b4e0b/src/renderer/cpu_engine/tvgSwCommon.h#L319-L330)은 `size`와 `buffer`를 보유하고 기본값 `16368`로 할당한다. [`tvg::malloc/realloc`](https://github.com/thorvg/thorvg/blob/18151add07ff7e16e5c931a4d0c0e558937b4e0b/src/common/tvgAllocator.h#L32-L50)은 인자를 그대로 C allocator의 byte 수로 전달하므로 이 값과 `size`의 단위는 cell 개수가 아니라 byte다.

같은 파일의 [`SwMpool`](https://github.com/thorvg/thorvg/blob/18151add07ff7e16e5c931a4d0c0e558937b4e0b/src/renderer/cpu_engine/tvgSwCommon.h#L332-L362)은 `threads + 1`개의 `SwCellPool`을 배열로 만든다. [`mpoolReq()`](https://github.com/thorvg/thorvg/blob/18151add07ff7e16e5c931a4d0c0e558937b4e0b/src/renderer/cpu_engine/tvgSwMemPool.cpp#L29-L56)의 pool은 `thread_local`이고 전역 목록에 보관되다가 `mpoolTerm()`에서 해제된다. 한 번 커진 cell buffer를 render 호출 후 줄이는 코드는 보이지 않으므로 peak 크기가 엔진 종료까지 유지되는 high-water 정책이다.

[`rleRender()`의 초기 sizing](https://github.com/thorvg/thorvg/blob/18151add07ff7e16e5c931a4d0c0e558937b4e0b/src/renderer/cpu_engine/tvgSwRle.cpp#L746-L780)은 `max(bbox width, bbox height) * 0.75 * sizeof(SwCell)`을 요구 크기로 계산하고, 현재 pool보다 클 때 1.25배 여유를 둬 재할당한다. 주석 자체가 이 결정을 experimental이라고 밝힌다. 이 경로는 old buffer를 먼저 free하고 새 malloc 결과를 검증하지 않으므로 allocation 실패 안전성도 별도 보완 대상이다.

[`rleRender()`의 band loop](https://github.com/thorvg/thorvg/blob/18151add07ff7e16e5c931a4d0c0e558937b4e0b/src/renderer/cpu_engine/tvgSwRle.cpp#L781-L858)는 buffer 앞부분을 scanline별 `SwCell*` 표로, 나머지를 실제 cell 저장 공간으로 함께 쓴다. `_genRle()`가 실패하거나 pointer table만으로 buffer가 소진되면 현재 band를 정확히 절반으로 나눠 stack에 넣는다. 한 scanline까지 줄였는데도 처리할 수 없으면 RLE 전체를 버리고 `nullptr`을 반환한다.

[`shapeGenRle()`과 `shapeGenStrokeRle()`](https://github.com/thorvg/thorvg/blob/18151add07ff7e16e5c931a4d0c0e558937b4e0b/src/renderer/cpu_engine/tvgSwShape.cpp#L423-L500)은 fill과 stroke outline 모두 이 함수로 보낸다. [`imageGenRle()`](https://github.com/thorvg/thorvg/blob/18151add07ff7e16e5c931a4d0c0e558937b4e0b/src/renderer/cpu_engine/tvgSwImage.cpp#L87-L92)도 같은 cell pool 경로를 공유한다. 최적화가 대형 Lottie shape만이 아니라 CPU backend의 일반 vector/image 변환 비용과 메모리에도 영향을 줄 수 있는 이유다.

선행 [draft PR #4775](https://github.com/thorvg/thorvg/pull/4775)은 기본 크기의 64배, 즉 `1,047,552` bytes를 각 pool의 상한으로 두고 overflow 때 `realloc` 후 같은 band를 재시도한다. 2026-09-11 현재 open·draft·unmerged이며 maintainer review는 상한의 근거와 저사양 장치의 메모리 부담을 이유로 changes requested 상태다. PR의 자동 pixel 검사에서는 CPU 534건을 포함해 비교 결과 차이가 없었지만, 성능 토론에는 stress asset의 수백 퍼센트 개선과 일부 일반 자산의 약 4~21% 회귀가 함께 보고됐다. 별도 macOS 측정에서는 Lottie +0.2%, 비교 자산 -0.6%로 효과가 거의 없었다.

## 원인 분석

### 확인된 사실

- 기본 cell pool은 16,368 bytes이고 `size`는 byte 단위다.
- current main은 bounding box의 긴 변만으로 요구 buffer를 추정하며, outline segment 수나 scanline별 교차 수를 sizing 식에 넣지 않는다.
- 실제 cell 공간이 부족하면 buffer를 늘리지 않고 band를 반으로 나눈 뒤 각 band에서 `_genRle()`를 다시 호출한다.
- 한 scanline도 현재 buffer에 들어오지 않으면 rendering은 실패한다.
- pool은 thread 수에 따라 여러 개 생성되며, 커진 buffer를 render 뒤 축소하는 경로가 없다.
- 선행안의 출력 비교는 통과했지만 성능 결과는 입력과 환경에 따라 큰 개선, 거의 변화 없음, 회귀가 모두 관측됐다.
- maintainer는 고정 최대치의 근거와 resource-constrained device의 메모리 사용을 해결 과제로 남겼고, 해당 변경은 main에 병합되지 않았다.

### 추론과 판단

- **근본 원인:** geometry의 실제 raster cell 수는 outline 복잡도와 edge가 scanline을 가로지르는 양상에 좌우되는데, 현재 사전 할당식은 bbox 한 변만 본다. 큰 canvas의 단순 shape와 같은 bbox의 복잡 shape를 구분하지 못해 후자에서 overflow와 반복 decomposition이 발생한다.
- **성능 이득은 allocation 자체보다 outline 재순회 제거에서 나올 가능성이 높다.** 선행 PR도 realloc 뒤 같은 band를 다시 시작하고, 성공한 경우 band 분할 횟수를 줄인다. 따라서 이슈 제목의 “allocation optimization”을 malloc 호출 수만으로 측정하면 핵심 비용을 놓칠 수 있다.
- **64배 상한은 근거가 충분하지 않다.** 한 pool당 약 1 MiB라는 값만 보면 작을 수 있지만 `SwMpool`은 `threads + 1`개의 pool을 가지며 성장분은 high-water로 남는다. renderer/pool 구성과 동시에 성장한 slot 수에 따라 실제 resident memory 증가는 여러 배가 될 수 있다.
- **무조건 최대치 선할당도 정답으로 확정할 수 없다.** 재할당 횟수는 줄지만 작은 shape가 대부분인 workload와 여러 thread에서는 사용하지 않는 메모리를 즉시 점유한다. 반대로 매 overflow마다 2배 성장하면 한 frame의 spike와 memory fragmentation을 만들 수 있다.
- **bbox 기반 초기 sizing은 유지 가치가 있지만 complexity signal이 필요하다.** outline point/contour 수, 첫 overflow 때 필요한 cell 수, 최근 high-water 등을 조합하면 단순한 shape에는 작은 pool을 유지하고 반복되는 복잡 shape에는 빠르게 적응할 수 있다.
- **allocation 실패는 정상 fallback이어야 한다.** 기존 buffer를 보존하는 `realloc` 임시 pointer 또는 allocate-first 방식으로만 갱신하고, 실패하면 current band-halving 경로를 계속 사용할 수 있어야 한다.

## 구현 방향

1. 먼저 `rleRender()`에 계측을 넣어 asset/frame/thread별 초기 pool 크기, overflow 횟수, band split 수, outline point·contour 수, `_genRle()` 재호출 수, 최종 high-water를 기록한다. 이 계측은 release build에 남기지 않거나 compile-time option으로 제한한다.
2. `test_20p.json`, `test_40p.json`과 회귀가 보고된 일반 자산을 같은 harness에서 실행해 문제를 “allocation 횟수”, “outline 재순회 시간”, “peak memory”로 분리한다. warm-up, tick 수, 반복 횟수, thread 수, compiler와 CPU를 결과에 함께 남긴다.
3. 성장 정책은 overflow에서만 동작시키되, `newSize`를 `min(oldSize * 2, budget)`처럼 overflow-safe하게 계산한다. byte 단위가 이름과 type에서 드러나는 `constexpr`를 사용하고, `uint32_t` 곱셈 overflow와 `sizeof(SwCell)` 정렬을 검사한다.
4. `realloc` 결과를 임시 pointer에 받아 성공한 경우에만 `cellPool->buffer`, `cellPool->size`, `rw.buffer`, `rw.bufferSize`를 함께 갱신한다. 실패·상한 도달 때는 기존 buffer를 보존한 채 band subdivision으로 fallback한다.
5. 같은 band 재시도는 loop 상단의 `yCells`, `cells`, `maxCells`, `cellsCnt`, `invalid`, y-range 초기화를 모두 다시 거치게 한다. `_sweep()` 전 실패한 시도에서 span이 commit되지 않는 현재 순서를 유지한다.
6. 상한은 임의의 64배가 아니라 thread 수와 전체 CPU-engine memory budget으로 정한다. 예를 들어 per-pool cap과 renderer 전체 cap을 함께 두고, 저메모리 profile이나 compile/runtime option으로 조절할 수 있는지 검토한다.
7. workload가 잠깐만 커지는 경우를 위해 즉시 축소하지 않는 hysteresis, frame 간 사용량 decay, engine idle/flush 때 reset 중 하나를 실험한다. 축소 비용과 allocator churn이 더 커지지 않는다는 수치가 있을 때만 채택한다.
8. 최종 패치는 출력 결과와 기존 band fallback을 보존하면서, benchmark에서 목표 asset의 p50/p95 frame time 개선과 일반 자산·memory budget의 허용 회귀 기준을 모두 만족하는 가장 단순한 정책으로 제한한다.

## 초심자 시작 가이드

1. `SwCellPool::size`가 byte 단위임을 allocator wrapper까지 따라가 확인하고, `DEFAULT_POOL_SIZE / sizeof(SwCell)`로 실제 저장 가능한 cell 수가 왜 더 작은지 계산한다. 앞부분의 scanline pointer table도 같은 buffer를 사용한다는 점을 포함한다.
2. `rleRender()`에 임시 counter를 넣어 한 asset에서 `_genRle()` 호출 횟수와 `reduce_bands` 진입 횟수를 출력한다. 먼저 동작을 바꾸지 않는 계측 patch로 baseline을 만든다.
3. 첨부된 두 stress asset의 frame을 고정하고 single-thread에서 30회 이상 반복해 median과 p95를 구한다. 그 다음 thread 수만 바꿔 같은 실험을 반복한다.
4. overflow 때 pool을 한 번만 두 배로 키우는 최소 실험을 하고, `continue`가 같은 band를 재시도하는지 debugger로 확인한다. allocation 실패를 강제로 주입해 기존 fallback이 유지되는지도 본다.
5. 메모리 profiler로 pool별 high-water와 process peak RSS를 기록한다. FPS만 좋아지고 engine 종료까지 과도한 buffer가 남는다면 완료로 보지 않는다.
6. 선행 PR의 숫자를 그대로 목표로 삼지 말고, 동일한 commit·build type·compiler·thread 수의 before/after pair를 직접 측정한다.

## 위험/검증

- 두 첨부 stress asset에서 before/after의 `_genRle()` 호출 수, split 수, allocation 수, p50/p95 frame time을 비교한다.
- 작은 rect, 매우 큰 단순 rect, 많은 contour/curve, self-intersection, 매우 높은/넓은 bbox, 한 scanline에 edge가 집중된 shape를 따로 측정한다.
- fill과 stroke, anti-alias on/off, transformed image RLE 경로를 모두 검증한다.
- single-thread와 여러 thread 수에서 각 pool과 process 전체의 peak RSS/high-water를 측정한다.
- 장시간 작은 animation 중 한 frame만 복잡한 workload를 넣고 메모리가 계속 유지될 때 허용 budget을 넘지 않는지 확인한다.
- `realloc`/`malloc` 실패를 fault injection으로 만들고 old pointer와 size가 보존되며 band fallback 또는 명시적 `nullptr` 반환으로 안전하게 끝나는지 확인한다.
- 최대 크기 계산의 integer overflow, `sizeof(SwCell)` alignment, pointer table이 cell 영역을 침범하지 않는지 UBSan/ASan으로 검사한다.
- 같은 band를 여러 번 재시도해도 이전 실패 시도의 cell pointer와 count가 남지 않고 span이 중복되지 않는지 확인한다.
- 기존 band subdivision 결과와 byte-for-byte 또는 pixel-for-pixel 동일한 출력을 비교한다. PR 자동 검사 범위뿐 아니라 stress asset의 모든 frame도 포함한다.
- Linux/macOS/Windows, GCC/Clang/MSVC와 release build에서 측정해 플랫폼별 allocator 차이를 분리한다.
- 일반 benchmark suite의 회귀 허용치를 사전에 정하고, 일부 자산의 개선 평균으로 개별 10% 이상 회귀를 숨기지 않는다.
- binary size, leak, engine init/term 반복, renderer 여러 개 생성/파괴도 검증한다.
