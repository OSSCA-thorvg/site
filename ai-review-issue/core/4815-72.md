## 이슈 요약

Lottie 문서에는 폰트의 위치를 설명하는 `fonts.list[].origin`과 animation 자체에 글자 윤곽을 담는 최상위 `chars`가 별도 데이터로 존재한다. 그런데 현재 구현은 font `origin`이 `Local(0)`이고 해당 font의 `chars`가 비어 있지 않을 때만 내장 글리프 경로를 사용한다. 같은 animation이 `chars`와 `fPath`를 함께 제공하면서 `origin`이 1~3이면 `chars`가 있어도 외부 폰트 경로로 간다.

이슈에 첨부된 두 샘플은 이 선택 때문에 기대한 윤곽과 metric 대신 다른 폰트가 사용되어 글자가 겹치거나 줄바꿈이 달라지는 현상을 보여 준다. 이슈 작성자는 `chars`가 있으면 이를 기본 우선순위로 삼되, 기존 font resolver 사용자가 외부 폰트를 선택하던 동작도 고려해 사용자 선택 API 또는 누락 글리프 fallback을 논의하자고 제안한다.

핵심은 `origin == Local` 조건 하나를 지우는 것보다 넓다. 내장 글리프 경로와 외부 폰트 경로가 각각 별도의 shaping·metric·wrapping 구현을 사용하므로, 어느 소스를 언제 고를지와 선택 실패를 어느 단위로 되돌릴지를 명시적인 정책으로 만들어야 한다.

## main 코드 조사

[Lottie font model](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/src/loaders/lottie/tvgLottieModel.h#L401-L434)은 `Origin`을 `Local`, `CssURL`, `ScriptURL`, `FontURL` 네 값으로 저장하고 기본값을 `Local`로 둔다. 같은 객체가 `chars`, 이름·family·style, `b64src`, `path`, ascent도 함께 보유한다. 즉 model에는 글리프 보유 여부와 font 출처가 각각 남아 있지만, 선택 우선순위를 나타내는 별도 상태는 없다.

[font parser](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/src/loaders/lottie/tvgLottieParser.cpp#L1069-L1121)는 `fPath`를 base64 font 또는 외부 경로로 해석하고 `origin` 값을 그대로 enum에 저장한다. 이후 [glyph 후처리](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/src/loaders/lottie/tvgLottieParser.cpp#L1623-L1640)는 각 `chars` 항목을 family와 style이 같은 font에 연결한다. 이 과정에도 `origin`에 따른 필터는 없다. 따라서 `origin != Local`인 font에도 `chars`가 정상적으로 연결될 수 있다.

결정적인 분기는 [현재 `updateText()`](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/src/loaders/lottie/tvgLottieBuilder.cpp#L1337-L1350)에 있다. `text->font`, `origin == Local`, `!chars.empty()` 세 조건이 모두 참일 때만 `updateLocalFont()`를 호출하고, 나머지는 모두 `updateURLFont()`로 보낸다. 여기서 포맷의 font 출처 값이 renderer의 내장 글리프 사용 여부로 재해석된다.

[외부 폰트 경로](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/src/loaders/lottie/tvgLottieBuilder.cpp#L987-L1035)는 먼저 이름으로 font를 선택한다. 실패하면 `fPath` 또는 `name:<font-name>`을 asset resolver에 전달하고, resolver도 실패하면 사용 가능한 임의 font로 fallback한다. 이후 `Text` 객체의 metric, smart wrapping, alignment와 spacing을 사용한다. 즉 내장 글리프를 우선하면 이 callback과 일반 text engine layout은 호출되지 않는다.

[내장 글리프 검색](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/src/loaders/lottie/tvgLottieBuilder.cpp#L1212-L1248)은 현재 byte pointer에서 glyph code prefix를 비교하고 small caps 변환을 적용한다. [내장 글리프 layout](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/src/loaders/lottie/tvgLottieBuilder.cpp#L1250-L1335)은 glyph width로 다음 단어 폭·줄바꿈·cursor를 직접 계산하고 shape를 장면에 추가한다. glyph를 찾지 못하면 해당 byte를 한 칸 넘길 뿐 외부 font 경로로 fallback하지 않는다. 따라서 `chars` 존재 여부만 보고 무조건 이 경로를 선택하면 불완전한 glyph 집합에서 문자가 조용히 사라질 수 있다.

[공개 asset resolver 문서](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/inc/thorvg.h#L1747-L1774)는 외부 image·font reference를 처리하며, callback이 `false`를 반환하면 내부 해석으로 fallback한다고 설명한다. 내장 글리프가 선택된 경우 callback 자체가 필요하지 않지만, 기존에는 `origin != Local`과 `chars`가 함께 있는 animation도 외부 경로로 갔으므로 기본 정책 변경은 callback 횟수와 전달 source를 바꾸는 호환성 변화다.

현재 명시적인 [Lottie asset resolver test](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/test/testLottie.cpp#L286-L325)는 외부 image와 font가 resolver를 거쳐 frame을 만드는 경우를 검증한다. [embedded font sharing test](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/test/testLottie.cpp#L435-L465)는 base64 font를 두 animation loader가 공유할 때의 lifetime을 검증한다. 두 테스트 모두 `chars + non-Local origin + fPath`의 선택 우선순위나 누락 glyph fallback을 직접 고정하지 않는다.

Lottie Docs의 [font list와 character data 설명](https://lottiefiles.github.io/lottie-docs/text/)은 `origin: 0`을 system font 예로, 1과 3을 각각 CSS URL·font URL 예로 설명하고, `chars`는 animation에 직접 담긴 별도 character data 배열로 정의한다. [Font Path Origin 열거형](https://lottiefiles.github.io/lottie-docs/constants/#font-path-origin)도 네 값을 font path의 출처로만 이름 붙인다. 이 자료에는 `origin`이 `chars` 소비 여부를 결정한다는 규칙이 없다.

## 원인 분석

### 확인된 사실

- parser는 `origin`과 `fPath`를 font metadata로 저장하고, `chars`는 family·style 일치 여부로 같은 font에 연결한다.
- `origin != Local`이어도 parser 단계에서 그 font의 `chars`가 제거되지는 않는다.
- renderer의 `updateText()`만 `origin == Local`을 내장 글리프 선택의 필수 조건으로 사용한다.
- 외부 폰트 경로는 이름·경로와 asset resolver를 사용한 뒤 일반 `Text` layout을 수행한다.
- 내장 글리프 경로는 glyph width, 줄바꿈, alignment와 text animator 적용을 자체 계산한다.
- 내장 경로에서 glyph를 찾지 못하면 현재 문자를 건너뛰며 외부 font로 되돌아가지 않는다.
- 공개 resolver 문서는 external resource 처리 계약을 제공하므로, 내장 글리프 우선순위 변경은 callback 관점에서 관찰 가능하다.
- 공식 Lottie 자료는 `origin`을 font path origin으로, `chars`를 별도 character data로 설명하며 둘 사이의 renderer 우선순위를 규정하지 않는다.

### 추론과 판단

- **직접 원인:** font를 어디서 얻는지를 설명하는 `origin` 값에, text를 `chars`로 그릴지 font로 그릴지 결정하는 정책 역할까지 부여했다. 이 의미 중첩 때문에 `chars`가 유효해도 non-Local font는 외부 경로로 강제된다.
- **구조적 원인:** 두 경로가 공통 text source abstraction 아래 있지 않고 완전히 다른 layout pipeline으로 나뉜다. 따라서 선택 실패를 glyph 한 개에서 fallback할지, 한 text document 전체에서 fallback할지 판단할 공통 경계가 없다.
- **첨부 결과의 설명:** 잘못 매칭된 외부 font는 exporter가 기록한 glyph width·outline과 다른 metric을 제공할 수 있다. 그러면 동일한 문자열이라도 cursor advance와 smart wrapping 결과가 달라져 겹침과 word-break 차이가 생긴다는 설명이 코드 흐름과 일치한다. 다만 각 첨부 샘플에서 실제로 선택된 font 이름과 metric 차이는 runtime trace로 추가 확인해야 한다.
- **무조건 `chars` 우선의 위험:** `chars`가 일부 문자만 포함한 animation에서는 현재 내장 경로가 누락 문자를 조용히 건너뛴다. 그러므로 `!chars.empty()`만으로 분기하는 수정은 제시된 샘플은 고쳐도 다른 파일에 문자 소실 회귀를 만들 수 있다.
- **glyph별 혼합 fallback의 위험:** 내장 outline과 font engine glyph를 한 줄에서 섞으면 ascent, advance, kerning과 animator index가 두 체계에서 달라질 수 있다. 먼저 text document 전체의 coverage를 검사해 한 경로를 고르는 방식이 구현과 검증이 더 단순하고 metric 일관성도 높다.
- **API 필요성:** 사용자가 resolver font를 의도적으로 대체하는 경우까지 지원하려면 우선순위 option이 유용할 수 있다. 그러나 포맷 준수 기본값만 정하면 되는지, 공개 API가 실제 요구인지 아직 확인되지 않았으므로 첫 수정부터 새 API를 확정하는 것은 범위가 과하다.

## 구현 방향

1. `origin`을 선택 조건에서 분리한다. `origin`은 font resource 획득 방식의 metadata로만 사용하고, `chars` 사용 여부는 별도의 내부 policy 함수가 결정하게 한다.
2. 기본 policy를 maintainer와 먼저 고정한다. 이슈의 재현 목표에 맞는 최소안은 “현재 text document의 필요한 glyph가 모두 있으면 embedded-first, coverage가 불완전하면 font/resolver 경로”다. `chars`가 없으면 기존 외부 경로를 그대로 유지한다.
3. `_searchGlyph()`의 실제 matching 규칙을 재사용하는 coverage preflight를 만든다. UTF-8 code point 길이, small caps 변환, 공백, `\r`, end-of-text marker를 rendering loop와 동일하게 처리해 preflight와 실제 draw 결과가 어긋나지 않게 한다.
4. fallback 단위는 우선 text document 전체로 둔다. glyph별 혼합이 정말 필요하다는 샘플이 생기기 전에는 한 document 안에서 하나의 metric/layout 체계를 유지한다.
5. resolver contract를 명시한다. embedded 경로가 선택되면 resolver를 호출하지 않고, external 경로가 선택된 경우에만 기존 `fPath`/`name:` callback과 내부 fallback을 유지한다. 이 변화는 release note 또는 API 문서에 기록한다.
6. 사용자 선택이 필요하다는 합의가 생기면 `Auto`, `PreferEmbedded`, `PreferFont` 같은 명시적 preference를 검토한다. `Auto`의 coverage 규칙과 각 mode에서 누락 glyph·resolver 실패가 무엇을 의미하는지도 함께 문서화한다. 내부 policy 수정과 public API 추가는 가능하면 별도 commit으로 나눈다.
7. `updateLocalFont()`와 `updateURLFont()`라는 이름도 정책과 구현을 구분하도록 정리한다. 전자는 실제로 “local font”가 아니라 embedded glyph shape renderer이므로 `updateEmbeddedGlyphs()` 같은 이름이 의미에 맞다.
8. 이슈의 두 animation을 축소한 test fixture를 추가한다. 외부 attachment 전체보다 `origin`, `fPath`, `chars`, text와 bbox만 남긴 작은 JSON이 분기와 layout 회귀 원인을 더 명확히 고정한다.

## 초심자 시작 가이드

이 이슈를 직접 구현하기보다 조사부터 돕고 싶다면 다음 순서가 안전하다.

1. 같은 한 글자와 font metadata를 가진 최소 Lottie JSON 네 개를 만든다: `chars`만, `fPath`만, 둘 다 + `origin: 0`, 둘 다 + `origin: 3`.
2. `updateText()`의 두 분기와 resolver callback에 임시 log를 넣어 각 fixture가 어느 경로로 가는지 기록한다.
3. `chars`에서 한 글자를 제거한 fixture를 추가하고 현재 내장 경로에서 그 글자가 사라지는지 확인한다.
4. `_searchGlyph()`가 소비한 byte 수와 `ctx.idx` 변화를 ASCII와 다중 byte 문자로 비교한다. coverage helper를 만들 때 rendering loop와 같은 규칙을 공유해야 한다.
5. 조건문을 바꾸기 전에 기대 결과 표를 maintainer에게 확인한다. 각 행에 선택 source, resolver 호출 횟수, 누락 glyph 처리, 예상 line count를 적으면 정책 논의가 구체화된다.
6. 가장 작은 내부 policy와 test부터 제출하고, 새 public preference API는 별도 합의가 있을 때 후속 변경으로 제안한다.

## 위험/검증

- `origin` 0, 1, 2, 3 각각에 대해 `chars` 없음/완전/불완전과 `fPath` 없음/있음 조합을 table-driven test로 검증한다.
- embedded glyph가 완전한 경우 정확히 embedded 경로를 선택하고 resolver가 호출되지 않는지 확인한다.
- coverage가 불완전한 경우 document 전체가 font 경로로 fallback하며 resolver에 기존 `fPath` 또는 `name:` 값이 전달되는지 확인한다.
- resolver 성공, `false` 반환, resolver 미등록의 세 경우에서 기존 내부 font fallback 결과가 유지되는지 확인한다.
- ASCII, 다중 byte UTF-8, 공백, 연속 개행, small caps, glyph에 없는 문자로 coverage와 rendering loop의 소비 위치가 같은지 검증한다.
- 내장 글리프와 외부 font 각각에서 advance, ascent, line count, bbox, 좌·우·가운데 정렬, tracking과 line height를 비교한다.
- fixed bbox의 smart wrapping, 긴 단어, 여러 줄에서 word-break가 기대 fixture와 일치하는지 확인한다.
- text range animator의 character/word/line index, opacity·색·stroke·transform이 source 선택 변경 뒤에도 올바른 glyph에 적용되는지 확인한다.
- text-on-path, small caps와 stroke-below처럼 embedded 경로가 별도 처리하는 기능을 regression test에 포함한다.
- 같은 animation의 frame 반복 갱신과 loader 공유에서 glyph/font resource lifetime, 중복 load·unload와 memory leak이 없는지 확인한다.
- software renderer의 golden image 또는 주요 pixel hash를 첨부 샘플의 문제 frame에서 비교하고, CPU 외 지원 backend에서도 장면 구조 변경이 같은 결과를 내는지 확인한다.
- 정책 또는 public API를 추가하면 기존 source compatibility와 default behavior를 확인하고 문서·예제·release note를 함께 갱신한다.
