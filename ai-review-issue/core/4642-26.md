## 이슈 요약

직전 변경은 SVG named color 검색을 선형 탐색에서 이진 탐색으로 바꾸고 테이블을 이름순으로 정렬했다. 새 이슈는 그 후속으로, 각 색상을 alpha가 포함된 `unsigned int`에 넣어 두고 객체 바이트를 역순 인덱싱하는 현재 표현을 `tvg::RGB` 값으로 교체하자는 제안이다. maintainer가 제시한 목표는 검색 성공 시 세 channel을 따로 계산하지 않고 RGB 객체를 직접 대입하는 것이다.

이 작업은 사용자 기능을 추가하는 것이 아니라 내부 표현을 실제 소비 타입에 맞추는 리팩터링이다. 올바르게 구현하면 opaque named color의 결과는 그대로여야 하며, 숫자 객체의 byte order에 기대는 현재 추출도 제거할 수 있다. 성능·binary size 개선 폭은 아직 측정되지 않았으므로 결과 보존과 코드 단순화가 우선 기준이다.

## main 코드 조사

current main의 [`colors[]` 테이블](https://github.com/thorvg/thorvg/blob/36842c93ae899cfb0e08d0e02fcd61385c6edde2/src/loaders/svg/tvgSvgLoader.cpp#L463-L617)은 `const char* name`과 `unsigned int value`로 이루어진 147개 항목이다. 모든 값은 `0xffRRGGBB` 형태라 상위 `0xff`를 포함하지만 named color lookup이 전달하는 출력은 red, green, blue 세 channel뿐이다. 스크립트로 확인한 main 테이블은 ASCII case-insensitive 이름순이며, 같은 RGB를 공유하는 gray/grey 계열 등을 포함한 alias group이 9개다.

[`_toColor()`의 named color 분기](https://github.com/thorvg/thorvg/blob/36842c93ae899cfb0e08d0e02fcd61385c6edde2/src/loaders/svg/tvgSvgLoader.cpp#L620-L716)는 `strcasecmp()` 기반 이진 탐색으로 항목을 찾은 뒤 정수 객체 주소를 `uint8_t*`로 바꾸고 byte 2, 1, 0을 각각 r, g, b에 넣는다.

```cpp
r = ((uint8_t*)(&(colors[mid].value)))[2];
g = ((uint8_t*)(&(colors[mid].value)))[1];
b = ((uint8_t*)(&(colors[mid].value)))[0];
```

이 배열 인덱스는 `0xffRRGGBB` 정수가 메모리에 `BB GG RR FF`로 놓이는 little-endian 표현에서 의도한 결과를 낸다. 반대 byte order에서는 같은 인덱스가 다른 channel을 읽는다. current main이 특정 big-endian target에서 실제 오동작한다는 실행 보고는 이슈에 없지만, 코드가 정수 객체 표현에 의존한다는 사실은 확인된다. `tvg::RGB {r, g, b}`를 직접 저장하면 channel 의미가 필드에 고정되어 이 의존을 제거할 수 있다.

공통 [`tvg::RGB`](https://github.com/thorvg/thorvg/blob/36842c93ae899cfb0e08d0e02fcd61385c6edde2/src/common/tvgColor.h#L29-L39)는 세 `uint8_t` field만 갖고, SVG 내부의 [`SvgColor`도 이 타입의 alias](https://github.com/thorvg/thorvg/blob/36842c93ae899cfb0e08d0e02fcd61385c6edde2/src/loaders/svg/tvgSvgCommon.h#L24-L33)다. 따라서 paint와 style color는 RGB 객체를 바로 받을 수 있다.

다만 `_toColor()`는 named color 전용 함수가 아니다. 같은 함수가 `#rgb`, `#rrggbb`, `rgb()`, `url()`, `hsl()`도 처리하고 현재는 `uint8_t& r, g, b` 세 인자를 받는다. [`paint`와 `color` attribute 호출](https://github.com/thorvg/thorvg/blob/36842c93ae899cfb0e08d0e02fcd61385c6edde2/src/loaders/svg/tvgSvgLoader.cpp#L922-L945)은 `SvgColor` field를 넘기지만, [두 gradient stop 호출](https://github.com/thorvg/thorvg/blob/36842c93ae899cfb0e08d0e02fcd61385c6edde2/src/loaders/svg/tvgSvgLoader.cpp#L2550-L2610)은 alpha와 offset도 가진 `Fill::ColorStop`의 개별 channel을 넘긴다. `color = colors[mid].value`를 쓰려면 helper가 `tvg::RGB&`를 받도록 바꾸고 gradient stop에 안전한 bridge를 두거나, 기존 overload를 보존해야 한다.

이 이슈가 갈라져 나온 [직전 PR #4640](https://github.com/thorvg/thorvg/pull/4640)은 이름순 정렬과 binary search를 도입했다. 실제 예제 계측에서는 `_toColor()` 시간이 약 16.6% 줄었지만 전체 content 실행에서 차지한 비중은 약 0.22%에서 0.17%로 바뀌어 일반 asset 영향은 작다고 기록됐다. 후속 RGB 표현도 microbenchmark뿐 아니라 전체 binary와 representative asset에서 측정해야 한다.

현재 [`testPicture.cpp`](https://github.com/thorvg/thorvg/blob/36842c93ae899cfb0e08d0e02fcd61385c6edde2/test/testPicture.cpp#L201-L250)는 몇 개 SVG fixture의 load 성공과 크기를 확인한다. 저장소 test에서 named color 147개와 expected RGB, case-insensitive lookup 또는 테이블 정렬을 직접 고정한 검증은 찾지 못했다. 기존 Pixel Inspector는 직전 변경에서 광범위한 결과 비교를 제공했지만, table entry 하나의 channel 오타를 반드시 모두 통과시키는 단위 계약은 아니다.

W3C CSS Color 4의 [named colors 표](https://www.w3.org/TR/css-color-4/#named-colors)는 각 opaque keyword를 sRGB의 세 channel로 정의하고 keyword를 ASCII case-insensitive로 처리한다. `transparent`와 `currentcolor`는 별도 값이다. 현재 테이블을 RGB aggregate로 옮길 때 이 표가 이름·channel expected value의 1차 기준이 된다.

## 원인 분석

### 확인된 사실

- main 테이블은 147개 opaque named color를 `unsigned int`의 `0xffRRGGBB` 값으로 저장한다.
- named color 성공 경로는 alpha byte를 출력하지 않고 정수 객체의 byte 2, 1, 0만 r, g, b로 복사한다.
- `tvg::RGB`는 r, g, b 세 `uint8_t` field를 가지며 `SvgColor`가 이미 이 타입을 사용한다.
- `_toColor()`는 named color 외의 모든 지원 색상 문법도 처리하고, paint/style 및 gradient stop을 포함한 네 호출 지점이 있다.
- latest main의 table은 case-insensitive 이름순이고 binary search는 이 정렬을 전제로 한다.
- 이슈의 screenshot은 목표로 `tvg::RGB value`와 `color = colors[mid].value`를 보여 주지만, current signature에는 `color` 객체가 없고 기존 정수 initializer는 RGB aggregate initializer로 그대로 사용할 수 없다.
- 저장소 unit test에는 전체 named color mapping을 직접 검증하는 table-driven test가 보이지 않는다.

### 추론과 판단

- **핵심 가치:** 이번 변경의 확실한 이점은 사용하지 않는 alpha 의미와 object-byte 인덱싱을 없애 타입으로 channel 의미를 표현하는 것이다. 실제 table section 크기는 pointer alignment와 tail padding 때문에 줄지 않을 수 있으므로 메모리 절감을 사실로 가정하지 않는다.
- **portability 판단:** little-endian byte 배치를 가정한 추출은 불필요하다. RGB aggregate 또는 bit shift 기반 constexpr 변환은 host byte order와 무관하게 같은 field 값을 만든다.
- **API 판단:** `_toColor(str, tvg::RGB&, ref)`를 primary helper로 두면 paint/style은 직접 대입할 수 있다. gradient stop은 임시 RGB를 사용해 성공 후 r/g/b만 복사하거나 기존 세-reference overload가 primary helper에 위임하도록 하면 alpha와 offset을 건드리지 않는다.
- **데이터 변환 판단:** 147개 값을 손으로 세 channel로 쪼개면 오타 위험이 크다. `constexpr tvg::RGB rgb(uint32_t value)`처럼 `0xRRGGBB`를 shift해 aggregate를 만드는 helper를 쓰면 compact table을 유지하면서 alpha와 endian 의존을 모두 없앨 수 있다.
- **범위 제한:** binary search 알고리즘이나 이름 목록을 다시 설계할 필요는 없다. 정렬 불변식과 CSS mapping을 test로 고정하고 value representation만 바꾸는 것이 안전하다.

## 구현 방향

1. table entry의 `value`를 `tvg::RGB`로 바꾼다. initializer는 `{r, g, b}` 또는 `0xRRGGBB`를 channel로 변환하는 작은 `constexpr` helper를 사용하고 상위 alpha byte를 제거한다.
2. `_toColor()` 내부에서 사용할 RGB 객체를 명시한다. hex, rgb(), hsl(), named color가 동일 객체에 결과를 기록하고 현재의 `true`/`false` 및 실패 시 기존 값 보존 동작을 유지한다.
3. named color 일치 시 `color = colors[mid].value`로 대입한다. integer pointer cast와 byte index 세 줄을 제거한다.
4. `SvgPaint::color`와 `SvgStyleProperty::color`는 RGB overload에 직접 전달한다. `Fill::ColorStop`은 alpha·offset을 보존하는 adapter 또는 임시 RGB를 거쳐 r/g/b만 갱신한다.
5. table 순서와 147개 name→RGB mapping을 data-driven test로 고정한다. 첫 항목, alias, 중간, 마지막 항목만 골라 검사하는 smoke test와 전체 표 검증을 함께 둔다.
6. 직전 PR의 benchmark 조건을 재사용하되 binary size의 text/data 변화와 전체 asset 시간을 함께 기록한다. 수치 개선이 없더라도 type safety와 endian 독립성을 변경 근거로 분리한다.

## 초심자 시작 가이드

1. 먼저 `aliceblue`, `darkgray`/`darkgrey`, `rebeccapurple`, `yellowgreen`을 사용하는 작은 SVG를 만들고 expected RGB를 기록한다. 첫·alias·중간·마지막 검색 위치를 대표한다.
2. table entry 하나만 `tvg::RGB` aggregate로 바꾸는 compile 실험으로 올바른 initializer 문법과 `sizeof`/padding을 확인한다.
3. `_toColor()`가 RGB 객체를 받도록 바꾸되 named color 분기 전에는 `#123`, `#112233`, `rgb()`, `hsl()`, `url()` test를 먼저 고정한다.
4. gradient stop 호출에는 alpha가 별도로 있다는 점을 확인하고, RGB 변환 뒤 기존 alpha가 유지되는 test를 추가한다.
5. 전체 147개 표를 W3C expected value와 비교하고 mixed-case 이름도 같은 결과인지 확인한 뒤 Pixel Inspector와 sanitizer를 실행한다.

첫 PR은 새로운 color 문법이나 lookup container 변경을 섞지 않는 편이 좋다. table type, helper signature, 네 호출 지점과 test만 포함하면 review가 쉽다.

## 위험/검증

- 147개 keyword의 r/g/b가 W3C 표와 정확히 일치하고 누락·중복 name이 없는지 확인한다.
- `gray`/`grey`, `aqua`/`cyan`, `fuchsia`/`magenta` 등 같은 RGB를 갖는 alias를 모두 검사한다.
- lower/upper/mixed case가 같은 결과이며 table이 `strcasecmp()` 기준 strict ascending인지 확인한다.
- binary search의 첫 항목, 짝수·홀수 경계 근처, 마지막 항목과 unknown name을 검사한다.
- `#rgb`, `#rrggbb`, `rgb()`, `hsl()`, `url()`, `currentColor`, `none`의 기존 결과와 반환값을 보존한다.
- fill, stroke, `color`, gradient `stop-color`에서 같은 keyword가 같은 RGB를 만들고 gradient alpha가 변하지 않는지 확인한다.
- 잘못된 숫자 색상에서 output을 기존대로 보존하는지 확인해 signature adapter가 초기화되지 않은 값을 복사하지 않게 한다.
- little-endian host의 기존 pixel 결과가 바뀌지 않는지 SW/GL/WG Pixel Inspector로 비교한다.
- 가능하면 big-endian cross target 또는 byte-order 독립 unit test로 정수 객체 표현에 더는 의존하지 않음을 확인한다.
- `sizeof(colors)`, object/data section과 optimized assembly를 변경 전후 비교하고, padding 때문에 table 크기가 그대로여도 이를 regression으로 오해하지 않는다.
- 직전 binary-search benchmark와 representative asset 계측을 같은 compiler·optimization 조건에서 반복한다.
- ASan/UBSan, 전체 SVG loader test와 build를 실행한다.
