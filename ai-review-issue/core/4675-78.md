## 이슈 요약

동일한 Lottie example을 1900×1900으로 실행했을 때 RTX 5080에서는 WebGPU가 GL보다 30.5% 빠르지만 Apple M1에서는 71.3% 느리고 GL이 약 3.48배 빠르다는 보고다. 기대 결과는 모든 장치에서 WebGPU가 GL을 이기는 것이 아니라, M1에서만 나타나는 큰 격차의 병목을 profile로 찾아 설명하고 줄이는 것이다.

이슈의 “sample 1000”은 source unit test 번호가 아니라 example이 출력하는 frame tick이다. 보고에는 두 플랫폼의 FPS 원시값, 측정 분산, macOS·Windows 버전, 전원·thermal 상태, build type, compiler, 연결된 display, wgpu-native build와 실제 로드한 Lottie 목록이 없다. 따라서 71.3%라는 관측은 유효한 조사 출발점이지만 특정 renderer 함수가 원인이라는 증거는 아직 아니다. 이슈를 참조하는 열린 source PR도 2026-08-13 현재 확인되지 않았다.

## main 코드 조사

### benchmark가 실제로 측정하는 범위

재현 명령의 `Lottie` 실행 파일은 core 저장소가 아니라 공식 example 저장소에서 만들어진다. 확인한 example `main`은 [`a13cb1d`](https://github.com/thorvg/thorvg.example/commit/a13cb1d98dc5cec97324d1c037111b76fd2b36ab)다. [`-e gl`과 `-e wg` 선택](https://github.com/thorvg/thorvg.example/blob/a13cb1d98dc5cec97324d1c037111b76fd2b36ab/src/Example.h#L598-L647)은 같은 `Example` object를 각각 `GlWindow`와 `WgWindow`에 연결한다. `-r 1900x1900`도 같은 argument parser에서 두 창의 width·height에 적용된다.

Lottie example은 [`res/lottie`를 순회해 최대 10×10 animation을 추가](https://github.com/thorvg/thorvg.example/blob/a13cb1d98dc5cec97324d1c037111b76fd2b36ab/src/Lottie.cpp#L29-L65)한다. 그런데 directory 순회는 [`readdir()` 또는 `FindFirstFileEx()` 결과를 정렬하지 않고 그대로 사용](https://github.com/thorvg/thorvg.example/blob/a13cb1d98dc5cec97324d1c037111b76fd2b36ab/src/Example.h#L86-L136)하며 100개에서 중단한다. 현재 directory에는 100개가 넘는 JSON 파일이 있으므로 console의 `Lottie: ...` 목록이나 명시적 manifest를 비교하지 않으면 Windows와 macOS가 같은 100개를 골랐다고 보장할 수 없다.

매 frame에는 모든 animation의 `frame()`과 전체 [`canvas->update()`](https://github.com/thorvg/thorvg.example/blob/a13cb1d98dc5cec97324d1c037111b76fd2b36ab/src/Lottie.cpp#L68-L76), `canvas->draw()`, `canvas->sync()` 및 window refresh가 들어간다. FPS는 이 event loop 전체의 frame interval을 exponential moving average로 계산하고 첫 60 frame 뒤 [`[tick]: current / mean fps`를 출력](https://github.com/thorvg/thorvg.example/blob/a13cb1d98dc5cec97324d1c037111b76fd2b36ab/src/Example.h#L184-L233)한다. 따라서 이 숫자는 사용자 체감에 가까운 end-to-end throughput이지 GPU shader time만의 측정값은 아니다. Lottie property 평가·tessellation, driver CPU overhead, queue back-pressure, surface acquire/present가 모두 포함될 수 있다.

GL example은 [`SDL_GL_SetSwapInterval(0)`으로 FPS 제한을 끄고](https://github.com/thorvg/thorvg.example/blob/a13cb1d98dc5cec97324d1c037111b76fd2b36ab/src/Example.h#L367-L418), WebGPU example은 CAMetalLayer surface를 만들고 frame 끝에 [`wgpuSurfacePresent()`](https://github.com/thorvg/thorvg.example/blob/a13cb1d98dc5cec97324d1c037111b76fd2b36ab/src/Example.h#L427-L528)를 호출한다. core의 macOS surface 설정도 [`WGPUPresentMode_Immediate`](https://github.com/thorvg/thorvg/blob/4b0ce6ace69ff82fa0c2131480d298330b98b3cd/src/renderer/gpu_engine/wg/tvgWgRenderer.cpp#L99-L119)를 요청한다. 의도상 두 경로 모두 vsync 제한을 피하지만 각 API가 실제로 block하거나 queue를 throttle하는 위치까지 같다는 뜻은 아니다.

### current WebGPU frame 경로

`Canvas::draw()`는 update가 필요하면 scene을 갱신한 뒤 renderer의 `preRender()`·`postRender()`까지 실행하고, 별도 [`Canvas::sync()`가 renderer sync를 호출](https://github.com/thorvg/thorvg/blob/4b0ce6ace69ff82fa0c2131480d298330b98b3cd/src/renderer/tvgCanvas.h#L77-L128)한다. 이 API 경계 때문에 WebGPU의 한 example frame은 정상 surface 크기에서 두 번 queue에 제출된다.

첫 번째 제출은 [`WgRenderer::postRender()`](https://github.com/thorvg/thorvg/blob/4b0ce6ace69ff82fa0c2131480d298330b98b3cd/src/renderer/gpu_engine/wg/tvgWgRenderer.cpp#L277-L302)에서 발생한다. CPU stage buffer를 GPU에 flush하고 command encoder 하나에 root scene을 기록한 뒤 `wgpuQueueSubmit()`한다. 두 번째 제출은 [`WgRenderer::sync()`](https://github.com/thorvg/thorvg/blob/4b0ce6ace69ff82fa0c2131480d298330b98b3cd/src/renderer/gpu_engine/wg/tvgWgRenderer.cpp#L383-L411)에서 surface texture를 얻고 root offscreen texture를 fullscreen blit하는 encoder를 새로 만들어 제출한다. 그 뒤 example loop가 present한다.

[`WgContext::submitCommandEncoder()`](https://github.com/thorvg/thorvg/blob/4b0ce6ace69ff82fa0c2131480d298330b98b3cd/src/renderer/gpu_engine/wg/tvgWgCommon.cpp#L229-L249)는 encoder를 finish해 command buffer 하나로 만들고 즉시 queue에 제출한다. 완료 대기나 timestamp 수집은 없다. 그러므로 CPU timer에서 `draw()` 또는 `sync()`가 빨리 반환해도 GPU가 빨랐다는 뜻은 아니고, 반대로 다음 surface 획득에서 누적 GPU 작업을 기다린 시간이 나타날 수도 있다.

root target은 [`RGBA8 storage texture와 4× MSAA color attachment`](https://github.com/thorvg/thorvg/blob/4b0ce6ace69ff82fa0c2131480d298330b98b3cd/src/renderer/gpu_engine/wg/tvgWgRenderTarget.cpp#L25-L35)를 항상 만든다. 1900×1900에서 format의 논리적 color payload는 single-sample 약 13.8 MiB, 4× attachment 약 55.1 MiB이며 실제 allocation은 alignment·compression에 따라 다를 수 있다. scene은 MSAA pass에서 single-sample root로 resolve되고, sync에서 다시 surface로 fullscreen sample/blit된다. 이 고정 비용은 해상도에 비례하므로 M1 profile에서 tile store/resolve와 두 번째 fullscreen pass를 우선 분리 측정할 가치가 있다. 하지만 GL도 MSAA offscreen과 최종 blit을 사용하므로 이 구조만으로 플랫폼 격차의 원인이라고 확정할 수는 없다.

geometry·paint·view matrix stage buffer는 [`postRender()` 직전 `wgpuQueueWriteBuffer()`로 갱신](https://github.com/thorvg/thorvg/blob/4b0ce6ace69ff82fa0c2131480d298330b98b3cd/src/renderer/gpu_engine/wg/tvgWgCommon.cpp#L167-L205)된다. 많은 Lottie node가 매 frame 바뀌면 CPU packing과 여러 queue write의 비용도 커질 수 있다. CPU profile에서 이 구간이 보이지 않으면 buffer 전략부터 바꾸면 안 된다.

current main에는 convex solid batch와 non-convex stencil batch가 있다. [`renderShape()`는 두 batch를 먼저 시도](https://github.com/thorvg/thorvg/blob/4b0ce6ace69ff82fa0c2131480d298330b98b3cd/src/renderer/gpu_engine/wg/tvgWgRenderer.cpp#L252-L263)하지만, solid batch는 normal blend·solid fill·convex·no clip·no stroke와 같은 viewport를 요구한다. [`stencil batch`](https://github.com/thorvg/thorvg/blob/4b0ce6ace69ff82fa0c2131480d298330b98b3cd/src/renderer/gpu_engine/wg/tvgWgStencilBatch.cpp#L26-L81)도 normal blend·no clip·no stroke·같은 viewport와 서로 겹치지 않는 bounds만 묶는다. sample의 실제 batch hit rate와 draw/pass 수가 없으므로 “Lottie라서 batching이 실패한다”는 아직 가설이다.

native WG engine은 Meson에서 [`dependency('wgpu_native')`](https://github.com/thorvg/thorvg/blob/4b0ce6ace69ff82fa0c2131480d298330b98b3cd/src/renderer/gpu_engine/wg/meson.build#L34-L42)를 찾으며 build file 자체에는 version constraint가 없다. README는 [`wgpu-native v29.0.1.1`](https://github.com/thorvg/thorvg/blob/4b0ce6ace69ff82fa0c2131480d298330b98b3cd/README.md#L625-L633)을 문서화하고 Ubuntu CI는 그 version을 고정하지만, 재현 환경이 실제로 같은 binary인지 보고되지 않았다. wgpu-native는 macOS에서 Metal backend를 사용하므로 library version과 adapter/backend 정보도 benchmark 결과에 포함해야 한다.

Ubuntu unit test와 pixel comparison은 WebGPU correctness를 확인하지만 software GL 환경으로 실행된다. [`macOS workflow`](https://github.com/thorvg/thorvg/blob/4b0ce6ace69ff82fa0c2131480d298330b98b3cd/.github/workflows/build_macos.yml#L28-L83)는 wgpu-native를 설치하거나 `-Dengines=wg`를 켜지 않는다. 현재 CI에는 Apple GPU에서 Lottie throughput을 추적하는 job이 없으므로 이번 격차를 자동 검출하지 못한다.

README의 기존 공개 benchmark는 Apple M1에서 여러 vector workload의 WebGPU가 GL보다 평균 1.8배 빠르다고 설명하면서 hardware·OS·driver·workload에 따라 달라질 수 있다고 명시한다. 이번 Lottie corpus 결과와 모순으로 단정하기보다, workload composition과 측정 harness가 다른지 먼저 맞춰야 한다.

## 원인 분석

### 확인된 사실

- 이슈가 보고한 M1 격차는 1900×1900 Lottie example의 end-to-end FPS 비교이며 GPU timestamp나 frame capture 결과가 아니다.
- example은 첫 100개 Lottie 파일만 사용하지만 directory entry를 정렬하지 않는다.
- GL은 swap interval 0, macOS WebGPU surface는 Immediate present mode를 요청한다.
- 한 WebGPU frame은 root scene rendering과 final surface blit을 서로 다른 command encoder로 기록해 두 번 queue에 제출한다.
- WebGPU는 full-size RGBA8 root texture와 4× MSAA attachment에 그린 뒤 surface로 fullscreen blit한다.
- stage buffer는 frame render 전에 queue write로 upload된다.
- current batching에는 blend, clip, stroke, convexity, viewport와 overlap에 따른 명시적 제한이 있다.
- current macOS CI는 WG engine을 build/test하지 않으며 Apple GPU performance baseline도 없다.
- issue를 직접 해결하는 열린 source PR은 확인되지 않았다.

### 추론과 판단

- **가장 먼저 배제할 측정 교란:** 두 OS가 서로 다른 100개 asset을 골랐거나 build/dependency 조건이 다를 가능성이다. 실제 `Lottie:` 목록 hash와 binary metadata가 같기 전에는 hardware 차이만 비교했다고 말하기 어렵다.
- **GPU-side 우선 가설:** 해상도에 비례하는 4× MSAA resolve, root texture store와 별도 fullscreen blit/submission이 Apple tile-based GPU에서 상대적으로 비쌀 수 있다. 950²·1344²·1900² 같은 resolution sweep에서 GPU time이 pixel 수에 가깝게 증가하고 Metal capture의 store/resolve가 지배적일 때만 이 가설이 강화된다.
- **CPU-side 우선 가설:** WebGPU command encoding, bind/pipeline 전환, batch miss, stage-buffer packing 또는 queue write가 GL driver 호출보다 비쌀 수 있다. CPU profile과 frame별 render pass·draw·pipeline switch·batch hit/miss counter가 필요하다.
- **scheduling 가설:** 두 제출과 acquire/present 사이 queue back-pressure가 특정 호출에 몰려 FPS를 낮출 수 있다. 각 API 호출의 wall time과 GPU completion을 함께 보지 않으면 “느린 함수”를 잘못 지목할 수 있다.
- **아직 확인되지 않은 주장:** M1의 Metal backend 자체가 느리다, wgpu-native translation overhead가 원인이다, batching만 확대하면 해결된다는 설명은 현재 자료로 확정할 수 없다.

## 구현 방향

1. benchmark contract를 먼저 고정한다. core·example commit, wgpu-native version/hash, adapter/backend, OS, compiler, release build flags, thread 수, display scale, 전원/thermal 상태, resolution과 asset manifest를 결과에 기록한다.
2. directory 순회를 정렬하거나 명시적 manifest를 받아 두 플랫폼에서 같은 100개를 같은 순서로 load한다. console 목록의 hash도 출력해 기존 run을 비교할 수 있게 한다.
3. warm-up 뒤 고정 frame 구간을 여러 번 실행하고 FPS 평균 하나가 아니라 median, p95 frame time, 분산과 raw sample을 저장한다. GL/WG 실행 순서를 교차해 thermal·cache 편향을 줄인다.
4. CPU 구간을 `animation->frame + canvas->update`, draw/scene encoding, first submit, surface acquire, blit submit, present로 나눠 측정한다. 이 timer는 GPU time이 아님을 output에 명시한다.
5. adapter가 지원하는 feature를 확인한 뒤 WebGPU timestamp query를 사용하거나, Apple의 Metal frame capture로 render pass, tile load/store, resolve, fullscreen blit과 GPU idle gap을 측정한다. Apple GPU에서 pass 내부 timestamp가 지원된다고 가정하지 말고 runtime capability를 기준으로 fallback한다.
6. frame마다 scene 수, render pass, draw, pipeline/bind-group switch, queue write byte·호출 수, solid/stencil batch hit·miss와 miss reason을 debug counter로 수집한다. counter가 꺼진 release 성능도 따로 측정한다.
7. capture 결과에 따라 한 가지 병목만 작은 PR로 다룬다. 예를 들어 submit overhead가 지배적이면 root encoder를 sync까지 보류해 final blit을 같은 command buffer에 기록할 수 있는지 검토한다. 이는 `draw()`와 `sync()` lifecycle 및 texture target client를 바꾸므로 단순히 submit 호출을 합치면 안 된다.
8. bandwidth/store가 지배적이면 direct-to-surface, MSAA 정책, partial region 또는 불필요한 offscreen 제거를 각각 prototype한다. masking·blend·effect가 root texture sampling을 요구하는 frame과 그렇지 않은 frame을 구분하고 pixel equivalence를 먼저 보장한다.
9. CPU encoding이 지배적이면 stage-buffer reuse/ring allocation과 batching eligibility를 profile 수치로 우선순위화한다. draw order, overlap, fill rule가 달라지는 batch 확대는 금지한다.

초기 PR은 renderer 최적화보다 재현 manifest, metadata, phase timer와 counter를 추가하는 방향이 안전하다. 그 결과를 issue에 첨부한 뒤 병목별 후속 PR을 분리하면 플랫폼 특화 workaround가 다른 backend를 악화시키는 위험을 줄일 수 있다.

## 초심자 시작 가이드

renderer 수정 전의 benchmark 정규화는 비교적 독립적인 하위 작업이지만, 결과 해석과 GPU code 변경은 숙련자와 함께 진행하는 것이 좋다.

1. example의 Lottie path를 정렬하고 실제 선택된 100개 path를 파일로 저장한다.
2. M1에서 GL/WG를 release build로 각각 5회 실행해 warm-up 이후 600 frame의 raw frame time을 CSV로 남긴다.
3. 950×950, 1344×1344, 1900×1900 결과를 비교해 비용이 pixel 수, animation 수 또는 draw 수 중 무엇과 함께 증가하는지 본다.
4. core에 코드를 바꾸지 않은 상태에서 Instruments/Xcode Metal capture와 CPU sampling profile을 먼저 얻는다.
5. profile screenshot만 올리지 말고 commit, dependency, asset hash, 실행 명령과 숫자 table을 함께 issue에 남긴다.

## 위험/검증

- 같은 asset manifest, animation frame progression과 1900×1900 output을 GL/WG에서 사용했는지 검증한다.
- M1뿐 아니라 다른 Apple Silicon 세대와 Windows discrete GPU에서 before/after를 반복한다.
- median·p95 frame time, CPU phase와 GPU phase를 분리하고 thermal throttling과 display refresh 영향을 기록한다.
- 1, 10, 100 animation 및 여러 resolution으로 CPU overhead와 fill-rate/bandwidth scaling을 분리한다.
- solid, gradient, stroke, clip, mask, blend와 blur/drop-shadow가 많은 corpus별로 batch/pass 통계를 비교한다.
- submit 병합 시 surface target과 external texture target, `draw()` 후 `sync()` 전 상태, resize·target 교체와 error path를 test한다.
- MSAA/offscreen 변경 시 GL·WG pixel comparison, alpha mode, edge antialiasing, composition과 effect 결과를 허용 오차 안에서 비교한다.
- queue write/buffer reuse 변경 시 frame 간 data overwrite, in-flight resource lifetime과 장시간 memory 증가를 확인한다.
- adapter feature가 없는 환경에서도 계측 code가 disable/fallback되고 production build에 overhead를 남기지 않는지 확인한다.
- 기존 WebGPU unit test, pixel inspector, ASan/UBSan을 실행하고 Apple GPU smoke/performance job을 별도 추가한다.
- 개선 기준은 단일 FPS 숫자가 아니라 “동일 화질·동일 workload에서 M1의 median/p95 개선, 다른 플랫폼의 허용 가능한 비회귀”로 합의한다.
