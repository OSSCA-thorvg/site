## 이슈 요약

hint가 들어간 CFF 기반 OTF glyph를 처리할 때 `OtfReader::charStrings()`가 같은 byte를 계속 읽어 `Canvas::update()`가 반환하지 않는다는 제보다. 제보자는 기존 `DMSans.otf`의 `H` glyph에 `hstem` 하나를 추가하는 최소 재현과 실제 hinted font 사례를 제공했다. 문제는 raster 크기나 scanline 성능이 아니라 glyph outline을 Type 2 bytecode에서 `RenderPath`로 바꾸는 단계에 있다.

이슈는 이전 #4614의 CID-keyed CFF hang 중 `Hello`에서 발생하는 부분을 hint operator 미처리로 더 좁힌다. 반면 #4614의 CFF2 access violation과 FDSelect/FDArray·glyph별 local subroutine 정확성은 이 수정으로 해결되지 않는다고 제보자도 구분했다. 따라서 이번 작업은 “hint가 있는 CFF1의 진행 보장”에 한정하고 CFF2/CID 전체 지원 완료로 표시하면 안 된다.

분석 기준 `main`은 이슈가 확인한 revision 뒤에 PNG loader 수정 하나가 추가된 상태이며 SFNT reader의 해당 구현은 바뀌지 않았다. 이슈를 참조하는 열린 source PR도 확인되지 않았다.

## main 코드 조사

[`OtfReader::operand()`](https://github.com/thorvg/thorvg/blob/de7ee587603275e91e4f82b9f67b9badfe0166c9/src/loaders/sfnt/tvgOtfReader.cpp#L313-L336)은 byte 32 이상, shortint 28과 29만 숫자로 decode하며 각 인코딩 길이만큼 `p`를 증가시킨다. 그 외 byte에는 반환값이나 fallback이 없고 `p`도 바꾸지 않는다. Type 2에서 29는 숫자가 아니라 `callgsubr`지만 `charStrings()`의 switch가 먼저 가로채므로 현재 경로에서 이 operand branch는 도달하지 않는다.

[`charStrings()`의 interpreter loop](https://github.com/thorvg/thorvg/blob/de7ee587603275e91e4f82b9f67b9badfe0166c9/src/loaders/sfnt/tvgOtfReader.cpp#L338-L465)는 일부 path operator와 local/global subroutine을 처리한다. switch에 없는 byte는 `operand(values, b, p); continue;`로 보낸다. 숫자라면 `operand()`가 cursor를 전진시키지만, 알려지지 않은 operator라면 `p`가 그대로인 채 `continue`가 실행되어 loop 조건과 다음 `u8(p)`가 완전히 같아진다.

같은 switch에는 Type 2의 [`hstem(1)`, `vstem(3)`, `hstemhm(18)`, `vstemhm(23)`, `hintmask(19)`, `cntrmask(20)` case가 없다](https://github.com/thorvg/thorvg/blob/de7ee587603275e91e4f82b9f67b9badfe0166c9/src/loaders/sfnt/tvgOtfReader.cpp#L361-L459). 따라서 이 여섯 operator는 모두 cursor가 정지하는 default 경로로 들어간다. 이는 이슈가 지목한 직접 원인과 current main이 일치하는 부분이다.

Adobe의 공식 [Type 2 CharString 기술 문서](https://adobe-type-tools.github.io/font-tech-notes/pdfs/5177.Type2.pdf)는 여섯 hint operator를 정의한다. stem operator의 argument는 위치·폭의 쌍이며, `hintmask`와 `cntrmask` 다음에는 지금까지 선언된 stem마다 한 bit를 갖는 `ceil(numStems / 8)` byte의 mask가 붙는다. mask byte는 일반 operator나 숫자가 아니므로 stem 수를 세지 않고 한 byte씩 해석하면 이후 cursor가 즉시 어긋난다.

Type 2에서는 첫 stack-clearing operator가 optional width argument 하나를 추가로 받을 수 있다. 첫 operator가 stem 또는 hint mask라면 stack count가 홀수일 수 있으므로 stem 수는 width 가능성을 제외한 pair 수로 계산해야 한다. 단순한 정상 font에서는 `values.count / 2`의 내림이 맞지만, 구현에는 “첫 width를 이미 소비했는가”와 operand 개수 유효성 검사를 명시하는 편이 안전하다.

subroutine은 [`charStrings()`의 동일한 `values` stack과 실행 상태를 사용](https://github.com/thorvg/thorvg/blob/de7ee587603275e91e4f82b9f67b9badfe0166c9/src/loaders/sfnt/tvgOtfReader.cpp#L397-L407)하고, Type 2 규격상 hint sequence 일부도 subroutine에 들어갈 수 있다. 따라서 stem 총수는 glyph 실행 전체에서 유지되어야 하며 mask를 건너뛸 때 현재 charstring/subroutine `end`를 넘지 않는지 확인해야 한다.

별도의 인접 결함도 보인다. [`case 12`](https://github.com/thorvg/thorvg/blob/de7ee587603275e91e4f82b9f67b9badfe0166c9/src/loaders/sfnt/tvgOtfReader.cpp#L409-L412)는 2-byte escape operator에서 `p += 2` 후 공통 `++p`까지 실행해 총 3 byte를 전진한다. Type 2 escape encoding은 총 2 byte다. 이슈 재현 font가 escape operator를 사용하지 않아 이번 hang의 원인은 아니지만, generic progress guard와 함께 무심코 수정하면 지원되지 않는 flex/arithmetic operator의 동작 범위까지 커질 수 있으므로 별도 test와 범위 합의가 필요하다.

[`SfntLoader::request()`와 text layout](https://github.com/thorvg/thorvg/blob/de7ee587603275e91e4f82b9f67b9badfe0166c9/src/loaders/sfnt/tvgSfntLoader.cpp#L187-L230)은 codepoint의 glyph 변환을 동기적으로 요청한다. `OtfReader::convert()`가 `charStrings()`를 호출하므로 cursor가 멈추면 glyph request와 이를 기다리는 canvas update도 끝나지 않는다. 화면 크기를 바꿔도 증상이 같다는 제보와 부합한다.

현재 [`Load OTF Data from a file` test](https://github.com/thorvg/thorvg/blob/de7ee587603275e91e4f82b9f67b9badfe0166c9/test/testText.cpp#L313-L337)는 `DMSans.otf`로 긴 문자열을 canvas에 올리고 `update()`·`sync()` 성공을 확인한다. 저장소에는 OTF fixture가 이 파일 하나뿐이다. 분석 과정에서 fontTools로 511 glyph의 decompiled program을 확인했을 때 여섯 hint operator의 사용 횟수는 0이었다. 따라서 test가 실제 render까지 수행해도 문제 분기를 통과하지 않는다.

build option은 [`ttf`와 `otf`를 별도 loader로 제공하고 기본값에는 `otf`를 포함하지 않는다](https://github.com/thorvg/thorvg/blob/de7ee587603275e91e4f82b9f67b9badfe0166c9/meson_options.txt#L12-L16). 이 설정은 OTF 지원을 켠 build에서 발생하는 무한 반복의 원인은 아니며, 지원 범위·문서 문제는 core parser 수정과 분리하는 편이 좋다.

## 원인 분석

### 확인된 사실

- current `charStrings()`에는 여섯 Type 2 hint operator case가 없다.
- default 경로는 모든 미인식 byte를 `operand()`로 보낸 뒤 공통 cursor 증가를 건너뛴다.
- `operand()`는 숫자가 아닌 byte를 받으면 cursor를 변경하지 않는다.
- 따라서 hint operator를 만나면 같은 `p`와 같은 byte로 다음 loop가 시작되어 종료 조건에 도달할 수 없다.
- `hintmask`와 `cntrmask`는 누적 stem 수에 따라 한 개 이상의 후속 mask byte를 소비해야 한다.
- hint 및 mask operator는 stack-clearing이며 첫 번째일 경우 optional width가 stack에 함께 있을 수 있다.
- 기존 OTF fixture의 511 glyph에는 decompile 결과 hint operator가 하나도 없다.
- 2-byte escape의 current cursor 계산은 공통 증가를 포함하면 3 byte가 되지만 이슈의 hinted-font hang과는 별도 결함이다.

### 추론과 판단

- **직접 root cause:** 이번 이슈의 무한 반복은 CID 선택보다 hint opcode가 “숫자일 것”이라고 가정한 default 분기에 들어가면서 cursor progress invariant가 깨지는 것으로 충분히 설명된다. 제보 font의 실제 마지막 byte와 current code가 일치하므로 확신도가 높다.
- **최소 기능 수정:** ThorVG가 hint를 rasterizer에 적용하지 않더라도 stem operator의 stack을 비우고 stem 수를 누적하며, mask operator가 지정한 길이를 정확히 건너뛰면 outline 좌표 처리를 이어갈 수 있다.
- **안전성 보강:** loop 시작의 `oldP`와 반복 뒤 `p`를 비교하는 guard 또는 operand decode의 성공 반환을 두어, 어떤 분기든 cursor 전진·subroutine 전환·명시적 실패 중 하나를 보장해야 한다. 알 수 없는 operator를 한 byte 건너뛰기만 하고 stale operand stack으로 계속하는 방식은 잘못된 outline을 조용히 만들 수 있다.
- **실패 정책:** Type 2 CFF1에서 reserved operator의 동작은 규격상 unspecified다. library parser에서는 잘못된 input을 억지로 계속하기보다 glyph 변환을 `false`로 끝내는 fail-closed 방식이 hang보다 예측 가능하다.
- **#4614와의 관계:** hinted CFF1의 `Hello` hang은 이 수정으로 풀릴 수 있지만, CID glyph가 올바른 Private DICT/local subroutine을 쓰는지와 CFF2 table parsing은 여전히 별도 검증 대상이다. 화면에 glyph가 나온다는 사실만으로 #4614 전체를 닫으면 안 된다.

## 구현 방향

1. `charStrings()`에 glyph 실행 전체에서 유지되는 `numStems`와 첫 stack-clearing operator/width 상태를 둔다.
2. `hstem`, `vstem`, `hstemhm`, `vstemhm`에서 operand count를 검증하고 optional width를 제외한 pair 수를 `numStems`에 더한 뒤 stack을 비운다. hint 자체는 path에 적용하지 않는다.
3. `hintmask`, `cntrmask` 앞의 stack operand는 implicit `vstemhm`일 수 있으므로 같은 규칙으로 stem 수에 포함한다. 이후 `(numStems + 7) / 8` mask byte와 operator byte를 함께 소비한다.
4. mask 길이를 더하기 전에 overflow와 `p + 1 + maskBytes <= end`를 검사한다. subroutine 안이라면 현재 실행 range를 기준으로 하고, 잘린 mask는 즉시 `false`를 반환한다.
5. `operand()`가 decode 성공 여부를 반환하게 하거나 byte class를 switch 전에 구분한다. default operator는 명시적으로 실패시키고, 매 loop가 cursor 전진·call/return 전환·종료 중 하나를 수행했는지 debug assertion/test로 고정한다.
6. escape operator의 off-by-one은 별도 regression을 먼저 추가한 뒤 수정한다. 지원하지 않는 two-byte operator를 ignore할지 reject할지 결정하고, flex를 구현하지 않은 상태에서 path를 성공으로 반환하지 않는다.
7. hinted fixture의 `hstem` 하나만 통과시키고 끝내지 말고 여섯 operator와 1·8·9·17 stem mask 길이를 최소 byte program 또는 생성 font로 검증한다.

첫 PR은 hint를 적용하는 rasterizer 기능이 아니라 “hint bytecode를 안전하게 소비하고 outline path를 보존하는 것”, progress guard와 직접 회귀 test로 제한하는 편이 좋다. CFF2, CID Font DICT 선택, flex 구현과 OTF build option 정책은 후속 작업으로 남긴다.

## 초심자 시작 가이드

직접 parser를 수정하기보다 재현·test fixture 하위 작업부터 시작하는 것을 권장한다.

1. fontTools로 기존 `DMSans.otf`의 `H` CharString을 decompile하고 `[0, 100, "hstem"]`을 앞에 넣은 작은 hinted fixture를 만든다. 원본 license와 생성 script/hash를 함께 기록한다.
2. 기존 OTF test와 같은 100×100 canvas에서 `H` 하나를 `update()`까지 실행하고 test runner에 timeout을 걸어 수정 전 hang을 확인한다.
3. debugger에서 `charStrings()`의 `p`, `b`, `values.count`를 기록해 `b=1`에서 `p`가 반복되는지 확인한다. 임시 log는 최종 PR에서 제거한다.
4. 수정 뒤에는 hinted glyph의 path command/point 수와 bounds를 unhinted 기준과 비교한다. hint는 outline geometry를 바꾸지 않으므로 같은 outline이 기대된다.
5. stem 수 9개와 `hintmask`를 가진 synthetic program에서 정확히 2 mask byte를 건너뛰는지 확인한다.

## 위험/검증

- `hstem`, `vstem`, `hstemhm`, `vstemhm` 각각이 있는 glyph가 제한 시간 안에 render되는지 확인한다.
- `hintmask`, `cntrmask`와 implicit vstem operand를 포함한 glyph의 다음 path operator가 정확한 byte에서 시작하는지 검사한다.
- optional width가 있는 첫 hint와 없는 첫 hint의 stem 수가 같게 계산되는지 확인한다.
- stem 수 1, 8, 9, 16, 17에서 mask 길이가 각각 1, 1, 2, 2, 3 byte인지 검사한다.
- hint declaration이나 mask가 local/global subroutine에 있을 때 누적 stem 수와 return cursor를 보존하는지 확인한다.
- mask payload가 current range 끝을 넘거나 operand pair가 부족한 손상 font를 hang·범위 밖 읽기 없이 거부한다.
- reserved one-byte operator와 잘린 number encoding이 progress guard를 통과하지 않고 deterministic하게 실패하는지 확인한다.
- two-byte escape가 정확히 2 byte를 소비하는지 별도 test를 두고, 미지원 flex/arithmetic operator의 실패 정책을 고정한다.
- 기존 `DMSans.otf`의 path command, point, bounds와 text pixel 결과가 바뀌지 않는지 확인한다.
- 실제 hinted CFF font 여러 개와 #4614의 CFF1 사례를 실행하되, CID outline 정확성과 CFF2 crash 결과는 별도 보고한다.
- ASan/UBSan, font corpus fuzzing과 wall-clock timeout으로 crash뿐 아니라 hang도 실패로 수집한다.
- OTF loader on/off build를 각각 실행해 feature guard와 기존 TTF loader에 영향이 없는지 확인한다.
