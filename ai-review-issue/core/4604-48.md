## 이슈 요약

외부 자산 resolver로 Lottie 폰트를 공급할 때, 폰트에 `fPath`가 있으면 콜백에는 경로만 전달된다. 그러나 콜백 구현자는 로드한 폰트를 텍스트가 요청하는 정확한 `fName`으로 등록해야 한다. 임의 URL이나 파일 경로만으로 그 이름을 일반적으로 복원할 수 없으므로, 현재 공개 콜백만 사용하면 호출자가 Lottie JSON을 따로 해석해 `fPath`와 `fName`의 대응표를 만들어야 한다.

목표는 폰트 요청에서 소스와 등록 이름을 함께 전달하되 이미지 resolver의 기존 의미를 흐리지 않는 것이다. 이름 인자를 추가한다면 이미지에는 `nullptr`, 폰트에는 원본 `fName`을 전달하는 식의 계약이 가장 직접적이다.

## main 코드 조사

공개 C++ API의 [`Picture::resolver`](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/inc/thorvg.h#L1739-L1760)는 콜백에 `Paint*`, `src`, 사용자 데이터만 전달한다. 문서는 `src`를 이미지 또는 폰트 경로로 설명하고, 경로가 없는 폰트에는 `name:<font name>` 형식을 사용한다고 적는다. 이 API는 Experimental로 표시되어 있다.

C API도 [`Tvg_Picture_Asset_Resolver`](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/bindings/capi/thorvg_capi.h#L400-L416)가 `paint`, `src`, `data` 세 값만 받는다. [C API 어댑터](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/bindings/capi/tvgCapi.cpp#L653-L659)도 같은 정보만 내부 콜백으로 전달한다. 내부 [`AssetResolver`](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/renderer/tvgLoader.h#L36-L40) 역시 동일한 시그니처이므로 한 계층만 수정해서는 정보가 끝까지 전달되지 않는다.

Lottie parser는 텍스트 문서의 `f`를 [`doc.name`](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/loaders/lottie/tvgLottieParser.cpp#L132-L138)에 보존한다. 폰트 목록에서는 [`fName`을 `font->name`에, `fPath`를 외부 폰트 경로에 저장](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/loaders/lottie/tvgLottieParser.cpp#L1144-L1161)한다. 즉, 필요한 두 정보는 모델에 모두 있다.

문제는 [`updateURLFont()`](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/loaders/lottie/tvgLottieBuilder.cpp#L989-L1008)에서 나타난다.

- 먼저 새 `Text`를 만들고 `paint->font(doc.name)`으로 이름 기반 조회를 시도한다.
- 조회에 실패하고 `font->path`가 있으면 `src`에 그 경로만 넣는다.
- 경로가 없을 때만 `name:<doc.name>` 문자열을 동적으로 만든다.
- resolver는 `paint`와 `src`만 받으므로 경로가 있는 요청에서 `doc.name`을 알 수 없다.

또한 같은 함수에는 텍스트 인스턴스를 매 프레임 다시 로드한다는 TODO가 있다. resolver가 제공한 폰트를 요청 이름으로 등록하지 못하면 이후 프레임에서도 이름 조회가 실패하고 콜백이 반복될 가능성이 있다.

현재 [`testLottie.cpp`의 resolver 테스트](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/test/testLottie.cpp#L291-L327)는 폰트를 로드하지만 콜백이 받은 소스, 폰트 이름, 호출 횟수를 검증하지 않는다. 따라서 공개 계약의 정보 손실과 반복 호출을 잡아내지 못한다.

## 원인 분석

### 확인된 사실

- parser는 `fName`과 `fPath`를 별도 필드로 읽고 보존한다.
- `updateURLFont()`는 경로가 있으면 resolver에 `fPath`만 넘기고, `fName`은 넘기지 않는다.
- 콜백이 받는 `src`가 임의 경로일 수 있으므로 공개 API만으로 그 값이 어떤 폰트 이름에 대응하는지 알 수 없다.
- C++, C, 내부 resolver 선언과 C 어댑터가 모두 현재의 3인자 계약을 공유한다.
- 폰트 이름으로 조회하지 못하면 resolver 경로에 진입하며, 현재 테스트는 인자와 호출 횟수를 검사하지 않는다.

### 추론과 판단

- 외부 콜백이 JSON을 별도로 파싱하도록 요구하는 것은 `Picture`가 이미 해석한 정보를 다시 복원하게 만드는 중복이며 resolver 추상화의 목적에 맞지 않는다.
- `src` 문자열에 구분자를 넣어 이름을 합치는 방식은 URL 문법, escaping, 기존 콜백 호환성을 새로 정의해야 하므로 별도 `name` 인자보다 취약하다.
- API가 Experimental이므로 시그니처 변경은 가능하지만, C 함수 포인터를 포함하므로 소스 호환과 ABI 변화는 릴리스 노트에 명시해야 한다.
- 폰트를 정확한 이름으로 등록하면 후속 프레임의 `paint->font(doc.name)`이 성공해 반복 콜백도 줄어들 가능성이 높다. 다만 호출 횟수 정책은 테스트로 고정해야 한다.

## 구현 방향

1. resolver 계약에 선택적 자산 이름을 추가한다. 예를 들어 C++은 `Paint*, const char* src, const char* name, void*`, C는 대응하는 함수 포인터 시그니처를 사용한다.
2. 문서에 각 인자의 의미와 수명을 명시한다.
   - Lottie 이미지: `src`는 자산 경로/URL, `name`은 `nullptr`
   - Lottie 폰트: `src`는 `fPath` 또는 경로 없음의 표현, `name`은 정확한 `fName`
   - 문자열은 콜백 실행 중에만 유효하며 콜백이 보관하려면 복사해야 함
3. 공개 C++ 선언, 내부 `AssetResolver`, C typedef와 C API 어댑터를 한 변경에서 동기화한다.
4. `updateURLFont()`는 경로 유무와 관계없이 `doc.name`을 별도 인자로 넘긴다. 기존 `name:` 접두사 표현을 유지할지 제거할지는 하위 호환 정책을 문서와 함께 결정한다.
5. 이미지 resolver 호출부는 새 이름 인자에 `nullptr`을 전달해 기존 소스 의미를 보존한다.
6. 예제와 테스트 콜백을 새 시그니처로 갱신하고, Experimental API 변경 사항을 사용자에게 알린다.

## 초심자 시작 가이드

먼저 작은 Lottie fixture에 서로 다른 `fName`과 알아보기 어려운 `fPath`를 넣는다. 콜백에서 받은 네 값을 기록하고 다음 두 단계를 분리해 확인한다.

1. 첫 호출에서 `src`가 원본 경로이고 `name`이 정확한 `fName`인지 확인한다.
2. 콜백이 그 이름으로 폰트를 등록한 뒤 여러 프레임을 갱신해 같은 요청이 불필요하게 반복되지 않는지 확인한다.

그 다음 `rg "AssetResolver|Asset_Resolver|resolver\\("`로 C++ 선언부터 C 어댑터와 모든 호출부까지 목록을 만들고, 시그니처를 한 계층씩 바꾸며 컴파일 오류가 사라지는지 확인한다. 문자열을 객체에 저장해야 한다면 콜백 인자 포인터를 그대로 보관하지 말고 복사한다.

## 위험/검증

- `fPath`가 있는 폰트와 없는 폰트 모두에서 정확한 `fName`이 전달되는지 검사한다.
- 이미지 자산은 기존 `src` 값이 바뀌지 않고 `name == nullptr`인지 검사한다.
- resolver 미설정, 콜백 성공, 콜백 실패 및 fallback font 경로를 모두 실행한다.
- 같은 애니메이션을 여러 프레임 갱신해 성공한 폰트 요청의 호출 횟수가 안정적인지 확인한다.
- C와 C++ 예제를 각각 빌드해 함수 포인터와 람다 시그니처가 문서와 일치하는지 확인한다.
- callback 안에서만 유효한 문자열 수명을 문서화하고 ASan으로 use-after-free가 없는지 검사한다.
- 여러 폰트가 같은 경로를 쓰거나 한 폰트가 여러 경로 표현을 갖는 경우에도 이름 기반 등록이 섞이지 않는지 확인한다.
- 기존 외부 구현에 대한 소스/ABI 변화가 Experimental 정책에 맞게 공지되었는지 검토한다.
