## 이슈 요약

이 이슈는 Software renderer에서 같은 최종 크기의 radial repeat gradient가 만들어진 방식에 따라 다른 경계 품질을 보인다고 보고한다. 비교 대상은 반지름 2048의 fill 자체에 0.0625 scale을 적용한 경우, 반지름 2048과 큰 shape를 함께 0.0625 scale한 경우, 그리고 반지름 128을 transform 없이 직접 그린 기준 경우다. 세 gradient의 screen-space 반지름은 모두 128이지만 앞의 두 결과는 기준 결과와 repeat 경계의 antialiasing이 다르다.

repeat gradient는 마지막 color stop 뒤에 첫 color stop이 다시 이어진다. 두 색이 다르면 이 wrap 경계가 갑자기 바뀌므로 renderer는 color table의 끝과 시작 일부를 섞어 aliasing을 줄인다. 현재 코드는 이 섞을 폭을 원본 radial radius 또는 linear length로 추정하고, 그 gradient와 shape에 적용된 transform을 계산에 포함하지 않는다. 따라서 최종 화면 주기가 같아도 원본 수치가 큰 transformed gradient에는 지나치게 작은 값, 이 사례에서는 정수 변환 뒤 0이 선택된다.

## main 코드 조사

repeat 경계의 폭을 정하는 [`_estimateAAMargin()`](https://github.com/thorvg/thorvg/blob/5ebb85a81423fe72acbc6305bb0f2d27806b7b5f/src/renderer/cpu_engine/tvgSwFill.cpp#L64-L75)은 고정 계수 800을 radial gradient의 원본 `r`, 또는 linear gradient의 원본 두 점 거리로 나눈 뒤 `uint32_t`로 변환한다. 함수 인자는 `Fill*` 하나뿐이라 shape transform과 fill transform을 받을 경로가 없다.

이슈의 수치를 그대로 대입하면 차이가 정량적으로 드러난다. 원본 반지름 2048인 두 transformed 사례는 `uint32_t(800 / 2048)`, 즉 0 table entry를 얻는다. 반지름 128인 기준 사례는 `uint32_t(800 / 128)`, 즉 6 entry를 얻는다. [`_applyAA()`](https://github.com/thorvg/thorvg/blob/5ebb85a81423fe72acbc6305bb0f2d27806b7b5f/src/renderer/cpu_engine/tvgSwFill.cpp#L103-L121)는 시작 또는 끝 폭이 0이면 바로 반환하므로, 앞의 두 사례에는 repeat seam 보간이 적용되지 않는다.

[`_updateColorTable()`의 repeat 분기](https://github.com/thorvg/thorvg/blob/5ebb85a81423fe72acbc6305bb0f2d27806b7b5f/src/renderer/cpu_engine/tvgSwFill.cpp#L124-L200)는 위 추정값으로 시작 폭을 만들고, 첫·마지막 stop이 차지하는 table 공간에 맞게 각 폭을 조정한 다음 table 끝과 시작을 원형으로 보간한다. 조정 함수는 [stop 구간의 10%와 40 entry로 상한을 둔다](https://github.com/thorvg/thorvg/blob/5ebb85a81423fe72acbc6305bb0f2d27806b7b5f/src/renderer/cpu_engine/tvgSwFill.cpp#L79-L87). 따라서 수정은 이 상한과 stop 공간 제한을 유지하면서 최초 추정값의 좌표계를 screen space에 맞추는 것이 핵심이다.

반면 실제 pixel sampling 준비는 transform을 이미 반영한다. [`_prepareLinear()`](https://github.com/thorvg/thorvg/blob/5ebb85a81423fe72acbc6305bb0f2d27806b7b5f/src/renderer/cpu_engine/tvgSwFill.cpp#L203-L234)은 shape 쪽 `pTransform`과 `linear->transform()`을 곱한 뒤 역행렬을 sampling 계수에 넣는다. [`_prepareRadial()`](https://github.com/thorvg/thorvg/blob/5ebb85a81423fe72acbc6305bb0f2d27806b7b5f/src/renderer/cpu_engine/tvgSwFill.cpp#L238-L270)도 같은 순서로 결합한 transform의 역행렬을 저장한다. 즉 gradient 위치와 반복 주기는 transformed 좌표로 sampling하면서 seam AA 폭만 원본 좌표에 남아 있다.

[`fillGenColorTable()`](https://github.com/thorvg/thorvg/blob/5ebb85a81423fe72acbc6305bb0f2d27806b7b5f/src/renderer/cpu_engine/tvgSwFill.cpp#L774-L785)은 transform을 받아 sampling 준비 함수에는 전달하지만 `_updateColorTable()`에는 전달하지 않는다. color table은 [`SW_COLOR_TABLE` 1024개 entry](https://github.com/thorvg/thorvg/blob/5ebb85a81423fe72acbc6305bb0f2d27806b7b5f/src/renderer/cpu_engine/tvgSwCommon.h#L34-L34)를 모든 pixel이 공유한다. transform에 따라 table 자체를 바꾸는 접근은 table 생성 함수의 signature뿐 아니라 언제 재생성할지도 함께 바꿔야 한다.

그 lifecycle은 [`shapeGenFillColors()`](https://github.com/thorvg/thorvg/blob/5ebb85a81423fe72acbc6305bb0f2d27806b7b5f/src/renderer/cpu_engine/tvgSwShape.cpp#L513-L523)에서 확인할 수 있다. 처음 `SwFill`을 만들 때는 color table을 강제로 생성하지만, 기존 fill은 caller가 `ctable`을 요청할 때만 reset·재생성한다. [`SwTask::run()`의 fill·stroke update](https://github.com/thorvg/thorvg/blob/5ebb85a81423fe72acbc6305bb0f2d27806b7b5f/src/renderer/cpu_engine/tvgSwRenderer.cpp#L128-L159)는 transform 변경에도 sampling 계수는 다시 준비하지만 일반 fill의 `ctable` 인자는 `Gradient` flag에만 의존한다. stroke도 transform-only update에서는 좌표를 다시 준비하면서 `GradientStroke`가 없으면 table을 재생성하지 않는다. AA 폭이 결합 transform에 의존하게 되면 이 경로를 그대로 둘 경우 최초 draw는 맞아도 이후 transform animation의 seam 폭은 stale 상태가 될 수 있다.

repeat sampling 자체는 [`_clamp()`](https://github.com/thorvg/thorvg/blob/5ebb85a81423fe72acbc6305bb0f2d27806b7b5f/src/renderer/cpu_engine/tvgSwFill.cpp#L274-L310)에서 table index를 modulo로 감싼다. 이번 문제는 wrapping 위치가 아니라 wrap 양쪽 color를 몇 entry에 걸쳐 섞을지에 있다. Pad와 Reflect는 `_applyAA()` 대상이 아니므로 수정 뒤에도 이 spread mode의 table 결과가 바뀌지 않는지 확인해야 한다.

current Software engine test의 [gradient 구간](https://github.com/thorvg/thorvg/blob/5ebb85a81423fe72acbc6305bb0f2d27806b7b5f/test/testSwEngine.cpp#L295-L333)은 Repeat linear와 Pad radial을 여러 blend·mask 조합으로 draw하고 `sync()` 성공을 검사한다. 문제의 Repeat radial, fill/shape transform 비교, seam 주변 pixel 동등성은 검증하지 않는다. 이 bug에는 API 성공 test보다 세 장면의 pixel buffer를 비교하는 regression test가 필요하다.

관련된 [기존 개선 PR](https://github.com/thorvg/thorvg/pull/2418)은 repeat의 마지막·첫 color 사이 AA를 추가하면서 현재의 margin 추정과 table 경계 보간을 도입했다. 이력상 이번 수정은 그 기능을 제거하는 것이 아니라 transform된 screen-space 주기에서도 동일한 의도가 유지되도록 좌표계와 갱신 조건을 보완하는 작업이다.

## 원인 분석

### 확인된 사실

- repeat seam AA 폭은 고정값 800을 원본 radial radius 또는 linear endpoint 거리로 나눈 정수값이다.
- 해당 계산에는 fill transform과 shape transform이 전달되지 않는다.
- 원본 반지름 2048은 margin 0, 원본 반지름 128은 margin 6을 만든다. margin 0이면 seam AA 함수는 아무 작업도 하지 않는다.
- 실제 linear/radial sampling은 shape transform과 fill transform을 결합한 역행렬을 사용한다.
- color table은 transform-only update에서 항상 재생성되지 않는다.
- current test는 Repeat linear와 Pad radial의 draw 성공을 확인하지만 이슈의 Repeat radial transform 비교나 pixel 결과는 검사하지 않는다.

### 추론과 판단

- **직접 원인 판단:** 이슈의 두 transformed 결과와 기준 결과의 차이는 sampling 좌표에는 transform이 적용되지만 seam AA margin에는 적용되지 않는 비대칭으로 설명된다. 수식과 제어 흐름은 일치하지만, 이 분석에서 첨부 이미지를 local build로 다시 render해 pixel 값을 계측한 것은 아니므로 시각 차이의 전부가 이 한 원인뿐이라고 단정하지는 않는다.
- **uniform scale:** 이슈처럼 0.0625 uniform scale이면 원본 반지름 2048에 scale을 적용한 screen-space 반지름 128을 사용해 기준과 같은 margin 6을 만들 수 있다. linear gradient도 결합 transform으로 두 endpoint를 screen space에 옮긴 뒤 거리를 재면 같은 원리가 적용된다.
- **일반 affine transform:** non-uniform scale이나 skew가 적용된 radial circle은 화면에서 ellipse가 된다. 방향마다 gradient parameter의 pixel당 변화량이 달라 하나의 전역 color-table margin으로 모든 seam을 동시에 정확하게 filter할 수 없다. 최소·최대 축 또는 singular value 하나를 택하면 특정 방향의 aliasing이나 과도한 blur가 남을 수 있다.
- **cache invalidation:** transform-derived margin을 table에 굽는다면 shape 또는 fill transform이 바뀔 때 table을 다시 만들어야 한다. sampling 계수만 갱신하는 현재 정책은 충분하지 않다.
- **더 정확한 대안:** arbitrary affine 품질까지 목표로 한다면 color table을 transform별로 수정하는 대신 sampling 지점의 gradient derivative로 filter width를 계산하는 방식이 더 정확할 수 있다. 대신 hot pixel loop, SIMD 경로와 성능 범위가 커지므로 이번 bug의 기대 범위와 분리해 검토할 필요가 있다.

## 구현 방향

1. issue의 세 장면을 offscreen buffer에 그리는 regression test부터 추가한다. 세 결과의 전체 배치 screenshot만 비교하지 말고 같은 local 좌표의 seam 주변 pixel을 별도 buffer로 render해 transform 방식과 무관하게 일치하는지 확인한다.
2. margin helper가 원본 `Fill`뿐 아니라 실제 결합 transform을 고려하도록 data flow를 정리한다. `fillGenColorTable()`이 이미 받는 shape transform과 `Fill::transform()`을 sampling 준비와 동일한 순서로 결합해야 한다.
3. linear gradient는 두 endpoint를 결합 transform으로 screen space에 투영한 길이를 사용한다. translation은 길이를 바꾸지 않고 rotation은 길이를 보존하므로 scale·skew의 결과만 자연스럽게 반영된다.
4. radial gradient는 먼저 uniform scale과 rotation에 대한 명확한 계약을 구현한다. arbitrary affine에서는 두 basis vector의 길이 또는 singular value 중 어떤 정책을 쓸지 test와 주석으로 명시한다. 한 scalar의 품질이 받아들일 수 없다면 sampling-time derivative 방식은 후속 설계로 분리한다.
5. transform이 AA margin을 바꿀 수 있으므로 transform-only update에서도 Repeat gradient table이 필요한 경우 재생성한다. 모든 gradient table을 매 frame 무조건 재생성하기보다 spread mode와 effective scale key를 확인하거나, transform-independent table과 seam filtering state를 분리해 비용을 제한한다.
6. fill과 gradient stroke가 같은 update 정책을 사용하도록 맞춘다. 최초 생성, gradient stop·spread 변경, fill transform 변경, shape transform 변경의 네 경우를 각각 test한다.
7. 기존 10%/40-entry cap과 첫·마지막 stop 공간 제한을 유지하고, zero radius·zero length·non-invertible transform에서는 기존의 안전한 failure/solid 처리와 out-of-bounds 방지를 보존한다.
8. Pad와 Reflect의 color table hash 또는 대표 pixel이 수정 전과 동일한지 확인하고, Repeat에서도 transform이 identity이면 기존 결과가 바뀌지 않도록 한다.

## 초심자 시작 가이드

1. issue 예제를 세 개의 독립된 512×512 Software canvas test로 옮긴다. 배치 위치가 다르더라도 비교 좌표가 같도록 각 장면의 translation은 제거하거나 정규화한다.
2. seam이 지나가는 ring 주변의 pixel 몇 개와 전체 buffer 차이 개수, channel별 최대 차이를 출력한다. 먼저 transformed fill, transformed shape, direct radius 128의 차이가 test 실패로 잡히는지 확인한다.
3. `_estimateAAMargin()` 직전에 원본 radius, 결합 transform의 scale과 계산된 margin을 임시로 기록한다. 2048 사례가 0, 128 사례가 6이 되는 현재 동작을 확인한 뒤 임시 출력은 제거한다.
4. uniform scale만 반영하는 작은 helper를 만들고 identity, 0.0625, 2.0, rotation+scale에 대한 단위 test를 작성한다. translation만 바뀌면 margin이 같아야 한다.
5. shape transform과 fill transform을 각각 적용한 결과가 같은지 확인한 뒤 두 transform이 동시에 있는 경우를 추가한다. 곱셈 순서는 `_prepareLinear()`과 `_prepareRadial()`의 existing path를 기준으로 한다.
6. 마지막으로 같은 object의 transform을 draw 사이에 바꿔 color table이 갱신되는지 확인한다. object를 새로 만들기만 하는 test는 cache invalidation bug를 놓칠 수 있다.

## 위험/검증

- issue의 세 radial Repeat 장면을 동일 local 좌표에서 pixel 비교하고 seam 주변의 최대 channel 차이와 불일치 pixel 수를 기록한다.
- radial radius와 linear length에 identity, uniform 축소·확대, rotation, translation, reflection을 적용해 기대 margin과 pixel 결과를 확인한다.
- non-uniform scale과 skew에서 aliasing을 줄이면서 긴 축 방향이 과도하게 흐려지지 않는지 reference image와 수치로 검증한다.
- fill transform, shape transform, 두 transform의 결합이 같은 final matrix일 때 결과가 일치하는지 확인한다.
- 같은 shape를 유지한 채 transform만 여러 frame 변경하고 table과 sampling 계수가 모두 새 상태를 반영하는지 확인한다.
- solid fill, gradient fill, gradient stroke에서 update flag와 table lifetime을 검사하고 fill·stroke 중 한쪽만 stale해지지 않는지 확인한다.
- Repeat linear와 radial에서 첫·마지막 color가 다른 경우, 같은 경우, alpha가 다른 경우를 검사한다.
- color stop이 0/1을 포함하거나 포함하지 않는 경우, 매우 짧은 첫·마지막 stop 구간, 중복 offset과 작은/큰 gradient 주기에서 10%/40-entry cap 및 table bounds를 확인한다.
- Pad와 Reflect spread가 bit-for-bit 또는 명시한 tolerance 안에서 기존 결과를 유지하는지 확인한다.
- zero radius·zero length, singular matrix, 매우 작은·큰 scale과 음수 scale에서 division, overflow, NaN과 out-of-bounds access가 없는지 sanitizer로 확인한다.
- full Software engine test, pixel regression suite와 representative repeat-gradient scene benchmark를 실행해 transform animation의 table 재생성 비용을 측정한다.
