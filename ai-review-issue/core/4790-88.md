- 실현 가능성: **중간** — sharp rectangle의 제한된 solid-fill fast path는 작게 시작할 수 있다. 하지만 current representation은 기본 도형을 즉시 일반 path로 펼쳐 도형 종류와 원래 매개변수를 잃는다. circle·round rect·stroke까지 안정적으로 확장하려면 metadata 보존/무효화 또는 엄격한 path pattern 인식이 선행되어야 한다.

## 이슈 요약

이슈는 사각형, 둥근 사각형, 원·타원처럼 구조가 알려진 도형을 임의 path와 동일하게 flatten/tessellate하지 말고 직접 geometry로 만들자는 최적화 제안이다. 예를 들어 사각 stroke를 general stroker 대신 border mesh로 구성하고, geometry가 겹치지 않는 경우 stencil-and-cover 없이 직접 그리면 CPU 준비 시간과 render pass를 줄일 수 있다.

목표는 일반 path pipeline을 제거하는 것이 아니라 지원되는 안전한 조합만 fast path로 보내고 나머지는 기존 renderer로 fallback하는 것이다. 따라서 성능보다 먼저 “언제 입력이 여전히 하나의 기본 도형인가”와 “어떤 fill/stroke/transform에서 direct draw가 기존 의미와 같은가”를 명확히 해야 한다.

## main 코드 조사

public [`Shape::appendCircle()`와 `appendRect()`](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/src/renderer/tvgShape.cpp#L94-L111)는 `ShapeImpl` helper를 호출한다. [`ShapeImpl::addCircle()`와 `addRect()`](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/src/renderer/tvgShape.h#L358-L369)는 모두 `rs.path`에 명령을 추가하고 `Path` dirty flag만 표시한다. 도형 kind나 x/y/radius를 별도 저장하지 않는다.

[`RenderPath::addCircle()`](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/src/renderer/tvgRender.cpp#L71-L108)는 ellipse를 네 cubic Bézier와 close로 확장한다. [`RenderPath::addRect()`](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/src/renderer/tvgRender.cpp#L110-L174)는 sharp rect를 네 꼭짓점의 line path로, round rect를 line과 cubic 조합으로 추가한다. 이 시점 이후 이 path가 append API로 만든 primitive인지 같은 command를 직접 넣은 custom path인지 구분할 수 없다.

공통 [`RenderShape`](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/src/renderer/tvgRender.h#L424-L503)는 path, fill, color, stroke와 fill rule만 보유한다. 하나의 `Shape`에 여러 `appendRect()`를 누적하거나 뒤에 `lineTo()`를 추가할 수 있으므로 단순히 마지막 API 호출을 기억하는 것만으로는 전체 shape를 primitive로 취급할 수 없다. `reset()`, `appendPath()`, trimpath, dash도 metadata 무효화 규칙에 들어가야 한다.

GL의 [`GlGeometry::prepare()`와 fill/stroke tessellation](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/src/renderer/gpu_engine/gl/tvgGlGeometry.cpp#L110-L223)은 모든 shape에 `gpuOptimize()`를 적용하고 fill은 `BWTessellator`, stroke는 `Stroker`로 mesh를 만든다. 다만 GL이 모든 기본 도형에 항상 stencil을 쓰는 것은 아니다. tessellator가 convex라고 판정하면 [`stencilMode()`가 None을 반환](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/src/renderer/gpu_engine/gl/tvgGlGeometry.cpp#L267-L278)하고, solid·normal blend·clip 없음 조건에서는 [`GlRenderer::drawPrimitive()`가 solid batch로 직접 보낸다](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/src/renderer/gpu_engine/gl/tvgGlRenderer.cpp#L292-L324). 따라서 GL sharp rect fill의 기대 이득은 stencil 제거뿐 아니라 optimizer/tessellator를 건너뛰는 CPU·geometry 비용에서 따로 측정해야 한다.

WebGPU의 [`WgShape::update()`](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/src/renderer/gpu_engine/wg/tvgWgRenderData.cpp#L125-L208)도 path를 최적화한 뒤 `WgBWTessellator` 또는 `WgStroker`를 실행하고 geometry가 갱신될 때 mesh를 reset한다. [`WgRenderer::renderShape()`](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/src/renderer/gpu_engine/wg/tvgWgRenderer.cpp#L252-L264)는 이미 solid batch, stencil batch 순으로 시도한다. [stencil batch의 append 조건](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/src/renderer/gpu_engine/wg/tvgWgStencilBatch.cpp#L52-L137)은 viewport·fill rule과 bbox 비중첩을 요구한다. primitive fast path는 이 기존 batch 계약과 충돌하지 않도록 geometry와 convex/bounds 정보를 공급해야 한다.

기존 public shape test는 [극단값과 0 크기 rect/circle의 API 성공](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/test/testShape.cpp#L68-L91)을 확인한다. GL과 WebGPU engine test는 각각 [round rect gradient와 mask/blend 조합](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/test/testGlEngine.cpp#L300-L337), [같은 WebGPU 조합](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/test/testWgEngine.cpp#L300-L336)을 draw/sync하지만 pixel과 mesh/pass 수는 검사하지 않는다.

## 원인 분석

### 확인된 사실

- circle/ellipse는 `RenderPath` 안에서 네 cubic으로, rect는 line 또는 line+cubic command로 즉시 변환된다.
- `RenderShape`에는 primitive kind와 원래 매개변수가 없다.
- GL과 WebGPU 모두 geometry 갱신 시 generic optimizer와 fill tessellator/stroker를 호출한다.
- GL은 convex fill을 이미 non-stencil 경로로 보낼 수 있고 두 GPU backend에는 batching 코드가 존재한다.
- 하나의 Shape에 primitive와 arbitrary path를 누적할 수 있으며 기존 test도 append API의 성공 중심이다.

### 추론과 판단

- **핵심 구조적 원인:** renderer가 입력 primitive의 의미를 받기 전에 command stream만 남기므로, backend가 값싼 전용 mesh를 선택하려면 canonical command를 역으로 인식하거나 상위 계층이 primitive metadata를 보존해야 한다.
- **metadata 보존이 더 빠르지만 invalidation이 어렵다.** `appendRect()` 직후에는 확실하지만 추가 `lineTo`, 두 번째 primitive, `appendPath`, reset/duplicate가 발생하면 single-primitive fast path를 해제해야 한다. 누락된 무효화 한 곳은 잘못된 그림으로 이어진다.
- **pattern recognition은 API 변화가 작지만 모호하다.** 같은 command를 사용자가 직접 만들 수도 있고 tolerance·direction·negative size·round radius clamp를 재구성해야 한다. 매 frame command 수를 검사하면 절감하려던 CPU 비용 일부를 다시 낸다.
- **sharp rect fill이 가장 낮은 위험의 첫 단계다.** affine transform된 rect는 네 꼭짓점을 직접 만들 수 있고 solid/gradient fill도 기존 shader에 같은 좌표를 줄 수 있다. 반면 round rect/ellipse의 곡선 근사와 antialias 품질, stroke의 cap/join/dash/trim은 별도 설계가 필요하다.
- **draw-call 감소를 자동으로 기대하면 안 된다.** current GL은 convex solid를 이미 direct batch하고 WebGPU도 solid/stencil batch를 갖는다. fast path의 효과는 workload별 tessellation 시간, vertex/index 수, pass와 draw count를 각각 측정해야 한다.

## 구현 방향

1. 대량 static/animated rect, round rect, circle/ellipse를 fill-only와 stroke로 나눈 benchmark를 먼저 추가한다. geometry update 시간, vertex/index 수, stencil/cover pass, draw call과 GPU time을 backend별 baseline으로 저장한다.
2. 첫 범위를 “single sharp rectangle + no trim/dash + 유효한 affine transform”으로 제한한다. `RenderShape`에 명시적 primitive descriptor를 둘지, `RenderPath`에 canonical primitive tag를 둘지 결정하고 모든 path mutation에서 invalidation test를 만든다.
3. GL과 WebGPU가 공유할 수 있는 helper로 transformed quad와 fill/stroke bounds를 계산한다. fill은 두 triangle, rectangular stroke는 겹치지 않는 border triangles로 만들되 음수 width/height와 winding, subpixel width를 정규화한다.
4. solid fill부터 기존 shader/batch에 mesh를 연결한다. gradient는 fill-space inverse transform과 좌표가 기존 generic path와 같은지 확인한 뒤 확장한다.
5. sharp rect stroke는 dash·trim 없음, 표준 join/cap에서 시작한다. miter limit과 very thick stroke가 내부에서 겹치는 경우에는 general stroker로 fallback한다.
6. round rect와 ellipse는 후속 단계로 둔다. analytic shader, 고정 segment mesh 또는 기존 cubic flatten보다 싼 adaptive mesh 중 backend 공통 품질을 만족하는 방식을 benchmark로 선택한다.
7. fast path eligibility를 한 함수에 모으고 실패하면 기존 `gpuOptimize → tessellator/stroker`를 그대로 사용한다. debug build에서는 선택 이유와 fallback 이유를 계측 가능하게 한다.

작은 PR 순서는 primitive descriptor/invalidation test → sharp rect fill → sharp rect stroke → round rect/ellipse가 적절하다. 처음부터 모든 기본 도형과 옵션을 한 번에 구현하면 pixel 차이와 성능 원인을 분리하기 어렵다.

## 위험/검증

- rect 뒤에 line/cubic/다른 rect를 추가한 compound path가 반드시 generic fallback하는지 확인한다.
- reset, duplicate, appendPath와 path 재사용 후 primitive tag가 stale하지 않은지 unit test를 둔다.
- clockwise/counter-clockwise, positive/negative/zero width·height와 negative radius 입력을 기존 결과와 비교한다.
- translation, rotation, skew, non-uniform/negative scale과 near-singular transform에서 bounds와 winding을 검사한다.
- nonzero/evenodd fill-rule, solid/linear/radial gradient, opacity와 blend mode에서 pixel 결과를 비교한다.
- stroke width 0/subpixel/도형보다 큰 값, miter/bevel/round join, cap, dash, trimpath는 지원 여부대로 fast path 또는 fallback하는지 확인한다.
- clip, alpha/luma mask, nested scene와 partial update에서 기존 stencil/compose 계약이 유지되는지 확인한다.
- GL과 WebGPU에서 같은 primitive 조합의 pixel diff를 CPU reference와 비교하고 antialias edge의 허용 오차를 수치화한다.
- 기존 convex direct/batch 경로와 비교해 draw call이 오히려 늘지 않는지 GPU capture로 확인한다.
- static shape는 geometry를 재생성하지 않고, animation에서 path/transform dirty flag가 필요한 부분만 갱신하는지 계측한다.
- 수천 개 rect/circle workload에서 CPU prepare time, upload byte, vertex/index 수, render pass, GPU time과 frame time을 모두 기록한다.
- unsupported 조합은 기존 path를 사용해 시각 결과가 변하지 않으며 fast-path 판정 비용이 baseline을 악화하지 않는지 확인한다.
