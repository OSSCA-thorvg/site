## 이슈 요약

이슈는 공개 `Text::gen() noexcept`가 평범한 `new TextImpl`을 호출하는데 메모리 할당에 실패하면 호출자가 어떤 결과를 기대해야 하는지 묻는다. 표준 동작의 throwing `operator new`를 주입한 재현에서는 `std::bad_alloc`이 `noexcept` 경계를 빠져나가려 하면서 `std::terminate`가 호출된다. 프로젝트의 기본 전역 `operator new`를 그대로 쓴 후속 재현에서는 그 함수가 `std::malloc`의 `nullptr`를 그대로 반환해 null 주소에서 생성자가 실행되는 형태의 crash가 관찰됐다.

핵심은 두 현상을 같은 정상 계약의 서로 다른 구현으로 볼 수 없다는 점이다. C++의 교체 가능한 throwing `operator new(std::size_t)`는 성공 시 non-null을 반환하고 실패 시 `std::bad_alloc`을 던져야 한다. 현재 구현은 이 throwing signature에서 null을 반환하므로 요구 조건을 위반한다. 반대로 공개 함수는 `noexcept`이고 프로젝트의 일반 Meson 빌드는 예외를 끈다. 따라서 “예외로 복구”, “null로 복구”, “프로세스 종료” 중 무엇을 보장할지 선언·할당기·factory·호출자 전체에서 명시해야 한다.

또한 `Text::gen()`의 바깥 `new`만 nothrow로 바꾸는 것은 충분하지 않다. `TextImpl` 생성자는 즉시 `Shape::gen()`으로 두 번째 객체를 만들고 반환값을 검사하지 않은 채 사용한다. 복구 가능한 null 계약을 택한다면 중첩 생성 실패까지 원자적으로 정리하고 호출자에게 null을 전달하는 별도 factory 경로가 필요하다.

## main 코드 조사

공개 헤더는 [`Text::gen()`을 `noexcept` 포인터 factory로 선언](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/inc/thorvg.h#L2304-L2317)하고 “새로 생성된 Text object의 포인터”를 반환한다고만 적는다. 실패 시 `nullptr`인지, 종료인지, 다른 오류 경로가 있는지는 문서화하지 않는다. 구현은 [`return new TextImpl;`](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/src/renderer/tvgText.cpp#L149-L154) 한 줄이다.

전역 replacement 함수는 [`operator new(std::size_t)`와 `operator new[]`에서 `tvg::malloc()` 결과를 그대로 반환](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/src/renderer/tvgInitializer.cpp#L132-L158)한다. [`tvg::malloc()`은 `std::malloc()`의 단순 wrapper](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/src/common/tvgAllocator.h#L31-L39)이므로 실패하면 null이다. 그러나 C++ draft의 [교체 가능한 throwing allocation 함수 요구](https://eel.is/c++draft/new.delete.single#2)는 non-null storage를 반환하거나 `bad_alloc`을 던지라고 명시하며 이 요구가 replacement에도 적용된다고 한다. 따라서 이슈의 stock allocator crash는 **정의된 null 반환 계약**이 아니라 요구를 어긴 replacement 함수가 만든 비정상 상태로 보는 것이 정확하다.

C++ draft의 [new-expression 규칙](https://eel.is/c++draft/expr.new#22)은 throwing allocation 함수는 실패를 `bad_alloc`으로 알리고, non-throwing allocation 함수는 null로 알린다고 구분한다. allocation 함수가 null을 반환한 경우에는 객체 초기화를 하지 않고 new-expression 값이 null이어야 한다고도 정한다. 다만 현재 replacement 함수는 signature는 throwing인데 구현이 null을 반환해 그 전제 자체를 깨뜨린다. 특정 컴파일러에서 생성자가 null 주소로 호출됐다는 관찰 결과를 모든 빌드가 보장하는 동작으로 일반화해서는 안 된다.

표준 throwing allocator 또는 정상적으로 `bad_alloc`을 던지는 교체 구현을 사용하면 `new TextImpl`의 예외가 `Text::gen() noexcept` 밖으로 전파되려 한다. C++ draft는 [`noexcept`를 non-throwing exception specification으로 정의](https://eel.is/c++draft/except.spec#1)하고, [handler 탐색이 non-throwing 함수 경계를 벗어나면 `std::terminate`를 호출](https://eel.is/c++draft/except.terminate#1)하도록 한다. 이슈의 첫 재현이 종료되는 이유는 이 규칙으로 확인된다.

일반 빌드 설정도 고려해야 한다. current main의 [Meson 설정은 sanitizer가 없을 때 Clang/GCC 계열에 `-fno-exceptions`와 `-fno-rtti`를 추가](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/src/meson.build#L43-L51)한다. 즉 catch 기반 처리를 도입하는 것만으로는 기본 빌드 계약이 되기 어렵다. 예외 활성 빌드와 비활성 빌드 모두에서 같은 공개 결과를 낼 수 있는 명시적인 allocation 경로가 필요하다.

`TextImpl`은 단일 allocation으로 끝나지 않는다. [생성자 initializer에서 `Shape::gen()`을 호출한 뒤](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/src/renderer/tvgText.h#L37-L49), 본문에서 바로 `PAINT(shape)->parent`와 `shape->strokeJoin()`을 사용한다. 따라서 `new (std::nothrow) TextImpl`로 바깥 저장소 실패만 null로 바꿔도 내부 `Shape` 생성이 실패하면 안전한 결과를 만들 수 없다. 생성자 자체가 실패 상태를 표현하지 못한다는 점이 Text 경로의 추가 난점이다.

동일 패턴은 Text에만 국한되지 않는다. current main 검색 결과 [Shape](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/src/renderer/tvgShape.cpp), [Scene](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/src/renderer/tvgScene.cpp), [Picture](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/src/renderer/tvgPicture.cpp), [gradient](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/src/renderer/tvgFill.cpp), [Animation](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/src/renderer/tvgAnimation.cpp), [Saver](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/src/renderer/tvgSaver.cpp), [Accessor](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/src/renderer/tvgAccessor.cpp)도 `gen() noexcept` 안에서 plain `new`를 사용한다. 한 class만 다른 실패 정책을 도입하면 공개 factory 사이의 일관성이 깨진다.

호출자도 현재 non-null을 사실상 전제한다. 예를 들어 [Lottie text builder는 `Text::gen()` 직후 `paint->font()`을 호출](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/src/loaders/lottie/tvgLottieBuilder.cpp)하고, [SVG builder도 반환 객체를 이어서 설정](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/src/loaders/svg/tvgSvgBuilder.cpp)한다. [C API의 `tvg_text_new()`는 결과를 그대로 opaque handle로 반환](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/src/bindings/capi/tvgCapi.cpp)한다. nullable 계약을 도입하면 공개 C/C++ 문서뿐 아니라 내부의 즉시 역참조 지점을 함께 보강해야 한다.

오류 표현 수단이 전혀 없는 것은 아니다. 공개 [`Result` enum에는 `FailedAllocation`](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/inc/thorvg.h#L99-L110)이 있다. 다만 `gen()`은 `Result`가 아니라 raw pointer를 반환하므로 이 값을 직접 전달할 수 없다. 기존 ABI를 유지하려면 null을 failure sentinel로 문서화하거나, 새 result/out-parameter factory를 추가하고 기존 `gen()` 정책을 별도로 유지하는 선택지가 있다.

현재 text test는 [정상 환경에서 `Text::gen()` 결과가 존재하는지만 검사](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/test/testText.cpp)한다. 할당 실패를 주입해 outer `TextImpl`, inner `ShapeImpl`, 문자열 복사와 loader allocation의 결과를 고정하는 회귀는 검색되지 않았다. 이슈가 보여 준 두 재현을 upstream test 형태로 축소할 필요가 있다.

## 원인 분석

### 확인된 사실

- `Text::gen()`은 `noexcept`이며 plain `new TextImpl`을 호출하고 실패 동작을 문서화하지 않는다.
- 프로젝트의 replacement `operator new(std::size_t)`는 `std::malloc`이 반환한 null을 그대로 반환한다.
- 표준의 throwing replacement `operator new`는 non-null을 반환하거나 `bad_alloc`을 던져야 한다.
- 정상적인 throwing allocation에서 발생한 예외가 `Text::gen() noexcept`를 빠져나가려 하면 `std::terminate`가 호출된다.
- 일반 Meson 빌드는 sanitizer가 없을 때 예외를 비활성화한다.
- `TextImpl` 생성 중 `Shape::gen()`이라는 두 번째 allocation이 발생하고 그 결과를 즉시 역참조한다.
- 여러 다른 공개 `gen() noexcept` 구현도 plain `new` 패턴을 공유한다.
- 내부 Lottie/SVG 호출자 중에는 `Text::gen()` 결과를 null 검사 없이 즉시 사용하는 경로가 있다.
- 공개 `Result`에는 `FailedAllocation`이 있지만 현재 pointer-returning `gen()` signature로는 이를 직접 반환할 수 없다.

### 추론과 판단

- **직접 원인:** public non-throwing factory 안에서 잠재적으로 실패하는 plain `new`를 사용하면서, throwing replacement allocator와 public API의 실패 정책을 정의하지 않았다.
- **더 근본적인 결함:** replacement `operator new`가 throwing signature의 표준 요구를 지키지 않는다. stock allocator에서 null 주소 생성자가 관찰된 것은 안정적인 API 결과가 아니라 이 계약 위반에서 파생된 undefined/non-portable 동작으로 판단해야 한다.
- **Text 한정 수정의 부족:** 바깥 allocation만 nothrow로 바꾸면 inner `Shape::gen()` 실패가 남는다. 안전한 nullable factory에는 “모든 필수 하위 객체 생성 성공 후 공개”라는 원자성이 필요하다.
- **API 범위 판단:** 같은 `gen() noexcept` 패턴이 여러 class에 있으므로 maintainer가 선택할 실패 정책은 Text 하나가 아니라 factory family 전체의 규칙이어야 한다. 첫 PR을 Text 회귀로 작게 시작할 수는 있지만 문서 계약을 Text 전용으로 확정하면 기술 부채가 생긴다.
- **후속 메서드 판단:** `text()`, `font()`, `load()` 등도 내부에서 메모리를 확보할 가능성이 있으나, 이슈가 각 지점의 실패 결과를 모두 실증한 것은 아니다. `gen()`의 확인된 결함과 이후 operation의 audit 대상을 구분하고, 근거 없이 모든 메서드가 같은 방식으로 crash한다고 단정하지 않는 편이 맞다.
- **호환성 판단:** 기존 `gen()`에서 새롭게 null을 반환시키는 것은 source/ABI signature는 유지하지만 행동 계약은 바뀐다. 현재 non-null을 가정하는 내부·외부 코드에는 실제 호환성 위험이 있으므로 release note와 호출자 수정이 필요하다.

## 구현 방향

1. maintainer가 factory allocation failure 정책을 먼저 결정한다. 선택지는 (a) unrecoverable로 명시하고 표준에 맞는 throwing/fatal 경로를 일관되게 제공하거나, (b) `gen()`이 null을 반환하는 recoverable contract를 문서화하거나, (c) 새 result 기반 factory를 추가하는 것이다.
2. 어떤 정책이든 현재 replacement `operator new`가 null을 그대로 반환하지 않게 한다. 예외 활성 빌드에서는 표준 요구대로 `bad_alloc`을 던지는 경로를 사용하고, 예외 비활성 빌드의 fatal 동작은 명시적인 handler로 분리해 우연한 null dereference에 맡기지 않는다.
3. recoverable 정책이면 throwing overload를 악용하지 말고 별도의 `operator new(size_t, const std::nothrow_t&) noexcept` 또는 프로젝트 전용 fallible allocator를 제공한다. factory가 의도적으로 그 경로를 호출하고 null을 반환하도록 한다.
4. `TextImpl` 생성은 두 단계로 바꾼다. 바깥 저장소와 필수 `Shape`를 각각 확보하고, 둘 다 성공한 뒤에만 parent/stroke 상태를 설정해 공개한다. 어느 단계든 실패하면 이미 확보한 자원을 정리하고 null을 반환한다.
5. `new (std::nothrow) TextImpl` 한 줄로 끝내지 않는다. nothrow new는 `TextImpl`용 저장소 allocation 실패를 null로 바꾸지만 생성자 안 `Shape::gen()`의 plain new 실패나 생성 중 다른 실패까지 자동으로 복구하지 않는다.
6. Shape, Scene, Picture, Fill, Animation, Saver, Accessor 등 모든 public `gen()`을 목록화해 같은 contract와 implementation helper를 적용한다. 생성자 내부에서 다른 factory를 호출하는 class를 우선 표시한다.
7. nullable을 택하면 내부 호출자부터 전부 검사한다. Lottie/SVG builder는 null이면 현재 build operation을 실패로 전환하고, C API는 null handle 의미를 문서화하며, sample과 binding도 dereference 전에 검사한다.
8. `Text::text()`처럼 `Result`를 반환하는 operation은 allocation 실패 시 `Result::FailedAllocation`을 실제로 전달할 수 있는지 별도 audit한다. 성공을 반환한 채 내부 포인터만 null이 되는 경로가 없는지 문자열 복사와 font loader부터 확인한다.
9. 기존 ABI를 보수적으로 유지해야 한다면 새 `Result Text::gen(Text** out) noexcept`와 같은 API를 검토한다. 구 API는 명시된 fatal/legacy 정책을 유지하고 새 API에서만 recoverable failure를 제공하는 migration도 가능하다.
10. 선택한 정책을 `Text::gen()` 한 곳이 아니라 factory 공통 문서와 release note에 기록한다. `noexcept`가 곧 “null을 반환한다”는 뜻은 아니므로 반환값과 process termination 조건을 별도로 적는다.

## 초심자 시작 가이드

구현 전체는 초심자에게 권하지 않지만, 아래 조사와 테스트 분리는 비교적 안전한 기여 단위다.

1. `gen() noexcept`를 검색해 class, 구현 파일, plain/nothrow allocation, 생성자 내부 추가 allocation 여부를 표로 만든다.
2. `TextImpl`만 대상으로 실패 지점을 ① outer Text 저장소, ② inner Shape 저장소, ③ 첫 문자열 복사의 세 단계로 나눈다.
3. 테스트 allocator에 “N번째 allocation만 실패”하는 counter를 두고 각 단계의 기대 결과를 먼저 적는다. nullable 정책이면 null/`FailedAllocation`, fatal 정책이면 death test가 기대값이다.
4. `Text::gen()` 반환 직후 `->`를 사용하는 내부 호출자를 `rg 'Text::gen'`으로 찾아 null 처리 위치를 표시한다.
5. exception-enabled와 기본 exception-disabled build를 나눠 같은 public 결과가 나오는지 비교한다. compiler crash message가 같다는 것보다 문서화한 contract가 같다는 것을 검증한다.
6. 수정 후 AddressSanitizer/UndefinedBehaviorSanitizer에서 null `this`, leak, double free가 없는지 확인한다.

## 위험/검증

- 정상 allocation에서 기존 `Text::gen()`/`Paint::rel()` 수명과 결과가 변하지 않는지 확인한다.
- outer `TextImpl` allocation을 첫 번째 실패로 주입해 문서화한 null/fatal 결과가 정확한지 검사한다.
- outer allocation은 성공하고 inner `ShapeImpl` allocation만 실패하게 해 null dereference 없이 partial object가 정리되는지 검사한다.
- 생성자 이후 `text()` 문자열 복사와 font loader의 allocation 실패에서 `Result::FailedAllocation` 또는 명시된 정책이 적용되는지 별도 검증한다.
- throwing standard allocator, 프로젝트 allocator, 명시적 nothrow allocator 세 경로를 구분해 테스트한다.
- exception-enabled, `-fno-exceptions`, sanitizer-enabled 설정에서 public observable result가 정책과 일치하는지 확인한다.
- global `operator new`, `new[]`, aligned allocation, nothrow overload와 대응 delete 조합을 점검해 overload mismatch와 leak을 막는다.
- Shape, Scene, Picture, Linear/RadialGradient, Animation, Saver, Accessor의 첫 allocation 실패를 parameterized test로 반복한다.
- 중첩 factory를 가진 object는 N번째 실패 주입으로 모든 하위 allocation 단계가 정리되는지 검사한다.
- Lottie와 SVG text builder가 null factory 결과를 역참조하지 않고 상위 load/build 실패로 전파하는지 확인한다.
- `tvg_text_new()`가 null handle을 반환할 수 있다면 C API 문서와 후속 C 함수의 null argument 결과를 고정한다.
- existing tests가 가정하는 정상 non-null 결과, renderer object count와 ref-count가 회귀하지 않는지 확인한다.
- OOM test 자체가 test framework와 allocator 초기화에 필요한 allocation을 잘못 실패시키지 않도록 범위를 thread-local/RAII guard로 제한한다.
- public documentation, header annotation, implementation의 세 곳이 동일한 실패 계약을 말하는지 release 전 검토한다.
