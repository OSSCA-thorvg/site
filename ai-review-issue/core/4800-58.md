## 이슈 요약

`Shape::cubicTo()`는 현재 point에서 시작하는 cubic Bézier를 추가하는 API다. 그런데 path의 첫 명령이면 시작점이 존재하지 않는다. 공개 문서는 이 경우 “path의 어떤 데이터도 렌더링되지 않는다”고 적고 있지만, 이슈의 동일 입력을 CPU, GL, WebGPU로 그리면 서로 다른 결과가 나온다. 단일 curve, 두 curve와 `close()`, stroke-only 세 경우가 모두 비교되었다.

이슈 작성자는 첫 명령이 `CubicTo`인 path를 버리는 결과를 기대한다. 반면 maintainer 토론에는 current position이 없는 예상 밖 입력이므로 해당 note를 삭제하는 편이 낫다는 의견도 있다. 따라서 이 작업은 단순 문서 오타가 아니라, 잘못된 command stream을 public API와 각 renderer가 어떻게 처리할지 정의하고 한 장소에서 강제하는 API 계약 문제다.

## main 코드 조사

[공개 API 문서](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/inc/thorvg.h#L1240-L1255)는 curve가 “current point”에서 시작한다고 설명하면서 첫 명령인 경우 렌더링하지 않는다는 note를 둔다. 시작점 인자를 받지 않는 cubic Bézier이므로 선행 `MoveTo` 없이 기하를 완전히 정의할 수 없다는 점은 API 형태에서도 확인된다.

[`Shape::cubicTo()` 구현](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/src/renderer/tvgShape.cpp#L82-L87)은 현재 command state를 검사하지 않고 세 점을 `RenderPath`에 추가한 뒤 path update flag를 표시하고 항상 `Result::Success`를 반환한다. 즉 잘못된 선두 명령은 API 경계에서 제거되거나 오류로 바뀌지 않고 renderer까지 전달된다.

[`RenderPath::cubicTo()`](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/src/renderer/tvgRender.h#L295-L301)도 control point 두 개와 end point를 그대로 저장한다. 반면 [`RenderPath::bounds()`](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/src/renderer/tvgRender.cpp#L199-L239)는 command가 비었거나 첫 명령이 `CubicTo`면 즉시 `false`를 반환한다. 중앙 자료구조가 잘못된 시작을 표현할 수는 있지만, 소비자마다 동일하게 무효화하지는 않는 상태다.

[CPU outline 생성](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/src/renderer/cpu_engine/tvgSwShape.cpp#L342-L406)은 첫 명령 여부를 확인하지 않고 `CubicTo`에서 `_outlineCubicTo()`를 호출한다. [GL stroker](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/src/renderer/gpu_engine/gl/tvgGlTessellator.cpp#L51-L91)와 [WebGPU stroker](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/src/renderer/gpu_engine/wg/tvgWgTessellator.cpp#L49-L91)도 `MoveTo`가 설정하는 `firstPt`/`prevPt` 상태 없이 곧바로 `cubicTo()`를 실행한다. 이처럼 초기 state를 준비하는 지점이 backend별 자료구조에 흩어져 있어 같은 malformed path가 다른 그림으로 나타날 수 있다.

[기존 Shape API 테스트](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/test/testShape.cpp#L35-L61)는 정상 `MoveTo` 뒤의 cubic 호출과 반환값만 확인한다. 첫 명령 cubic의 저장 결과, bounds, 실제 pixel 출력은 고정하지 않는다. `appendPath()` 테스트도 command/point 배열 round-trip 중심이어서 잘못된 command 순서의 renderer 계약을 보호하지 않는다.

관련 [PR #4805](https://github.com/thorvg/thorvg/pull/4805)는 wrap-around trim path가 `MoveTo` 없이 curve부터 시작하지 않도록 수정되어 이미 main에 포함됐다. 이는 내부 path 생산자가 leading `CubicTo`를 피해야 한다는 강한 사례지만, 사용자가 public API로 같은 stream을 만든 경우의 계약까지 해결하지는 않는다.

## 원인 분석

### 확인된 사실

- `cubicTo()`는 시작점 인자를 받지 않고 current point를 전제로 한다.
- 공개 문서는 첫 명령 cubic인 path가 렌더링되지 않는다고 명시한다.
- public API와 `RenderPath::cubicTo()`는 선행 명령을 검사하지 않고 command와 세 점을 저장한다.
- `bounds()`는 선두 `CubicTo`를 명시적으로 거부하지만 CPU outline과 GPU stroker는 command를 각자 처리한다.
- 이슈 재현에서 CPU, GL, WebGPU 출력이 서로 다르다.
- maintainer는 note 삭제를 선호한다는 의견을 남겼지만 최종 계약은 확정하지 않았다.
- 현재 테스트는 첫 명령 cubic의 저장·bounds·fill·stroke 출력을 고정하지 않는다.

### 추론과 판단

- **근본 원인은 정의되지 않은 path state가 renderer까지 유입되는 것과 분산된 검증이다.** 선행 `MoveTo`가 만들어야 할 시작점이 없는데 각 backend가 자신의 초기/default state로 curve를 해석한다.
- 문서 note만 삭제하면 API 설명과 동작의 모순 하나는 사라지지만 backend parity 문제와 초기화되지 않은 state 의존은 남는다. 동일 입력이 backend 선택에 따라 달라지는 상태를 공식 계약으로 삼기는 어렵다.
- 가장 예측 가능한 계약은 malformed subpath를 중앙에서 제거하고 다음 `MoveTo`에서 정상 처리를 재개하는 것이다. 다만 이슈의 “path 전체를 버린다”는 문구와 차이가 있으므로 전체 path와 subpath 중 어느 범위를 무효화할지 먼저 합의해야 한다.
- `Shape::cubicTo()`에서 첫 호출을 단순 no-op 처리하면 뒤따르는 두 번째 cubic 역시 시작점이 없다. “최초 한 명령만 버리기”가 아니라 `MoveTo`가 나올 때까지 invalid-subpath 상태를 유지해야 한다.
- `appendPath()`와 trim/dash 같은 내부 생산자를 빼고 public method만 고치면 동일한 malformed stream이 다른 진입점으로 다시 들어온다. 소비 직전의 공통 normalization 또는 `RenderPath` 불변식이 필요하다.

## 구현 방향

1. maintainer와 먼저 계약을 고정한다. 후보는 (a) 첫 cubic이 있으면 path 전체 무효, (b) 해당 subpath를 다음 `MoveTo`까지 무효, (c) 암시적 `(0, 0)` 시작점이다. 기존 문서·기대 결과와 안전성을 고려하면 (a) 또는 (b)가 적합하며, backend가 임의 origin을 택하게 두어서는 안 된다.
2. command stream을 검증·정규화하는 공통 함수를 `RenderPath` 또는 renderer 진입 직전에 둔다. command마다 필요한 point 수를 소비하면서 `hasCurrentPoint`를 추적하고, `MoveTo`에서만 새 subpath를 시작한다.
3. invalid `LineTo`와 `Close`도 같은 state machine에서 정의한다. 이번 이슈만 특별 처리해 또 다른 선행 명령이 backend별로 갈라지지 않게 한다.
4. 오류 반환을 도입한다면 기존 `Result::Success` ABI/API 기대와 `appendPath()`의 validation 정책을 검토한다. 호환성을 우선하면 command를 저장하되 render normalization에서 무효화하고 문서에 범위를 명확히 쓰는 방식이 작다.
5. `bounds()`, CPU outline, GL/WG fill tessellation과 stroker가 모두 정규화된 stream만 받게 한다. backend별 `if (first cubic)` 복제는 피한다.
6. 내부 trim/dash producer에는 `MoveTo` 불변식을 assertion 또는 debug validation으로 추가한다. PR #4805 같은 회귀를 renderer 결과가 달라진 뒤에야 찾지 않도록 한다.
7. 결정한 계약에 맞춰 `thorvg.h` note를 구체화한다. “path data”가 전체 shape인지 해당 subpath인지, 뒤의 정상 `MoveTo`가 복구되는지를 명시한다.

## 초심자 시작 가이드

1. `RenderPath`의 command 하나가 소비하는 point 수를 표로 만든다: `MoveTo`/`LineTo`는 1, `CubicTo`는 3, `Close`는 0이다.
2. `hasCurrentPoint`, `subpathStart`, `invalidSubpath` 세 상태만 가진 작은 validator를 테스트 코드에서 먼저 작성한다.
3. `CubicTo`, `CubicTo + Close`, `CubicTo + MoveTo + LineTo`, 정상 `MoveTo + CubicTo` 배열을 넣고 예상 normalized command/point 수를 확인한다.
4. 그 validator를 한 backend에만 넣지 말고 공통 진입점에 연결한 뒤 CPU/GL/WG 예제를 다시 실행한다.
5. API 반환값 테스트와 실제 pixel 테스트를 분리한다. command를 받아들였다는 사실이 “렌더링 결과 없음”을 증명하지는 않는다.

## 위험/검증

- 첫 명령이 각각 `MoveTo`, `LineTo`, `CubicTo`, `Close`인 path의 fill과 stroke를 검증한다.
- invalid subpath 뒤 정상 `MoveTo`가 있는 경우 정상 부분이 그려지는지 계약대로 확인한다.
- 단일 cubic, 연속 cubic, cubic+close, zero-length curve, 여러 subpath를 CPU/GL/WebGPU에서 pixel 비교한다.
- butt/round/square cap과 여러 join에서 선행 cubic이 GPU stroker의 default point를 사용하지 않는지 확인한다.
- `appendPath()`의 command/point 개수 오류와 순서 오류를 별도로 검사해 out-of-bounds point 접근이 없는지 ASan/UBSan으로 확인한다.
- bounds가 false인 path가 renderer 단계에서는 우연히 그려지는 불일치가 사라졌는지 확인한다.
- SVG/Lottie/trim/dash가 생성하는 정상 path의 pixel inspector 결과가 바뀌지 않는지 확인한다.
- 기존 사용자가 선행 cubic을 암시적 origin처럼 사용했을 가능성을 release note와 호환성 검토에 포함한다.
