## 이슈 요약

이 issue는 현재 별도 `<thorvg_lottie.h>`에서 제공하는 `LottieAnimation`을 기본 `<thorvg.h>` API로 옮기고, 사용자가 extra header 없이 Lottie marker, tween, slot, quality, audio와 expression capability를 쓰게 하자는 제안이다. 동시에 class 이름을 `LottieAnimation`에서 `Lottie`로 줄이려 한다.

문제는 이 class가 단순 실험 type이 아니라 이미 `@since 0.15` public API이고 프로젝트 history에서도 공식 API로 승격된 적이 있다는 점이다. header 위치 변경은 include 편의성 개선이지만 class rename은 source 식별자와 C++ mangled symbol을 바꾸는 별도 호환성 변경이다. 두 목표를 하나로 취급하면 기존 source는 alias로 빌드돼도 이미 배포된 binary가 새 shared library에 link되지 않을 수 있다.

또한 Lottie는 default loader 목록에는 들어 있지만 여전히 Meson에서 끌 수 있는 optional module이다. 기본 header가 class를 항상 선언한다면 `-Dloaders=''`로 만든 library가 `Lottie::gen()`과 나머지 method symbol을 어떻게 제공할지도 정해야 한다.

## main 코드 조사

current project version은 [`1.2.0`](https://github.com/thorvg/thorvg/blob/2b78e1bd7225be4eacb8817b18a493cf567b4f87/meson.build#L1-L8)이다. `LottieAnimation`은 [2024년 API 정리에서 v0.15 공식 C++ API로 승격](https://github.com/thorvg/thorvg/commit/76fb3f3cd9eda9ae258b065ebf20a1c04a4c1d09)됐고 이후 marker, tween, slot, quality와 audio method가 계속 추가됐다. 따라서 “extra header에 있다”와 “experimental class다”는 같은 뜻이 아니다.

기본 [`thorvg.h`](https://github.com/thorvg/thorvg/blob/2b78e1bd7225be4eacb8817b18a493cf567b4f87/inc/thorvg.h#L2585-L2725)는 generic `Animation`을 선언하고 marker overload 문서에서 `LottieAnimation`을 참조하지만, 그 type 정의는 포함하지 않는다. [`inc/meson.build`](https://github.com/thorvg/thorvg/blob/2b78e1bd7225be4eacb8817b18a493cf567b4f87/inc/meson.build#L1-L5)는 `thorvg.h`를 항상 설치한다.

별도 [`thorvg_lottie.h`](https://github.com/thorvg/thorvg/blob/2b78e1bd7225be4eacb8817b18a493cf567b4f87/src/loaders/lottie/thorvg_lottie.h#L1-L262)는 `thorvg.h`를 include하고 `LottieAudioResolver`와 `final : Animation`인 `LottieAnimation` 전체를 정의한다. marker, 두 종류 tween, slot gen/apply/del, quality, audio resolver, expression support query와 static object factory가 이 type에 모여 있다.

이 header는 [Lottie loader subdirectory가 선택될 때만 설치](https://github.com/thorvg/thorvg/blob/2b78e1bd7225be4eacb8817b18a493cf567b4f87/src/loaders/lottie/meson.build#L1-L36)된다. loader 선택은 [`src/loaders/meson.build`](https://github.com/thorvg/thorvg/blob/2b78e1bd7225be4eacb8817b18a493cf567b4f87/src/loaders/meson.build#L1-L47)의 `if lottie_loader`가 제어한다.

Meson의 default `loaders`는 [`svg`, `lottie`, `ttf`](https://github.com/thorvg/thorvg/blob/2b78e1bd7225be4eacb8817b18a493cf567b4f87/meson_options.txt#L12-L16)이지만 option은 빈 목록과 개별 loader를 계속 허용한다. 즉 “기본 build에 포함”은 맞지만 “항상 library에 포함”은 아니다.

[`tvgLottieAnimation.cpp`](https://github.com/thorvg/thorvg/blob/2b78e1bd7225be4eacb8817b18a493cf567b4f87/src/loaders/lottie/tvgLottieAnimation.cpp#L24-L155)는 별도 header를 include하고 모든 method에서 내부 `LottieLoader`를 fetch한다. 이 source 자체도 Lottie loader의 `source_file` 안에 있으므로 loader를 끄면 class implementation symbol이 library에 들어가지 않는다. 선언만 `thorvg.h`로 옮기면 loader-disabled consumer는 compile은 되고 실제 method 사용 시 link가 실패할 수 있다.

반대로 engine class는 optional backend라도 기본 header에 항상 선언되고 [`SwCanvas::gen()`, `GlCanvas::gen()`, `WgCanvas::gen()` 구현이 항상 compile되어 feature macro가 없을 때 `nullptr`을 반환](https://github.com/thorvg/thorvg/blob/2b78e1bd7225be4eacb8817b18a493cf567b4f87/src/renderer/tvgCanvas.cpp#L248-L337)한다. Lottie를 기본 API로 승격할 때 참고할 수 있는 existing optional-feature 계약이다.

current unit test는 [`<thorvg.h>` 다음 loader macro 안에서 `<thorvg_lottie.h>`를 추가 include](https://github.com/thorvg/thorvg/blob/2b78e1bd7225be4eacb8817b18a493cf567b4f87/test/testLottie.cpp#L22-L33)하고 기존 class 이름으로 수백 개 assertion을 수행한다. repository 내부 build만 바꾸면 installed consumer의 single-header 사용성과 old header 호환성을 놓칠 수 있다.

C binding implementation도 [Lottie loader 지원일 때 별도 header를 include](https://github.com/thorvg/thorvg/blob/2b78e1bd7225be4eacb8817b18a493cf567b4f87/src/bindings/capi/tvgCapi.cpp#L22-L32)하고 내부에서 `LottieAnimation*`으로 cast한다. 공개 C 함수명은 이미 `tvg_lottie_animation_*` 계열이므로 C++ class를 짧게 바꾸더라도 C API rename은 요구되지 않았다.

분석 당일 main에 merge된 [expression capability 변경](https://github.com/thorvg/thorvg/commit/2b78e1bd7225be4eacb8817b18a493cf567b4f87)은 `LottieAnimation::expressions()`와 대응 C 함수를 추가했다. 이는 rename 시 확인할 public surface가 현재도 늘고 있으며 C++/C parity와 문서 link를 함께 갱신해야 함을 보여 준다.

`LottieAnimation`은 `TVG_API` exported class다. 일반적인 C++ ABI에서 out-of-line destructor와 method symbol에는 class type name이 들어간다. 기존 이름을 새 class 이름으로 직접 바꾸면 source alias만으로 이미 old symbol을 참조하는 binary를 구제할 수 없다. symbol 보존 여부를 실제 shared library의 exported symbol diff로 확인해야 한다.

## 원인 분석

### 확인된 사실

- `LottieAnimation`은 별도 installed header에 있지만 v0.15부터 공식 public C++ API다.
- current main의 기본 header는 generic `Animation`만 정의하고 Lottie type은 문서에서만 참조한다.
- default build는 Lottie loader를 켜지만 Meson은 loader를 끄는 build를 지원한다.
- Lottie header와 class implementation은 현재 loader가 켜질 때만 설치·compile된다.
- current class는 `TVG_API`, `final`, `Animation` 파생 type이며 여러 out-of-line method와 destructor를 갖는다.
- unit test와 C binding은 `<thorvg_lottie.h>` 및 `LottieAnimation` 이름에 직접 의존한다.
- main에는 issue 등록 직후 새 C++ static method와 대응 C 함수가 추가됐다.
- issue에는 기존 이름/header의 deprecation 기간, binary compatibility와 loader-disabled 동작이 명시돼 있지 않다.

### 추론과 판단

- **요구의 두 층:** header 승격은 include 경험 개선이고 class rename은 호환성 정책 변경이다. 전자는 기존 type을 그대로 옮겨 낮은 위험으로 완성할 수 있으므로 두 결정을 분리하는 편이 좋다.
- **안전한 새 이름:** `using Lottie = LottieAnimation`을 기본 header에 제공하면 새 source는 짧은 이름을 쓰면서 실제 class와 exported symbol은 유지된다. 목표의 “이름 단순화”를 만족하는 최소 호환 경로다.
- **반대 alias의 한계:** class 자체를 `Lottie`로 바꾸고 `using LottieAnimation = Lottie`를 두면 old source는 다시 compile되지만 기존 binary가 요구하는 `LottieAnimation::*` symbol은 사라질 수 있다.
- **별도 wrapper 위험:** old class와 new class를 둘 다 실제 exported type으로 유지하면 factory return type, RTTI, deletion, `final` 상속과 C cast가 복잡해진다. 한 실제 type과 alias 하나가 더 단순하다.
- **optional module 계약:** 기본 header에서 type을 항상 보이게 하려면 loader-disabled build에서도 최소 factory symbol을 제공해 `nullptr`/`NonSupport`로 실패시키는 방식이 existing Canvas factory와 일관된다. 또는 public feature macro로 type 자체를 gate해야 하지만 현재 installed config header 계약은 없다.
- **loader 필수화 판단:** Lottie를 default API로 승격한다고 해서 `loaders` option에서 제거해야 한다는 근거는 issue에 없다. binary size와 embedded use case에 영향을 주므로 별도 제안 없이 mandatory로 바꾸지 않는 편이 안전하다.
- **C API 판단:** C 함수는 이미 format을 이름에 포함하고 opaque handle을 사용한다. 이 issue의 C++ 편의성 개선 때문에 C symbol까지 rename할 이유는 없으며 기존 이름을 유지하는 것이 ABI에 유리하다.

## 구현 방향

1. acceptance criteria를 세 부분으로 분리한다: `<thorvg.h>` 단독 사용, 새 `tvg::Lottie` spelling, 기존 header/name의 source·binary 호환성. loader 필수화는 별도 항목으로 두고 기본값과 availability를 혼동하지 않는다.
2. `LottieAudioResolver`와 실제 class 정의를 `Animation` 뒤의 `thorvg.h`로 옮긴다. `Animation` 문서의 cross-reference도 새 canonical spelling에 맞춘다.
3. 1.x 호환 우선이라면 실제 exported class 이름은 `LottieAnimation`으로 유지하고 `using Lottie = LottieAnimation`을 제공한다. 새 문서와 example은 `Lottie`를 사용하되 old 이름을 즉시 제거하지 않는다.
4. `<thorvg_lottie.h>`는 중복 type 정의 없이 `<thorvg.h>`만 include하는 compatibility shim으로 남긴다. 제거 예정이라면 release note와 충분한 deprecation window를 명시한다.
5. Lottie implementation의 내부 include를 기본 header로 바꾸고, 중복 선언이 없는지 unity/non-unity build에서 확인한다.
6. loader-disabled 동작을 결정한다. 권장안은 factory와 capability query symbol을 core 쪽에서 항상 제공하고 loader가 없으면 `nullptr`/`false`를 반환하는 것이다. 나머지 instance method는 객체를 만들 수 없다는 불변식 아래 정리한다.
7. method implementation을 항상 compile할 필요가 있다면 `LottieLoader` 접근부만 feature macro로 감싸고 unsupported 결과를 반환한다. loader type을 disabled build에서 참조하지 않게 dependency를 분리한다.
8. C API 함수명과 opaque type은 유지하고 내부 cast만 실제 class 이름에 맞춘다. 새 C++ alias 때문에 C header group이나 ABI를 바꾸지 않는다.
9. installed-header consumer test를 추가한다. source tree include path가 아니라 `meson install` 결과만 사용해 `<thorvg.h>` + `tvg::Lottie::gen()`을 compile/link한다.
10. class를 실제 rename해야 한다면 major-version ABI 정책, old symbol forwarding 방법과 downstream migration을 먼저 문서화하고 별도 breaking-change PR로 진행한다.

## 초심자 시작 가이드

전체 API migration은 초심자에게 권하지 않지만 header compatibility test는 시작하기 좋다.

1. default build를 install한 임시 prefix에서 `<thorvg.h>`와 `<thorvg_lottie.h>`의 실제 설치 목록을 기록한다.
2. 기존 이름과 old header를 쓰는 10줄짜리 consumer를 compile/link/run해 baseline을 만든다.
3. 새 이름과 `<thorvg.h>`만 쓰는 같은 consumer를 작성하고 현재 실패가 include/type 단계인지 확인한다.
4. `using Lottie = LottieAnimation`만 적용한 실험에서 두 source가 같은 pointer type인지 `std::is_same`으로 확인한다.
5. `-Dloaders=''` build를 install하고 generic API consumer, Lottie factory consumer가 각각 compile/link/runtime 중 어느 단계에서 실패하는지 기록한다.
6. shared library의 `nm -D -C` 또는 platform symbol tool 결과에서 `LottieAnimation` symbol을 저장하고 변경 뒤 사라지지 않는지 비교한다.

## 위험/검증

- `<thorvg.h>`만 include한 source에서 `tvg::Lottie`, audio resolver, marker, tween, slot, quality와 `expressions()`가 compile되는지 확인한다.
- `<thorvg_lottie.h>`와 `LottieAnimation`을 쓰는 기존 source가 warning 정책에 맞게 계속 compile/link되는지 확인한다.
- 두 header를 함께 include하거나 순서를 바꿔도 재정의·include cycle이 없는지 검증한다.
- default loader, `-Dloaders=lottie`, `-Dloaders=''`, `-Dloaders=svg` build를 각각 install하고 외부 consumer를 test한다.
- loader-disabled factory의 `nullptr` 또는 `NonSupport` 계약이 Canvas optional backend 동작과 문서상 일관적인지 확인한다.
- shared/static library와 Linux ELF, macOS Mach-O, Windows DLL에서 old exported symbol을 비교한다.
- 기존 binary를 rebuild하지 않고 새 shared library와 load하는 ABI smoke test를 수행한다.
- RTTI/exceptions disabled라는 project compiler option에서 alias/wrapper 설계가 typeinfo나 destructor link 문제를 만들지 않는지 확인한다.
- C API 전체 Lottie test와 `tvg_lottie_animation_*` exported symbol이 바뀌지 않는지 검사한다.
- current expression capability query가 loader/expressions on-off 조합에서 C++과 C에 같은 값을 주는지 확인한다.
- Doxygen link, `@class`, `@see`, `@since`, example와 migration guide에서 canonical/legacy 이름을 일관되게 쓴다.
- downstream C++/WASM binding과 package build를 검색해 old header/name 의존성을 목록화하고 migration compile을 수행한다.
- 전체 unit test, install test, ABI symbol diff와 consumer matrix가 모두 통과한 뒤 legacy header 제거 일정을 논의한다.
