## 이슈 요약

PR의 clang-format check가 실제 포맷 위반을 막지 못하고 성공으로 끝난다는 인프라 이슈다. 제보에는 성공한 check 화면과 “고칠지 제거할지”라는 질문만 있고, 위반 source diff나 workflow log는 없다.

제거보다는 수정이 타당하다. 현재 기여 가이드는 clang-format 18로 모든 기여를 포맷해야 한다고 명시하지만 local helper는 기여자가 직접 실행해야 하고 파일을 고치는 도구다. CI만이 제출된 patch를 독립적으로 차단하는 자동 gate이므로, 동작하지 않는다는 이유로 없애면 문서의 필수 규칙을 자동 검증할 수단이 사라진다.

분석한 current `main`에서 이 workflow와 local helper는 도입 뒤 해당 부분이 바뀌지 않았고, 이 이슈를 해결한다고 표시한 열린 source PR도 확인되지 않았다.

## main 코드 조사

현재 [clang-format workflow](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/.github/workflows/clang_format.yml#L1-L39)는 모든 `pull_request`에서 전체 history를 checkout한다. clang-format 18과 LLVM release/18.x의 `clang-format-diff.py`를 설치하고, unversioned `clang-format`을 18 binary에 연결한 뒤 reviewdog를 설치한다.

검사 step은 [`git diff | clang-format-diff | reviewdog`](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/.github/workflows/clang_format.yml#L30-L39) 세 단계를 pipeline으로 실행한다. Bash의 기본 pipeline 종료 상태는 마지막 command의 상태다. GNU Bash 공식 [pipeline 문서](https://www.gnu.org/software/bash/manual/html_node/Pipelines.html)는 `pipefail`을 켜야 오른쪽 끝의 실패한 command 상태가 pipeline 결과가 된다고 설명한다. 이 step에는 `set -euo pipefail`이 없다.

따라서 `git diff`가 base commit을 읽지 못하거나 `clang-format-diff`가 실행·parse·format 과정에서 실패해도, 마지막 reviewdog가 빈 입력을 성공으로 처리하면 step 전체가 성공할 수 있다. 이는 screenshot의 정확한 실행 경로가 없어도 current workflow에 존재한다고 확정할 수 있는 false-green 경로다.

반면 local [`tvg-format.sh`](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/tvg-format.sh#L29-L29)는 시작부터 `set -euo pipefail`을 사용한다. 도구와 commit을 검사한 뒤 [`git show`의 diff를 formatter에 전달해 파일을 직접 수정](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/tvg-format.sh#L82-L89)한다. 이 helper의 안전 장치가 CI에는 빠져 있다.

LLVM 공식 [clang-format 문서](https://clang.llvm.org/docs/ClangFormat.html#script-for-patch-reformatting)는 `clang-format-diff.py`가 unified diff를 읽어 변경된 줄의 formatting patch를 출력한다고 설명하며 `git diff -U0 --no-color --relative ... | clang-format-diff.py -p1` 패턴을 제시한다. current CI는 `-U0`와 `-p1`을 쓰지만 `--no-color`, `--relative`, 명시적인 `-binary clang-format-18`과 출력 patch의 독립 판정은 없다.

reviewdog의 공식 [exit-code 문서](https://github.com/reviewdog/reviewdog#exit-codes)에 따르면 기본값은 진단을 찾아도 0이고 `-fail-level`을 주면 지정 severity 이상의 진단에서 1을 반환한다. current workflow는 `-fail-level=error`를 이미 넘긴다. 따라서 flag가 전혀 없다는 설명은 current main과 맞지 않는다. 하지만 formatter가 진단 diff를 만들기 전에 실패하거나 filter/report 과정에서 진단이 사라지는 경우까지 이 flag가 대신 검증하지는 못한다.

workflow의 [권한은 `contents: read`, `pull-requests: write`](https://github.com/thorvg/thorvg/blob/1bee1f490de59b1ed63ce7bfde375d8e12cc69d9/.github/workflows/clang_format.yml#L6-L8)로 제한되어 있고 reporter는 `github-pr-check`다. GitHub 공식 [workflow permissions 문서](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)는 명시되지 않은 권한이 `none`이 되며 fork PR의 write token에는 추가 제한이 있다고 설명한다. 현재 화면만으로 reporter가 어느 경로에서 check를 게시했는지 알 수 없으므로 권한은 실제 fork PR에서 별도로 확인해야 한다.

## 원인 분석

### 확인된 사실

- format step은 세 command pipeline이지만 `pipefail`을 활성화하지 않는다.
- Bash 기본 규칙에서는 앞선 `git diff`나 `clang-format-diff` 실패가 마지막 reviewdog 성공에 가려질 수 있다.
- local formatting script는 동일한 종류의 pipeline에 `set -euo pipefail`을 적용한다.
- CI는 clang-format 18 binary symlink를 만들고 release/18.x의 diff script를 내려받지만 `curl --fail`이나 다운로드 내용 검증은 하지 않는다.
- reviewdog에는 이미 `-fail-level=error`가 설정되어 있다.
- `-filter-mode=added`는 PR에서 추가·수정된 줄에 annotation을 제한한다.
- 저장소 규칙은 clang-format 18 적용을 필수로 명시하므로 CI를 제거하면 자동 enforcement가 없어진다.

### 추론과 판단

- **확정 가능한 구조적 root cause:** upstream command 실패가 pipeline 결과에 반영되지 않는 것이 false green을 허용한다. 이 경로는 실제 제보 실행이 formatter crash, 잘못된 base, 다운로드 오류 중 무엇이었든 고쳐야 한다.
- **아직 미확정인 직접 trigger:** screenshot만으로는 formatter가 위반 patch를 출력했는데 reviewdog가 놓친 것인지, formatter가 빈 출력/오류로 끝난 것인지 구분할 수 없다. 원본 PR diff와 raw log 없이 `-filter-mode` 또는 권한을 단일 원인으로 단정하면 안 된다.
- **설계 판단:** formatting patch가 비어 있지 않으면 reporter와 무관하게 job을 실패시켜야 한다. reviewdog는 보기 좋은 annotation 담당이고, quality gate의 진실 공급원은 formatter 출력이어야 한다.
- **정책 판단:** CI 제거가 아니라 작은 fail-closed gate로 수리하는 편이 기여 가이드와 일치한다.

## 구현 방향

1. format step 첫 줄에 `set -euo pipefail`을 두고 모든 변수·SHA를 quote한다.
2. `git diff -U0 --no-color --relative "${base_sha}"..."${head_sha}"`처럼 비교 범위를 명시한다. checkout된 merge commit에 암묵적으로 의존하지 말고 PR base/head 정책을 주석과 test로 고정한다.
3. `clang-format-diff.py -p1 -binary clang-format-18`의 출력을 임시 patch 파일에 저장한다. script와 binary version도 log에 출력한다.
4. patch가 비어 있지 않으면 annotation 성공 여부와 관계없이 명시적으로 non-zero 종료한다. reviewdog에는 같은 patch를 전달하되 annotation/report 실패도 별도로 표시한다.
5. 다운로드에는 `curl --fail --show-error --location`을 사용하고, 가능하면 curl 대신 package에 포함된 version-matched script나 검증된 commit SHA/해시를 사용한다.
6. `-filter-mode=added`가 원하는 정책인지 결정한다. “PR이 건드린 줄만 차단”이면 유지하고, 수정 파일 전체를 요구한다면 `file`로 바꾸되 기존 미포맷 코드가 정상 PR을 막지 않는지 먼저 측정한다.
7. reporter에 필요한 최소 token 권한과 fork PR 동작을 GitHub 공식 권한 모델에 맞춰 검증한다. annotation 권한이 없더라도 console에 patch를 남기고 format gate 자체는 실패해야 한다.

## 초심자 시작 가이드

workflow를 바로 바꾸기 전에 작은 source PR 두 개로 현재 행위를 고정하는 것이 좋다.

1. 이미 포맷된 한 줄만 추가한 PR에서 formatter patch 파일이 0 byte이고 job이 성공하는지 확인한다.
2. 들여쓰기·pointer spacing을 의도적으로 어긴 한 줄을 추가한 PR에서 `clang-format-diff` 출력과 세 command의 `PIPESTATUS`를 log로 남긴다.
3. `clang-format-diff` 경로를 잠시 잘못 지정한 test branch에서 job이 반드시 실패하는지 확인한다.
4. local `tvg-format.sh`를 실행했을 때 두 번째 PR의 위반이 실제로 고쳐지는지 대조한다.
5. 원인 파악용 출력은 유지할 version/tool 정보만 남기고 임시 debug log는 제거한다.

## 위험/검증

- 정상 formatting patch는 성공하고, 추가된 비정상 C/C++ 줄은 annotation 유무와 관계없이 실패해야 한다.
- `git diff`의 잘못된 SHA, formatter script 실행 실패, clang-format binary 부재, 깨진 formatter 출력은 모두 성공이 아니라 실패가 되어야 한다.
- 빈 diff와 문서만 바꾼 PR은 성공해야 한다.
- rename, delete, 새 파일, 여러 commit, base branch 갱신 뒤에도 정확한 PR 변경 범위를 검사해야 한다.
- fork PR에서 read-only token으로도 formatter 판정이 실행되고, annotation 권한 부족이 false green으로 바뀌지 않는지 확인한다.
- `-filter-mode=added` 유지 시 기존 줄의 위반과 새 줄의 위반이 정책대로 구분되는지 확인한다.
- formatter 출력 patch를 artifact 또는 log로 남겨 실패 원인을 재현 가능하게 한다.
- workflow YAML lint와 실제 pull-request event를 모두 사용한다. 로컬 shell 성공만으로 GitHub token/report 동작을 검증했다고 보지 않는다.
- CI가 사용한 clang-format과 script가 모두 major 18인지 출력으로 고정한다.
