## 이슈 요약

이 이슈는 unit test project와 asset을 별도 repository로 옮기고, build/CI와 문서를 새 구조에 맞게 갱신해 main repository의 크기와 복잡도를 줄이자는 제안이다.

현재 unit test는 단순한 외부 consumer가 아니다. 같은 Meson project의 target·include path·generated configuration·source-tree resource path를 직접 사용하며, CI도 한 checkout에서 source와 test를 동시에 설정한다. 따라서 핵심 과제는 파일 이동보다 “어떤 source revision을 어떤 test revision·옵션·asset으로 검증했는가”를 재현 가능한 계약으로 바꾸는 일이다.

## main 코드 조사

root [`meson.build`](https://github.com/thorvg/thorvg/blob/d8342de1aae57284b56ad4241efa8f9dd7d43fd4/meson.build#L1-L18)는 source tree의 `test/resources`를 가리키는 `TEST_DIR` macro를 project argument로 추가한다. 같은 파일은 [`tests` option이 켜졌을 때 `subdir('test')`](https://github.com/thorvg/thorvg/blob/d8342de1aae57284b56ad4241efa8f9dd7d43fd4/meson.build#L170-L180)를 호출하므로 test가 main build graph 내부에 있다.

[`meson_options.txt`](https://github.com/thorvg/thorvg/blob/d8342de1aae57284b56ad4241efa8f9dd7d43fd4/meson_options.txt#L38-L45)는 `tests`를 boolean build option으로 노출한다. 현재 사용자는 source checkout 하나에서 `-Dtests=true`로 library와 tests를 함께 구성한다.

[`test/meson.build`](https://github.com/thorvg/thorvg/blob/d8342de1aae57284b56ad4241efa8f9dd7d43fd4/test/meson.build#L1-L69)는 test source를 직접 열거하고 `tvgUnitTests` 실행 파일을 내부 `thorvg_lib` target에 link한다. project의 `headers`, `compiler_flags` 변수도 상위 scope에서 전달받으며 platform 조건에 따라 OpenGL/EGL과 WebGPU test source·dependency를 추가한다. 이 결합은 directory만 다른 repository로 옮겨서는 해소되지 않는다.

반면 [`src/meson.build`](https://github.com/thorvg/thorvg/blob/d8342de1aae57284b56ad4241efa8f9dd7d43fd4/src/meson.build#L59-L92)는 library target과 공개 `thorvg_dep`를 만들고 `thorvg-1` dependency override도 등록한다. 공개 API test는 이 dependency를 소비하도록 전환할 수 있다. 하지만 current tests의 generated `config.h`와 build option 접근까지 공개 dependency가 제공한다는 의미는 아니다.

예를 들어 [`testLottie.cpp`](https://github.com/thorvg/thorvg/blob/d8342de1aae57284b56ad4241efa8f9dd7d43fd4/test/testLottie.cpp#L23-L64)는 generated `config.h`의 feature macro와 `TEST_DIR`를 사용한다. SW·GL·WG test들도 local harness와 renderer별 build 조건을 공유한다. 이 의존을 명시적인 Meson option, generated test config 또는 feature probe로 바꿔야 standalone 실행이 가능하다.

Ubuntu [`unit_test` job](https://github.com/thorvg/thorvg/blob/d8342de1aae57284b56ad4241efa8f9dd7d43fd4/.github/workflows/build_ubuntu.yml#L49-L99)은 main checkout에 dependency를 설치하고 `-Dtests=true`로 setup한 뒤 같은 build directory에서 compile/install/`meson test`를 수행한다. Windows와 macOS workflow도 같은 in-tree option을 사용한다. 외부 test repository로 바꾸면 checkout 순서, revision pin, working directory와 artifact 경로를 모든 platform에 일관되게 추가해야 한다.

sanitizer/Valgrind script와 test resource, 단일-header Catch도 현재 source repository의 `test` tree에 있다. 이슈의 “project and assets” 범위에는 source 파일만이 아니라 실행 script, license/attribution, fixture history와 결과 경로도 포함된다고 보는 것이 안전하다.

## 원인 분석

### 확인된 사실

- tests는 root Meson option으로 활성화되고 main build graph의 `subdir('test')`로 구성된다.
- test executable은 공개 설치 package가 아니라 내부 `thorvg_lib`, 상위 `headers`와 compiler flag에 직접 연결된다.
- tests는 generated `config.h`와 source-tree 절대 경로로 정의된 `TEST_DIR`에 의존한다.
- GL/EGL과 WebGPU tests는 platform·dependency 탐지 결과에 따라 조건부로 포함된다.
- Linux·Windows·macOS CI는 source와 tests를 한 checkout, 한 Meson configure에서 빌드한다.
- source build는 공개 `thorvg_dep`와 `thorvg-1` dependency override를 이미 제공한다.
- test resource와 memory-check script도 main repository에 함께 있다.

### 추론과 판단

- 저장소 크기 감소 효과는 현재 object/history와 asset 크기를 측정하지 않으면 확정할 수 없다. working tree에서 파일을 지워도 과거 Git history는 그대로 남을 수 있다.
- 새 test repository의 `main`을 항상 source PR에 붙이면 test 쪽 breaking change가 source PR을 오탐 실패시킬 수 있다. 반대로 오래된 pinned test만 쓰면 새 회귀 test가 source main에 적용되지 않는다.
- source 변경과 그 회귀 test가 서로 다른 PR이어야 하면 atomic review가 깨진다. 양쪽이 호환되는 순서, 임시 branch/ref 또는 compatibility window가 필요하다.
- tests가 private/internal header 접근을 계속하면 별도 repository의 이점은 작아지고 checkout layout에 의존한다. public API test와 white-box test의 경계를 먼저 분류해야 한다.
- reusable workflow 또는 cross-repository dispatch를 사용할 경우 fork PR의 token 권한과 untrusted code 실행을 별도로 설계해야 한다. write token을 source PR code에 노출하면 안 된다.
- history-preserving 이동은 attribution·bisect에는 유리하지만 새 repository 초기 크기를 늘린다. 목표가 clone size인지 ownership인지에 따라 선택이 달라진다.

## 구현 방향

1. 먼저 inventory를 만든다. test source, renderer별 harness, resource, generated config, internal target/header, sanitizer script와 workflow를 `public API`, `white-box`, `tooling`, `asset`으로 분류한다.
2. 이동 전 현재 repository에서 `test/meson.build`를 standalone-compatible하게 만든다. public test는 `dependency('thorvg-1')` 또는 override를 받고, source/build/resource root를 명시적 option으로 주입한다.
3. feature macro는 main의 private `config.h`를 직접 include하지 않도록 test용 generated config 또는 Meson dependency feature detection으로 치환한다. GL/WG 활성 조건도 test project 입력으로 고정·출력한다.
4. 새 repository에 license, CODEOWNERS, asset provenance, fixture 추가 규칙과 독립 `meson setup/compile/test` 문서를 먼저 만든다. history를 보존할지 snapshot으로 시작할지는 측정 결과와 maintainer 정책으로 결정한다.
5. source CI는 test repository의 검증된 revision을 명시적으로 checkout하고 현재 source PR SHA를 library input으로 제공한다. 실행 결과에는 두 commit SHA와 build option을 artifact로 남긴다.
6. test repository CI는 최소한 pinned stable source와 source main을 구분해 실행한다. stable 조합은 required, moving main 조합은 초기에는 non-blocking으로 운영해 호환 문제를 분류한다.
7. source 변경과 새 regression test가 함께 필요한 경우를 위한 절차를 만든다. 호환되는 두 단계 merge, temporary test ref 입력 또는 maintainer가 승인한 paired-PR convention 중 하나를 문서화한다.
8. 한동안 in-tree와 external runner를 같은 source revision에서 병행해 test 목록, skip, exit code와 report를 비교한다. 동등성이 확인된 뒤 main의 `test` subdir와 `tests` option을 제거한다.
9. 마지막으로 sanitizer, coverage, cache, release verification, documentation link와 branch protection을 새 job 이름에 맞게 갱신한다.
10. migration 전후 `git clone` 전송량, checkout 크기, CI duration/cache와 실패율을 측정해 이슈 목표가 실제로 달성됐는지 확인한다.

## 초심자 시작 가이드

repository 이동 자체보다 dependency inventory와 standalone smoke runner 작업을 추천한다.

1. `test/meson.build`의 각 변수·target이 어느 상위 Meson 파일에서 오는지 표로 만든다.
2. `config.h`, `TEST_DIR`, `thorvg_lib`, renderer dependency를 사용하는 test 파일을 검색해 public/private 의존으로 분류한다.
3. 기존 source checkout 옆 임시 directory에서 설치된 ThorVG를 사용해 가장 단순한 public API test 하나를 compile·run한다.
4. resource root를 command-line/Meson option으로 넘겨 cwd가 달라도 같은 fixture를 찾는지 확인한다.
5. test binary에 source SHA, test SHA, feature option을 출력하는 metadata command를 추가해 재현 정보를 보존한다.

첫 PR은 파일 삭제나 workflow 전환보다 dependency inventory, standalone proof-of-concept와 migration 문서를 목표로 하는 편이 안전하다.

## 위험/검증

- source PR SHA와 test revision을 항상 log·artifact에 남기고 재실행 시 같은 조합을 복원한다.
- Linux·Windows·macOS에서 source sibling checkout, installed dependency와 Meson subproject 방식의 path 차이를 검증한다.
- SW 기본 tests와 조건부 GL/EGL·WG tests의 test 수·skip·timeout이 migration 전후 같은지 비교한다.
- `TEST_DIR`가 cwd, symlink, Windows path separator와 install/archive layout에서 올바르게 동작하는지 확인한다.
- sanitizer·Valgrind script가 새 build directory와 resource path를 사용하고 failure exit code를 보존하는지 확인한다.
- fork PR에서는 read-only token만 사용하고 external repository write/dispatch secret이 untrusted source code에 노출되지 않는지 검증한다.
- source API가 먼저/나중에 바뀌는 양방향 mismatch를 의도적으로 만들어 실패 메시지가 원인을 식별하는지 확인한다.
- fixture license, 원본 URL, checksum과 변경 history가 repository 이동 후에도 추적되는지 확인한다.
- dependency cache key에 source SHA, test SHA, compiler, build option이 모두 포함되는지 확인한다.
- old in-tree job과 new external job을 일정 기간 병행해 누락 test와 flaky 증가를 집계한다.
- branch protection required check 이름을 바꾸는 시점에 merge가 무조건 차단되거나 반대로 무검증 통과하지 않는지 확인한다.
- migration 전후 shallow/full clone 전송량과 `.git` object 크기를 따로 측정한다.
