## 이슈 요약

Lottie 문서의 외부 image asset은 `u` 경로와 `p` 파일명으로 resource를 가리킬 수 있다. 이슈는 host가 `AssetResolver`를 등록해도 ThorVG의 기본 resource 해석이 먼저 실행되어 로컬 파일에 접근할 수 있으므로, resolver를 먼저 시도하는 정책을 공개 API로 선택하게 하자고 제안한다. 기본값은 현재 동작을 보존하고, resolver가 성공하면 내부 loader를 건너뛰는 것이 핵심 요구다.

FFmpeg 같은 host는 자체 I/O와 protocol 허용 정책 안에서 모든 resource 접근을 관리해야 한다. 따라서 이 작업의 성공 조건은 callback이 먼저 “호출되는 것”만이 아니라, resolver가 처리한 asset에 대해 ThorVG의 기본 파일 접근이 실제로 발생하지 않는 것이다. 반대로 resolver가 처리하지 못한 경우 내부 fallback을 허용할지는 호환성 정책과 보안 정책을 분리해 명시해야 한다.

Lottie 공식 사양도 image asset의 `p`를 파일명 또는 data URL, `u`를 파일 경로로 정의하며 외부 image reference의 보안 고려가 필요하다고 설명한다. 이 정책은 Lottie JSON 문법을 바꾸는 기능이 아니라 player가 외부 reference를 어떤 권한 경계에서 해석할지 정하는 host API다.

## main 코드 조사

### 공개 API와 resolver 전달

현재 C++ [`Picture::resolver()` 문서와 선언](https://github.com/thorvg/thorvg/blob/67809897e95ab9e515bb82a66536d808d79ad5a0/inc/thorvg.h#L1739-L1760)은 image·font 외부 asset용 callback을 load 전에 등록하게 한다. callback이 `false`를 반환하면 내부 해석을 fallback으로 시도한다고 문서화하지만, resolver의 우선순위를 받는 매개변수나 별도 policy type은 없다. API는 Experimental이지만 기존 두 인자 함수의 symbol을 없애거나 signature만 바꾸면 source default argument와 별개로 기존 binary의 ABI에는 영향을 줄 수 있다.

내부 [`AssetResolver`와 `PictureOps`](https://github.com/thorvg/thorvg/blob/67809897e95ab9e515bb82a66536d808d79ad5a0/src/renderer/tvgLoader.h#L36-L54)는 callback과 user data만 보관하고 이를 picture loader에 전달한다. [`PictureImpl::set()`](https://github.com/thorvg/thorvg/blob/67809897e95ab9e515bb82a66536d808d79ad5a0/src/renderer/tvgPicture.h#L164-L176)은 picture가 load되기 전에 callback을 저장하거나 해제하며 policy state는 없다. 파일 또는 memory로 picture를 load할 때는 같은 resolver pointer가 `PictureOps`에 들어간다.

Lottie loader는 [memory 입력의 `rpath`와 resolver를 builder에 복사](https://github.com/thorvg/thorvg/blob/67809897e95ab9e515bb82a66536d808d79ad5a0/src/loaders/lottie/tvgLottieLoader.cpp#L210-L226)하고, file 입력도 [Lottie 파일을 연 뒤 resolver를 builder에 전달](https://github.com/thorvg/thorvg/blob/67809897e95ab9e515bb82a66536d808d79ad5a0/src/loaders/lottie/tvgLottieLoader.cpp#L229-L238)한다. 따라서 policy를 resolver와 함께 저장하면 builder까지 전달할 기존 통로는 있지만, 현재 data structure와 constructor를 확장해야 한다.

### image asset은 내부 loader가 먼저 실행된다

[`parseAssetSource()`](https://github.com/thorvg/thorvg/blob/67809897e95ab9e515bb82a66536d808d79ad5a0/src/loaders/lottie/tvgLottieParser.cpp#L999-L1035)은 embedded data URL을 decode하고, HTTP(S) URL은 그대로 보관하며, 그 외 `u`/`p` 조합은 `dirName + '/' + subPath + data` 문자열로 만들어 `external=true`로 표시한다. 이 단계는 아직 파일을 열지 않지만 host가 전달한 Lottie의 상대 경로를 내부 filesystem 경로로 구체화한다.

실제 선행 접근은 [`LottieImage::get()`](https://github.com/thorvg/thorvg/blob/67809897e95ab9e515bb82a66536d808d79ad5a0/src/loaders/lottie/tvgLottieModel.cpp#L297-L310)에 있다. image가 처음 필요할 때 `Picture`를 만든 뒤 embedded data가 있으면 memory load를, `asset.external`이면 `picture->load(asset.path)`를 먼저 호출하고 그 결과로 `valid`를 정한다. file I/O가 활성화된 build에서 내부 [`Loader::open()`은 `fopen()`으로 path를 연다](https://github.com/thorvg/thorvg/blob/67809897e95ab9e515bb82a66536d808d79ad5a0/src/renderer/tvgLoader.h#L122-L136). 즉 current main에서는 resolver callback 전에 파일 open 시도가 일어날 수 있다는 이슈 설명이 코드와 일치한다.

그 뒤 [`LottieBuilder::updateImage()`](https://github.com/thorvg/thorvg/blob/67809897e95ab9e515bb82a66536d808d79ad5a0/src/loaders/lottie/tvgLottieBuilder.cpp#L964-L985)은 image가 아직 valid하지 않을 때만 resolver를 호출한다. callback 반환값을 확인하지 않고 size를 다시 지정한 뒤 `valid=true`로 바꾸므로, current 구현의 boolean은 이 분기에서 재시도 여부까지 정확하게 표현하지 않는다. 기존 image 파일이 성공적으로 열리면 `valid=true`라 callback은 전혀 호출되지 않는다.

따라서 `PreferResolver`는 `updateImage()`의 조건만 뒤집어서는 구현되지 않는다. `LottieImage::get()`이 외부 path를 먼저 여는 구조를 분리해, empty `Picture` 생성 → resolver 시도 → callback 결과에 따른 default load → 최종 size/valid 결정 순서를 하나의 명시적 상태 기계로 만들어야 한다. embedded image는 이미 animation data 안에 있으므로 정책 적용 대상인지 별도로 결정하되, 기존 동작을 보존하려면 보통 내부 memory decode를 유지하는 편이 자연스럽다.

### font도 별도 내부-first 경로를 가진다

[`updateURLFont()`](https://github.com/thorvg/thorvg/blob/67809897e95ab9e515bb82a66536d808d79ad5a0/src/loaders/lottie/tvgLottieBuilder.cpp#L989-L1007)은 새 `Text`를 만든 뒤 먼저 `paint->font(doc.name)`으로 이미 등록된 font를 찾는다. 이것이 실패할 때만 path 또는 `name:` identifier를 resolver에 전달하고, resolver도 실패하면 `font(nullptr)`로 임의의 사용 가능한 font에 fallback한다.

이슈 본문은 주로 `u`/`p` image reference를 설명하지만 기존 공개 resolver 계약은 image와 font를 함께 다룬다. policy를 image에만 적용하면 API 이름과 문서에 비해 동작이 비대칭이 된다. 반대로 font까지 resolver-first로 바꾸면 이미 host process에 등록된 font보다 callback을 먼저 호출하게 되므로, 기존 출력과 callback 횟수가 달라질 수 있다. policy의 resource 범위를 문서와 test로 확정해야 한다.

### C API와 현재 test의 빈틈

C binding은 [`tvg_picture_set_asset_resolver()`에서 C callback을 C++ lambda로 감싼다](https://github.com/thorvg/thorvg/blob/67809897e95ab9e515bb82a66536d808d79ad5a0/src/bindings/capi/tvgCapi.cpp#L656-L662). [C API 문서와 함수](https://github.com/thorvg/thorvg/blob/67809897e95ab9e515bb82a66536d808d79ad5a0/src/bindings/capi/thorvg_capi.h#L2028-L2050)도 `false`면 내부 fallback이라고 약속한다. C++에 enum이나 overload를 추가할 때 C enum과 새 함수 또는 확장 가능한 별도 setter가 없으면 FFmpeg 같은 C client는 새 정책을 사용할 수 없다.

현재 [`Lottie Asset Resolver` unit test](https://github.com/thorvg/thorvg/blob/67809897e95ab9e515bb82a66536d808d79ad5a0/test/testLottie.cpp#L324-L359)는 존재하지 않는 image/font path를 resolver가 다른 test resource로 바꾸는 성공 경로와 등록 시점을 확인한다. 기본 path가 성공하는 경우 callback이 호출되지 않는다는 현재 순서, resolver-first의 성공·실패 순서, 내부 `fopen()` 미호출, embedded asset, C API policy는 검증하지 않는다. callback count만으로는 선행 filesystem 접근을 잡을 수 없으므로 접근 가능한 sentinel path와 접근을 금지한 path를 구분하는 test seam이 필요하다.

## 원인 분석

### 확인된 사실

- 공개 C++·C API는 resolver callback과 user data만 받고 priority policy는 받지 않는다.
- 문서는 callback이 `false`면 ThorVG 내부 해석으로 fallback한다고 명시한다.
- Lottie parser는 local image의 `u`와 `p`를 animation 경로 기준 filesystem path로 조합한다.
- 외부 image의 첫 사용 시 `LottieImage::get()`이 `Picture::load(path)`를 resolver보다 먼저 호출한다.
- 내부 image load가 성공하면 `valid=true`가 되어 resolver는 호출되지 않는다.
- 내부 image load가 실패하면 builder가 resolver를 호출하지만 그 boolean 결과와 관계없이 image를 valid로 표시한다.
- font는 등록된 이름을 내부에서 먼저 찾고 실패할 때 resolver를 호출하며, 둘 다 실패하면 임의 font로 fallback한다.
- resolver는 Lottie loader에서 builder로 pointer가 전달되므로 policy를 함께 전달할 구조적 경로는 이미 있다.
- C binding과 문서에도 현재 fallback 의미가 노출되어 있다.
- existing unit test는 missing asset을 resolver가 성공적으로 대체하는 한 경로만 다루고 resolver-first나 실제 file-access 차단을 검증하지 않는다.

### 추론과 판단

- **직접 원인:** resolver는 “외부 asset 해석 전략”이 아니라 current builder에서 “내부 해석 실패 후 복구 callback”으로 배치되어 있다. API 문구는 custom resolution을 강조하지만 control flow는 default-first로 고정돼 있다.
- **보안 경계:** `PreferResolver`에서 callback이 `true`이면 내부 load를 생략할 수 있다. 하지만 callback이 `false`일 때 자동 fallback한다면 host가 모르는 path 접근을 절대 금지하는 정책은 아니다. priority와 resolver-only/deny semantics를 구분해야 한다.
- **정책 후보:** 최소 요구는 `PreferDefault`와 `PreferResolver`다. sandbox 요구가 resolver 실패 시에도 내부 접근 금지를 뜻한다면 `ResolverOnly` 또는 callback의 `Resolved / Unresolved / Denied` tri-state가 필요하다. 이는 이슈 본문만으로 확정할 수 없는 설계 결정이다.
- **호환성:** 기존 두 인자 C++ symbol을 유지하고 새 overload가 그것을 `PreferDefault`로 위임하는 방식이 default argument로 signature를 교체하는 방식보다 binary 호환에 유리하다. C API는 기존 함수를 유지한 채 policy를 받는 새 함수 또는 별도 policy setter가 필요하다.
- **image 상태:** `Picture` 생성, default load, resolver load, size 설정과 `valid` 갱신을 여러 함수에 흩어 두면 callback 실패 후 재시도와 shared image duplicate가 흔들릴 수 있다. 한 함수가 최종 outcome을 소유해야 한다.
- **font 범위:** image만 resolver-first로 만들 수도 있지만 public resolver가 font를 명시하므로 같은 policy를 적용하는 편이 일관적이다. 다만 기본 등록 font 우선순위를 바꾸는 동작이므로 release note와 회귀 test가 필요하다.
- **embedded/URL 판단:** embedded data는 host 외부 접근이 아니므로 기존 decode를 우선해도 목표와 충돌하지 않는다. HTTP(S)는 current parser에서 local `external` flag와 다르게 저장되므로 URL을 resolver-only 대상으로 볼지 정책 문서에 명시해야 한다.

## 구현 방향

1. 먼저 policy contract를 결정한다. `PreferDefault`, `PreferResolver` 각각에서 callback `true`·`false`와 default 성공·실패의 정확한 순서를 table로 문서화한다. host가 내부 접근을 완전히 거부할 수 있어야 하는지도 합의한다.
2. 기존 C++ `resolver(func, data)`와 C `tvg_picture_set_asset_resolver()`는 그대로 유지하고 `PreferDefault`로 위임한다. policy를 받는 새 overload/함수와 대응 C enum을 추가해 기존 binary와 source를 보존한다.
3. 내부 `AssetResolver`에 policy를 저장하고 `PictureOps` → `LottieLoader` → `LottieBuilder` 전달 경로에서 callback, data, policy를 하나의 불변 설정으로 취급한다.
4. image resolution을 단일 함수로 모은다. embedded memory data, local path, URL을 분류한 뒤 policy에 따라 resolver와 default loader를 정확히 한 번씩만 호출하고 최종 `Result`와 `valid`를 함께 갱신한다.
5. `PreferResolver`에서는 empty `Picture`에 callback을 먼저 호출한다. callback이 성공하면 default `Picture::load(path)`를 호출하지 않고 Lottie width/height를 마지막에 적용한다. 실패 시 fallback 허용 정책일 때만 default load를 시도한다.
6. `PreferDefault`는 기존 성공 path와 callback 횟수를 보존한다. 다만 resolver 반환값을 무시하고 무조건 valid로 만드는 current image 동작은 명시적 outcome으로 교체해 실패 상태를 test 가능하게 한다.
7. font path도 같은 policy table에 맞춘다. resolver-first라면 callback이 `Text`에 font를 성공적으로 설정했을 때 이름 lookup과 임의 font fallback을 건너뛰고, 실패/deny 결과에 따라 다음 단계가 달라지게 한다.
8. C++와 C 문서에 image/font/embedded/URL 범위, callback이 성공할 때 paint를 완성해야 한다는 책임, false/deny fallback과 등록 가능 시점을 명시한다.
9. FFmpeg integration에는 resolver가 host의 허용된 I/O로 bytes를 얻어 `Picture::load(data, ...)` 또는 font 등록을 수행하는 예를 제공한다. callback success 뒤 ThorVG가 path를 다시 열지 않는 것을 integration test로 고정한다.

첫 PR은 public policy contract, image resolver 순서와 C/C++ test를 함께 묶고 font 적용 여부를 명확히 하는 것이 좋다. strict deny가 별도 정책으로 필요하다면 이름과 callback outcome을 먼저 합의해, 단순 우선순위 변경을 보안 차단 기능으로 오해하지 않게 해야 한다.

## 초심자 시작 가이드

이 작업은 API 최종 설계보다 test harness부터 기여하는 편이 안전하다.

1. 임시 directory에 실제로 존재하는 PNG와 Lottie JSON을 만들고 current `PreferDefault` 상당 동작에서 resolver call count가 0인지 확인한다.
2. 같은 JSON의 image path를 존재하지 않게 바꾸어 resolver가 한 번 호출되고 대체 image가 load되는 현재 경로를 확인한다.
3. resolver-first prototype에서 존재하는 path여도 callback이 먼저 호출되고 성공 시 default loader가 실행되지 않는지 검사한다.
4. callback이 `false`인 경우 default fallback 허용 정책과 deny 정책을 별도 test case로 작성한다.
5. image resolver 안에서 memory data를 load한 뒤 Lottie `w`/`h`가 최종 picture size에 적용되는지 확인한다.
6. font name이 이미 등록된 경우와 path resolver가 필요한 경우를 나눠 callback 순서와 최종 glyph output을 확인한다.
7. C API로 같은 네 가지 성공·실패 조합을 호출해 enum 값과 기존 함수 default가 C++ 결과와 같은지 확인한다.

구현 전 `resolver`, `default loader`, `fallback` 세 단계의 호출 순서를 작은 table test로 고정하면 image/font code를 수정하면서 의미가 뒤집히는 실수를 줄일 수 있다.

## 위험/검증

- 기존 두 인자 C++ API와 기존 C 함수가 계속 `PreferDefault`로 동작하고 symbol/ABI가 유지되는지 확인한다.
- default path 성공·실패와 resolver 성공·실패의 4개 조합에서 호출 순서·횟수·최종 결과를 검사한다.
- resolver 성공 시 접근 가능한 sentinel file도 내부 loader가 열지 않았음을 open hook, permission-denied directory 또는 dependency injection으로 검증한다.
- strict deny가 제공되면 callback 실패 시에도 local path와 HTTP(S) URL을 내부에서 열지 않는지 확인한다.
- embedded base64 image는 policy와 무관하게 기존 decode와 pixel output을 보존하는지 확인한다.
- file path 입력과 memory+rpath 입력이 같은 `u`/`p` source string과 정책 결과를 내는지 비교한다.
- `../`, absolute path, 빈 `u`, URL과 잘못된 data URL을 넣어 callback이 받는 `src`와 fallback 경계를 기록한다. 이 항목은 path traversal 취약점을 확정하는 test가 아니라 policy가 모든 source 형태에 일관되게 적용되는지 확인하는 test다.
- resolver가 `true`를 반환했지만 paint를 load하지 않은 경우를 문서 계약대로 실패로 볼지 빈 asset 처리로 볼지 test로 고정한다.
- 같은 image asset을 여러 layer가 공유하거나 slot override로 교체할 때 resolver가 불필요하게 반복 호출되지 않고 duplicate 결과가 유지되는지 확인한다.
- image size, aspect ratio와 callback 후 `picture->size()` 순서가 기존 pixel output을 보존하는지 regression image로 비교한다.
- font resolver-first에서 기존 등록 font, path font, `name:` identifier, resolver 실패 후 임의 font fallback을 각각 검증한다.
- resolver 설정/해제는 load 전에만 허용되고 load 후 `InsufficientCondition`을 반환하는 기존 lifecycle을 보존한다.
- `-Dfile=false` build와 C API enabled build를 포함해 compile/test하고 sanitizer로 resolver/user-data 수명을 확인한다.
- 전체 Lottie unit test, C API build, example와 FFmpeg 연동 test를 실행한다.
