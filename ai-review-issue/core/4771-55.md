## 이슈 요약

이슈에는 4개 병렬 Valgrind shard의 합친 로그가 첨부돼 있다. CPU·OpenGL 중심 shard는 102개, GL image와 WG canvas shard는 7개, 나머지 WG shard는 3개 test를 모두 통과하고 Memcheck error도 0개다. 반면 `WG Image Draw`와 `WG Image Rotation`만 묶은 shard는 두 test 자체는 통과하지만 `llvmpipe-0` thread에서 해제된 120-byte block을 읽거나 쓰는 4-byte invalid access를 보고한다. 최종 결과는 6개 context의 9개 error다.

표시된 실행 stack의 실제 접근 지점은 `pthread_cond_broadcast` 또는 `pthread_mutex_unlock`이고 그 아래 호출, block 할당, block 해제의 비-libc frame은 모두 Ubuntu system의 `libgallium` shared object다. 그러나 해당 binary가 stripped 상태라 함수 이름이 모두 `???`이며, 로그에는 ThorVG나 wgpu-native의 자원 생성·해제 호출 stack이 남아 있지 않다.

따라서 목표는 단순히 붉은 로그를 없애는 것이 아니다. 먼저 이 context가 특정 Mesa llvmpipe 버전의 이미 알려진 진단인지, WebGPU host code의 종료 순서가 driver worker를 잘못 끝내도록 만든 것인지 구분해야 한다. 외부 요인으로 귀속할 수 있을 때만 접근 종류·상위 pthread 함수·driver object frame을 함께 고정한 좁은 suppression을 추가하고, 그 밖의 새로운 Memcheck error는 CI가 실패하도록 만들어야 한다.

## main 코드 조사

현재 [Ubuntu workflow](https://github.com/thorvg/thorvg/blob/4f968a5f49173d9acf6ef527b1e4b1cf81889cd5/.github/workflows/build_ubuntu.yml#L33-L72)는 PR에서 모든 engine과 test를 build한 뒤 [`memcheck_valgrind.sh`](https://github.com/thorvg/thorvg/blob/4f968a5f49173d9acf6ef527b1e4b1cf81889cd5/.github/workflows/memcheck_valgrind.sh#L8-L30)를 실행한다. script는 software renderer를 강제하고 `LP_NUM_THREADS=1`을 지정한 상태로 네 process를 background 실행한다. 문제의 세 번째 shard는 `[tvgWgEngine]` suite에서 `WG Image Draw`와 `WG Image Rotation`만 선택하므로, 이슈 로그의 9개 error가 다른 112개 test와 섞여 발생한 것은 아니다.

이 분할은 [`a023616`](https://github.com/thorvg/thorvg/commit/a02361640be2c93468bcb6e34defb3bc9a6721cd)에서 도입됐다. 병렬화는 오류가 발견된 시점과 범위를 설명하지만, 그 commit이 memory defect를 새로 만들었다는 증거는 아니다. 이전의 단일 process 실행에서도 같은 종료 경로가 있었을 수 있고, process 경계와 실행 순서가 바뀌며 기존 timing-sensitive 진단이 드러났을 수도 있다.

[`WG Image Draw`](https://github.com/thorvg/thorvg/blob/4f968a5f49173d9acf6ef527b1e4b1cf81889cd5/test/testWgEngine.cpp#L141-L218)는 한 canvas에 raw image의 duplicate, clip, rotate, scale, mask와 blend 조합을 반복해서 추가하고 매 반복마다 `draw`·`sync`·`remove`를 수행한다. [`WG Image Rotation`](https://github.com/thorvg/thorvg/blob/4f968a5f49173d9acf6ef527b1e4b1cf81889cd5/test/testWgEngine.cpp#L341-L375)은 큰 target에 raw image를 올리고 transform한 뒤 `draw(true)`와 `sync`를 호출한다. 두 test 모두 canvas scope를 빠져나간 다음 `Initializer::term()`을 호출하므로 명시적 render synchronization은 존재한다. 이것만으로 WebGPU device, GLES context, Mesa worker가 완전히 종료됐다는 보장은 없으며, 그 순서는 symbol 없는 로그에서 확인할 수 없다.

[wgpu-native 설치 script](https://github.com/thorvg/thorvg/blob/4f968a5f49173d9acf6ef527b1e4b1cf81889cd5/.github/workflows/install_wgpu_native.sh#L3-L24)는 기본값으로 release `v29.0.1.1`의 prebuilt shared library를 사용한다. runner는 `ubuntu-latest`이고 이슈 로그에는 Mesa Gallium `25.2.8-0ubuntu0.24.04.2`가 나타난다. 재현 환경은 이 두 dependency와 Valgrind 3.22.0까지 함께 고정해야 하며, 어느 하나만 바꿔서 사라진 결과로 원인을 단정하면 안 된다.

현재 [suppression 파일](https://github.com/thorvg/thorvg/blob/4f968a5f49173d9acf6ef527b1e4b1cf81889cd5/.github/workflows/valgrind.supp#L1-L38)은 wgpu-native GLES의 EGL instance cache와 GLSL writer cache에서 나온 `Memcheck:Leak` 두 종류만 다룬다. 이번 오류는 invalid 4-byte address access이므로 Memcheck suppression type이 `Addr4`이고, 기존 leak 규칙으로는 일치할 수 없다. 실제로 정상 WG shard 두 개의 로그는 기존 규칙으로 각각 2개 context가 suppressed됐지만 문제 shard에는 9개 error가 그대로 남았다.

분석 시점의 [open PR #4772](https://github.com/thorvg/thorvg/pull/4772)는 각 shard log를 먼저 판정해 문제가 있는 shard만 PR comment에 싣고, condition-variable와 mutex 경로를 위한 `Memcheck:Addr4` suppression 두 개를 추가한다. [current PR head의 suppression](https://github.com/thorvg/thorvg/blob/a08e504bbbffca9ff0fccf12453ae7583319df4c/.github/workflows/valgrind.supp#L39-L66) 중 condition 규칙은 pthread call 바로 다음의 Gallium frame을 요구하지만, mutex 규칙은 `fun:*mutex_unlock*` 다음에 `...`를 둔 뒤 Gallium object를 찾는다. 이 wildcard는 둘 사이의 임의 frame을 허용하므로 “다음 frame이 driver 내부인 관찰된 context만”이라는 주석보다 넓다. 해당 PR은 아직 merge되지 않았고 current `main`의 두 파일은 바뀌지 않았으므로, 이 리뷰는 제안된 diff를 선행 구현으로 평가하되 완료된 사실로 보지 않는다.

[Valgrind script의 판정](https://github.com/thorvg/thorvg/blob/4f968a5f49173d9acf6ef527b1e4b1cf81889cd5/.github/workflows/memcheck_valgrind.sh#L32-L69)은 각 process를 `wait`하고 합친 로그에서 `ERROR SUMMARY`, definitely-lost byte, `Invalid read`, `Invalid write`를 찾으면 step summary와 PR comment를 만든다. 그러나 마지막 `exit 1`은 Valgrind process 중 하나가 nonzero였을 때만 실행된다. 현재 command에는 `--error-exitcode`가 없고 Valgrind의 기본값은 0이므로, test executable이 성공하면 unsuppressed error가 있어도 process exit code는 그대로 0일 수 있다. 즉 current main은 이번 9개 error를 알리지만 그 자체로 job을 실패시키지는 않는다.

별도 [ASan/UBSan job](https://github.com/thorvg/thorvg/blob/4f968a5f49173d9acf6ef527b1e4b1cf81889cd5/.github/workflows/build_ubuntu.yml#L73-L95)은 project를 sanitizer option으로 다시 build하고 같은 software GL 환경에서 전체 test를 실행한다. 이는 project-owned code의 보완 신호지만 prebuilt wgpu-native와 system Mesa가 같은 sanitizer instrumentation으로 build됐다는 뜻은 아니다. 따라서 ASan 성공만으로 `libgallium` stack의 invalid access가 무해하다고 결론 내릴 수 없다.

Valgrind 공식 문서는 dynamically linked graphical library까지 검사하며 제어할 수 없는 system library 오류를 선택적으로 suppress할 수 있다고 설명한다. 동시에 suppression은 모든 세부 항목이 맞을 때만 적용되고, `fun:`, `obj:`, `src:` 및 frame wildcard `...`를 조합할 수 있다. `--gen-suppressions=all`은 각 error의 가장 구체적인 초안을 비대화형으로 출력하며, `--error-exitcode`를 nonzero로 설정하면 unsuppressed error를 자동화 test의 실패로 바꿀 수 있다.

## 원인 분석

### 확인된 사실

- 네 shard 중 `WG Image Draw`와 `WG Image Rotation` 두 test를 실행한 shard에서만 9개 Memcheck error가 나왔고, 두 test의 assertion은 모두 통과했다.
- 오류 thread 이름은 `llvmpipe-0`이며 invalid access, 관련 block의 할당과 해제 stack에 보이는 비-libc frame은 모두 같은 `libgallium` shared object다.
- 접근 대상은 이미 해제된 120-byte block 내부이고, 보고된 연산은 4-byte read 또는 write다. 이는 단순 “still reachable” leak과 다른 use-after-free 형태의 신호다.
- 로그의 driver frame은 symbol이 없어 모두 `???`이고 project frame은 표시되지 않는다. 따라서 현재 로그만으로 자원 소유자와 최초 잘못된 lifecycle event를 특정할 수 없다.
- `LP_NUM_THREADS=1`이어도 `llvmpipe-0` worker thread 하나는 존재한다. 해당 변수는 병렬도를 줄일 뿐 driver thread를 없애지 않는다.
- current suppression은 `Memcheck:Leak` 두 항목뿐이므로 `Memcheck:Addr4` 오류를 억제하지 않는다.
- open PR #4772는 report를 shard별로 거르고 두 `Addr4` suppression을 제안하지만 current `main`에는 아직 없으며, mutex 규칙의 첫 `...`는 pthread와 Gallium frame 사이를 넓게 허용한다.
- current command는 `--error-exitcode`를 설정하지 않았고 script는 parsed error count가 아니라 Valgrind process의 nonzero exit만 최종 실패로 전파한다.
- ASan job은 project source를 sanitizer로 build하지만 issue stack에 나타난 prebuilt/system shared library의 instrumentation 여부는 보장하지 않는다.

### 추론과 판단

- **가장 유력한 위치:** stack과 thread 이름으로 보면 Mesa llvmpipe worker의 종료·동기화 경로에서 진단이 발생했을 가능성이 높다. 그러나 host가 device/context를 너무 일찍 해제해 driver의 잘못된 순서를 촉발했을 가능성도 남아 있으므로 “Mesa false positive” 또는 “upstream bug”로 확정할 근거는 아직 없다.
- **병렬화의 역할:** 새 shard가 두 image test를 별도 process에 배치하면서 engine 초기화·종료 시점과 runner 부하가 바뀌었다. 이는 재현 조건일 수 있으나, 병렬화 자체가 120-byte object를 잘못 해제했다는 직접 증거는 아니다.
- **suppression 적합 조건:** symbol 또는 standalone 재현으로 동일 context가 특정 Mesa build 내부에 국한되고 project의 destruction order를 바꿔도 유지됨을 확인하면 system dependency suppression은 합리적이다. 그 전의 broad suppression은 조사 중인 defect를 “효과 없는 report”로 선결론 내린다.
- **범위 설계:** `obj:*libgallium*` 한 줄만으로 모든 invalid access를 가리는 규칙은 위험하다. `Addr4`, 최상단 pthread operation, 연속된 driver frame을 함께 매치하고, 필요 최소한의 `...`만 써야 unrelated Gallium 오류가 통과하지 않는다.
- **CI 계약:** 알려진 context를 정확히 suppress한 뒤 `--error-exitcode`를 켜야 “이 진단만 제외하고 새 오류는 실패”라는 계약이 성립한다. 현재처럼 comment만 남기면 같은 오류가 반복 이슈를 만들 수 있고, 전혀 다른 unsuppressed error도 green job으로 끝날 수 있다.

## 구현 방향

1. issue와 같은 runner image, wgpu-native `v29.0.1.1`, Mesa package, Valgrind 3.22.0을 기록하고 `wg_image_rotate` shard를 여러 번 단독 실행한다. `--gen-suppressions=all --error-limit=no -s`를 추가해 6개 context별 generated suppression과 사용 횟수를 보존한다.
2. Mesa debug symbol을 사용할 수 있는 재현 환경에서 같은 stack을 다시 얻는다. symbol 설치가 어렵다면 ThorVG 없이 wgpu-native의 GLES backend로 device/context를 만들고 image upload·draw·submit·poll·drop만 수행하는 최소 program을 작성해 동일한 pthread/libgallium context가 발생하는지 확인한다.
3. project-side 종료 순서를 점검한다. canvas `sync`, canvas destruction, WebGPU instance/device/queue/context release, `Initializer::term()` 순서를 trace하고, 명시적인 device poll/wait 또는 scope 변경으로 오류가 사라지는지 비교한다. lifecycle 수정으로 해결되면 suppression 대신 그 수정과 regression test를 선택한다.
4. 외부 dependency context로 귀속되면 generated suppression을 출발점으로 `Memcheck:Addr4` 규칙을 만든다. read/write는 같은 `Addr4` 종류지만 최상단 `pthread_cond_broadcast`와 `pthread_mutex_unlock` call chain이 다르면 별도 규칙으로 유지한다. open PR #4772의 mutex 규칙처럼 첫 driver frame 전에 `...`를 두지 말고, 관찰된 pthread frame 바로 다음에 Gallium object frame이 오도록 고정한다. version이 포함된 절대 경로 대신 필요한 범위의 object wildcard를 쓰되 driver frame 수와 pthread frame을 함께 제한한다.
5. suppression 이름에 backend, operation, 조사한 dependency 범위와 이유가 드러나게 하고 바로 위 comment에 재현 환경과 upstream/minimal-repro 근거를 남긴다. 나중에 Mesa/wgpu-native version을 올릴 때 삭제 가능성을 재평가할 수 있어야 한다.
6. Valgrind 공통 command에 nonzero `--error-exitcode`를 추가한다. 알려진 error는 suppression 후 error count와 exit code에서 제외되고, 다른 unsuppressed error나 test 실패는 해당 shard의 nonzero status로 전체 job을 실패시키게 한다.
7. PR comment는 실패한 경우의 진단으로 제한하고, `-s` 또는 verbose summary로 실제 사용된 suppression 이름·횟수는 Actions log에 남긴다. suppression이 더 이상 사용되지 않으면 dependency update 후 제거 후보로 감지할 수 있다.
8. CI 변경을 작게 유지한다. suppression과 fail-closed exit policy를 한 PR에서 검증하되 unrelated test shard 재편은 분리해, 결과가 바뀌면 suppression match와 process partition 중 어느 쪽이 원인인지 추적할 수 있게 한다.

## 초심자 시작 가이드

1. `memcheck_valgrind.sh`에서 세 번째 `run_shard`의 filter를 그대로 복사해 local에서 한 process만 실행한다. 먼저 기존 command의 log와 exit code를 각각 저장한다.
2. 같은 command에 `--gen-suppressions=all --error-limit=no -s`를 더하고, 9회 발생과 6개 context의 관계를 표로 정리한다. read/write 문구 수가 아니라 generated suppression의 call context를 기준으로 중복을 판단한다.
3. 공식 문서의 `Memcheck:Addr4`, `fun:`, `obj:`, `...` 의미를 확인한다. 기존 파일의 `Memcheck:Leak` 규칙을 복사해 종류만 바꾸지 않는다.
4. generated 규칙을 임시 suppression 파일에 넣어 같은 test를 다시 실행한다. error가 0이 되고 `used_suppression`에 예상 이름과 횟수가 나타나는지 확인한다.
5. 규칙을 하나씩 넓히거나 줄여 최소 match를 찾는다. 다른 WG shard에 의도적인 invalid access test를 잠시 추가해 그 error는 suppression되지 않고 nonzero exit가 되는지 확인한다.
6. 환경 matrix 결과와 project lifecycle 실험을 maintainer에게 공유하고, 외부 dependency 귀속에 동의가 생긴 뒤 저장소 suppression 파일을 수정한다.

## 위험/검증

- issue와 동일한 dependency 조합에서 문제 shard를 최소 5회 실행해 발생 횟수와 context가 안정적인지 확인한다.
- 네 shard를 동시에 실행했을 때와 문제 shard만 실행했을 때를 비교해 runner contention 또는 process timing 의존성을 기록한다.
- Mesa의 현재 package, 한 단계 이전/이후 version, 가능한 실제 GPU driver에서 같은 최소 재현을 실행해 llvmpipe 특정 여부를 확인한다.
- wgpu-native version을 바꾸지 않은 실험과 바꾼 실험을 분리해 어느 dependency가 결과를 바꿨는지 보존한다.
- symbol이 있는 stack 또는 standalone reproduction 없이 shared-object 이름만으로 upstream defect를 확정하지 않는다.
- suppression 적용 후 문제 context는 0 unsuppressed error가 되고 예상 `used_suppression` 횟수만 증가하는지 확인한다.
- CPU, GL, 다른 WG shard에 발생시킨 별도 `Addr4` 오류는 suppression되지 않는 음성 test를 수행한다.
- `--error-exitcode`가 test assertion 실패와 unsuppressed Memcheck error를 모두 nonzero로 전파하고, suppressed-only run은 성공하는지 세 경우를 검증한다.
- suppression object wildcard가 runner의 library 경로 차이는 견디되 다른 Gallium call chain 전체를 가리지 않는지 generated context와 비교한다.
- ASan/UBSan job을 계속 실행하고, 그 성공을 prebuilt/system library의 무결성 증명으로 해석하지 않는다.
- runner image 또는 Mesa/wgpu-native update 후 suppression 사용 횟수가 0이면 규칙 제거와 원인 해결 여부를 다시 검토한다.
- final PR의 log가 반복 자동 comment를 만들지 않으면서도 새 오류의 full context를 artifact나 step summary에 남기는지 확인한다.
