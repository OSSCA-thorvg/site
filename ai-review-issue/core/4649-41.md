- 실현 가능성: **높음** — audio layer의 intrinsic volume은 이미 하나의 builder 경로에서 resolver 값으로 계산된다. 여기에 기본값 1.0의 master 상태와 명시적인 변경 통지를 더하면 되며 decoder나 platform audio backend를 새로 만들 필요는 없다.

## 이슈 요약

이슈는 `LottieAnimation::volume(float value)`를 추가해 animation에 포함된 media asset 전체의 재생 음량을 한 번에 조절하자고 제안한다. 각 asset의 고유 음량은 유지하고 resolver에 전달할 최종 음량만 `animationVolume × mediaVolume`으로 계산한다. 1.0은 원래 음량, 0.0은 mute, 1.0 초과는 증폭이며 권장 범위는 0.0~2.0이다.

ThorVG가 Lottie audio를 직접 재생하는 구조는 아니다. application이 등록한 resolver callback에 source, 활성 상태, offset, volume을 전달하고 실제 재생은 application의 audio engine이 담당한다. 따라서 이 기능의 핵심은 backend mixer 제어가 아니라 모든 audio callback에 일관된 master gain을 반영하고, gain만 바뀐 경우에도 application이 새 값을 받을 수 있게 하는 것이다.

## main 코드 조사

current main의 공개 [`LottieAnimation`](https://github.com/thorvg/thorvg/blob/61c3e744c0a02244d7e38e019e4c9c4a24719b20/src/loaders/lottie/thorvg_lottie.h#L44-L254)은 marker, tween, quality, audio resolver API를 제공하지만 master volume 상태나 setter는 없다. [`LottieAudioResolver::volume`](https://github.com/thorvg/thorvg/blob/61c3e744c0a02244d7e38e019e4c9c4a24719b20/src/loaders/lottie/thorvg_lottie.h#L32-L42)은 현재 0~100 범위의 layer volume이라고 문서화되어 있다.

[`LottieParser`](https://github.com/thorvg/thorvg/blob/61c3e744c0a02244d7e38e019e4c9c4a24719b20/src/loaders/lottie/tvgLottieParser.cpp#L988-L1000)는 audio layer의 `lv` property를 읽고, [`AudioControl`](https://github.com/thorvg/thorvg/blob/61c3e744c0a02244d7e38e019e4c9c4a24719b20/src/loaders/lottie/tvgLottieModel.h#L1120-L1147)은 기본 intrinsic volume 100, 직전 volume -1, 직전 active 상태를 layer별로 보관한다. Lottie specification도 audio settings의 `lv`를 layer level property로 정의한다.

실제 callback 값은 [`LottieBuilder::updateAudio()`](https://github.com/thorvg/thorvg/blob/61c3e744c0a02244d7e38e019e4c9c4a24719b20/src/loaders/lottie/tvgLottieBuilder.cpp#L1717-L1737) 한 곳에서 만들어진다.

```cpp
auto active = frameNo >= layer->inFrame && frameNo < layer->outFrame;
auto volume = active ? ctrl->volume(frameNo, tween, exps) : 100.0f;

if ((active != ctrl->prevActive) ||
    (active && !tvg::equal(volume, ctrl->prevVolume))) {
    LottieAudioResolver info = {
        src.data, src.mimeType, src.size, offset, volume, active, (src.size > 0)
    };
    audioResolver.func(info, audioResolver.data);
}
```

즉 현재 resolver volume은 animation master 값 없이 `lv` 평가 결과만 전달되고, callback 발생 여부도 같은 값과 `prevVolume`을 비교해 정한다. master를 저장하고 반환값만 곱해도 기본 frame 진행 중에는 동작할 수 있지만, 비교 대상을 intrinsic 값으로 그대로 두면 `volume(0.5f)`만 호출했을 때 callback이 발생하지 않는다. 비교·cache는 최종 effective volume 또는 master 변경 revision을 기준으로 해야 한다.

같은 frame 재통지는 별도 고려가 필요하다. [`LottieLoader::frame()`](https://github.com/thorvg/thorvg/blob/61c3e744c0a02244d7e38e019e4c9c4a24719b20/src/loaders/lottie/tvgLottieLoader.cpp#L378-L399)은 현재 frame과 차이가 0.0009 이하이면 update를 생략한다. 따라서 setter가 상태만 기록하고 사용자가 현재 frame을 다시 설정하도록 요구하면 resolver가 새 volume을 못 받을 수 있다. setter가 audio update를 예약하거나 audio cache를 무효화하고 현재 composition update를 명시적으로 요청해야 한다.

[`LottieAnimation::quality()`와 `resolver()`](https://github.com/thorvg/thorvg/blob/61c3e744c0a02244d7e38e019e4c9c4a24719b20/src/loaders/lottie/tvgLottieAnimation.cpp#L125-L140)은 `FETCH_LOADER`로 load된 Lottie loader를 찾고, 없으면 `InsufficientCondition`을 반환한다. 새 setter가 이 패턴을 따르면 load 전 호출의 결과도 자연스럽게 정해진다. 다만 이슈 자체는 load 전 값을 예약할지 명시하지 않았으므로 API 계약으로 확정해야 한다.

C API는 [`tvg_lottie_animation_set_quality()`와 audio resolver 등록 함수](https://github.com/thorvg/thorvg/blob/61c3e744c0a02244d7e38e019e4c9c4a24719b20/src/bindings/capi/thorvg_capi.h#L3247-L3328)를 C++ API와 나란히 노출하고, [`tvgCapi.cpp`](https://github.com/thorvg/thorvg/blob/61c3e744c0a02244d7e38e019e4c9c4a24719b20/src/bindings/capi/tvgCapi.cpp#L1311-L1335)가 결과와 resolver payload를 bridge한다. 이슈의 signature는 C++만 제시하지만 프로젝트의 기존 surface를 보면 C API 제공 여부도 범위 결정이 필요하다.

현재 [`Lottie Audio Layer` test](https://github.com/thorvg/thorvg/blob/61c3e744c0a02244d7e38e019e4c9c4a24719b20/test/testLottie.cpp#L358-L415)는 load 전 resolver 실패, 기본 volume 100, 활성/비활성 전환, seek와 resolver 해제를 확인한다. master mute·감쇠·증폭이나 동일 frame에서 volume만 변경한 callback은 고정하지 않는다.

## 원인 분석

### 확인된 사실

- 공개 `LottieAnimation`과 `LottieLoader`에는 animation-wide volume 상태나 setter가 없다.
- audio layer의 `lv`는 `LottieFloat`로 parsing되며 기본값은 100이다.
- active layer의 resolver volume은 `updateAudio()`에서 intrinsic `lv` 평가값을 그대로 사용한다.
- callback change detection은 layer별 `prevVolume`과 `prevActive`에만 의존한다.
- 같은 frame을 다시 설정하는 것만으로는 loader update가 예약되지 않는다.
- current C API는 Lottie quality와 audio resolver를 노출하지만 master volume 함수는 없다.
- 기존 Lottie audio test는 기본 100과 timeline 상태 변경만 검증한다.

### 추론과 판단

- **최종 단위:** resolver의 기존 단위가 0~100이고 master는 1.0 기준 배수이므로, 자연스러운 계산은 `effective = intrinsicPercent × masterGain`이다. 50% layer와 master 0.5는 resolver에 25를 전달한다.
- **clamp 판단:** 이슈가 1.0 초과 증폭을 명시하므로 기존 0~100에 다시 clamp하면 요구와 충돌한다. 0~2가 단지 권장 범위인지 hard limit인지는 문구만으로 확정할 수 없다.
- **invalid input 판단:** 음수, NaN, infinity를 허용하면 의미 없는 volume 또는 매 frame callback을 만들 수 있다. 최소한 finite·non-negative 계약을 정하고 문서·test·C API에 동일하게 적용하는 편이 안전하다.
- **통지 판단:** master 변경은 frame이 움직이지 않아도 audio playback state 변화다. active layer마다 변경된 effective volume을 한 번 통지하고, 같은 값을 다시 설정했을 때는 중복 callback을 만들지 않는 동작이 가장 예측 가능하다.
- **cache 판단:** `prevVolume`에 effective 값을 저장하거나, builder의 master revision과 layer의 last-seen revision을 비교하면 animated intrinsic volume과 master 변경을 모두 감지할 수 있다. intrinsic 값과 effective 값을 섞어 cache하면 이후 frame 비교가 잘못된다.
- **대상 범위:** current main에서 volume payload를 갖는 Lottie media 경로는 audio layer resolver다. 이슈의 “all media assets”가 향후 video asset까지 뜻하는지는 확인되지 않았으므로, 이번 구현은 현재 audio layer 전체로 범위를 명시하는 것이 안전하다.
- **C API 판단:** C++ 전용 실험 API로 시작할 수도 있지만 기존 Lottie extension 기능은 C surface가 대응한다. C API를 제외한다면 의도적인 제한임을 PR에서 설명해야 한다.

## 구현 방향

1. `LottieAnimation::volume(float value) noexcept`의 유효 입력, load 전 결과, 동일 값 재설정과 적용 시점을 먼저 API 문서로 확정한다. amplification을 보존하고 음수·NaN·infinity 정책을 명시한다.
2. loader 또는 builder에 기본값 `1.0f`인 master gain을 둔다. composition의 `lv` property는 수정하지 말고 원본 animation data와 분리한다.
3. `updateAudio()`에서 active layer의 intrinsic volume을 평가한 뒤 master gain을 곱해 resolver payload를 만든다. change detection과 `prevVolume`도 같은 effective 단위를 사용한다.
4. setter가 값을 바꾸면 active audio layer가 현재 frame에서 다시 평가되도록 audio state를 invalidation하고 update를 예약한다. 일반 frame의 “차이가 너무 작으면 skip” 경로에 의존하지 않는다.
5. master 값이 실제로 달라졌을 때만 callback을 발생시킨다. resolver가 없을 때 설정한 값도 저장해 두고, 이후 resolver와 frame update가 같은 master를 사용하게 한다.
6. public C API parity를 채택한다면 header, implementation, null animation, loader 미지원 build의 결과를 기존 Lottie 함수 패턴과 맞춘다.
7. 기존 audio fixture에 고정·animated `lv`와 두 개 이상의 audio layer case를 추가해 master가 각 layer 고유 값을 덮어쓰지 않고 곱한다는 계약을 검증한다.

## 초심자 시작 가이드

1. 먼저 기존 `audio_layer.json`과 resolver test에서 기본 master 1.0이 volume 100을 그대로 내보내는 것을 baseline으로 고정한다.
2. public API를 추가하기 전에 `LottieBuilder`에 master field를 두고 `updateAudio()`의 최종 값만 0.5배로 만드는 작은 실험을 한다.
3. test fixture의 `lv`를 40으로 바꿔 master 0.5에서 20, master 2.0에서 80이 전달되는지 확인한다. master 값으로 50이나 200을 직접 전달하지 않도록 단위를 구분한다.
4. 같은 frame에서 `volume(0.0f)`을 호출하고 resolver가 mute 값을 정확히 한 번 받는 test를 먼저 실패시킨 뒤 cache invalidation을 구현한다.
5. 동일 master를 두 번 설정했을 때 callback count가 늘지 않는지, 다음 frame에서 animated `lv` 변화는 계속 감지되는지 확인한다.
6. 마지막에 C API wrapper와 negative/NaN/infinity case를 추가하고 Lottie loader 비활성 build도 compile한다.

첫 PR은 seek, playback rate, per-layer override 같은 별도 audio control을 섞지 않는 편이 좋다. master gain, resolver payload, 상태 통지와 대응 test에 범위를 제한하면 review가 쉽다.

## 위험/검증

- 기본 master 1.0에서 기존 resolver volume과 callback 횟수가 바뀌지 않는지 확인한다.
- master 0.0, 0.5, 1.0, 2.0과 허용한다면 2.0 초과 값을 검증한다.
- intrinsic `lv`가 100이 아닌 layer와 animated `lv`에서 매 frame `intrinsic × master`가 적용되는지 확인한다.
- 두 개 이상 audio layer가 서로 다른 intrinsic volume을 유지한 채 같은 master를 적용받는지 확인한다.
- 같은 frame에서 master만 변경해도 active layer resolver가 한 번 호출되는지 확인한다.
- 같은 master를 반복 설정하거나 inactive layer만 있을 때 불필요한 callback이 늘지 않는지 확인한다.
- active→inactive callback에서 source 식별자와 offset의 기존 계약이 유지되는지 확인한다.
- resolver 등록 전 설정, resolver 해제 후 설정, 다시 등록한 뒤 frame 갱신의 결과를 확인한다.
- load 전 setter, null C handle, Lottie loader 미지원 build의 `Result`가 문서와 일치하는지 확인한다.
- 음수, NaN, infinity 입력이 상태를 오염시키지 않고 합의한 오류를 반환하는지 확인한다.
- amplification 때문에 resolver의 기존 “[0, 100]” 문서가 더는 항상 참이 아니라면 C++·C 문서를 함께 수정한다.
- C++ 및 C API test, Lottie 전체 test, ASan/UBSan과 thread-enabled build를 실행한다.
