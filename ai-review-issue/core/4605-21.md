## 이슈 요약

`@font-face` 블록의 마지막 `src` 선언 뒤에 세미콜론이 없으면 SVG 로더가 충돌한다. CSS 블록 끝은 마지막 선언을 닫을 수 있으므로 이 입력은 안전하게 처리되어야 한다. 현재 parser는 다음 세미콜론을 찾지 못해 `nullptr`을 받은 뒤에도 그 포인터에 1을 더하고 다시 검색한다.

2026-07-28 현재 [수정 PR #4609](https://github.com/thorvg/thorvg/pull/4609)가 열려 있다. 이 변경은 최초 세미콜론 포인터가 유효할 때만 `src`의 추가 세미콜론 검색을 수행하고, 제보된 SVG를 그림 로드 테스트에 추가한다. 아직 `main`에는 병합되지 않았다.

## main 코드 조사

[`xmlParseW3CAttribute()`](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/loaders/svg/tvgXmlParser.cpp#L424-L470)는 버퍼에서 `:`를 `sep`, `;`를 `next`로 찾는다. `src` 속성에는 URL 또는 data URL 안의 세미콜론이 있을 수 있어, `src`가 첫 구분자보다 앞이면 두 번째 세미콜론을 찾으려는 특례가 있다.

문제 입력에는 마지막 세미콜론이 없으므로 [`strchr(buf, ';')`가 `nullptr`을 반환](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/loaders/svg/tvgXmlParser.cpp#L437-L444)한다. 그러나 현재 조건은 `src < sep`만 검사하고 `next`를 검사하지 않은 채 `next + 1`을 계산한다. null 포인터에 대한 산술은 정의되지 않으며, 분기 결과에 따라 유효하지 않은 주소로 `strchr()`를 호출할 수 있다.

뒤쪽 코드는 [`sep != nullptr && next == nullptr`](https://github.com/thorvg/thorvg/blob/7d82829d7acf93cf417cc12347b8b768d30b700f/src/loaders/svg/tvgXmlParser.cpp#L447-L468)인 경우 버퍼 끝까지를 값으로 복사하는 경로를 이미 갖고 있다. 따라서 앞의 `src` 특례가 null 포인터를 건드리지 않으면 마지막 무세미콜론 선언을 처리할 수 있는 구조다.

W3C [CSS Syntax Module Level 3의 오류 복구 설명](https://www.w3.org/TR/css-syntax-3/#error-handling)은 선언 목록을 해석할 때 세미콜론 또는 블록 끝까지 이동하며, 문서가 열린 구문 중 끝나면 자동으로 닫는다고 설명한다. 마지막 선언 뒤 세미콜론이 없다는 이유로 메모리 안전성 오류가 발생해서는 안 된다.

[열린 수정 PR의 패치](https://github.com/thorvg/thorvg/pull/4609/files)는 조건을 `if (next && src < sep)`로 좁히고, 문제의 `@font-face`가 포함된 SVG를 `Picture::load()`가 성공하는 회귀 테스트로 추가한다. 이 분석 시점의 `main`에는 해당 guard와 테스트가 없다.

## 원인 분석

### 확인된 사실

- `strchr()`는 세미콜론이 없으면 `nullptr`을 반환한다.
- 현재 `src` 특례는 `next`의 null 여부를 검사하기 전에 `next + 1`을 계산한다.
- 같은 함수의 일반 경로는 `next == nullptr`일 때 버퍼 끝을 선언 값의 끝으로 처리할 수 있다.
- 최소 재현 SVG는 마지막 `src` 선언에 세미콜론이 없고, 현재 이슈는 showstopper로 분류되어 있다.
- 열린 PR #4609는 null guard와 회귀 테스트를 추가하지만 아직 `main`에 반영되지 않았다.

### 추론과 판단

- 직접적인 충돌 원인은 CSS 문법의 유효성 논쟁이 아니라, nullable 검색 결과를 유효한 포인터로 가정한 것이다.
- `next`를 확인하는 국소 guard는 기존의 `src` 내부 추가 세미콜론 검색을 그대로 유지하므로 가장 작은 안전한 수정이다.
- 테스트가 단순히 “충돌하지 않음”만 보는 것보다 `load()` 결과와 후속 선언 처리까지 확인하면 parser가 조용히 속성을 잃는 회귀도 더 잘 잡을 수 있다.
- 이 함수는 `strchr()`처럼 버퍼 길이를 모르는 검색을 사용하므로 장기적으로는 bounded search가 더 안전하지만, 이번 수정 범위를 parser 전면 개편으로 넓힐 필요는 없다.

## 구현 방향

1. `src` 특례에 들어가기 전에 `next != nullptr`을 확인한다.
2. 세미콜론이 없으면 기존의 `next == nullptr` 경로가 버퍼 끝까지 값을 처리하도록 둔다.
3. 이슈의 최소 SVG를 그림 로드 회귀 테스트로 추가하고 `Picture::load()`가 `Success`를 반환하는지 확인한다.
4. 같은 parser가 처리하는 다음 경우를 표 기반 테스트로 보강한다.
   - 마지막 선언에 세미콜론 없음
   - 마지막 선언에 세미콜론 있음
   - `src` 뒤에 다른 선언이 있음
   - `src` 값 내부에 세미콜론이 있음
5. 열린 PR #4609의 guard와 fixture를 기준으로 검토하되, 입력 끝과 포인터 비교가 모두 동일 버퍼 범위 안에서만 일어나는지 확인한다.

## 초심자 시작 가이드

먼저 아래 네 값이 각각 무엇을 가리키는지 종이에 적는다.

- `buf`: 현재 선언 시작
- `end`: 속성 버퍼 끝
- `sep`: 첫 `:`
- `next`: 첫 `;` 또는 `nullptr`

최소 재현에서 `next == nullptr`임을 debugger나 작은 단위 테스트로 확인한다. 수정 후에는 세미콜론 한 글자만 추가한 대조 입력도 함께 실행한다. guard를 추가하는 데서 끝내지 말고 ASan/UBSan 빌드로 기존 null 포인터 산술이 더 이상 실행되지 않는지 확인한다.

## 위험/검증

- 제보된 최소 SVG가 충돌 없이 로드되는지 확인한다.
- 같은 `@font-face`에 마지막 세미콜론을 추가해 기존 정상 경로가 유지되는지 확인한다.
- `font-family`, `src`, 추가 descriptor가 연속된 경우 각 key/value가 올바르게 분리되는지 검사한다.
- data URL이나 URL 문자열 안의 세미콜론을 선언 구분자로 오인하지 않는지 확인한다.
- `src:`의 값이 비었거나 `:` 또는 `;` 자체가 없는 비정상 입력도 안전하게 종료되는지 검사한다.
- Linux의 ASan/UBSan과 Windows/MSVC에서 회귀 fixture를 실행한다.
- 외부 폰트를 찾지 못하더라도 crash가 아니라 기존 fallback/오류 결과로 이어지는지 확인한다.
