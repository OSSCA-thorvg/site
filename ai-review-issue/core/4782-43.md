## 이슈 요약

제보된 SVG는 `M4 4`로 시작한 뒤 상대 cubic command `c25 218 200 50 0 0` 하나를 그린다. 상대 좌표를 절대 좌표로 풀면 시작점 `P0=(4,4)`, 제어점 `P1=(29,222)`, `P2=(204,54)`, 끝점 `P3=(4,4)`이다. 시작점과 끝점은 같지만 두 제어점은 크게 떨어져 있으므로 점이나 길이 0 선분이 아니라 꽃잎 모양의 닫힌 cubic이다.

예를 들어 cubic 식에 `t=0.5`를 대입하면 곡선 위 점은 `(88.375, 104.5)`가 된다. 이는 시작점 `(4,4)`와 명백히 다르다. 따라서 `P0 == P3`만으로 segment 전체를 퇴화했다고 판정할 수 없다. SVG 2도 cubic을 현재 점, 끝점, 두 제어점으로 정의하며, fill은 open subpath에도 암묵적인 close를 적용한다. 재현 path는 `Z`가 없어도 기본 검정 fill로 내부가 그려져야 한다.

제보자는 충분히 큰 꽃잎이 사라지며 zoom에 따라 성공·실패가 달라질 수 있다고 설명한다. current main은 GPU path 최적화에서 변환된 시작점과 끝점이 0.25 pixel 이내이면 제어점을 검사하지 않고 cubic을 제거한다. 정확히 같은 끝점인 최소 재현은 이 조건을 항상 만족하며, 거의 같은 끝점을 가진 다른 자산은 transform과 zoom에 따라 같은 tolerance 안팎을 오갈 수 있다.

## main 코드 조사

SVG parser의 [`_processCommand()`](https://github.com/thorvg/thorvg/blob/e4cd269838750c21bf28093eb68a899eca435874/src/loaders/svg/tvgSvgPath.cpp#L221-L270)는 소문자 `c`의 여섯 좌표를 현재 점에 더한 뒤 첫 제어점, 둘째 제어점과 끝점을 그대로 `out.cubicTo()`에 전달한다. 재현 입력은 이 단계에서 `(29,222)`, `(204,54)`, `(4,4)`로 정상 변환되며, 시작점과 끝점이 같다는 이유로 제거되지 않는다.

[`RenderPath::cubicTo()`](https://github.com/thorvg/thorvg/blob/e4cd269838750c21bf28093eb68a899eca435874/src/renderer/tvgRender.h#L288-L306)도 두 제어점과 끝점 세 개를 저장하고 `PathCommand::CubicTo`를 추가한다. 즉 loader와 공통 path 표현은 곡선 정보를 모두 보존한다.

문제가 드러나는 곳은 공통 GPU 전처리인 [`gpuOptimize()`의 cubic 처리](https://github.com/thorvg/thorvg/blob/e4cd269838750c21bf28093eb68a899eca435874/src/renderer/gpu_engine/tvgGpuCommon.cpp#L279-L316)다. 함수는 먼저 두 제어점과 끝점을 device space로 변환하고 thin-path tracker에는 닫힌 cubic의 제어점을 전달한다. 그러나 실제 출력 path를 만들 때는 `tvg::closed(startOutT, endT, PATH_OPT_PX_TOLERANCE)`가 참이면 즉시 반환한다. 이 분기에는 제어점 검사, `out.cubicTo()`, `subpathHasSegment = true`가 없다.

허용 오차는 같은 파일에서 [`PATH_OPT_PX_TOLERANCE = 0.25f`](https://github.com/thorvg/thorvg/blob/e4cd269838750c21bf28093eb68a899eca435874/src/renderer/gpu_engine/tvgGpuCommon.cpp#L28-L37)로 고정되어 있다. 비교가 transform 이후 좌표에 적용되므로 끝점이 정확히 같지 않은 자산도 scale에 따라 0.25px 안에 들어오거나 밖으로 나갈 수 있다. 이는 제보된 zoom 의존성과 일치하는 코드 근거다.

[`gpuOptimize()`의 command loop와 결과 판정](https://github.com/thorvg/thorvg/blob/e4cd269838750c21bf28093eb68a899eca435874/src/renderer/gpu_engine/tvgGpuCommon.cpp#L318-L383)을 보면 cubic 호출 뒤 입력 포인터만 세 점 전진한다. 최소 재현의 출력에는 사실상 `MoveTo`와 `Close`만 남고, 조기 반환 때문에 drawable segment 수도 증가하지 않는다. 따라서 thin-fill fallback도 활성화되지 않으며, 이후 fill tessellation에 전달할 곡선이 사라진다.

이 전처리는 특정 GPU backend에만 국한되지 않는다. GL의 [`GlGeometry::updatePath()`와 fill tessellation](https://github.com/thorvg/thorvg/blob/e4cd269838750c21bf28093eb68a899eca435874/src/renderer/gpu_engine/gl/tvgGlGeometry.cpp#L116-L165)은 `gpuOptimize()` 결과인 `optPath`를 `BWTessellator`에 넘긴다. WebGPU의 [`WgRenderData::updateShape()` 경로](https://github.com/thorvg/thorvg/blob/e4cd269838750c21bf28093eb68a899eca435874/src/renderer/gpu_engine/wg/tvgWgRenderData.cpp#L134-L183)도 같은 optimizer를 거쳐 `WgBWTessellator`를 호출한다. 공통 단계에서 삭제된 cubic은 어느 tessellator에도 도달하지 않는다.

반면 downstream의 공통 [`Bezier::flatten()`과 `Bezier::segments()`](https://github.com/thorvg/thorvg/blob/e4cd269838750c21bf28093eb68a899eca435874/src/common/tvgMath.cpp#L386-L421)는 시작점과 끝점만 보지 않는다. 두 제어점으로부터 deviation을 계산하고 tolerance를 만족할 때까지 curve를 반으로 나누므로, 같은 끝점을 가진 비퇴화 cubic도 subdivision할 수 있다. GL의 [`BWTessellator` cubic 처리](https://github.com/thorvg/thorvg/blob/e4cd269838750c21bf28093eb68a899eca435874/src/renderer/gpu_engine/gl/tvgGlTessellator.cpp#L443-L508)와 WebGPU의 [동일 처리](https://github.com/thorvg/thorvg/blob/e4cd269838750c21bf28093eb68a899eca435874/src/renderer/gpu_engine/wg/tvgWgTessellator.cpp#L430-L498)는 이 segment 수만큼 점을 샘플링한다. optimizer가 곡선을 보존하면 기존 tessellation 경로를 재사용할 수 있다.

Software rasterizer의 [`_cubicTo()`](https://github.com/thorvg/thorvg/blob/e4cd269838750c21bf28093eb68a899eca435874/src/renderer/cpu_engine/tvgSwRle.cpp#L623-L689)는 endpoint chord 길이뿐 아니라 두 control-point vector의 cross product와 dot product를 검사해 subdivision 여부를 정한다. `P0 == P3`이면 chord 길이와 cross product는 0이지만, 제어점이 끝점과 다르면 dot product 조건이 양수가 되어 curve를 분할한다. 이 코드는 GPU optimizer처럼 같은 끝점만으로 곡선을 즉시 버리지 않는다.

현재 public shape API test는 [`cubicTo()`가 같은 끝점을 포함한 입력을 받아들이는지](https://github.com/thorvg/thorvg/blob/e4cd269838750c21bf28093eb68a899eca435874/test/testShape.cpp#L43-L60)는 확인하지만 render pixel은 검사하지 않는다. GL과 WebGPU engine test의 cubic도 각각 [시작점과 다른 끝점](https://github.com/thorvg/thorvg/blob/e4cd269838750c21bf28093eb68a899eca435874/test/testGlEngine.cpp#L94-L135), [시작점과 다른 끝점](https://github.com/thorvg/thorvg/blob/e4cd269838750c21bf28093eb68a899eca435874/test/testWgEngine.cpp#L94-L134)을 사용하고 draw/sync 성공만 확인한다. 이 때문에 명령은 성공하지만 fill이 비는 회귀를 잡지 못한다.

## 원인 분석

### 확인된 사실

- SVG의 상대 cubic은 current parser에서 절대 좌표로 올바르게 변환되고 두 제어점과 끝점이 `RenderPath`에 모두 저장된다.
- 재현 cubic은 `P0=P3`이지만 `P1`, `P2`가 다르며, `t=0.5`의 곡선 점도 시작점과 다르다.
- 공통 GPU optimizer는 변환된 시작점과 끝점이 0.25px 이내이면 제어점과 무관하게 `processCubicTo()`에서 반환한다.
- 이 반환은 출력 path에 `CubicTo`를 추가하지 않고 drawable segment도 표시하지 않는다.
- GL과 WebGPU shape 경로 모두 fill tessellation 전에 이 공통 optimizer를 호출한다.
- downstream GPU subdivision은 제어점을 포함한 flatness를 사용하므로 같은 끝점만으로 segment 수를 0으로 만들지 않는다.
- Software RLE의 cubic subdivision도 제어점의 이탈을 검사하며 동일한 endpoint 조건만으로 curve를 삭제하지 않는다.
- 기존 API test는 입력 수락만, GPU engine test는 서로 다른 endpoint의 cubic에 대한 실행 성공만 확인한다.

### 추론과 판단

- **근본 원인:** line segment의 중복 endpoint 제거 규칙을 cubic segment에도 적용하면서, cubic의 geometry를 결정하는 두 제어점을 고려하지 않은 것이 핵심이다. `start ≈ end`는 chord가 짧다는 뜻이지 curve 자체가 짧거나 면적이 없다는 뜻이 아니다.
- **영향 backend:** 코드상 직접 영향은 공통 optimizer를 사용하는 GL과 WebGPU다. Software 경로는 같은 조기 반환을 사용하지 않으므로 최소 재현을 그릴 가능성이 높다. 다만 backend별 실제 pixel 결과는 수정 전 test로 확정해야 한다.
- **zoom 의존성:** exact `P0=P3`인 최소 예시는 모든 scale에서 조기 반환 조건을 만족한다. 다른 꽃잎들이 zoom에 따라 달라지는 현상은 device-space 0.25px tolerance가 near-equal endpoint를 분류하는 방식으로 설명된다. 이는 코드와 제보를 연결한 추론이며, 해당 자산 좌표를 확보해 경계값을 측정해야 확정된다.
- **thin tracker와 출력 path의 불일치:** optimizer는 닫힌 cubic의 control points를 thin tracker에 기억시키지만 실제 curve는 출력하지 않는다. 분석용 상태가 geometry 보존을 대신할 수 없으며, 최소 재현에서는 tracker도 ready 상태가 되지 않아 fallback이 생성되지 않는다.
- **단순한 조기 반환 삭제는 위험:** 바로 아래 `validateCubic()`은 `end-start` 길이의 역수를 계산한다. endpoint가 같으면 0으로 나누게 되므로, 조기 반환만 지우고 기존 일반 분기로 흘려보내면 새로운 NaN/Inf 문제가 생길 수 있다.
- **안전한 구분 기준:** endpoint가 같더라도 어느 제어점이 start에서 의미 있게 떨어져 있으면 cubic을 보존해야 한다. endpoint와 두 제어점이 모두 tolerance 안에 있는 경우만 실제 no-op 후보로 취급하는 방식이 현재 optimizer의 목적과 가장 잘 맞는다. 정확한 tolerance 정책은 subpixel loop의 fill 보존 요구와 함께 test로 결정해야 한다.

## 구현 방향

1. `processCubicTo()`의 closed-endpoint 처리를 일반 chord 기반 `validateCubic()`보다 앞선 명시적 분기로 유지한다. endpoint chord가 0인 상태로 길이의 역수를 계산하지 않는다.
2. `startOutT ≈ endT`일 때 두 transformed control point도 start와 가까운지 검사한다. 세 점이 모두 같은 위치로 축약되는 진짜 퇴화 cubic만 생략하고, control point가 떨어진 loop cubic은 출력 path에 보존한다.
3. 보존 분기에서는 `out.cubicTo(ctrl1T, ctrl2T, endT)`, stroke용 `localOut->cubicTo(...)`, `lastOutT`, `subpathHasSegment`를 일반 cubic 분기와 같은 계약으로 갱신한다. 중복 코드를 작은 helper로 묶으면 두 분기의 상태 갱신이 다시 어긋날 위험을 줄일 수 있다.
4. 기존 `trackClosedCubic()` 호출은 geometry 출력 여부와 독립적으로 검토한다. loop가 실제로 thin하지 않다면 tracker가 정상적으로 candidate를 해제하거나 최종 `thin=false`가 되는지 unit test로 고정한다.
5. 공통 optimizer test를 추가해 `MoveTo → closed-endpoint CubicTo → Close` 입력의 출력 command와 세 점이 보존되는지 확인한다. 모든 control/end point가 같은 cubic은 계속 제거되는지도 짝 test로 둔다.
6. 이슈 SVG 또는 동일한 public `Shape`를 GL과 WebGPU canvas에 그려 non-transparent pixel 수가 0보다 큰지 확인한다. 가능하면 Software 결과의 bounds/coverage와 비교하되 backend별 antialias 차이 때문에 전체 bitmap 완전 일치만 요구하지 않는다.
7. scale을 0.001배부터 수 배까지 바꾸고, endpoint 차이를 0, 0.24px, 0.25px, 0.26px로 만든 case를 검사해 tolerance 경계에서 큰 control excursion이 삭제되지 않는지 확인한다.

첫 수정은 공통 optimizer의 closed cubic 판정과 직접 회귀 test에 집중하는 편이 좋다. tessellator의 subdivision 방식은 이미 control point를 고려하므로, 재현이 optimizer 수정만으로 해소된다면 backend별 tessellator 변경은 범위에서 제외할 수 있다.

## 초심자 시작 가이드

1. 재현 SVG를 Viewer에서 Software, GL, WebGPU backend로 각각 열고 같은 zoom에서 screenshot과 non-transparent pixel 수를 기록한다. backend 선택 결과를 이슈 설명과 분리해 남긴다.
2. SVG parser 직후 `RenderPath`를 확인해 command가 `MoveTo, CubicTo`이고 점이 `(4,4), (29,222), (204,54), (4,4)`인지 검증한다.
3. `gpuOptimize()` 전후의 command 수를 출력해 입력 `CubicTo`가 출력에서 사라지는지 확인한다. 임시 로그는 test를 만든 뒤 제거한다.
4. `processCubicTo()`의 조기 반환 직전에 `startOutT`, `ctrl1T`, `ctrl2T`, `endT`와 `closed()` 결과를 기록한다. endpoint만 같고 controls는 멀다는 사실을 실행으로 확인한다.
5. closed-endpoint special case에서 실제 no-op과 loop를 분리하고, 이슈 SVG가 `out.cubicTo()`까지 도달하는지 확인한다. 조기 반환만 제거해 `validateCubic()`의 0 길이 chord 분기로 보내지 않는다.
6. GL과 WebGPU에서 여러 zoom을 반복하고, SVG 대신 동일 좌표의 `Shape::cubicTo()`도 그려 loader와 renderer 책임을 분리한다.

## 위험/검증

- 최소 SVG를 GL·WebGPU에서 render해 수정 전에는 fill pixel이 없고 수정 후에는 안정적으로 존재하는지 확인한다.
- 동일 좌표를 `Shape::moveTo()`와 `Shape::cubicTo()`로 구성해 SVG loader를 거치지 않아도 같은 결과인지 확인한다.
- Software backend 결과를 기준으로 bounds, 대략적인 채워진 영역과 winding 방향을 비교한다.
- exact same endpoint와 0.24/0.25/0.26px 차이의 near-equal endpoint를 여러 scale에서 검사한다.
- 두 control point가 모두 start와 같은 진짜 퇴화 cubic은 계속 mesh와 pixel을 만들지 않는지 확인한다.
- control point 하나만 떨어진 cusp, 두 controls가 반대편에 있는 loop, self-intersecting cubic도 과도하게 생략되지 않는지 확인한다.
- open subpath의 기본 fill, 명시적 `Close`, `nonzero`와 `evenodd` fill-rule 조합을 검사한다.
- solid fill, gradient, alpha, clip, mask와 composite에서 optimized path가 올바르게 전달되는지 확인한다.
- fill이 없는 stroke-only shape에서 local path가 보존되고 line cap/join과 dash 결과가 바뀌지 않는지 확인한다.
- 매우 작은 scale에서 subpixel loop를 무조건 큰 fill로 만들지 않고 기존 thin-fill 정책과 일관되는지 확인한다.
- translation, rotation, non-uniform scale과 음수 scale 후 device-space tolerance 판정이 안정적인지 확인한다.
- sanitizer와 GL·WebGPU test suite를 실행해 0 길이 chord에 의한 division-by-zero, NaN과 빈 index buffer가 생기지 않는지 확인한다.
- 대표 SVG asset으로 optimizer의 output command 수와 GPU tessellation 비용을 비교해 진짜 no-op 제거 성능을 보존하는지 기록한다.
