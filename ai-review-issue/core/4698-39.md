## 이슈 요약

Windows 11의 MSYS2 CLANG64 환경에서 `meson setup build -Db_sanitize=address` 후 `ninja -C build`를 실행하면 shared library 링크가 실패한다. 제보된 진단은 프로젝트의 `operator new(std::size_t)`와 `operator delete(void*)`가 AddressSanitizer runtime import archive의 동일 심볼과 중복된다고 가리킨다. `undefined` sanitizer만 켠 build는 실패하지 않는다고 한다.

이는 sanitizer 플래그 자체가 컴파일되지 않는 문제가 아니다. 최종 DLL을 링크하는 시점에 프로젝트와 AddressSanitizer runtime이 process-wide C++ 할당 연산자를 각각 제공하면서 강한 심볼 두 개가 경쟁하는 문제다. 현재 코드는 scalar뿐 아니라 array `new[]/delete[]`도 무조건 정의하므로, 보고된 두 scalar 심볼만 예외 처리하면 같은 유형의 잠재 충돌이 남는다.

## main 코드 조사

프로젝트는 [`tvgInitializer.cpp`](https://github.com/thorvg/thorvg/blob/35488343f2bc2a9d56ac86b58bec6c7443312812/src/renderer/tvgInitializer.cpp#L136-L157)에서 전역 scalar `new/delete`와 array `new[]/delete[]` 네 개를 조건 없이 정의한다. scalar 두 함수는 [`tvgCommon.h`](https://github.com/thorvg/thorvg/blob/35488343f2bc2a9d56ac86b58bec6c7443312812/src/common/tvgCommon.h#L66-L67)에도 전역 선언되어 있다. 이슈의 linker 진단이 가리킨 줄은 이 정의와 정확히 일치한다.

각 연산자는 [`tvgAllocator.h`](https://github.com/thorvg/thorvg/blob/35488343f2bc2a9d56ac86b58bec6c7443312812/src/common/tvgAllocator.h#L29-L54)의 wrapper를 호출한다. 주석은 allocator customization을 위한 분리를 설명하지만 current main의 구현은 `std::malloc`, `std::calloc`, `std::realloc`, `std::free`로 바로 위임한다. 따라서 sanitizer build에서 프로젝트의 전역 override를 생략하더라도 별도의 allocator 상태를 잃는 구조는 현재 보이지 않는다. 다만 public ABI와 외부 consumer의 allocation 경계는 실행 검증이 필요하다.

root [`meson.build`](https://github.com/thorvg/thorvg/blob/35488343f2bc2a9d56ac86b58bec6c7443312812/meson.build#L1-L16)는 `b_sanitize=none`을 기본값으로 두고 `config_h`를 만든다. 이 설정 데이터는 이후 [`config.h`로 생성된다](https://github.com/thorvg/thorvg/blob/35488343f2bc2a9d56ac86b58bec6c7443312812/meson.build#L170-L176). 즉 `get_option('b_sanitize')`에서 address 포함 여부를 계산해 C++ 조건부 컴파일 macro로 전달할 기존 통로가 있다.

[`src/meson.build`](https://github.com/thorvg/thorvg/blob/35488343f2bc2a9d56ac86b58bec6c7443312812/src/meson.build#L18-L53)는 clang-cl과 그 밖의 non-MSVC compiler 모두 `b_sanitize == 'none'`일 때만 exception, RTTI, stack protector와 unwind 관련 옵션을 끈다. sanitizer가 켜지면 이 최적화 옵션을 생략하지만, 전역 할당 연산자 정의를 제어하는 조건은 없다. 이어지는 [`library()` 선언](https://github.com/thorvg/thorvg/blob/35488343f2bc2a9d56ac86b58bec6c7443312812/src/meson.build#L70-L80)이 sanitizer 옵션이 적용된 shared library의 최종 링크 지점이다.

LLVM compiler-rt의 current source는 [`asan_new_delete.cpp`의 Windows 분기](https://github.com/llvm/llvm-project/blob/2678a67b21a455c336a9cd42b5ce72483ac56f9b/compiler-rt/lib/asan/asan_new_delete.cpp#L21-L50)에서 C++ scalar와 array allocation/deallocation 심볼을 export한다. 이 Windows 분기에서는 다른 플랫폼에 적용되는 weak interceptor attribute가 비어 있다. 같은 파일은 실제 [`operator new/new[]`](https://github.com/llvm/llvm-project/blob/2678a67b21a455c336a9cd42b5ce72483ac56f9b/compiler-rt/lib/asan/asan_new_delete.cpp#L107-L120)와 [`operator delete/delete[]`](https://github.com/llvm/llvm-project/blob/2678a67b21a455c336a9cd42b5ce72483ac56f9b/compiler-rt/lib/asan/asan_new_delete.cpp#L174-L180)를 구현한다. Clang 문서도 AddressSanitizer runtime이 최종 executable 또는 shared library link에 포함된다고 설명한다.

현재 CI에는 Ubuntu에서 `-Db_sanitize="address,undefined"`로 build하고 검사 script를 실행하는 [memcheck job](https://github.com/thorvg/thorvg/blob/35488343f2bc2a9d56ac86b58bec6c7443312812/.github/workflows/build_ubuntu.yml#L91-L100)과 같은 조합으로 도구를 만드는 [SVG regression job](https://github.com/thorvg/thorvg/blob/35488343f2bc2a9d56ac86b58bec6c7443312812/.github/workflows/svg_regression.yml#L22-L25)이 있다. 하지만 Windows/MSYS2의 ASan DLL 링크를 고정하는 job은 current workflow에서 확인되지 않는다. Linux에서 runtime interceptor가 weak symbol을 쓰는 성공 사례만으로 Windows의 강한 심볼 충돌을 잡기 어렵다.

unit test executable은 [`test/meson.build`](https://github.com/thorvg/thorvg/blob/35488343f2bc2a9d56ac86b58bec6c7443312812/test/meson.build#L63-L70)에서 library를 링크하고 실행된다. 그러나 이번 실패는 unit test 실행 전 library link에서 발생하므로, MSYS2 sanitizer configuration 자체를 CI matrix에 넣지 않으면 기존 test가 아무리 많아도 회귀를 발견할 수 없다.

## 원인 분석

### 확인된 사실

- 프로젝트는 sanitizer 설정과 무관하게 전역 scalar·array `new/delete` 네 개를 정의한다.
- 이슈의 실제 linker 진단은 project object와 AddressSanitizer runtime archive가 scalar `new`와 `delete`를 중복 정의한다고 명시한다.
- LLVM의 Windows AddressSanitizer runtime도 scalar와 array 전역 할당·해제 연산자를 정의하고 export한다.
- current Meson 처리는 sanitizer build에서 일부 `-fno-*` 옵션을 빼지만 프로젝트의 전역 할당 연산자를 비활성화하지 않는다.
- `undefined`만 사용한 build는 제보상 성공한다. 이 설정에는 AddressSanitizer의 allocation interceptor runtime이 들어오지 않으므로 관찰 결과가 충돌 원인과 일치한다.
- Ubuntu ASan CI는 존재하지만 MSYS2/Windows ASan shared-library link coverage는 확인되지 않는다.

### 추론과 판단

- **근본 원인:** Windows AddressSanitizer build에서 runtime과 library가 동일한 replaceable allocation function의 강한 정의를 동시에 제공한다. 이는 일반적인 undefined symbol이나 link order 문제가 아니라 심볼 소유권 충돌이다.
- **배열 연산자:** 제보 로그에는 `new[]/delete[]` 중복이 나타나지 않았지만 LLVM runtime과 project 양쪽 모두 이를 정의한다. import archive에서 실제로 끌려온 심볼, 참조 여부 또는 진단 순서 차이일 수 있으므로 배열 연산자가 안전하다고 확정할 근거는 아니다. 네 개를 한 계약으로 다루어야 한다.
- **우선 수정 범위:** address sanitizer가 활성화된 build에서는 sanitizer runtime이 전역 할당 연산자를 소유하게 하고 project 선언·정의를 함께 제외하는 방식이 가장 직접적이다. Windows에만 제한하면 영향 범위는 작지만, 모든 ASan build에서 소유권을 일관되게 정하는 편이 플랫폼별 우연한 weak-symbol 동작에 덜 의존한다. 어느 범위를 택할지는 ABI test 결과로 결정할 수 있다.
- **option 판별:** `b_sanitize`는 `none`, 단일 값 또는 쉼표로 결합된 문자열이므로 `== 'address'`만 검사하면 현재 CI의 `address,undefined`를 놓친다. token 단위로 address 포함 여부를 계산해 generated config macro로 전달해야 한다.
- **피해야 할 해결:** `--allow-multiple-definition`이나 link order 변경은 어느 구현이 실제 allocation을 가로채는지 모호하게 하고 ASan의 alloc/dealloc mismatch 탐지까지 약화시킬 수 있다. 충돌을 숨기는 linker workaround는 적절하지 않다.
- **별도 경계:** ASan으로 instrument된 application이 ASan 없이 build된 shared library를 불러오는 조합은 이번 재현과 다르다. library가 process-wide 연산자를 export하는 현재 정책의 영향은 후속 ABI/consumer 검토로 분리하는 편이 좋다.

## 구현 방향

1. root Meson에서 `get_option('b_sanitize')`를 읽고 쉼표 단위 값에 `address`가 포함되는지 계산한다. 결과를 `config_h`의 의미가 명확한 macro로 기록한다.
2. `tvgCommon.h`의 scalar 선언과 `tvgInitializer.cpp`의 scalar·array 네 정의를 같은 macro로 감싼다. 선언과 정의의 조건이 어긋나지 않게 한다.
3. 우선 MSYS2 CLANG64 shared build에서 ASan runtime이 네 연산자를 제공하도록 한다. 모든 플랫폼의 ASan build에 같은 규칙을 적용할지, Windows에만 적용할지는 Ubuntu/macOS와 static-link matrix 결과를 보고 정한다.
4. `b_sanitize=address`, `address,undefined`, `undefined`, `none`을 각각 configure한다. 앞의 두 값만 project override가 빠지고 나머지는 기존 ABI와 symbol export를 유지하는지 확인한다.
5. MSYS2 CLANG64 CI에서 shared library와 unit test executable을 link·run한다. 가능하면 static library consumer도 추가해 runtime 중복과 unresolved symbol이 모두 없는지 확인한다.
6. 작은 allocation test에서 scalar `new/delete`, array `new[]/delete[]`, aligned·sized delete가 사용되는 compiler 경로를 실행한다. 별도 test에서는 use-after-free, heap overflow, alloc/dealloc mismatch를 의도적으로 발생시켜 ASan이 계속 진단하는지 확인한다.
7. build artifact의 symbol/import table을 기록해 ASan build에서는 runtime이, normal build에서는 project가 의도한 연산자를 제공하는지 검증한다.

첫 PR은 sanitizer option의 config 전달, 네 기본 연산자의 일관된 guard, MSYS2 link regression에 집중하는 편이 좋다. allocation 정책 전체나 외부 application과의 mixed-instrumentation 계약은 별도 논의로 분리하면 수정의 검토 가능성을 유지할 수 있다.

## 초심자 시작 가이드

1. 이슈와 같은 MSYS2 CLANG64 shell에서 clean build directory를 만들고 `b_sanitize=address`로 configure한 뒤 실패한 link command를 `ninja -v`로 저장한다.
2. `llvm-nm`, `objdump` 또는 MSYS2 환경의 동등한 도구로 project object와 ASan import archive에서 `operator new/delete` 관련 심볼을 각각 확인한다.
3. 임시로 네 project 정의를 모두 제외해 shared library가 link되는지 확인한다. 두 scalar만 지워서 성공하더라도 array allocation을 실제로 호출하는 작은 consumer를 추가해 잠재 충돌을 확인한다.
4. Meson에서 `b_sanitize` 값을 출력해 `address`와 `address,undefined`가 어떻게 전달되는지 확인하고, generated `config.h`에 두 경우 모두 같은 macro가 생기는 test를 만든다.
5. normal build와 UBSan-only build에서 project 심볼이 그대로 남는지 비교한다. 수정이 비-ASan ABI를 바꾸지 않았다는 최소 증거다.
6. ASan build의 test program에서 의도적인 heap 오류가 실제 보고되는지 확인한다. 단순히 link 성공만 보면 runtime interception이 약해진 잘못된 수정도 통과할 수 있다.

처음부터 linker flag를 바꾸기보다 두 구현이 어떤 심볼을 내보내는지 확인하고 소유자를 하나로 줄이면 원인과 수정 효과를 명확히 분리할 수 있다.

## 위험/검증

- MSYS2 CLANG64에서 clean `b_sanitize=address` shared build와 unit test link·run을 확인한다.
- `address,undefined` 조합도 같은 guard를 사용하고 두 sanitizer의 진단이 모두 활성화되는지 확인한다.
- `b_sanitize=undefined`와 `none`에서는 기존 project 전역 연산자와 normal build 결과가 유지되는지 확인한다.
- scalar `new/delete`와 array `new[]/delete[]`를 모두 호출해 link 결과와 runtime 동작을 검사한다.
- compiler가 sized delete 또는 aligned allocation overload를 선택하는 C++ 표준·최적화 조합을 확인하고, 필요한 overload 계약이 누락되지 않았는지 점검한다.
- shared와 static library를 각각 작은 consumer에 링크해 duplicate와 unresolved symbol이 없는지 확인한다.
- ASan이 heap overflow, use-after-free, double free, alloc/dealloc mismatch를 실제로 보고하는지 negative test로 검증한다.
- artifact의 export/import symbol을 수정 전후 비교해 ASan build의 allocation owner가 하나인지 확인한다.
- normal Windows DLL을 사용하는 기존 application에서 library 경계를 넘는 allocation/deallocation이 깨지지 않는지 확인한다.
- Ubuntu의 기존 `address,undefined` memcheck 및 SVG regression과 전체 unit test를 실행해 cross-platform 회귀를 확인한다.
- Meson configure test 또는 CI log에서 `address`, `address,undefined`, `undefined`, `none`의 macro 결과를 고정한다.
- sanitizer가 켜진 executable과 꺼진 library, 반대 조합의 지원 정책을 문서화하고 지원한다면 별도 consumer test를 추가한다.
