## 이슈 요약

제보자는 제공된 Lottie JSON을 `thorvg.example/Animation -r 300x300`으로 재생하면 animation 중 Text(LTE)가 일부만 표시된다고 보고했다. 현상은 CPU engine에서만 관찰되며, issue 본문은 partial rendering 기능의 활성화 여부와 관계없이 발생한다고 명시한다. 따라서 손상 영역만 잘못 계산하는 문제로 한정하면 안 되고, CPU render data가 프레임 변경 뒤 실제로 어떤 내용으로 준비되는지도 조사해야 한다.

이 issue가 생성되기 약 두 시간 전 animation frame 변경이 전체 renderer data를 무효화하던 `All` 대신 새 `Children` flag를 사용하도록 바뀌었다. 변경 목적은 Lottie 내부 child paint를 순회하되 변하지 않은 image data까지 다시 올리지 않는 것이다. 시간적 인접성, animation update 경로와 CPU 전용 증상이 일치하므로 가장 먼저 이 commit 전후를 bisect할 가치가 높다. 다만 issue에는 원인 commit이 명시되지 않았으므로 실제 재현·bisect 전까지는 강한 추론이지 확정 사실은 아니다.

## main 코드 조사

[`Animation::frame()`](https://github.com/thorvg/thorvg/blob/2a5bed5e21d2ef6d83c10bc3c8580660e70ea894/src/renderer/tvgAnimation.cpp#L36-L49)은 loader가 새 frame을 받아들이면 animation picture에 `RenderUpdateFlag::Children`을 표시한다. Lottie의 slot apply/delete와 tween도 [같은 `Children` 표시를 사용한다](https://github.com/thorvg/thorvg/blob/2a5bed5e21d2ef6d83c10bc3c8580660e70ea894/src/loaders/lottie/tvgLottieAnimation.cpp#L40-L101). 이 동작은 [`renderer: optimize animation updates` 변경](https://github.com/thorvg/thorvg/commit/4a089b8b3bc576c147846b7efc4f174fea7e15a6)에서 기존 `All`을 교체하며 도입됐다.

현재 [`RenderUpdateFlag`](https://github.com/thorvg/thorvg/blob/2a5bed5e21d2ef6d83c10bc3c8580660e70ea894/src/renderer/tvgRender.h#L43-L59)는 path, color, gradient, stroke, transform, image, clip처럼 leaf renderer가 실제로 소비하는 bit들과 `Children`을 같은 bitmask에 둔다. `Children`의 주석은 child paint로 update를 강제 전파하기 위한 flag라고 설명하지만, leaf 준비 단계에서 제거해야 하는지 또는 새 leaf에 어떤 초기화 flag를 보충해야 하는지는 enum 자체에 표현되지 않는다.

vector picture의 [`PictureImpl::update()`](https://github.com/thorvg/thorvg/blob/2a5bed5e21d2ef6d83c10bc3c8580660e70ea894/src/renderer/tvgPicture.h#L63-L96)는 전달받은 flag로 내부 vector paint를 갱신한다. animation loader의 `load()`는 property가 본질적으로 갱신된다는 이유로 vector animation에 별도 update flag를 반환하지 않으며, [bitmap의 새 frame에만 `Image`를 반환한다](https://github.com/thorvg/thorvg/blob/2a5bed5e21d2ef6d83c10bc3c8580660e70ea894/src/renderer/tvgPicture.h#L239-L270). 따라서 Lottie vector subtree 진입 시 공통으로 보장되는 parent flag는 `Children`이다.

[`Paint::Impl::update()`](https://github.com/thorvg/thorvg/blob/2a5bed5e21d2ef6d83c10bc3c8580660e70ea894/src/renderer/tvgPaint.cpp#L198-L269)는 parent flag와 paint 자신의 `renderFlag`를 OR해 skip 여부와 type별 update에 전달한다. [`SceneImpl::update()`](https://github.com/thorvg/thorvg/blob/2a5bed5e21d2ef6d83c10bc3c8580660e70ea894/src/renderer/tvgScene.h#L81-L127)는 그 flag를 모든 child paint에 그대로 전달한다. 즉 `Children`은 순회를 여는 데 그치지 않고 shape/image 준비 함수까지 도달할 수 있다.

CPU renderer의 [`prepareCommon()`](https://github.com/thorvg/thorvg/blob/2a5bed5e21d2ef6d83c10bc3c8580660e70ea894/src/renderer/cpu_engine/tvgSwRenderer.cpp#L825-L855)은 flag가 0이 아니면 task를 scheduler에 요청하고, 준비 직전에 `valid`를 false로 바꾼다. 그러나 [`SwShapeTask::run()`](https://github.com/thorvg/thorvg/blob/2a5bed5e21d2ef6d83c10bc3c8580660e70ea894/src/renderer/cpu_engine/tvgSwRenderer.cpp#L128-L179)은 geometry를 만드는 조건에서 `Path | Transform | Clip`, fill을 만드는 조건에서 `Color | Gradient | Transform`만 검사한다. `Children` 자체는 어느 조건에도 포함되지 않는다. 새 CPU shape task가 leaf 고유 flag 없이 `Children`만 받는다면 task는 실행되지만 path RLE와 fill data를 만들 근거가 없는 상태가 된다. 기존 task에서도 `Children`은 실제 geometry 변경 종류를 설명하지 못한다.

텍스트 경로는 이 최초 준비 계약에 민감하다. Lottie의 URL font 경로는 [매 frame 새 `Text` paint를 생성하고 layer scene에 추가한다](https://github.com/thorvg/thorvg/blob/2a5bed5e21d2ef6d83c10bc3c8580660e70ea894/src/loaders/lottie/tvgLottieBuilder.cpp#L988-L1048). local font 경로도 [glyph별 pooled shape와 중첩 scene을 조립한다](https://github.com/thorvg/thorvg/blob/2a5bed5e21d2ef6d83c10bc3c8580660e70ea894/src/loaders/lottie/tvgLottieBuilder.cpp#L1251-L1336). [`TextImpl::update()`](https://github.com/thorvg/thorvg/blob/2a5bed5e21d2ef6d83c10bc3c8580660e70ea894/src/renderer/tvgText.h#L178-L201)은 font outline을 내부 Shape로 만든 뒤 parent flag를 그 shape에 전달한다. 따라서 재사용 paint와 새 paint, Text와 내부 Shape 각각의 own flag가 언제 설정·소비되는지 확인해야 한다.

partial rendering은 CPU의 [`preRender()`](https://github.com/thorvg/thorvg/blob/2a5bed5e21d2ef6d83c10bc3c8580660e70ea894/src/renderer/cpu_engine/tvgSwRenderer.cpp#L318-L335)에서 dirty region만 clear하고, shape render는 [full draw가 아니면 dirty region과 교차하는 영역만 다시 그린다](https://github.com/thorvg/thorvg/blob/2a5bed5e21d2ef6d83c10bc3c8580660e70ea894/src/renderer/cpu_engine/tvgSwRenderer.cpp#L431-L486). 하지만 issue가 partial rendering off에서도 재현된다고 명시하므로 dirty rectangle 누락만으로는 설명이 부족하다. CPU task의 geometry/fill 준비 여부를 먼저 검증하고, dirty region은 별도의 동반 회귀 가능성으로 다뤄야 한다.

현재 [`testAnimation.cpp`](https://github.com/thorvg/thorvg/blob/2a5bed5e21d2ef6d83c10bc3c8580660e70ea894/test/testAnimation.cpp#L75-L112)는 frame 이동과 frame count를 확인하지만 render pixel을 비교하지 않는다. [`testText.cpp`](https://github.com/thorvg/thorvg/blob/2a5bed5e21d2ef6d83c10bc3c8580660e70ea894/test/testText.cpp#L129-L153)의 기본 text test도 API 성공과 draw/sync 경로가 중심이다. animation frame을 바꾼 뒤 CPU buffer의 glyph coverage가 유지되는지, full rendering과 smart rendering이 같은 결과인지 고정하는 통합 regression test가 필요하다.

## 원인 분석

### 확인된 사실

- issue는 제공 asset에서 animation 중 Lottie text가 일부 표시되지 않으며 CPU engine에서만 관찰된다고 보고한다.
- issue 본문은 partial rendering 기능을 켜거나 꺼도 현상이 발생한다고 명시한다.
- issue 생성 직전 animation frame 갱신이 `All` 대신 새 `Children` flag를 사용하도록 바뀌었다.
- `Children`은 picture와 scene을 거쳐 child leaf의 update 인자까지 그대로 전파된다.
- CPU `prepareCommon()`은 `Children`만 있어도 task를 schedule하지만, CPU shape task의 path/fill/stroke 갱신 조건은 `Children` bit를 실제 data 변경 종류로 해석하지 않는다.
- Lottie text는 frame 갱신 중 새 Text paint를 만들거나 pooled glyph Shape와 Scene을 다시 조립할 수 있다.
- current animation/text test는 문제 asset의 frame별 CPU pixel 결과를 비교하지 않는다.

### 추론과 판단

- **가장 강한 회귀 가설:** `All`→`Children` 최적화 뒤 container traversal은 유지됐지만, 새로 나타나거나 재조립된 text leaf가 CPU render data를 처음 만드는 데 필요한 Path/Color/Transform 계열 flag를 충분히 받지 못한다. CPU는 `Children` task를 실행하면서도 geometry 종류를 알 수 없어 glyph 일부를 준비하지 못할 수 있다.
- **아직 확정되지 않은 부분:** 제공 JSON의 어느 frame, URL font와 local glyph 중 어느 경로, 어떤 leaf가 `Children`만 받는지는 실행 trace가 필요하다. commit 시점과 코드 구조만으로 특정 leaf를 단정하면 안 된다.
- **partial rendering 판단:** issue가 기능 off에서도 재현되므로 dirty region 계산은 근본 원인의 필요조건이 아니다. 다만 smart rendering 결과도 함께 비교해 old/new bounds 손상 누락이 추가로 없는지는 확인해야 한다.
- **단순 revert 위험:** `Children`을 다시 `All`로 돌리면 증상은 사라질 수 있지만, animation frame마다 변하지 않은 bitmap/image renderer data를 다시 준비하는 이전 성능 문제를 되살릴 수 있다. bisect 증명에는 유용하지만 최종 수정으로는 범위가 너무 넓다.
- **권장 계약:** `Children`은 subtree 순회를 여는 control flag로만 사용하고 leaf renderer에는 실제 property flag만 전달한다. 단, render data가 없는 새 leaf는 type별 최소 최초 준비 flag를 받아야 한다. “existing leaf의 변경 없음”과 “new leaf의 초기 준비”를 분리해야 한다.
- **backend 차이:** CPU만 관찰된다는 사실은 loader가 text를 만들지 못한 전역 문제보다 renderer별 flag 소비 차이를 의심하게 한다. 동일 frame의 scene tree와 own flags가 backend 사이에서 같은지 먼저 확인하면 loader와 CPU 책임을 빠르게 분리할 수 있다.

## 구현 방향

1. 제공 asset에서 첫 정상 frame과 첫 누락 frame을 찾고, 최적화 commit의 직전·직후 binary로 같은 frame을 render해 regression boundary를 확정한다.
2. `Animation::frame()`부터 Picture, Scene, Text, 내부 Shape와 CPU `prepareCommon()`까지 paint id/type, 새 render data 여부, parent flag, own flag와 최종 flag를 임시 trace한다. 누락 glyph가 `Children`만 받는지 확인한 뒤 trace는 제거한다.
3. update flag의 의미를 분리한다. `Children`은 container skip을 방지하고 subtree를 순회시키되 Shape/Image 같은 leaf의 renderer `prepare()`에는 그대로 전달하지 않는 방식을 우선 검토한다.
4. leaf에 기존 render data가 없으면 type별 최초 준비를 강제한다. Shape는 path·fill·stroke·transform·clip 상태를, bitmap은 `Image`를 준비해야 한다. 모든 type에 `All`을 주어 image upload 최적화를 무효화하지 않는다.
5. 기존 render data가 있는 leaf는 own `renderFlag`만으로 필요한 geometry/color/transform을 갱신한다. parent transform·opacity·clip 변화가 child에게 필요한 bit로 전환되는 현재 계약도 별도로 보존한다.
6. URL font의 frame별 새 Text와 local glyph pooling 경로를 모두 test한다. 문자열 일부가 등장·사라지는 keyframe, transform/opacity만 바뀌는 frame, outline·fill이 바뀌는 frame을 포함한다.
7. 제공 asset을 CPU full-render 기준으로 frame별 render하고, 수정 결과와 pixel buffer를 비교한다. SmartRender on 결과도 같은 기준과 일치시켜 partial damage의 동반 회귀를 배제한다.
8. embedded image가 있는 animation에서 unchanged frame의 image prepare/upload 횟수를 계측해 최적화 목적이 유지되는지 성능 회귀 test 또는 benchmark로 남긴다.

첫 PR은 update flag 계약 수정과 재현 가능한 최소 Lottie text pixel test에 집중하는 편이 좋다. loader text layout 개선이나 일반 dirty-region 최적화는 이번 회귀의 필수 조건으로 확인될 때만 포함한다.

## 초심자 시작 가이드

이 issue의 최종 수정은 renderer 상태 계약 때문에 초심자에게 쉽지 않지만, 재현과 trace 작업은 좋은 시작점이다.

1. 제공 JSON을 CPU engine 300×300으로 frame별 PNG 또는 raw buffer로 저장하고, 처음 글자가 누락되는 frame 번호를 기록한다.
2. 같은 frame을 `renderer: optimize animation updates` commit 직전과 직후에서 render해 결과 이미지를 비교한다. 직후에만 실패하면 회귀 commit을 실행 근거로 확정할 수 있다.
3. 누락 frame에서 각 Text/Shape의 최종 update flag를 16진수로 출력하고 `Children`, `Path`, `Color`, `Transform` 포함 여부와 render data가 새로 만들어졌는지를 함께 기록한다.
4. CPU `SwShapeTask::run()`에서 누락 glyph task의 `updateShape`와 `updateFill` 값을 확인한다. false라면 해당 task가 어느 parent에서 property flag를 잃었는지 호출 경로를 역추적한다.
5. 실험적으로 해당 새 leaf에만 최소 초기화 flag를 주고 text가 복구되는지 확인한다. 전체 picture를 `All`로 바꾸는 실험은 bisect 확인용으로만 사용한다.
6. 수정 뒤 동일 frame의 CPU full render, SmartRender와 가능한 GPU backend buffer를 비교하고 image 포함 animation의 prepare 횟수도 확인한다.

## 위험/검증

- issue asset의 모든 frame을 CPU engine 300×300으로 render하고 정상 기준과 pixel 단위로 비교한다.
- partial rendering 활성·비활성 결과가 동일하며 두 모드 모두 text를 완전히 표시하는지 확인한다.
- URL font Text와 Lottie에 내장된 local glyph Shape 경로를 각각 검사한다.
- 문자열 keyframe으로 glyph가 추가·삭제·교체되는 frame과 빈 문자열 전환을 검사한다.
- 새 render data를 가진 Shape가 path, solid/gradient fill, stroke와 transform을 최초 frame에 모두 준비하는지 확인한다.
- 기존 render data는 color-only, transform-only, opacity-only, clip-only 변경에서 필요한 부분만 갱신하는지 확인한다.
- glyph Scene의 pooling/reuse, frame skip, 역방향 seek, fractional frame과 segment/tween 경로에서도 동일한 결과인지 검사한다.
- CPU Default/SmartRender/Aliased option과 thread 수 0/1/다중에서 결과를 비교해 task scheduling race가 없는지 확인한다.
- GL과 WebGPU가 지원되는 환경에서는 같은 scene tree/frame의 시각 결과를 비교하되 backend별 허용 오차를 문서화한다.
- embedded bitmap이 변하지 않는 animation에서 frame별 image prepare/upload가 다시 발생하지 않는지 계측한다.
- image frame 자체가 바뀌는 animation은 `Image` flag로 정상 갱신되는지 확인한다.
- mask, matte, clip, group opacity와 effect 안의 text가 old/new bounds와 composition을 올바르게 갱신하는지 확인한다.
- 반복 frame 전환에서 stale CPU task, disposed render data, use-after-free가 없는지 ASan/TSan 가능한 구성으로 검사한다.
- Lottie loader, animation, text, SW engine 전체 test와 representative animation benchmark를 실행한다.
