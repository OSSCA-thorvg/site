## 이슈 요약

구조체 멤버 사이 또는 끝에 생기는 바이트 패딩을 빌드 중 찾아 메모리 사용량과 캐시 효율을 개선할 기회를 찾자는 제안이다. 방향 자체는 타당하지만 “패딩이 있으면 실패”로 바로 정의하면 안 된다. 자연 정렬을 지키기 위한 패딩, GPU 셰이더와 CPU 데이터의 배치를 맞추는 패딩, ABI를 보존하는 패딩은 제거 대상이 아닐 수 있다.

따라서 이 작업의 결과물은 단일 경고 플래그보다 다음 정책에 가깝다.

1. 지원되는 컴파일러에서 첫 번째 당사자 코드의 패딩 진단을 수집한다.
2. 결과를 의도적 정렬, 저위험 재배치 후보, 공개/외부 레이아웃 위험으로 분류한다.
3. 반복적으로 확인할 가치가 있는 대상만 CI 기준선이나 명시적 크기 계약으로 고정한다.

## main 코드 조사

최상위 [`meson.build`](https://github.com/thorvg/thorvg/blob/0bb8d8a78c9042bf721bca5b335ec37d7fd4cadd/meson.build#L1-L14)는 C++14와 `werror=false`를 기본으로 설정한다. 현재 패딩 진단을 켜는 프로젝트 옵션이나 전역 인자는 없다.

[`src/meson.build`](https://github.com/thorvg/thorvg/blob/0bb8d8a78c9042bf721bca5b335ec37d7fd4cadd/src/meson.build#L1-L54)는 `meson.get_compiler('cpp')`로 컴파일러를 구하고 `clang-cl`, MSVC 이외 컴파일러 등을 나눠 `compiler_flags`를 구성한다. 이 목록은 같은 파일의 [주 라이브러리 `cpp_args`](https://github.com/thorvg/thorvg/blob/0bb8d8a78c9042bf721bca5b335ec37d7fd4cadd/src/meson.build#L70-L80)에 전달된다. 즉, 진단 모드를 추가한다면 기존 컴파일러 분기와 플래그 전달 지점을 활용할 수 있다.

기존 [binary-size 워크플로](https://github.com/thorvg/thorvg/blob/0bb8d8a78c9042bf721bca5b335ec37d7fd4cadd/.github/workflows/binary_size.yml#L115-L147)는 행렬의 `c_args`와 `cpp_args`를 Meson 설정에 넘긴다. 프로덕션 기본 빌드를 바꾸기 전에 별도 CI 구성에서 패딩 경고를 수집하는 방식을 시험할 수 있다는 근거다.

현재 코드에는 제거하면 안 되는 명시적 패딩도 있다.

- GL drop-shadow 데이터의 [`dummy1`](https://github.com/thorvg/thorvg/blob/0bb8d8a78c9042bf721bca5b335ec37d7fd4cadd/src/renderer/gpu_engine/gl/tvgGlEffect.cpp#L105-L113)은 셰이더의 `std140` 블록 정렬을 맞추기 위한 두 개의 `float`다.
- WebGPU 셰이더 타입의 [`_padding`](https://github.com/thorvg/thorvg/blob/0bb8d8a78c9042bf721bca5b335ec37d7fd4cadd/src/renderer/gpu_engine/wg/tvgWgShaderTypes.h#L45-L49)과 [256바이트 크기 검사](https://github.com/thorvg/thorvg/blob/0bb8d8a78c9042bf721bca5b335ec37d7fd4cadd/src/renderer/gpu_engine/wg/tvgWgShaderTypes.h#L78-L91)는 uniform-buffer 정렬 계약을 코드로 표현한다.
- 번들된 Catch 헤더는 [`-Wpadded`를 명시적으로 억제](https://github.com/thorvg/thorvg/blob/0bb8d8a78c9042bf721bca5b335ec37d7fd4cadd/test/catch.hpp#L30-L48)한다. 진단을 테스트 전체에 전역 적용하면 프로젝트가 직접 관리하지 않는 코드의 소음도 함께 들어올 수 있다.

이슈가 언급한 [관련 변경](https://github.com/thorvg/thorvg/pull/4505)은 CPU 쪽 구조체가 40바이트인데 `std140` 셰이더 블록은 48바이트를 요구한 문제를 명시적 꼬리 패딩으로 해결했다. 이는 “일반 C++ 구조체의 불필요한 패딩을 줄이자”는 사례가 아니라, 서로 다른 레이아웃 규칙 사이에 **필요한 패딩이 빠졌던** 사례다. 따라서 해당 변경은 패딩 진단의 필요성을 뒷받침하는 동시에 자동 재배치의 위험도 보여 준다.

GCC의 [`-Wpadded`](https://gcc.gnu.org/onlinedocs/gcc/Warning-Options.html#index-Wpadded)는 멤버 또는 전체 구조체 정렬을 위해 패딩이 들어가면 경고하며, 경우에 따라 멤버 재배치로 크기를 줄일 수 있다고 설명한다. [Clang의 같은 진단](https://clang.llvm.org/docs/DiagnosticsReference.html#wpadded)은 멤버 정렬 및 구조체 끝 정렬에 추가된 바이트를 보고한다. MSVC의 [C4820](https://learn.microsoft.com/en-us/cpp/error-messages/compiler-warnings/compiler-warning-level-4-c4820?view=msvc-170)은 구조체 끝에 추가된 패딩을 보고하며 기본적으로 꺼져 있다. 세 진단의 범위와 메시지가 완전히 같지는 않으므로 하나의 보편적 결과로 취급할 수 없다.

Meson의 [`compiler.has_argument()`](https://mesonbuild.com/Reference-manual_returned_compiler.html#compilerhas_argument)은 컴파일러가 알 수 없는 플래그 경고 없이 인자를 받아들이는지 검사한다. 컴파일러 이름만 하드코딩하는 것보다 이 기능으로 각 진단 인자를 확인하고 추가하는 편이 이식성이 높다.

## 원인 분석

### 확인된 사실

- 현재 기본 빌드는 패딩 진단을 활성화하지 않는다.
- 빌드 파일에는 이미 컴파일러 종류별 플래그 구성과 라이브러리별 `cpp_args` 전달 지점이 있다.
- 주요 컴파일러는 구조체 패딩을 보고하는 진단을 제공하지만, MSVC C4820은 기본적으로 비활성화되어 있고 각 진단의 범위가 다르다.
- 렌더러에는 `std140` 및 WebGPU uniform-buffer 계약을 만족시키기 위한 명시적 패딩과 크기 검사가 존재한다.
- 번들 테스트 헤더는 자체적으로 `-Wpadded`를 억제한다.
- 관련 GPU 변경은 패딩을 줄인 것이 아니라 필요한 꼬리 패딩을 추가한 수정이다.

### 추론과 판단

- 전역 `-Werror`와 패딩 진단을 함께 켜면 의도적 배치 및 외부 헤더까지 실패시켜 유지하기 어려운 CI가 될 가능성이 높다.
- 실제 절감 효과는 “경고 개수”가 아니라 해당 타입의 인스턴스 수, 수명, 배열 사용, 캐시 접근 패턴에 좌우된다. 경고가 있다는 사실만으로 멤버 재배치의 우선순위를 정할 수 없다.
- 공개 구조체, 직렬화 데이터, 셰이더 전송 구조체는 크기 축소보다 호환성과 명시적 레이아웃이 우선일 수 있다.
- 초기 도입은 보고 전용 CI 또는 개발자 선택 옵션으로 결과를 수집하고, 합의된 새 회귀만 차단하는 기준선 방식이 가장 안전하다.

## 구현 방향

1. Meson에 기본값이 꺼진 개발자용 기능 옵션(예: `padding-diagnostics`)을 추가한다. 공개 릴리스의 기본 컴파일 플래그는 바꾸지 않는다.
2. C++ 컴파일러가 지원하는 인자를 `cc.has_argument()`로 확인한다.
   - GCC/Clang 계열: `-Wpadded`
   - MSVC 계열: C4820을 개별 활성화하는 옵션을 공식 문서와 실제 CI 도구 버전에서 확인
3. 진단 인자는 주 라이브러리의 첫 번째 당사자 소스에만 적용한다. 번들 Catch, 외부 로더, 시스템 헤더는 범위에서 제외한다.
4. 별도 CI 작업에서 GCC와 Clang 결과를 먼저 수집한다. 처음에는 경고 수와 타입 목록을 아티팩트 또는 로그로 남기되 빌드를 실패시키지 않는다.
5. 각 결과를 다음처럼 분류해 짧은 기준선을 만든다.
   - 의도적/필수 정렬: 근거 주석 또는 `static_assert` 유지
   - 내부 전용 재배치 후보: 크기 전후와 실제 인스턴스 규모를 측정
   - ABI·직렬화·GPU 계약 대상: 자동 수정 금지, 별도 검토
   - 외부 코드: 진단 범위에서 제외
6. 크기 변화가 실제로 의미 있는 내부 타입만 멤버 순서를 조정한다. 주요 레이아웃에는 `sizeof`, `alignof`, 필요 시 `offsetof` 검사를 추가한다.
7. 기준선이 안정된 뒤에만 “새로운 미분류 경고”를 CI 실패로 승격한다. 기존 경고 전체를 곧바로 오류로 만들지 않는다.

## 초심자 시작 가이드

작은 독립 실험으로 컴파일러가 어떤 패딩을 보고하는지 먼저 확인한다.

```cpp
struct Sample {
    char tag;
    int value;
    char enabled;
};
```

GCC 또는 Clang에서 `-Wpadded`로 컴파일한 뒤 멤버 순서를 바꾸며 `sizeof(Sample)`을 비교한다. 다음으로 ThorVG 전체를 고치려 하지 말고, Meson 옵션이 꺼졌을 때 기존 플래그가 전혀 달라지지 않는지부터 테스트한다.

첫 진단 결과에서는 타입별로 다음 질문을 적는다.

- 이 타입은 외부 ABI나 파일/네트워크 형식에 노출되는가?
- CPU 데이터가 GPU 버퍼에 그대로 복사되는가?
- 패딩이 명시적 정렬 계약인가?
- 실제로 많은 인스턴스가 동시에 존재하는가?
- 재배치 후 `sizeof` 감소가 모든 대상 플랫폼에서 유지되는가?

이 질문에 답하기 전에는 `#pragma pack`이나 `__attribute__((packed))`로 경고를 없애지 않는다. 비정렬 접근 비용이나 하드웨어 예외, ABI 변경을 만들 수 있다.

## 위험/검증

- 옵션이 기본적으로 꺼져 있고 기존 릴리스 빌드의 명령행이 변하지 않는지 확인한다.
- GCC·Clang·MSVC에서 지원되는 진단만 추가되며 알 수 없는 옵션 경고가 없는지 확인한다.
- 첫 번째 당사자 소스와 외부/번들 헤더의 진단 범위가 분리되는지 확인한다.
- 32비트와 64비트, Debug/Release, 주요 엔진 조합에서 결과를 비교한다.
- 후보 타입은 변경 전후 `sizeof`와 `alignof`를 기록하고, 배열 또는 대량 할당 시 실제 절감량을 계산한다.
- 공개 API, 직렬화, `memcpy`/해시 입력, FFI에 쓰이는 타입은 ABI 및 바이트 표현 회귀를 별도 검사한다.
- GL `std140`과 WebGPU uniform 타입은 셰이더 쪽 레이아웃, 바인딩 크기, 정적 크기 검사를 함께 유지한다.
- 렌더링 픽셀 테스트와 sanitizers를 실행해 재배치에 따른 동작 회귀가 없는지 확인한다.
- 기준선 파일을 도입한다면 타입명·컴파일러·플랫폼을 함께 기록하고, 새 경고만 명확하게 드러나는지 테스트한다.
