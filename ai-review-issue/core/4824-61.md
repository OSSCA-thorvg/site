- 실현 가능성: **높음** — 각 공식 action에는 Node.js 24 기반 후속 major가 있고 현재 사용 입력 대부분이 새 버전에도 존재한다. 유일하게 직접 후속 버전이 없는 Windows 설정 action도 Node.js 24를 사용하는 호환 목적의 fork가 있다. 다만 2026-09-23 강제 제거 전에 labeler 설정 변환과 Windows job을 포함한 전체 CI 실행을 끝내야 한다.

## 이슈 요약

GitHub는 Actions runner의 Node.js 20 런타임을 2026-09-23에 제거한다. 현재 저장소의 workflow는 이미 여러 JavaScript action을 Node.js 24로 강제 실행하면서 경고를 내고 있으며, 제거일 이후에는 Node.js 20만 선언한 action을 계속 사용할 수 없다.

표면적으로는 action의 major 버전을 올리는 작업이지만 실제 변경은 세 종류다. `checkout`, cache, artifact, `github-script`처럼 공식 Node.js 24 버전으로 올리는 항목, 설정 형식도 함께 바뀐 `labeler`, 그리고 Node.js 24 릴리스가 없는 `ilammy/msvc-dev-cmd`를 다른 action으로 교체하는 항목이다. 따라서 모든 pin을 일괄 치환하는 것만으로는 안전하게 완료되지 않는다.

## main 코드 조사

[분석한 main의 workflow 디렉터리](https://github.com/thorvg/thorvg/tree/c2ff5523da81d5219c9ef3505d48496056e41d78/.github/workflows)에는 이슈가 열거한 12개 workflow가 그대로 존재한다. 현재 pin은 다음 실행 경로에 분산되어 있다.

- [binary size 생성 workflow](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/.github/workflows/binary_size.yml#L73-L82)는 `checkout@v4`, `cache@v4`를 쓰고, [결과 업로드](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/.github/workflows/binary_size.yml#L184-L189)는 `upload-artifact@v4`를 쓴다.
- [binary size 보고 workflow](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/.github/workflows/binary_size_report.yml#L16-L26)는 이전 run의 여러 artifact를 `pattern`, `merge-multiple`, `run-id`, `github-token`으로 내려받고, [댓글 작성](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/.github/workflows/binary_size_report.yml#L84-L151)은 `github-script@v7`에서 `github.rest.*`와 `github.paginate()`를 사용한다.
- [Android workflow](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/.github/workflows/build_android.yml#L16-L40)는 `setup-ndk@v1.3.1`의 `ndk-version`, `local-cache`, `ndk-path` 출력에 의존한다. 동일 구조가 aarch64 job에도 반복된다.
- [iOS](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/.github/workflows/build_ios.yml), [macOS](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/.github/workflows/build_macos.yml), [Ubuntu](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/.github/workflows/build_ubuntu.yml)는 여러 job에서 `checkout@v4`와 `upload-artifact@v4`를 반복 사용한다.
- [Windows workflow](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/.github/workflows/build_windows.yml#L16-L52)는 두 job 모두 입력 없이 `ilammy/msvc-dev-cmd@v1`을 호출한 뒤 Meson/Ninja 빌드를 실행한다. 이 action의 현재 `v1`은 Node.js 20을 선언하며 Node.js 24 후속 릴리스가 없다.
- [pixel inspector workflow](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/.github/workflows/pixel_inspector.yml)는 checkout, Chrome 설정, artifact 업로드·다운로드를 조합한다. [후속 보고 workflow](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/.github/workflows/pixel_inspector_report.yml)는 다른 run의 artifact를 받아 `github-script@v7`으로 PR 댓글과 보고서 링크를 만든다.
- [release workflow](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/.github/workflows/release.yml#L7-L25)는 `path: thorvg`로 checkout하고 만들어진 `builddir/meson-dist/*.xz`를 `softprops/action-gh-release@v2`로 첨부한다.

공식 action의 후속 major는 Node.js 24를 사용한다. `checkout@v5`, `cache@v5`, `upload-artifact@v6`, `download-artifact@v7`, `github-script@v8`, `labeler@v6`가 해당한다. `cache@v5`, artifact v6/v7, `github-script@v8`, `labeler@v6`의 공식 문서는 self-hosted runner가 최소 `v2.327.1`이어야 한다고 명시한다. 현재 workflow의 `runs-on`은 GitHub-hosted label이어서 즉시 자체 runner 업그레이드가 필요하다는 증거는 없지만, 새 major의 공통 실행 전제는 기록해야 한다.

`github-script@v8`은 Octokit 호출을 `github.rest.*` namespace로 사용해야 한다. 두 보고 script는 이미 이 형태와 `github.paginate()`를 사용하므로 API namespace 마이그레이션은 필요하지 않다. 반면 artifact 다운로드는 다른 `workflow_run`의 `run-id`와 token, 여러 artifact 병합을 사용하므로 단순 step 성공뿐 아니라 결과 디렉터리와 후속 댓글까지 확인해야 한다.

가장 중요한 비기계적 변경은 labeler다. [현재 workflow](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/.github/workflows/pr_labeler.yml#L1-L11)는 `actions/labeler@v4`를 사용하고, [현재 규칙 파일](https://github.com/thorvg/thorvg/blob/c2ff5523da81d5219c9ef3505d48496056e41d78/.github/labeler.yml#L1-L45)은 label 아래에 glob 목록을 바로 두는 구형 형식이다. `labeler`의 v5/v6 문서는 설정 형식이 호환되지 않게 변경됐다고 명시한다. 각 label을 `changed-files`와 `any-glob-to-any-file` 같은 새 matcher로 옮기지 않고 action pin만 v6로 올리면 자동 라벨이 깨질 수 있다.

Windows 대안으로 제안된 [`TheMrMilchmann/setup-msvc-dev`](https://github.com/TheMrMilchmann/setup-msvc-dev)는 원래 action의 fork이며 `v4.1.0`에서 Node.js 24를 사용한다. 현재 workflow는 원래 action에 별도 입력을 넘기지 않으므로 YAML 치환은 작지만, 새 action이 설정한 compiler 경로와 environment가 두 기존 Meson job에서 같게 보이는지는 Windows runner에서 확인해야 한다.

## 원인 분석

### 확인된 사실

- GitHub의 공식 공지는 Node.js 20 runtime 제거일을 2026-09-23으로 안내하며, Node.js 24 기반 action 버전으로 갱신할 것을 요구한다.
- 분석한 main에는 이슈가 열거한 12개 workflow와 Node.js 20 기반 action pin이 그대로 있다.
- 공식 checkout, cache, artifact, github-script, labeler의 제시된 후속 major는 Node.js 24를 선언한다.
- 현재 두 `github-script` 본문은 이미 `github.rest.*` namespace를 사용한다.
- 현재 labeler rule은 v4 형식이며, v5에서 도입된 새 설정 형식과 호환되지 않는다.
- `ilammy/msvc-dev-cmd@v1`에는 Node.js 24 릴리스가 없고, 제안된 fork의 v4.1.0은 Node.js 24를 사용한다.
- 현재 Android workflow가 사용하는 `ndk-version`, `local-cache`, `ndk-path` 계약과 Chrome workflow의 `chrome-version` 입력은 제시된 새 버전에도 존재한다.

### 추론과 판단

- **근본 원인은 workflow 자체의 build 명령이 아니라 각 JavaScript action이 선언한 런타임이 플랫폼 지원 수명과 어긋난 것이다.** GitHub의 임시 강제 실행 덕분에 지금 성공하는 job도 제거일 이후의 호환성을 보장하지 않는다.
- 공식 action pin 교체만 검색·치환하면 labeler 설정 불일치가 남는다. 이 이슈의 완료 조건에는 `.github/labeler.yml`의 의미 보존 변환도 포함되어야 한다.
- Windows action 교체는 입력이 없어 코드 변경은 작지만, 서로 다른 저장소의 action으로 바뀌므로 compiler 탐색, `PATH`, `INCLUDE`, `LIB` 같은 환경 효과가 동일하다고 문서만으로 확정할 수 없다.
- artifact v4에서 v6, download v4에서 v7로의 전환은 Node.js runtime 외 major 변경도 건너뛴다. 현재 입력 이름은 지원되지만, 단일 artifact와 pattern 병합의 추출 경로가 기존 후속 script가 기대하는 트리와 같은지 실행 결과를 비교해야 한다.
- Node.js 20 강제 실행 opt-out 환경 변수는 제거일까지의 임시 완화일 뿐 해결책이 아니다. 적용하더라도 최종 PR의 구현 방향으로 삼아서는 안 된다.

## 구현 방향

1. 먼저 공식 action을 Node.js 24 기반 major로 올린다: `checkout@v5`, `cache@v5`, `upload-artifact@v6`, `download-artifact@v7`, `github-script@v8`, `labeler@v6`. 각 workflow에서 현재 `with` 입력, artifact 이름과 경로, 권한, `if` 조건은 의도적으로 그대로 둔다.
2. `nttld/setup-ndk`는 Node.js 24를 선언한 `v1.6.0` 이상, `browser-actions/setup-chrome`은 `v2`, `softprops/action-gh-release`는 `v3`으로 올린다. Android의 `ndk-path` 출력과 release의 `files` glob을 별도 회귀 항목으로 둔다.
3. `ilammy/msvc-dev-cmd@v1`을 `TheMrMilchmann/setup-msvc-dev@v4`로 교체한다. 현재처럼 기본 입력을 사용할 수 있는지 확인하고, 두 Windows job에서 Meson이 같은 MSVC toolchain을 감지하는지 로그로 비교한다.
4. `.github/labeler.yml`의 각 glob 목록을 v6 schema로 옮긴다. 기존 의미는 “목록 중 하나라도 변경되면 label 적용”이므로 각 label에 `changed-files` → `any-glob-to-any-file`을 사용하고, 현재 glob 문자열을 누락 없이 보존한다.
5. upgrade와 무관한 workflow 구조 개선이나 action pinning 정책 변경은 분리한다. 이번 PR은 런타임 호환과 필수 migration에 집중해야 실패 원인과 rollback 범위가 선명하다.
6. 저장소에 self-hosted runner가 추가될 가능성이 있다면 최소 runner `v2.327.1` 요구사항을 문서나 체크리스트에 남긴다. 현재 GitHub-hosted runner만 쓴다는 이유로 action의 runtime 전제를 숨기지 않는다.
7. 제거일 전 PR을 main과 동기화한 뒤 모든 변경 workflow를 실제로 한 번 이상 실행한다. 이벤트 때문에 자동 실행하기 어려운 labeler, `workflow_run`, release는 안전한 검증 절차를 별도로 마련한다.

## 초심자 시작 가이드

1. `rg 'uses:' .github/workflows` 결과를 표로 만들고, 같은 action이 여러 파일에 남지 않도록 old pin과 new pin을 각각 검색한다.
2. 공식 action부터 한 종류씩 교체한다. 각 변경 뒤 `with`의 입력 이름과 공식 새 버전 README를 대조한다.
3. labeler는 작은 fixture를 만든다. `inc/`, `src/bindings/`, `.github/`, GPU 공통 경로를 각각 바꾼 가상 파일 목록에 기존과 같은 label 집합이 나와야 한다.
4. Windows 교체는 기본 action call부터 시도하고, 빌드 로그에서 `cl`, `link`, SDK와 architecture 선택을 확인한다. 동작하지 않을 때만 명시적 `arch`나 toolset 입력을 추가한다.
5. artifact job은 업로드 성공에서 멈추지 않는다. 후속 `workflow_run`이 해당 run의 artifact를 내려받아 보고서와 PR 댓글까지 만드는지 확인한다.

## 위험/검증

- 모든 workflow YAML이 파싱되는지 확인하고, 가능하면 `actionlint`로 action expression과 shell도 검사한다.
- old pin(`checkout@v4`, `cache@v4`, artifact v4, `github-script@v7`, `labeler@v4`, 나머지 구버전)이 의도한 예외 없이 사라졌는지 저장소 전체를 검색한다.
- Ubuntu의 binary-size matrix와 일반 build, Android x86_64/aarch64, iOS 세 target, macOS, Windows 두 job을 실제 runner에서 실행한다.
- cache hit/miss 두 경우를 확인하고, artifact의 이름·보존 파일·압축 결과가 동일한지 비교한다.
- binary-size와 pixel-inspector의 `workflow_run`이 다른 run-id의 artifact를 내려받아 기존 디렉터리 구조로 합치고 PR 댓글을 생성·갱신하는지 확인한다.
- pixel inspector에서 Chrome stable 설치 경로와 버전 출력이 유지되고 브라우저 기반 비교가 완료되는지 확인한다.
- labeler fixture와 실제 시험 PR에서 기존 label별 positive case와 무관 파일 negative case, `sync-labels: true`에 따른 label 제거를 확인한다.
- Windows에서 compiler/SDK 환경 변수, Meson compiler detection, Ninja 빌드와 artifact 업로드를 모두 확인한다.
- 통제된 release 또는 임시 repository에서 source archive가 만들어지고 `*.xz`가 release asset으로 첨부되는지 확인한다. 운영 release를 검증용으로 발행하지 않는다.
- job 로그에 Node.js 20 deprecation/forced-runtime 경고가 더 남지 않는지 확인한다.
- self-hosted runner를 쓰는 외부 mirror나 downstream CI가 있다면 runner `v2.327.1` 이상인지 확인한다.
