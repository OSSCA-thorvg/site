# Issue #4810 — 여러 Lottie 자산 사이 표현식 상태 오염으로 깨지는 stroke

- 링크: https://github.com/thorvg/thorvg/issues/4810
- 상태: Open, 담당자 없음 (2026-09-15 확인)
- 분석 기준: `main` @ [`b07c83f`](https://github.com/thorvg/thorvg/commit/b07c83fe13a33b85a38350bfaa708be772a3e9ea)
- 난이도: 82/100
- 초심자 추천: 비추천 (공유 JavaScript realm, native function cache와 수명, 자산 평가 순서, transform/stroke 갱신을 함께 추적하고 성능·격리 trade-off를 검증해야 함)
- 관련 영역: Lottie loader, expression engine, JerryScript realm, cached native bindings, transform, stroke width, multi-asset playback
- 배울 수 있는 것: interpreter context isolation, mutable global state, native pointer binding, cache invalidation, order-dependent bugs, minimal reproducer와 performance regression 설계

## 이슈 요약

Lottie 예제에서 자산 디렉터리를 한꺼번에 재생할 때 `5036829.1.json`의 stroke가 깨진다. 일부 다른 자산을 제거하면 정상 재생되고, transform을 매번 다시 만들도록 하면 올바르게 렌더링된다는 후속 조사 결과가 있다. 단독 자산의 geometry나 CPU/GPU rasterizer보다는 Lottie expression engine의 자산 간 상태 공유가 의심되는 이유다.

문제 자산의 stroke width 표현식은 `transform.scale[0]`을 읽어 기본 폭 42를 scale에 반비례하도록 계산한다. 따라서 global `transform` 객체 또는 scale property binding이 앞서 평가된 다른 자산의 상태를 가리키면 폭이 잘못될 수 있다. 하지만 후속 댓글도 “appears”와 “seems”로 표현하므로 이는 아직 확인된 root cause가 아니라 유력한 가설이다.

## main 코드 조사

[문제 자산의 저장본](https://github.com/thorvg/thorvg.pixel-inspector/blob/1195f7cfa3b52e3983ce2c27f70559af81a615be/res/default/lottie/5036829.1.json)은 `Stroke 1`의 width에 `index = transform.scale[0]`과 `42 / (index / 100)`을 계산하는 expression을 둔다. 자산 자체가 다른 파일을 참조하지 않는데 실행 디렉터리의 다른 자산 유무에 따라 결과가 달라진다는 보고는 loader 외부의 공유 상태를 조사해야 함을 뜻한다.

[`LottieBuilder` 생성자와 소멸자](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/src/loaders/lottie/tvgLottieBuilder.h#L158-L174)는 각각 `LottieExpressions::instance()`와 `retrieve()`를 사용한다. [`instance()`](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/src/loaders/lottie/tvgLottieExpressions.cpp#L1564-L1581)는 정적 `_exps` 한 개를 ref-count해 모든 활성 builder가 공유한다.

[`LottieExpressions::context()`](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/src/loaders/lottie/tvgLottieExpressions.cpp#L1585-L1608)는 thread support가 있으면 thread id당, 없으면 첫 context 한 개를 재사용한다. context에는 [global realm, `thisComp`, `thisLayer`, `thisProperty`](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/src/loaders/lottie/tvgLottieExpressions.h#L134-L154)가 들어간다. 자산/loader 식별자는 context key가 아니다.

[`evaluate()`](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/src/loaders/lottie/tvgLottieExpressions.cpp#L1516-L1556)는 그 공유 context에 composition, current layer/property와 transform을 채운 다음 `jerry_eval()`로 자산의 코드를 같은 realm에서 실행한다. `var` 선언이나 global property 대입이 평가 뒤 자동으로 초기 realm snapshot으로 돌아가는 코드는 이 경로에 없다.

[`_buildProperty()`](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/src/loaders/lottie/tvgLottieExpressions.cpp#L1192-L1293)는 `valueAtTime`이 undefined인지로 최초 등록을 판단하고, 이후에는 기존 function object를 가져와 native pointer만 현재 expression으로 바꾼다. `wiggle`, loop 함수들은 하나의 `ExpContent`를 공유하며 기존 `wiggle` object에서 native pointer를 찾아 구조체를 갱신한다. JS가 이 이름을 다른 값으로 덮어쓰면 pointer를 찾지 못해 log만 남기고 canonical function을 복구하지 않는다.

[과거 Issue #4310](https://github.com/thorvg/thorvg/issues/4310)은 한 expression engine에서 function reference를 cache한 뒤 사용자가 common object/function을 덮어쓰면 cache가 무효화되지 않는 문제를 같은 root cause로 기록했다. [PR #4309](https://github.com/thorvg/thorvg/pull/4309)는 매 frame function object를 만들던 `_buildProperty()`를 현재의 재사용 방식으로 바꿔 약 13~18% 성능 개선을 목표로 했다. 과거 토론에서는 ECMA에서 built-in overwrite가 허용되고 anti-pattern 격리 비용이 크다는 이유로 완전 격리를 채택하지 않았다.

[`LottieBuilder::updateTransform()`](https://github.com/thorvg/thorvg/blob/b07c83fe13a33b85a38350bfaa708be772a3e9ea/src/loaders/lottie/tvgLottieBuilder.cpp#L173-L201)는 같은 frame이면 layer transform cache를 재사용하고, frame이 바뀔 때 `_update()`로 expression을 포함한 position/rotation/scale/opacity를 평가한다. 후속 조사에서 “항상 transform 재생성”이 증상을 고쳤다는 사실은 stale transform 또는 expression binding 가설과 일치하지만 어느 쪽인지 단독으로 증명하지는 않는다.

## 원인 분석

### 확인된 사실

- 문제 자산의 stroke width expression은 global `transform.scale[0]`에 의존한다.
- 단독 파일 내용에는 다른 자산 의존성이 없지만, 다른 자산 일부를 제거하면 정상 재생된다는 결과가 보고됐다.
- 모든 Lottie builder는 ref-count된 `LottieExpressions` singleton을 공유한다.
- expression context는 loader별이 아니라 thread별이며 global realm과 contextual objects를 재사용한다.
- `_buildProperty()`는 function object를 매 frame 새로 만들지 않고 global/context의 기존 object와 native pointer를 갱신한다.
- 기존 function이 JS에서 덮어써졌을 때 일부 경로는 log만 남기며 canonical object를 다시 등록하지 않는다.
- 과거 같은 cache/overwrite 문제와 완전 격리의 성능 trade-off가 논의됐다.
- transform을 항상 다시 만들면 이번 증상이 정상화된다는 관찰은 있지만, current main에서 최소 오염 순서와 손상 slot은 아직 공개되지 않았다.

### 추론과 판단

- **가장 유력한 원인은 loader 경계를 넘는 mutable JavaScript realm과 cached binding의 결합이다.** 같은 thread에서 먼저 평가된 자산이 global 이름이나 object property를 바꾸면 다음 자산이 그 state를 볼 수 있다.
- 문제 자산은 `transform.scale`을 읽으므로 global `transform`, 그 `scale` array/object, 또는 native property reference가 이전 expression을 가리키는지 우선 확인할 가치가 있다.
- `_buildProperty()`의 `valueAtTime` 존재만으로 전체 binding set이 정상이라고 판단하는 것은 약한 불변식이다. 일부 이름만 overwrite된 partial corruption을 “initialized”로 처리한다.
- transform 강제 재생성으로 해결된 것은 cache invalidation 누락일 수도 있다. shared realm과 layer transform frame cache를 각각 끄는 A/B 실험 없이는 둘 중 하나를 root cause로 확정하면 안 된다.
- loader마다 완전한 JerryScript realm을 만들면 격리는 명확하지만 활성 animation 수에 비례한 memory와 init cost가 생긴다. canonical native handles를 engine-private storage에 두고 평가 전 public global binding만 복원하는 더 작은 대안도 비교해야 한다.
- JS 표준상 사용자가 global을 덮어쓰는 동작과 엔진이 다음 **다른 자산**에 깨진 binding을 전파하는 것은 별개다. 같은 expression 안의 overwrite 의미는 유지하면서 asset boundary에서만 격리할 수 있다.

## 구현 방향

1. 문제 자산 앞에 놓았을 때 깨지는 최소 선행 자산 하나를 찾는다. 디렉터리를 이분 탐색하고 두 파일의 순서를 바꿔 `A→B`, `B→A`, `B 단독` 결과를 저장한다.
2. `evaluate()` 전후로 `transform`, `transform.scale`, `valueAtTime`, `wiggle`, `content`의 JerryScript value type, identity, native pointer와 현재 `exp/property/layer`를 debug 로그로 기록한다. 정상/실패 첫 divergence를 찾는다.
3. layer transform cache만 비활성화한 실험, expression global rebuild만 수행한 실험, loader별 context를 준 실험을 나눠 어느 상태가 필요한지 확인한다. 여러 변경을 한꺼번에 넣지 않는다.
4. 최소 수정은 canonical native function/object를 JS가 접근할 수 없는 C++ side registry에 보관하고, 매 evaluation 또는 asset switch 때 public binding의 type/native pointer를 검증해 손상된 slot만 복원하는 방식으로 검토한다.
5. asset boundary가 필요하면 context key를 thread id뿐 아니라 expression owner/loader identity까지 확장하거나 loader 전환 시 realm snapshot을 reset한다. 같은 자산 내 frame 간 function cache는 유지해 PR #4309의 성능 이득을 보존한다.
6. `_buildProperty()`의 `init` 판정은 한 이름의 존재가 아니라 필요한 binding 각각의 function type과 native metadata를 검사하게 한다. overwrite된 값에 무조건 native pointer를 설정하지 말고 새 canonical function으로 교체한다.
7. transform cache가 실제 원인이라면 expression이 참조하는 외부/global dependency가 변했을 때 `layer->cache.frameNo`만으로 재사용하지 않도록 expression generation/version을 cache key에 포함한다.
8. 수정 뒤 같은 expression 내부에서 사용자가 이름을 덮어쓰는 ECMA 동작, 같은 자산의 다음 expression, 다른 자산의 동작을 각각 명시해 호환성 경계를 문서화한다.

## 위험/검증

- 최소 두 자산을 모든 순서로 로드하고 단독 결과와 pixel-by-pixel 비교한다.
- 디렉터리 전체 재생 시 파일 시스템 열거 순서를 여러 permutation으로 바꿔 결과가 순서 독립적인지 확인한다.
- 문제 stroke의 frame별 width와 `transform.scale[0]` expression 결과를 숫자로 assertion한다.
- 같은 thread의 여러 loader, 서로 다른 worker thread, loader 생성/파괴와 singleton ref-count 변화를 검증한다.
- seek, 반복 재생, 같은 frame 재요청, tween 활성화 시 transform cache와 expression context가 갱신되는지 확인한다.
- global/native function을 의도적으로 덮어쓰는 과거 #4310 fixture를 포함해 같은 자산 내 의미와 다음 자산 격리를 모두 확인한다.
- `valueAtTime`만 정상이고 `wiggle` 또는 `content`만 손상된 partial overwrite를 만들어 복구 경로를 테스트한다.
- invalid native pointer를 dereference하지 않는지 ASan/UBSan으로 검사하고 JerryScript value ref/free 균형과 loader 반복 leak을 확인한다.
- PR #4309 전후 benchmark와 같은 frame 수로 expression-heavy 자산의 FPS, CPU samples, memory와 binary size를 비교한다.
- expressions support on/off, thread support on/off 빌드 조합을 모두 컴파일하고 실행한다.
- 전체 Lottie pixel inspector corpus에서 의도하지 않은 기준 이미지 변화가 없는지 확인한다.
