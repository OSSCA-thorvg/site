## 이슈 요약

`style="src url('missing.svg');"`처럼 속성명과 값 사이의 콜론이 빠진 SVG를 읽을 때, 일반 build는 성공할 수 있지만 엄격한 pointer-pair 검사를 켠 GCC/Clang AddressSanitizer가 `xmlParseW3CAttribute()`의 포인터 비교를 보고한다. 이슈는 잘못된 CSS를 완전히 복구해 달라는 요청이 아니라, 이런 입력을 방어적으로 무시할지 지원 범위 밖으로 둘지 정책을 명확히 하자는 제안이다.

CSS Syntax 규칙은 declaration 이름 뒤에 콜론이 없으면 parse error로 해당 declaration을 반환하지 않도록 정의한다. 따라서 잘못된 declaration을 적용하지 않고 다음 세미콜론 뒤에서 parsing을 계속하는 동작은 규격의 오류 복구 방향과 맞는다. 입력이 비정상이라는 이유로 null 포인터와 버퍼 포인터의 순서를 비교하는 경로를 남길 필요는 없다.

## main 코드 조사

[`xmlParseW3CAttribute()`](https://github.com/thorvg/thorvg/blob/12132e8ebe329bf549a3f3248b8e8cef295e5c94/src/loaders/svg/tvgXmlParser.cpp#L424-L489)는 현재 declaration 시작점에서 `strchr()`로 첫 콜론 `sep`과 세미콜론 `next`를 찾는다. 재현 입력에서는 `sep == nullptr`이고 `next`는 같은 버퍼 안의 세미콜론을 가리키며, `strstr()`가 찾은 `src`도 버퍼 안을 가리킨다.

```cpp
auto sep = (char*)strchr(buf, ':');
auto next = (char*)strchr(buf, ';');

if (auto src = strstr(buf, "src")) {
    if (next && src < sep) {
        // ...
    }
}

if (sep >= end) next = sep = nullptr;
if (next >= end) next = nullptr;
```

`next`만 검사한 뒤 `src < sep`를 평가하므로 콜론이 없으면 non-null 버퍼 포인터와 null을 순서 비교한다. 이어지는 `sep >= end`와 `next >= end`도 각 탐색 결과가 null일 수 있는데 null 확인보다 먼저 순서 비교한다. C++의 built-in pointer ordering은 같은 배열과 정의된 subobject 관계를 중심으로 규정되며, 그 밖의 비교 결과는 unspecified다. GCC의 `-fsanitize=pointer-compare`는 AddressSanitizer 및 `detect_invalid_pointer_pairs=2`와 함께 한쪽이 null인 비교를 검출한다.

`src` 특례는 valid `@font-face` 값 안의 추가 세미콜론을 declaration 끝으로 오인하지 않게 다음 세미콜론을 선택한다. 이 분기는 [최근 수정 `16c23ad`](https://github.com/thorvg/thorvg/commit/16c23ad9c48243eef01080596e3aa64a8da43a57)에서 `next`가 없을 때 `next + 1`을 만들지 않도록 보강됐지만, 콜론이 없는 현재 입력의 `sep`까지 보호하지는 않는다. 따라서 `if (sep && next && src < sep)` 한 줄만 고치는 것으로는 뒤의 `sep >= end`와 `next >= end` 비교가 남는다.

SVG root의 [`style` 처리 경로](https://github.com/thorvg/thorvg/blob/12132e8ebe329bf549a3f3248b8e8cef295e5c94/src/loaders/svg/tvgSvgLoader.cpp#L900-L914)를 포함한 여러 element handler가 `strlen(value)`과 `_parseStyleAttr` callback으로 이 함수를 호출한다. callback은 [지원하는 style key를 찾아 node에 적용](https://github.com/thorvg/thorvg/blob/12132e8ebe329bf549a3f3248b8e8cef295e5c94/src/loaders/svg/tvgSvgLoader.cpp#L1156-L1201)하므로, 공용 parser에서 오류 declaration만 버리고 뒤의 정상 declaration은 계속 전달하는 것이 중요하다.

현재 [`testPicture.cpp`](https://github.com/thorvg/thorvg/blob/12132e8ebe329bf549a3f3248b8e8cef295e5c94/test/testPicture.cpp#L201-L250)는 소수 SVG fixture의 load와 크기를 확인한다. 콜론 없는 inline style, 오류 declaration 뒤의 정상 declaration, pointer-compare sanitizer를 직접 검증하는 회귀는 보이지 않는다.

## 원인 분석

### 확인된 사실

- 이슈의 style 문자열에는 콜론이 없으므로 `strchr(buf, ':')`는 null을 반환한다.
- 같은 문자열의 `src`와 세미콜론 검색 결과는 버퍼 내부를 가리키며, line 441은 이 포인터와 null `sep`을 `<`로 비교한다.
- 바로 뒤의 범위 정규화도 `sep >= end`, `next >= end`를 null 검사보다 먼저 수행한다.
- 이슈에 기록된 일반 GCC/MSVC 및 MSVC ASan 실행은 PNG를 만들지만, GCC/Clang의 address + pointer-compare 조합은 invalid-pointer-pair를 검출한다.
- CSS Syntax의 declaration 소비 알고리즘은 이름 다음 토큰이 콜론이 아니면 parse error를 내고 declaration을 반환하지 않는다.
- 이 parser는 여러 SVG element의 inline style에 공통으로 사용되고, `src`의 내부 세미콜론을 건너뛰는 기존 특례가 있다.

### 추론과 판단

- **정책 판단:** 잘못된 declaration은 무시하되 같은 `style` 안의 다음 정상 declaration은 계속 처리하는 것이 가장 좁고 규격 친화적인 동작이다. 전체 SVG load를 실패시키거나 불완전한 key/value를 callback에 넘길 이유가 없다.
- **수정 범위 판단:** 모든 nullable 탐색 결과를 먼저 검사한 후에만 `end` 또는 서로의 순서를 비교해야 한다. line 441만 조건 추가하는 부분 수정은 sanitizer 경로를 완전히 제거하지 못한다.
- **구현 선택:** `bufLength` 안에서 콜론·세미콜론을 찾는 `memchr()` 또는 명시적 bounded helper를 쓰면 탐색 결과가 `end` 밖인지 사후 비교하는 단계 자체를 줄일 수 있다. `strchr()`를 유지한다면 `ptr && ptr < end` 형태로 정규화 순서를 고정해야 한다.
- **범위 제한:** `strstr(buf, "src")`는 declaration 이름이 아닌 값이나 더 긴 식별자의 부분 문자열도 찾을 수 있다. 장기적으로 key 경계를 먼저 식별하는 편이 견고하지만, 이번 수정이 완전한 CSS tokenizer 교체로 커질 필요는 없다.

## 구현 방향

1. 콜론과 세미콜론 검색 결과를 얻은 직후 각각 null·범위 여부를 정규화한다. null 가능 포인터를 `<`, `>=` 같은 순서 비교의 피연산자로 두지 않는다.
2. 현재 declaration에 콜론이 없으면 callback을 호출하지 않는다. 세미콜론이 있으면 그 다음 문자부터 계속하고, 없으면 parsing을 정상 종료한다.
3. 콜론이 유효할 때만 `src` 특례를 적용한다. `src: url(data:font/ttf;base64,...)`처럼 값 내부의 첫 세미콜론을 건너뛰는 기존 동작을 보존한다.
4. 가능하면 검색을 `[buf, end)`로 제한해 다음 declaration의 콜론이나 NUL 뒤 데이터를 현재 declaration의 separator로 오인하지 않게 한다.
5. parser 회귀 test를 먼저 추가하고, 수정 전 pointer-compare sanitizer에서 실패하며 수정 후 통과하는지 확인한다.

완전한 CSS error recovery를 구현하거나 모든 잘못된 style을 load 실패로 바꾸는 것은 이 이슈의 최소 범위를 벗어난다. 핵심은 “invalid declaration은 적용하지 않음, 다음 declaration은 유지, 어떤 경우에도 유효하지 않은 포인터 순서 비교를 하지 않음”이다.

## 초심자 시작 가이드

1. 이슈의 최소 SVG를 fixture로 추가하고 현재 sanitizer 명령으로 실패 위치를 고정한다.
2. `sep`, `next`, `src`, `end`가 각 입력에서 null인지 버퍼 안인지 표로 적는다. 포인터끼리 비교하기 전에 양쪽의 유효 조건을 코드에 그대로 반영한다.
3. `style="src url('missing.svg');fill:red"`를 추가해 잘못된 첫 declaration은 무시되고 뒤의 `fill`은 적용되는지 확인한다.
4. 기존 `src: url(data:font/ttf;base64,...)` fixture를 찾아 trailing semicolon 유무 두 경우를 회귀 test로 고정한다.
5. 정상 build test가 통과한 뒤 GCC와 Clang에서 pointer-compare sanitizer를 각각 실행한다.

수정량은 작지만 포인터 비교의 전제와 declaration 경계를 test로 설명할 수 있어야 한다. `sep`에 임의의 sentinel 주소를 넣어 비교를 계속하는 방식보다는 null을 control flow로 처리하는 편이 읽기 쉽고 안전하다.

## 위험/검증

- 콜론 없음 + 세미콜론 있음, 둘 다 없음, 콜론만 있음, 빈 declaration, 연속 세미콜론을 각각 검사한다.
- 잘못된 declaration 앞뒤에 정상 `fill`, `stroke`, `opacity`를 두고 정상 항목만 callback에 전달되는지 확인한다.
- `src: url(data:...)`의 내부 세미콜론, declaration 끝 세미콜론, trailing semicolon 없음 조합으로 기존 font-face 수정의 회귀를 막는다.
- `src`가 값 안이나 더 긴 식별자에 나타날 때 잘못된 특례가 활성화되지 않는지 확인한다.
- style을 받는 대표 element 둘 이상에서 load 성공뿐 아니라 적용된 property 결과를 검사한다.
- 빈 문자열과 length 경계에서 `strchr`/`strstr`가 논리적 `end` 밖 결과를 사용하지 않는지 확인한다.
- GCC/Clang에서 `-fsanitize=address,pointer-compare`와 `ASAN_OPTIONS=detect_invalid_pointer_pairs=2`를 사용한다.
- 일반 debug/release build와 기존 SVG, embedded font, picture tests를 함께 실행한다.
- 가능하면 malformed style seed를 SVG fuzz corpus에 넣어 null separator 조합을 지속적으로 탐색한다.
