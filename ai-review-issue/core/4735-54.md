- 분석 기준: `main` @ [`e3c505f`](https://github.com/thorvg/thorvg/commit/e3c505f628a9abc267514bc0975cd5feae5bdd26)

## 이슈 요약

이 issue는 v1.1.1과 당시 main을 Pixel Inspector로 비교했을 때 여러 SVG, Lottie, C++ draw test에서 pixel mismatch가 발생한다는 보고다. 보고 표의 결과는 하나의 버그가 아니라 최소 두 계층으로 나뉜다.

- 두 Lottie asset은 animation update 최적화 commit부터 WebGPU 출력이 달라졌다. 특히 `lottie/18580.json`은 비교 pixel의 약 26.35%가 달랐다.
- mix-blend-mode SVG와 blending draw test 두 개는 CPU raster diagnostics 변경부터 달라졌다. 보고된 diff ratio는 약 16.92%~27.95%다.

CPU 경로는 issue 조사 중 32-bit blending surface를 8-bit로 잘못 검사한 copy/paste 오류로 확인돼 current main에 이미 hotfix가 들어갔다. 반면 WebGPU 차이는 issue가 잠시 닫힌 뒤 main과 의심 commit revert의 영상이 다르다는 추가 확인으로 다시 열렸다. parent scene이 바뀐 Paint에 `Transform`뿐 아니라 `Color`도 표시하는 후보 commit이 만들어졌지만, 분석 기준 current main에는 포함돼 있지 않다.

따라서 이 작업의 실제 범위는 “모든 v1.1.1 대비 차이를 0으로 만든다”가 아니다. release 이후 의도된 기능 변화와 진짜 회귀를 구분하고, 이미 해결된 CPU 회귀는 검증으로 고정하며, 남은 WebGPU effective-opacity cache invalidation을 최소 수정과 test로 마무리하는 것이다.

## main 코드 조사

현재 Pixel Inspector workflow는 [`THORVG_PIXEL_GOLDEN_REF`를 `main`으로 지정](https://github.com/thorvg/thorvg/blob/e3c505f628a9abc267514bc0975cd5feae5bdd26/.github/workflows/pixel_inspector.yml#L9-L16)한다. PR merge ref를 build한 뒤 [먼저 golden ref를 설치해 `--update-golden`을 실행하고, 이어 PR ref를 같은 asset·backend로 비교](https://github.com/thorvg/thorvg/blob/e3c505f628a9abc267514bc0975cd5feae5bdd26/.github/workflows/pixel_inspector.yml#L60-L111)한다. 이 기준은 [최근 release tag에서 main으로 변경](https://github.com/thorvg/thorvg/commit/3700f6d3304f37c62f031454d5ed12f6a3e32f75)됐다. 즉 현재 PR CI는 “release 호환성”보다 “PR이 현재 main에서 새 pixel 변화를 만들었는가”를 감시한다.

Pixel Inspector 자체 문서는 [RGBA 채널의 Chebyshev distance로 pixel을 비교](https://github.com/thorvg/thorvg.pixel-inspector/blob/5cf24268430adb9f2f5df02da0e212f74d4307d8/README.md#evaluator)하며, 두 이미지에서 모두 완전 투명한 pixel만 제외한다고 설명한다. 기본 channel-distance와 diff-ratio threshold는 모두 0이므로 한 channel의 한 pixel만 달라도 차이로 판정한다. 이 엄격함은 작은 opacity 회귀 탐지에는 적합하지만, v1.1.1 이후 추가된 정상 기능까지 회귀처럼 보이게 할 수 있다.

CPU 최초 불량 commit은 raster log를 정리하면서 [`_rasterBlendingRect()`와 `_rasterBlendingRle()`의 기존 `sizeof(uint32_t)` 조건을 실수로 `sizeof(uint8_t)`로 변경](https://github.com/thorvg/thorvg/commit/4c79c84cd155807ca791db33e8d663cd5f2458ae)했다. 두 함수는 바로 뒤에서 `buf32`와 32-bit packed color를 사용하므로 정상 32-bit surface에서도 조기에 `false`를 반환하게 된다. current main은 [두 조건과 진단 문구를 32-bit로 복구한 hotfix](https://github.com/thorvg/thorvg/commit/842319398b9baa3cd1be4c154a380a251839fcc5)를 포함하며, 실제 코드도 [`_rasterBlendingRect()`가 `sizeof(uint32_t)`를 요구](https://github.com/thorvg/thorvg/blob/e3c505f628a9abc267514bc0975cd5feae5bdd26/src/renderer/cpu_engine/tvgSwRaster.cpp#L421-L435)하고 RLE 경로도 [같은 32-bit 조건](https://github.com/thorvg/thorvg/blob/e3c505f628a9abc267514bc0975cd5feae5bdd26/src/renderer/cpu_engine/tvgSwRaster.cpp#L595-L610)을 쓴다.

WebGPU 최초 불량 commit은 animation frame/apply/tween 시 Picture 전체를 `All`로 무효화하던 동작을 [`Children` 전파로 축소](https://github.com/thorvg/thorvg/commit/4a089b8b3bc576c147846b7efc4f174fea7e15a6)했다. 최적화 자체는 매 frame 모든 renderer data를 버리지 않기 위한 합리적인 변화다. 하지만 이 이후에는 child가 바뀐 property에 해당하는 구체 flag를 빠짐없이 표시해야 cached data가 갱신된다.

Lottie builder는 shape group에 들어갈 때 [pool에서 얻은 Paint를 duplicate하거나 기존 propagator를 재사용](https://github.com/thorvg/thorvg/blob/e3c505f628a9abc267514bc0975cd5feae5bdd26/src/loaders/lottie/tvgLottieBuilder.cpp#L258-L305)하고, repeater도 [pooling된 Shape를 여러 parent context에 재배치](https://github.com/thorvg/thorvg/blob/e3c505f628a9abc267514bc0975cd5feae5bdd26/src/loaders/lottie/tvgLottieBuilder.cpp#L405-L456)한다. `Scene::insert()`는 parent가 없는 Paint만 받으며, 현재 [“current scene space로 재배치”한다는 주석과 함께 `Transform`만 mark](https://github.com/thorvg/thorvg/blob/e3c505f628a9abc267514bc0975cd5feae5bdd26/src/renderer/tvgScene.h#L333-L350)한다.

그러나 child에 전달되는 opacity는 child 자체 값만이 아니다. Scene update는 [상위에서 받은 opacity를 각 Paint update로 전달](https://github.com/thorvg/thorvg/blob/e3c505f628a9abc267514bc0975cd5feae5bdd26/src/renderer/tvgScene.h#L86-L105)하고, 공통 Paint update는 [그 값을 자기 opacity와 곱해 backend에 전달](https://github.com/thorvg/thorvg/blob/e3c505f628a9abc267514bc0975cd5feae5bdd26/src/renderer/tvgPaint.cpp#L253-L264)한다. 같은 Paint가 opacity가 다른 Scene으로 옮겨지면 geometry와 local color가 같아도 effective opacity는 바뀐다.

WebGPU renderer는 기존 `RenderData`가 있으면 [`Transform`, `Blend`, `Color` 중 하나가 표시될 때만 cached solid opacity를 다시 계산](https://github.com/thorvg/thorvg/blob/e3c505f628a9abc267514bc0975cd5feae5bdd26/src/renderer/gpu_engine/wg/tvgWgRenderer.cpp#L146-L170)한다. image surface도 [`Blend` 또는 `Color`일 때만 opacity uniform을 갱신](https://github.com/thorvg/thorvg/blob/e3c505f628a9abc267514bc0975cd5feae5bdd26/src/renderer/gpu_engine/wg/tvgWgRenderer.cpp#L197-L207)한다. `Scene::insert()`의 `Transform`만으로 shape opacity는 우연히 다시 계산되지만, 이 의존성은 renderer data 종류별로 다를 수 있고 “parent 변경은 effective color/opacity 변경”이라는 의미가 표현되지 않는다.

실제로 issue에 연결된 후보 commit은 [`Scene::insert()`에서 `Transform | Color`를 mark](https://github.com/thorvg/thorvg/commit/fb993d4f3a82eecefe68c981960ad730f21621e6)한다. commit 설명도 parent 변경으로 inherited opacity가 바뀔 수 있으며 재사용된 Paint의 stale effective opacity를 막는다고 명시한다. 다만 이 commit은 분석 기준 current main의 조상이 아니고 current source는 여전히 `Transform`만 표시하므로, 후보를 적용해 재현 asset과 성능을 검증하는 단계가 남아 있다.

현재 backend 단위 test는 CPU/GL/WebGPU의 여러 blend method를 draw하고 API 성공을 확인하지만, [WebGPU blend test도 output pixel이나 parent 재부착 뒤 opacity 변화를 직접 assert하지 않는다](https://github.com/thorvg/thorvg/blob/e3c505f628a9abc267514bc0975cd5feae5bdd26/test/testWgEngine.cpp#L49-L137). 따라서 stale uniform처럼 draw/sync 자체는 성공하는 오류가 일반 unit test를 통과하고 Pixel Inspector에서만 드러날 수 있다.

## 원인 분석

### 확인된 사실

- issue는 v1.1.1 대비 main의 WebGPU Lottie 두 건과 CPU blend 세 건을 서로 다른 최초 불량 commit으로 좁혔다.
- CPU 최초 불량 변경은 32-bit blending 함수의 channel-size guard를 8-bit로 바꿨고, current main hotfix가 이를 32-bit로 복구했다.
- animation 최적화는 frame/apply/tween의 invalidation을 `All`에서 `Children`으로 줄였다.
- Lottie builder는 pooling/duplicate된 Paint를 Scene에 삽입하며, `Scene::insert()`는 재배치 시 현재 `Transform`만 mark한다.
- child의 최종 opacity는 parent에서 전달된 opacity와 child opacity의 곱이다.
- WebGPU는 기존 render data의 opacity를 특정 update flag가 있을 때만 다시 계산한다.
- parent 재배치 시 `Color`도 mark하는 후보 commit이 있지만 분석 기준 current main에는 없다.
- Pixel Inspector 기본 비교는 threshold 0으로 매우 엄격하며, 현재 PR workflow의 golden ref는 release가 아니라 main이다.

### 추론과 판단

- **CPU root cause는 확정적이다.** 최초 불량 diff, 함수의 `buf32` 사용, hotfix가 같은 두 조건만 되돌린 사실이 일치한다. 이 부분은 추가 설계보다 회귀 test 고정이 남은 상태다.
- **WebGPU root cause는 높은 신뢰도의 추론이다.** `All`이 사라지면서 이전에는 가려지던 누락 invalidation이 노출됐고, parent 변경이 effective opacity를 바꾸는데 `Scene::insert()`는 그 의미를 `Color`로 표시하지 않는다. issue의 후보 commit도 같은 결론이다. 다만 후보 적용 전후의 Pixel Inspector 결과가 공개된 current main에는 없으므로 문서만으로 완전 확정할 수는 없다.
- **최적화 commit 전체를 되돌릴 필요는 낮다.** 불량 asset의 최초 변화가 그 commit이라는 사실은 “최적화 자체가 틀렸다”보다 “정밀 invalidation이 기존 누락을 드러냈다”는 설명과 더 잘 맞는다. `All` 복귀는 진단용 대조군으로 유용하지만 장기 수정은 parent 변경 계약을 명시하는 편이 범위가 작다.
- **`Color`는 현재 flag 체계에서 opacity를 대표하는 현실적인 선택이다.** RenderUpdateFlag 정의에도 color와 opacity 분리가 TODO로 남아 있다. 별도 `Opacity` flag 추가는 더 명확할 수 있지만 모든 backend 소비자를 고쳐야 하므로 이 issue의 최소 수정 범위를 넘어간다.
- **release 대비 모든 pixel 차이를 없애면 안 된다.** mix-blend-mode 같은 기능 추가와 golden 기준 변경이 섞여 있으므로, CPU hotfix 및 WebGPU 후보 전후를 current main 기준으로 비교해야 진짜 회귀만 검증할 수 있다.

## 구현 방향

1. issue에 기록된 CPU 세 case를 current main과 CPU hotfix의 parent에서 다시 실행한다. current main에서 blending 결과가 생성되고 diff가 사라지는지 확인해 이미 해결된 범위를 고정한다.
2. WebGPU Lottie 두 asset은 current main, animation 최적화의 parent, current main에 `Transform | Color` 후보만 적용한 build의 동일 frame으로 비교한다. 후보 build가 최적화 parent와 pixel-identical해야 한다.
3. public API로 더 작은 재현을 만든다. opacity 255 Scene과 opacity가 낮은 Scene 사이에서 동일 Paint를 remove/insert한 뒤 같은 WebGPU canvas에 다시 draw하고, 재부착 전후 pixel alpha 또는 packed color가 새 parent opacity를 반영하는지 검사한다.
4. `Scene::insert()`가 parent 변경의 semantic invalidation으로 `Transform | Color`를 표시하도록 수정한다. 주석에는 좌표계뿐 아니라 inherited opacity도 바뀐다는 이유를 남겨 이후 최적화에서 `Color`가 다시 제거되지 않게 한다.
5. Shape와 Picture/Surface를 각각 검증한다. WebGPU의 두 `prepare()` overload가 opacity cache를 다른 조건으로 갱신하므로 shape만 통과하는 test로 충분하지 않다.
6. CPU와 GL에서도 같은 최소 scene을 실행한다. 공통 flag 변경이 backend마다 output을 바꾸지 않고, 재부착 전후 예상 opacity만 달라지는지 확인한다.
7. Pixel Inspector의 golden은 수정 전 current main으로 만들고 수정 branch를 비교한다. v1.1.1 golden은 release 차이 조사 자료로만 유지해 신규 기능 차이를 수정 회귀와 혼동하지 않는다.
8. animation benchmark에서 frame당 prepare 호출, WebGPU uniform upload, frame time을 비교한다. 모든 child를 `All`로 되돌리는 방식보다 후보 수정의 갱신 증가가 parent 재배치 시점으로 제한되는지 확인한다.

## 초심자 시작 가이드

이 issue는 수정 후보가 구체적이므로 renderer를 처음 보는 기여자도 검증 부분부터 시작할 수 있다.

1. `Scene A(opacity=255)`, `Scene B(opacity=128)`, 불투명한 단색 사각형 하나를 만든다.
2. 사각형을 A에 넣어 한 번 draw/sync한 뒤 remove하고 B에 넣어 다시 draw/sync한다. 두 번째 결과 alpha가 첫 번째의 절반에 가까운지 pixel로 확인한다.
3. 같은 순서를 B→A로도 실행한다. cache가 한 방향에서만 우연히 맞는 경우를 막는다.
4. Shape 다음에는 작은 raw Picture로 반복한다. WebGPU renderer의 shape와 surface prepare 경로를 모두 건드릴 수 있다.
5. `Scene::insert()`의 mark를 임시로 `All`, `Transform`, `Transform | Color` 세 가지로 바꿔 결과를 비교한다. `All`과 `Transform | Color`는 같고 `Transform`만 다르면 가설을 작은 test로 입증한 것이다.
6. 최소 test가 실패하는 current main과 통과하는 후보 patch의 PNG 및 측정 pixel 값을 issue에 공유한다. 큰 Lottie asset보다 유지보수 가능한 회귀 test가 된다.

## 위험/검증

- CPU `blending`과 `issue_4190_nonseparable_blend` draw test를 SW backend에서 strict pixel 비교한다.
- CPU rect와 RLE shape가 모두 32-bit blend path를 지나며 오류 없이 실제 destination pixel을 갱신하는지 확인한다.
- WebGPU 문제 Lottie의 첫 frame, 중간 frame, loop 경계, 순차 재생과 임의 seek 결과를 비교한다.
- parent opacity를 0, 1, 127, 254, 255로 바꾸고 A→B 및 B→A 재부착을 반복한다.
- Shape, gradient Shape, raw Picture, vector Picture를 각각 opacity가 다른 Scene 사이에서 이동한다.
- Scene이 composition을 요구하는 mask/blend/effect를 가질 때와 단순 Scene일 때를 모두 검사한다.
- 같은 Paint의 geometry/local color가 그대로여도 inherited opacity만 바뀌는 case를 별도로 둔다.
- CPU, GL, WebGPU output이 허용 오차 없이 일치하는 단순 solid-color fixture를 사용한다.
- `Children` 최적화를 유지한 build와 `All` 대조군의 문제 asset 결과가 pixel-identical한지 확인한다.
- Pixel Inspector는 current-main golden과 수정 branch 비교로 실행하고, release-to-main 결과는 의도된 기능 변화와 별도 분류한다.
- 전체 unit test와 sanitizer build를 실행해 remove/insert/ref-count 수명 문제가 없는지 확인한다.
- animation frame time, prepare 횟수, WebGPU buffer/uniform update 수를 측정해 `Color` mark의 성능 영향을 확인한다.
