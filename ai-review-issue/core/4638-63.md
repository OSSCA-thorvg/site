## 이슈 요약

현재 SVG 테스트는 발견된 문제를 fixture로 추가하는 회귀 중심 방식이어서, SVG 규격의 어떤 기능을 얼마나 지원하는지 체계적으로 측정하기 어렵다는 제안이다. 외부의 resvg test suite, W3C SVG 1.1/Tiny 1.2 suite, web-platform-tests를 후보로 삼아 Inspector CI에 연결하거나 별도 검증 페이지를 운영하자는 내용이다.

maintainer 답변은 두 목적을 분리한다. 모든 규격 사례를 기존 PR CI에 넣기보다, 전체 지원 현황은 별도 도구에서 측정하고 공식 지원이 확인된 asset만 회귀 CI에 포함하는 방향을 선호한다. 따라서 첫 산출물은 workflow 한 개가 아니라 “conformance inventory”와 “blocking regression set”의 경계를 정의하는 설계 문서·manifest가 되어야 한다.

## main 코드 조사

현재 main에는 이미 [`SVG Regression` workflow](https://github.com/thorvg/thorvg/blob/b22b16a66c4b28c620d82405cb6351c919bb751b/.github/workflows/svg_regression.yml#L1-L58)가 있다. 모든 main 대상 PR에서 PR 버전과 새로 clone한 main 버전의 `tvg-svg2png`를 빌드하고, 외부 regression finder와 valid/not-valid archive를 내려받아 crash·leak·timeout 및 출력 차이를 검사한다.

비교 설정은 [`settings_comparison.toml`](https://github.com/thorvg/thorvg/blob/b22b16a66c4b28c620d82405cb6351c919bb751b/test/regression/settings_comparison.toml#L1-L38)에서 400×400 흰 배경, PR 대 main 비교를 사용한다. text/filter 등 미지원 항목을 무시하고 차이 임계값을 적용한다. 이는 “이전 main과 달라졌는가”를 찾는 regression 장치이지, 규격의 expected PNG와 비교해 conformance를 판정하는 장치는 아니다.

별도 [`Pixel Inspector` workflow](https://github.com/thorvg/thorvg/blob/b22b16a66c4b28c620d82405cb6351c919bb751b/.github/workflows/pixel_inspector.yml#L1-L35)는 모든 PR에서 전용 repository를 checkout한다. 고정 golden ref로 golden을 만들고 PR merge ref를 SW/GL/WG backend에서 렌더링해 비교하며, report와 PDF artifact를 생성한다. 현재 workflow에는 SVG 관련 path filter가 없고 timeout은 60분이다.

Pixel Inspector 자체는 [외부 resource directory와 backend 목록, pixel threshold를 받는 기능](https://github.com/thorvg/thorvg.pixel-inspector/blob/7d60d186176fff469e8aaa99bae40d113e8d403c/README.md#usage)을 이미 제공한다. SVG/Lottie PNG를 golden과 비교하고 HTML·Markdown report를 만드는 구조이므로 별도 spec corpus runner의 기반으로 재사용할 수 있다.

[`tvg-svg2png`](https://github.com/thorvg/thorvg/blob/b22b16a66c4b28c620d82405cb6351c919bb751b/tools/svg2png/svg2png.cpp#L68-L155)는 software canvas로 SVG를 load하고 지정 크기·배경의 PNG를 생성한다. [directory 입력을 재귀 처리](https://github.com/thorvg/thorvg/blob/b22b16a66c4b28c620d82405cb6351c919bb751b/tools/svg2png/svg2png.cpp#L331-L405)하지만 결과 PNG를 입력 SVG 옆에 쓰고, 한 실행의 크기·배경을 모든 파일에 공통 적용한다. 외부 suite를 그대로 실행할 수는 있어도 fixture별 viewport, resource/font 설치, expected image 위치와 결과 수집을 위한 adapter가 필요하다.

unit test는 [`testPicture.cpp`](https://github.com/thorvg/thorvg/blob/b22b16a66c4b28c620d82405cb6351c919bb751b/test/testPicture.cpp#L201-L250)에서 저장소의 소수 SVG fixture가 load되는지 확인한다. pixel expected output이나 feature별 지원 matrix는 여기서 검사하지 않는다.

프로젝트 README는 [SVG Tiny 기반과 미지원 animation·interactivity·multimedia](https://github.com/thorvg/thorvg/blob/b22b16a66c4b28c620d82405cb6351c919bb751b/README.md#L319-L326)를 명시한다. W3C Tiny suite에는 DOM·animation·media처럼 현재 범위 밖 사례도 있으므로 suite 전체 실패 수를 곧바로 loader 결함 수로 해석하면 안 된다.

resvg test suite의 [고정 revision README](https://github.com/linebender/resvg-test-suite/blob/d8e064337faf01bc5a9579187a56dbdbe3eacc72/README.md)는 `tests`, `resources`, `fonts`, 수동 결과 CSV와 도구를 분리하며 MIT license를 명시한다. standalone fixture가 많아 좋은 출발점이지만, resvg는 SVG Tiny 1.2가 아니라 static SVG subset을 목표로 하므로 ThorVG의 공식 profile과 case별 매핑이 필요하다.

## 원인 분석

### 확인된 사실

- main에는 PR↔main SVG regression workflow와 golden↔PR Pixel Inspector가 이미 있다.
- 기존 regression은 output 변화와 crash를 찾지만 규격 expected result 및 feature coverage를 계산하지 않는다.
- Pixel Inspector는 SVG resource directory, 여러 backend, strict/relaxed pixel threshold와 report 생성을 지원한다.
- `tvg-svg2png`는 재귀 directory 변환이 가능하지만 SW backend만 사용하고 fixture별 실행 조건이나 manifest는 받지 않는다.
- 공식 설명은 SVG Tiny 기반의 정적 기능 범위를 두며 animation·interactivity·multimedia를 미지원으로 명시한다.
- 후보 suite들은 profile과 harness가 서로 다르고, W3C suite에는 browser/DOM/media 의존 사례가 포함된다.
- maintainer는 전체 corpus를 모든 PR의 차단 CI로 넣기보다 별도 현황 도구 또는 공식 지원 asset 선별을 제안했다.

### 추론과 판단

- 핵심 공백은 SVG fixture 개수가 아니라 “feature/profile → test case → 기대 상태 → 마지막 검증 결과”를 잇는 versioned manifest의 부재다.
- conformance와 regression을 같은 pass/fail로 합치면 이미 알려진 미지원 기능 때문에 CI가 항상 실패하거나, 대량 allowlist가 실제 회귀를 가릴 가능성이 높다.
- golden PNG가 다른 renderer에서 생성됐다면 anti-aliasing, font rasterization과 color 처리 차이가 규격 위반이 아닌 pixel diff를 만들 수 있다. 구조적 assertion이나 per-case threshold가 필요한 사례가 있다.
- 외부 main branch를 매번 받으면 test 자체 변경으로 결과가 흔들린다. commit pin, checksum, license/attribution과 명시적 update 절차가 필요하다.
- 가장 유지 가능한 구조는 야간/수동 full inventory와 PR용 supported subset을 분리하고, 동일 manifest에서 두 실행 목록을 생성하는 방식이다.

## 구현 방향

1. 먼저 목표와 결과 상태를 정의한다.
   - `supported-pass`: PR 차단 후보
   - `known-fail`: 현황에는 표시하되 차단하지 않음
   - `out-of-scope`: profile 밖 기능
   - `harness-required`: DOM/script/network 등 standalone 변환 불가
   - `needs-review`: expected image 또는 규격 해석 확인 필요
2. 한 suite의 작은 category부터 pinned commit으로 가져온다. license와 원본 path를 보존하고 update script가 revision/checksum을 기록하게 한다.
3. versioned manifest에 suite, case id, spec/profile, required resources/fonts, viewport/background, expected image, threshold와 상태/근거를 저장한다.
4. adapter가 fixture별 조건을 적용하고 결과를 공통 directory layout으로 수집하도록 한다. input tree에 PNG를 직접 쓰는 `svg2png` 기본 동작에 의존하지 않는다.
5. 첫 단계는 SW backend 하나의 별도 `workflow_dispatch` 또는 schedule로 full inventory를 생성한다. 총 case·pass·known-fail·out-of-scope·error와 category별 추이를 artifact/page로 남긴다.
6. maintainer가 공식 지원으로 승인한 `supported-pass`만 작은 shard로 만들어 SVG 관련 path가 바뀐 PR에 blocking regression으로 실행한다.
7. Pixel Inspector의 GL/WG 비교는 SW baseline이 안정된 뒤 별도 backend matrix로 확장한다. renderer별 golden과 threshold를 섞지 않는다.
8. manifest 상태 변경은 결과 screenshot/diff, spec link와 reviewer 근거를 요구한다. 실패를 삭제하거나 threshold만 넓혀 녹색으로 만들지 않는다.

## 초심자 시작 가이드

전체 CI 통합보다 corpus inventory 하위 작업을 추천한다.

1. resvg suite의 `shapes` 같은 작은 category 10~20개를 고른다.
2. 각 case를 현재 `tvg-svg2png`로 같은 viewport·배경에서 실행하고 exit code, 생성 크기와 pixel diff를 기록한다.
3. 결과를 `supported-pass`, `known-fail`, `out-of-scope`, `needs-review`로 분류하되 각 판단에 spec/공식 지원표 링크를 붙인다.
4. system font에 의존하는 test는 제외하지 말고 필요한 font와 fallback 결과를 명시한다.
5. 같은 container에서 두 번 실행해 PNG hash와 결과 JSON이 재현되는지 확인한다.

첫 PR은 workflow를 required check로 만들지 말고 manifest schema, 10~20개 fixture와 로컬 runner까지만 제안하는 것이 안전하다.

## 위험/검증

- 외부 suite revision, archive checksum, license와 원본 case id가 report까지 추적되는지 확인한다.
- network/script/DOM/animation/media와 system font 의존 사례를 실행 전에 분류한다.
- viewport, DPI, 배경, color space, locale, timezone, font set과 renderer backend를 고정한다.
- transparent pixel, premultiplication, anti-aliasing edge와 font rasterization에 대한 비교 규칙을 문서화한다.
- strict pixel equality와 perceptual/threshold diff를 대표 case로 비교하고 false positive/negative를 수동 검토한다.
- known-fail이 pass로 바뀌는 improvement와 supported-pass가 fail로 바뀌는 regression을 별도 집계한다.
- corpus update 전후 추가·삭제·상태 변경 수를 review 가능한 diff로 출력한다.
- 전체 실행 시간, download/cache 크기, artifact 크기와 shard별 p95 시간을 측정한다.
- fork PR에서 외부 fixture나 generated report를 실행할 때 script injection과 artifact path traversal을 막는다.
- 기존 SVG Regression/Pixel Inspector와 중복 실행되는 case 및 비용을 계측해 workflow 역할을 정리한다.
- flaky case를 자동 재시도로 숨기지 말고 반복 실행으로 원인을 분류한다.
