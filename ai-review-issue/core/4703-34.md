- 실현 가능성: **높음** — current main의 member ordering에는 실제 padding이 있고, x86_64 GCC 측정에서 `GlShape` 344→328 bytes, `GlSolidBatch` 72→64 bytes의 후보를 확인했다. 그러나 이는 특정 ABI의 진단값이며, 프로젝트 전체 memory 절감은 object 수와 target별 layout을 측정한 뒤 주장해야 한다.

## 이슈 요약

이슈는 GL renderer의 `GlShape`와 `GlSolidBatch`에서 크기가 다른 member가 섞여 생기는 padding을 줄이기 위해 member 순서를 재배치하자고 제안한다. C++ object는 각 member의 alignment 요구를 맞추기 위해 member 사이와 object 끝에 padding을 둘 수 있으므로, 작은 `uint8_t` enum이나 `bool` 사이에 4·8-byte member가 오면 빈 공간이 늘어날 수 있다.

제안 방향은 타당하지만 "정렬 순서만 바꾸면 항상 몇 byte 절약된다"고 일반화할 수는 없다. compiler, architecture, pointer size, 각 내부 container의 alignment에 따라 결과가 달라진다. 실제 current header를 x86_64 GCC 13.3으로 측정했을 때 `GlShape`는 이슈 설명의 8-byte 예상과 달리 16 bytes 줄일 수 있었고, `GlSolidBatch` 후보는 8 bytes 줄었다.

두 구조체의 효과도 같지 않다. `GlShape`는 image와 shape render data마다 heap allocation되어 큰 scene에서 절감이 object 수만큼 누적된다. 반면 `GlSolidBatch`는 renderer 안의 단일 member이므로 object-size 8-byte 감소만으로 전체 RSS가 의미 있게 줄 가능성은 낮다. 후자는 cache locality나 hot path 효과를 별도로 측정해야 한다.

## main 코드 조사

[`GlShape`의 current member 순서](https://github.com/thorvg/thorvg/blob/ab798d8242def84e17025552a5f3c303a8bf072f/src/renderer/gpu_engine/gl/tvgGlCommon.h#L126-L143)는 pointer, `float`, `uint32_t`, 16-bit flag, `GLuint`, pointer, 8-bit enum, `uint32_t`, 8-bit enum, 큰 geometry/container, 16-bit stamp, `bool`을 차례로 둔다. 작은 member 뒤에 더 큰 alignment의 member가 반복되어 내부 padding 후보가 여러 곳 생긴다.

작은 타입의 크기는 명시적으로 확인된다. [`RenderUpdateFlag`](https://github.com/thorvg/thorvg/blob/ab798d8242def84e17025552a5f3c303a8bf072f/src/renderer/tvgRender.h#L43-L45)는 `uint16_t` 기반이고, public [`ColorSpace`](https://github.com/thorvg/thorvg/blob/ab798d8242def84e17025552a5f3c303a8bf072f/inc/thorvg.h#L110-L118)와 [`FilterMethod`](https://github.com/thorvg/thorvg/blob/ab798d8242def84e17025552a5f3c303a8bf072f/inc/thorvg.h#L202-L206)는 `uint8_t` 기반 enum이다. 따라서 enum을 무조건 `int` 크기로 가정하는 계산은 current 선언과 맞지 않는다.

current header를 그대로 포함한 x86_64 GCC 13.3 진단 프로그램에서 `GlShape`는 `sizeof=344`, `alignof=8`이었다. 주요 offset은 `deferredFlags=20`, `texId=24`, `texSource=32`, `texFilter=40`, `texFlipY=44`, `texColorSpace=48`, `geometry=56`, `clips=320`, `texStamp=336`이었다. 작은 texture metadata를 정렬 요구가 비슷한 순서로 묶고 geometry를 앞당긴 후보는 `sizeof=328`이었다. 이는 current main의 축소 가능성을 확인하지만 다른 target에서도 16-byte 절감을 보장하지는 않는다.

[`GlSolidBatch`](https://github.com/thorvg/thorvg/blob/ab798d8242def84e17025552a5f3c303a8bf072f/src/renderer/gpu_engine/gl/tvgGlSolidBatch.h#L32-L57)는 pass pointer, bounds, 4-byte color/flag, `float`, 2-byte stamp와 `bool`을 가진다. 같은 환경에서 current layout은 `sizeof=72`, `alignof=8`, `depth=48`, `promoted=64`였고, 4-byte member와 작은 tail member를 모은 후보는 64 bytes였다.

`GlShape`의 allocation 빈도는 renderer code에서 확인된다. image prepare 경로는 [render data가 없을 때 `new GlShape`를 만들고 texture·geometry 정보를 채운다](https://github.com/thorvg/thorvg/blob/ab798d8242def84e17025552a5f3c303a8bf072f/src/renderer/gpu_engine/gl/tvgGlRenderer.cpp#L1281-L1328). shape prepare 경로도 [paint별 render data로 `GlShape`를 만들고 재사용한다](https://github.com/thorvg/thorvg/blob/ab798d8242def84e17025552a5f3c303a8bf072f/src/renderer/gpu_engine/gl/tvgGlRenderer.cpp#L1331-L1383). [`dispose()`](https://github.com/thorvg/thorvg/blob/ab798d8242def84e17025552a5f3c303a8bf072f/src/renderer/gpu_engine/gl/tvgGlRenderer.cpp#L1272-L1278)는 해당 object를 삭제한다. 따라서 scene의 GL render-data 수가 `GlShape` 절감의 배수다.

반대로 [`GlRenderer`는 `GlSolidBatch`를 한 개의 직접 member로 보유](https://github.com/thorvg/thorvg/blob/ab798d8242def84e17025552a5f3c303a8bf072f/src/renderer/gpu_engine/gl/tvgGlRenderer.h#L225-L236)한다. batch object 크기만 8 bytes 줄었다는 수치로 대규모 heap 절감을 주장할 수 없는 이유다.

source 전체 검색에서 positional `GlShape{...}`/`GlSolidBatch{...}`, `offsetof`, raw `memcpy`로 layout을 직접 소비하는 사용은 확인되지 않았다. `GlSolidBatch::clear()`의 `*this = {}`처럼 value initialization하는 형태는 member 순서에 의존하지 않는다. 다만 검색 결과는 current tree의 확인 범위이며 외부 binary가 private header를 비공식 사용하거나 compiler-specific tooling이 layout을 가정하는 가능성까지 증명하지는 않는다.

GL test source는 [GL dependency가 있을 때만 test executable에 추가](https://github.com/thorvg/thorvg/blob/ab798d8242def84e17025552a5f3c303a8bf072f/test/meson.build#L29-L50)된다. existing tests는 draw/image/fill/effect/solid batch 동작을 폭넓게 다루지만 `sizeof`나 member offset을 계약으로 고정하지 않는다. layout 최적화 검증에는 별도 진단과 representative scene 측정이 필요하다.

## 원인 분석

### 확인된 사실

- `GlShape`는 1·2·4·8-byte alignment를 요구하는 member가 섞여 있고, current x86_64 GCC layout에 member 사이 및 tail padding이 존재한다.
- current main의 enum underlying type은 명시적으로 8-bit 또는 16-bit라서 작은 metadata를 같은 alignment 그룹으로 모을 여지가 있다.
- 동일한 member와 타입을 유지하고 순서만 바꾼 진단 후보에서 x86_64 GCC 기준 `GlShape`는 344→328 bytes, `GlSolidBatch`는 72→64 bytes가 됐다.
- `GlShape`는 image/shape render data마다 동적 생성되고 유지되므로 object 수가 많을수록 절감이 누적된다.
- `GlSolidBatch`는 renderer의 단일 직접 member라서 object-size 감소의 aggregate memory 효과는 작다.
- current source 검색에서는 positional aggregate initialization, raw copy, `offsetof`처럼 두 구조체의 구체적 member 순서를 소비하는 코드를 찾지 못했다.
- GL tests는 dependency 조건을 만족할 때만 build되며 layout 크기 자체를 검사하는 current test는 없다.

### 추론과 판단

- **근본 원인:** 논리적으로 관련된 순서와 alignment가 큰 순서가 혼재되어, 작은 enum/flag 뒤에서 compiler가 다음 pointer·4-byte·8-byte member를 정렬하기 위한 빈 공간을 넣는다.
- **효과 범위:** `GlShape`는 scene complexity에 비례해 aggregate memory를 줄일 가능성이 높다. 예를 들어 특정 target에서 16 bytes가 실제로 줄고 10,000개가 살아 있다면 object payload 기준 약 160,000 bytes지만, allocator overhead와 RSS는 별도 측정해야 한다.
- **수치 불확실성:** object layout은 implementation과 ABI에 의존한다. 이슈에 적힌 예상, 한 Linux GCC 측정, Clang/MSVC 및 32-bit 결과가 서로 다를 수 있으므로 단일 수치를 모든 platform의 계약처럼 쓰면 안 된다.
- **성능 판단:** 더 작은 object가 cache density를 높일 수 있지만 hot field가 멀어지거나 접근 순서가 나빠지면 이점이 상쇄될 수 있다. size 감소만으로 frame-time 개선을 확정할 수 없다.
- **ABI 판단:** 두 타입은 GL backend 내부 구현에 있지만 private header라도 external consumer가 비공식으로 포함할 가능성은 완전히 배제할 수 없다. public ABI 변경은 아니라고 보되 release note가 필요한지 maintainer 기준을 확인할 가치가 있다.
- **구현 판단:** `#pragma pack`이나 packed attribute로 padding을 강제 제거하는 것은 unaligned access와 platform portability 위험을 만든다. 자연 alignment를 유지한 member 재배치가 우선이다.
- **범위 판단:** 첫 PR은 이슈가 지목한 두 구조체와 측정 결과로 한정해야 한다. `-Wpadded` 결과를 보고 repository 전체 구조체를 한꺼번에 재배치하면 review와 회귀 범위가 불필요하게 커진다.

## 구현 방향

1. 변경 전 GCC, Clang, 가능하면 MSVC의 32/64-bit target에서 `sizeof`, `alignof`, 각 member의 `offsetof`를 출력한다. compiler version과 build flags도 결과에 기록한다.
2. `GlShape`에서는 pointer/geometry/container처럼 큰 alignment member, 4-byte texture metadata, 1·2-byte enum/flag/bool을 자연 alignment에 맞게 묶되 함께 자주 읽는 texture field의 locality도 유지한다.
3. `GlSolidBatch`에서는 pointer와 bounds, 4-byte color/depth/flag, 2-byte stamp, bool 순으로 후보를 만들고 current hot path의 접근 묶음과 비교한다.
4. 동일 diagnostic을 변경 후 실행해 target별 delta를 표로 남긴다. 모든 platform에 하나의 절대 size를 강제하는 unconditional `static_assert(sizeof(...) == N)`은 피한다.
5. 대표적으로 1,000개와 10,000개의 shape/image render data를 유지하는 scene에서 allocation count, payload 추정치, process RSS와 frame time을 전후 비교한다.
6. GL draw, image, fill, effect, clipping, solid batching test를 실제 GL-enabled target에서 실행하고 sanitizer build도 확인한다.
7. 첫 변경에는 타입 축소, bit-field, packing attribute를 섞지 않는다. member reorder만으로 효과와 위험을 분리한 뒤 추가 최적화는 별도 근거와 PR로 다룬다.

## 초심자 시작 가이드

1. 두 header를 포함하는 작은 diagnostic executable을 만들고 `sizeof`, `alignof`, `offsetof`를 출력한다. 결과에 compiler와 architecture를 함께 적는다.
2. `RenderUpdateFlag`, `ColorSpace`, `FilterMethod`의 underlying type을 선언부에서 확인하고 `sizeof(enum)`을 추측하지 않는다.
3. 종이에 각 member의 size/alignment와 current offset을 표로 만들고 alignment boundary 때문에 비는 구간을 표시한다.
4. header에서 member 순서만 바꾼 후보를 만든 뒤 diagnostic을 다시 실행한다. packed attribute나 type 변경은 하지 않는다.
5. `GlShape{...}`, `GlSolidBatch{...}`, `memcpy`, `offsetof`, serialization 사용을 전체 source에서 검색해 순서 의존 코드가 없는지 확인한다.
6. 10,000개 object의 `sizeof` 합계뿐 아니라 실제 process RSS를 측정해 allocator가 절감을 반영하는지 비교한다.
7. GL test가 skip되지 않았는지 Meson configure와 test log를 확인하고, solid batching을 포함한 대표 scene의 render 결과를 비교한다.

## 위험/검증

- GCC와 Clang의 x86_64, 가능한 32-bit 및 MSVC에서 전후 `sizeof`/`alignof`/offset을 기록한다.
- debug/release와 sanitizer build에서 layout 결과와 compile warning을 확인한다.
- `-Wpadded`를 진단용으로 사용하되 third-party나 의도된 padding까지 warning-as-error 범위에 무조건 넣지 않는다.
- positional aggregate initialization, raw memory copy, serialization, reflection, debugger script, `offsetof` 의존을 전체 tree에서 다시 검색한다.
- `GlShape` 생성·재사용·삭제 경로에서 모든 member가 이전과 같은 값으로 초기화되는지 검사한다.
- image와 shape, texture filter/color space/flip, clip stack, fill/stroke, effect 경로의 GL regression test를 실행한다.
- solid batch의 promote/flush/clear 경로와 batch 경계, depth, color/flag 상태가 보존되는지 확인한다.
- GL dependency가 없어 관련 test가 제외된 build는 renderer 회귀 검증 완료로 계산하지 않는다.
- 대표 scene의 live `GlShape` 수, allocation payload, RSS와 frame time을 전후 측정한다.
- member size 감소가 없는 target에서는 source churn을 정당화할 다른 cache/performance 근거가 있는지 확인한다.
- public header나 exported ABI에는 영향이 없는지 release build의 symbol/API 검사로 확인한다.
