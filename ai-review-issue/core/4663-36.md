## 이슈 요약

15×15 SVG 안에 두 개의 닫힌 path가 있다. 파란 path는 `h`와 `v`만 사용해 좌표 2.5, 4.5, 6, 10.5를 잇는 축 정렬 사각형을 만든다. 빨간 path는 비슷한 수평·수직 선분을 가지지만 마지막 닫힘 선분이 대각선이다. 제보자는 최신 viewer의 Software backend와 PNG export에서 파란 path의 fractional 경계가 antialias되지 않고, 빨간 path는 antialias된다고 보고했다.

사용자가 보는 차이는 SVG command 자체보다 두 outline이 software renderer에서 서로 다른 경로를 선택하는 데서 생긴다. 파란 outline은 axis-aligned rectangle fast path에 들어가 정수 pixel rectangle으로 그려지고, 대각선이 있는 빨간 outline은 일반 RLE coverage rasterizer를 통과한다. 따라서 수정 대상은 SVG의 `h`/`v` parser가 아니라 SW renderer의 fast path 정확성 조건이다.

제보자는 SVG `rect`도 같은 현상을 낼 가능성을 언급했지만 latest viewer에서 직접 확인하지는 않았다고 명시했다. current main 구조상 `appendRect()`도 같은 axis-aligned outline 판정을 받을 수 있으므로 가능성은 높지만, 구현 전 별도 재현으로 확정해야 한다.

## main 코드 조사

SVG path parser는 command마다 필요한 숫자 개수를 정하고 [`H`/`h`, `V`/`v`에 각각 숫자 하나를 요구한다](https://github.com/thorvg/thorvg/blob/1b62e79f3dcd9d41417ee32ad1f38f5ef99ed7ac/src/loaders/svg/tvgSvgPath.cpp#L176-L217). [`_processCommand()`](https://github.com/thorvg/thorvg/blob/1b62e79f3dcd9d41417ee32ad1f38f5ef99ed7ac/src/loaders/svg/tvgSvgPath.cpp#L221-L330)는 상대 command의 좌표를 현재 점에 더한 뒤, `H`는 `{x, current.y}`, `V`는 `{current.x, y}`를 `lineTo()`로 내보내고 `Z`는 path를 닫는다. 두 path 모두 이 단계에서는 평범한 직선 segment outline이며 parser가 H/V 선분의 antialias 속성을 별도로 저장하지 않는다.

SW shape 생성부의 [`_axisAlignedRect()`](https://github.com/thorvg/thorvg/blob/1b62e79f3dcd9d41417ee32ad1f38f5ef99ed7ac/src/renderer/cpu_engine/tvgSwShape.cpp#L329-L346)는 다섯 점의 닫힌 non-cubic outline이 축 정렬 사각형 형태인지 검사한다. 함수 첫 줄에는 fractional part가 있으면 `false`를 반환해 rectangle 이동을 더 부드럽게 만들 수 있다는 TODO가 있지만, 실제 조건은 좌표의 소수부를 검사하지 않는다. 따라서 2.5와 4.5 같은 fractional 경계를 가진 파란 outline도 `true`가 된다. 빨간 outline은 마지막 점과 시작점을 잇는 변이 대각선이라 같은 판정을 통과하지 못한다.

[`shapeGenRle()`](https://github.com/thorvg/thorvg/blob/1b62e79f3dcd9d41417ee32ad1f38f5ef99ed7ac/src/renderer/cpu_engine/tvgSwShape.cpp#L419-L440)는 outline을 transform한 다음 composite가 아니고 `_axisAlignedRect(outline)`가 참이면 `shape.fastTrack`을 켠다. 이어서 fast-track 방식의 bbox를 계산하고, fast-track이면 `rleRender()`를 호출하지 않고 즉시 반환한다. 즉 renderer의 antialias 설정이 활성화되어 있어도 이 분기에서는 coverage outline 자체가 생성되지 않는다.

좌표 export와 bbox 계산은 [`tvgSwUtil.cpp`](https://github.com/thorvg/thorvg/blob/1b62e79f3dcd9d41417ee32ad1f38f5ef99ed7ac/src/renderer/cpu_engine/tvgSwUtil.cpp#L30-L57)에 있다. transform 결과를 64배한 26.6 fixed-point 정수로 저장하고, 일반 경로는 최소값을 내림·최대값을 올림하지만 fast-track은 양 끝을 가장 가까운 정수 pixel로 반올림한다. 재현 입력의 파란 bbox `(2.5, 4.5)–(6, 10.5)`는 이 과정에서 subpixel coverage 정보가 없는 정수 rectangle이 된다.

실제 raster 단계도 두 경로가 다르다. [`_rasterRect()`](https://github.com/thorvg/thorvg/blob/1b62e79f3dcd9d41417ee32ad1f38f5ef99ed7ac/src/renderer/cpu_engine/tvgSwRaster.cpp#L451-L485)는 bbox의 전체 pixel span을 paint alpha로 채우며 경계별 coverage를 계산하지 않는다. [`rasterShape()`](https://github.com/thorvg/thorvg/blob/1b62e79f3dcd9d41417ee32ad1f38f5ef99ed7ac/src/renderer/cpu_engine/tvgSwRaster.cpp#L1737-L1746)는 `fastTrack`이면 이 rectangle 함수를, 아니면 RLE span 함수를 선택한다.

반대로 일반 SW RLE의 [`_horizLine()`](https://github.com/thorvg/thorvg/blob/1b62e79f3dcd9d41417ee32ad1f38f5ef99ed7ac/src/renderer/cpu_engine/tvgSwRle.cpp#L314-L367)은 누적 area를 0–255 coverage로 변환하고 antialias가 꺼진 경우에만 coverage를 255로 강제한다. [`_lineTo()`](https://github.com/thorvg/thorvg/blob/1b62e79f3dcd9d41417ee32ad1f38f5ef99ed7ac/src/renderer/cpu_engine/tvgSwRle.cpp#L494-L607)는 수평·수직·일반 edge를 모두 scanline area에 반영한다. 그러므로 H/V 선분을 antialias할 기능이 없는 것이 아니라, 파란 outline만 그 기능을 우회하는 상황이다.

[`SwRenderer::prepare()`의 shape 경로](https://github.com/thorvg/thorvg/blob/1b62e79f3dcd9d41417ee32ad1f38f5ef99ed7ac/src/renderer/cpu_engine/tvgSwRenderer.cpp#L103-L153)는 renderer의 AA 값을 `shapeGenRle()`에 전달한다. stroke가 없는 재현 path에서도 AA 값은 전달되지만, 앞선 fast-track 조기 반환 때문에 coverage render가 실행되지 않는다. 전역 AA 설정 문제로 해석하기 어려운 근거다.

현재 [`testSwEngine.cpp`](https://github.com/thorvg/thorvg/blob/1b62e79f3dcd9d41417ee32ad1f38f5ef99ed7ac/test/testSwEngine.cpp#L280-L334)는 integer rectangle, gradient와 mask를 포함한 render 성공 경로를 다룬다. 하지만 fractional axis-aligned rectangle의 경계 pixel alpha가 0과 255 사이인지 고정하는 전용 회귀 test는 이 구간에서 보이지 않는다. 단순히 `sync()` 성공만 확인하면 이번 시각적 차이는 잡히지 않으므로 buffer pixel을 직접 검사해야 한다.

## 원인 분석

### 확인된 사실

- SVG `h`와 `v`는 current parser에서 ordinary `lineTo()` segment가 되며 별도의 antialias flag를 잃는 경로는 없다.
- 파란 재현 path는 다섯 점의 axis-aligned rectangle 조건을 만족하고, 빨간 path는 닫힘 변이 대각선이라 만족하지 않는다.
- `_axisAlignedRect()`에는 fractional 좌표를 배제할 수 있다는 TODO가 있지만 현재 구현은 소수부를 검사하지 않는다.
- fast-track shape는 bbox를 정수 pixel 경계로 반올림한 뒤 RLE coverage 생성을 건너뛴다.
- rectangle raster 함수는 edge coverage 없이 bbox span을 채우고, 일반 RLE 함수는 수평·수직 edge도 coverage로 변환한다.
- renderer의 AA 값은 shape 생성 함수에 전달된다. 이번 차이는 AA가 전역으로 꺼졌기 때문이 아니라 fast-track이 해당 값을 활용하는 RLE 경로를 우회하기 때문이다.
- existing SW engine test에는 이 재현처럼 fractional rectangle의 edge alpha를 명시적으로 검사하는 항목이 보이지 않는다.

### 추론과 판단

- **근본 원인:** fractional transform 결과도 integer-aligned rectangle과 동일한 fast-track 전제에 넣은 것이 핵심이다. geometric axis alignment와 pixel alignment는 서로 다른 조건인데 current code는 전자만 확인한다.
- **범위 판단:** 이는 SVG 전용 문제라기보다 SW engine의 공통 outline 최적화 문제다. `Shape::appendRect()` 또는 다른 loader가 동일한 transform 후 outline을 만들면 같은 결과가 예상된다. 다만 각 API의 실제 재현은 test로 확정해야 한다.
- **최소 수정:** antialias가 켜졌을 때 transform 후 outline의 모든 rectangle 경계가 정수 pixel에 정렬된 경우에만 fast-track을 허용하고, 하나라도 fractional이면 기존 RLE 경로로 fallback하는 방식이 가장 작고 안전하다.
- **AA 비활성 모드:** 사용자가 aliased rendering을 명시한 경우 current rectangle fast path를 유지할 수 있다. 조건은 개념적으로 `!antiAlias || pixelAligned(outline)`을 axis-aligned 판정에 더하는 형태가 된다.
- **transform 위치:** source path 좌표가 아니라 `utilOutlineGen()` 이후 renderer가 실제로 사용할 26.6 좌표에서 정렬을 판단해야 한다. integer source도 scale·translate 결과가 fractional일 수 있고 그 반대도 가능하다.
- **음수 좌표:** fixed-point 값의 fractional 여부는 음수에서도 올바른 방법으로 검사해야 한다. `coord % 64 != 0`처럼 의미가 분명한 판정이 안전하며, signed representation에 대한 암묵적 bit-mask 가정은 피하는 편이 좋다.
- **대안 판단:** bbox의 `round()`만 `floor()`/`ceil()`로 바꾸어도 partial alpha를 표현할 수 없으므로 antialias 문제는 해결되지 않는다. 정확성 수정은 RLE fallback 또는 coverage-aware rectangle fast path가 필요하다.
- **성능 판단:** 장기적으로 네 edge coverage를 직접 계산하는 fractional rectangle fast path를 추가할 수 있지만, 첫 수정에서는 기존 검증된 RLE 경로를 재사용하고 실제 asset 성능 저하를 측정하는 편이 review 범위를 작게 유지한다.

## 구현 방향

1. axis-aligned rectangle 판정과 pixel-aligned 판정을 분리한다. 전자는 기존 다섯 점/edge 구조를 확인하고, 후자는 transform 후 26.6 좌표가 64의 배수인지 확인한다.
2. `shape.fastTrack`은 composite가 아니며 axis-aligned이고, AA가 꺼져 있거나 모든 경계가 pixel-aligned일 때만 켠다. AA가 켜진 fractional rectangle은 `rleRender()`로 보내 coverage span을 생성한다.
3. 판정은 source SVG 숫자가 아닌 transformed outline에서 수행한다. translation, scale, negative coordinate와 viewport 변환을 같은 규칙으로 처리한다.
4. integer-aligned rectangle의 기존 fast path와 AA 비활성 fractional rectangle의 현재 aliased 결과를 보존하는 test를 먼저 둔다.
5. 이슈의 두 path를 작은 transparent buffer에 각각 render한다. 파란 rectangle의 fractional edge pixel alpha가 `0 < alpha < 255`, 내부가 255, 바깥이 0인지 확인하고 빨간 path와도 일관된 coverage를 비교한다.
6. 같은 좌표를 `Shape::appendRect()`로 만든 test를 추가해 SVG parser와 무관한 engine 계약을 고정한다. 필요하면 SVG load test는 integration regression으로 별도 추가한다.
7. pixel-aligned rectangle benchmark와 representative animation에서 fast-track hit 수와 frame time을 전후 비교한다. fractional rectangle만 fallback되는지 계측한다.

첫 PR은 rectangle fast-track 조건과 직접적인 SW pixel test만 포함하는 편이 좋다. 새로운 coverage-aware fast path나 다른 geometry 최적화는 측정 결과가 필요할 때 후속 작업으로 분리할 수 있다.

## 초심자 시작 가이드

1. 이슈 SVG를 15×15 transparent buffer에 Software backend로 render하고, x=2·3 및 y=4·5 부근 pixel의 RGBA를 출력해 현재 파란 edge가 0/255로만 나오는지 확인한다.
2. 파란 path를 `Shape::appendRect(2.5f, 4.5f, 3.5f, 6.0f)`로 바꾸어 같은 pixel을 비교한다. 같으면 SVG parser가 아닌 renderer 공통 문제라는 실행 근거가 된다.
3. `_axisAlignedRect()`와 `shapeGenRle()`에 임시 로그를 넣어 파란 path만 `fastTrack=true`, 빨간 path는 `false`인지 확인한다. 결과를 얻은 뒤 로그는 제거한다.
4. transformed outline의 26.6 좌표를 출력해 2.5가 160, 4.5가 288처럼 64의 배수가 아닌 값으로 저장되는지 확인한다.
5. fractional rectangle만 fast-track에서 제외하는 작은 조건을 추가하고 동일 pixel dump에서 edge alpha가 partial coverage로 바뀌는지 확인한다.
6. x/y를 정수로 바꾼 rectangle, AA off, 음수 fractional translation, 0.5 scale을 각각 test해 의도한 분기만 바뀌는지 확인한다.

처음부터 raster loop를 수정하기보다 fast-track 조건을 제한해 기존 RLE 결과를 기준값으로 삼으면 원인과 수정 효과를 더 쉽게 분리할 수 있다.

## 위험/검증

- 이슈의 파란 H/V path와 빨간 대각선-close path를 Software backend에서 render하고 경계 pixel alpha를 수치로 비교한다.
- 동일 geometry를 SVG `rect`와 public `Shape::appendRect()`로 만들어 같은 coverage를 얻는지 확인한다.
- 좌표가 모두 정수인 rectangle은 fast-track을 계속 사용하고 이전 pixel 결과와 성능을 보존하는지 확인한다.
- 0.25, 0.5, 0.75 fractional edge에서 expected coverage가 단조롭게 변하는지 검사한다.
- 음수 좌표와 viewport 밖에서 시작하는 rectangle의 fractional 판정·clipping이 올바른지 확인한다.
- integer source에 fractional translate/scale을 적용한 경우와 fractional source가 transform 후 integer가 되는 경우를 모두 검사한다.
- antialias 옵션을 끈 경우에는 fractional rectangle이 기존 aliased fast path 결과를 유지하는지 확인한다.
- solid color뿐 아니라 alpha color, linear/radial gradient와 texture fill에서 edge coverage가 paint alpha와 올바르게 합성되는지 확인한다.
- clip, mask와 composite가 있는 shape는 기존부터 fast-track 제한을 받으므로 수정 전후 분기와 결과가 바뀌지 않는지 확인한다.
- zero width/height, 매우 작은 rectangle, 반전된 path winding과 중복 점이 axis-aligned 판정을 잘못 통과하지 않는지 확인한다.
- SW renderer의 pixel regression suite, SVG loader test, sanitizer와 전체 build를 실행한다.
- representative asset에서 fast-track hit rate와 render time을 전후 측정해 fractional fallback의 성능 비용을 기록한다.
