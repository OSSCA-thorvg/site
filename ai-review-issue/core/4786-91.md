## 이슈 요약

큰 Gaussian blur를 원본 해상도에서 계산하면 pixel 수와 kernel 범위가 함께 커진다. 이슈는 입력을 절반 또는 1/4 해상도로 줄이고, 같은 시각적 blur 폭을 유지하도록 sigma를 축소한 뒤 결과를 다시 확대하는 방법을 제안한다. 낮은 `quality`에서는 더 큰 축소를 허용하고 높은 품질에서는 원본 해상도를 선호하되, 변환 후 sigma와 실제 처리 영역도 정책에 포함해야 한다.

제보된 CPU prototype은 303×280 입력에서 약 520ms를 241ms로 줄였다고 보고한다. 다만 이 수치는 특정 prototype과 입력의 단일 결과이며 current main의 보장 성능은 아니다. GPU는 작은 render target의 이득과 두 번의 resampling·추가 texture/pass 비용을 함께 측정해야 하므로 같은 비율을 가정할 수 없다.

## main 코드 조사

공개 effect 열거형은 [`GaussianBlur`의 네 번째 인자를 0~100 품질 값으로 설명](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/inc/thorvg.h#L268-L280)한다. 내부 [`RenderEffectGaussianBlur`](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/src/renderer/tvgRender.h#L507-L527)는 sigma, direction, border, quality만 저장한다. 해상도 scale이나 선택된 정책을 backend 사이에 전달하는 필드는 아직 없다.

CPU의 [`_gaussianInit()`](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/src/renderer/cpu_engine/tvgSwPostEffect.cpp#L107-L135)는 품질을 1~3회의 box-filter level로 바꾸고 각 kernel 반경을 계산한다. [`effectGaussianBlurUpdate()`](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/src/renderer/cpu_engine/tvgSwPostEffect.cpp#L155-L169)는 transform scale을 sigma의 variance에 반영하지만 해상도는 바꾸지 않는다. 실제 [`effectGaussianBlur()`](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/src/renderer/cpu_engine/tvgSwPostEffect.cpp#L171-L220)는 compositor bbox의 전체 폭·높이를 대상으로 수평 filter와 transpose 기반 수직 filter를 반복한다.

이슈 댓글이 가리키는 [CPU prototype commit](https://github.com/thorvg/thorvg/commit/961e808ee86c523954e8389d7fae37984f31a25f)은 variance 256/1024를 기준으로 2배/4배 downsample을 선택하고 reduced kernel, box average downsample, bilinear upsample을 추가했다. 또한 양방향 blur만 축소하고 기존 scratch surface에 두 reduced ping-pong image가 들어갈 때만 fast path를 사용한다. 그러나 이 commit의 변경은 분석한 current main의 `tvgSwPostEffect.cpp`에 존재하지 않는다.

GL은 [`GlEffect::update()`](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/src/renderer/gpu_engine/gl/tvgGlEffect.cpp#L36-L76)에서 quality를 1, 2, 3 pixel 간격의 sample step으로 바꾼다. [`GlEffect::render()`](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/src/renderer/gpu_engine/gl/tvgGlEffect.cpp#L78-L114)는 viewport 크기의 두 임시 render target을 받고 수평·수직 task를 만든다. GL [Gaussian shader](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/src/renderer/gpu_engine/gl/tvgGlShaderSrc.cpp#L1065-L1163)는 그 간격으로 tap 수를 줄이지만 texture 자체는 원본 해상도다.

WebGPU의 [`WgShaderTypeEffectParams::update()`](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/src/renderer/gpu_engine/wg/tvgWgShaderTypes.cpp#L198-L209)는 sigma, transform scale과 kernel 범위만 uniform에 기록하며 `quality`를 읽지 않는다. [WebGPU Gaussian shader](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/src/renderer/gpu_engine/wg/tvgWgShaderSrc.cpp#L889-L934)는 반경 내 모든 integer tap을 돈다. [`WgCompositor::gaussianBlur()`](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/src/renderer/gpu_engine/wg/tvgWgCompositor.cpp#L942-L990)도 전체 target을 복사한 뒤 같은 크기의 임시 target과 destination 사이에서 pass를 실행한다.

기존 GL과 WebGPU scene-effect test는 각각 [세 direction에서 draw/sync 성공](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/test/testGlEngine.cpp#L381-L425), [같은 호출 성공](https://github.com/thorvg/thorvg/blob/03aabc1157b208ca3d3b2358686560026afce9fc/test/testWgEngine.cpp#L380-L424)을 확인한다. 품질별 pixel 오차, 선택된 target 크기나 pass 비용을 검증하지 않으므로 adaptive resolution의 시각·성능 회귀를 잡는 기준은 새로 만들어야 한다.

## 원인 분석

### 확인된 사실

- current API에는 0~100 quality 값이 있지만 backend 공통의 해상도 축소율 계약은 없다.
- CPU quality는 box-filter 반복 횟수, GL quality는 sample tap 간격에 사용된다.
- 분석한 WebGPU blur update와 shader는 quality 값을 사용하지 않는다.
- 세 backend 모두 current main에서는 blur 대상의 원본 해상도를 유지한다.
- CPU prototype은 2배/4배 축소 경로와 확대를 구현했지만 current main에는 들어 있지 않다.
- 기존 engine test는 blur 호출의 성공만 확인하고 품질별 이미지 또는 성능을 고정하지 않는다.

### 추론과 판단

- **이 이슈는 결함의 단일 근본 원인보다 최적화 정책 부재에 가깝다.** 현재 quality가 backend별로 다른 연산량 knob이므로 `quality=50이면 half resolution` 같은 규칙을 바로 추가하면 기존 의미와 시각 결과가 backend마다 다르게 바뀔 수 있다.
- **처리 pixel 수 감소가 핵심 이득 후보다.** 큰 sigma에서 tap 간격만 늘리는 GL보다 작은 texture에서 같은 pass를 수행하면 shader invocation과 memory bandwidth가 줄 수 있다. 다만 resample pass와 texture allocation 비용 때문에 작은 영역이나 작은 sigma에서는 손해일 수 있다.
- **sigma는 device space와 축소 space를 구분해야 한다.** transform을 반영한 device-space sigma를 축소율로 나눈 값으로 reduced kernel을 만들되, 외곽 확장 영역은 최종 해상도에서 원래 blur support를 덮어야 잘림이 없다.
- **prototype threshold는 출발점이지 계약이 아니다.** variance 256/1024와 양방향 전용 조건은 보고된 CPU 실험의 heuristic이다. quality, bbox 면적, 방향, scratch capacity와 backend 비용 모델을 포함한 측정으로 재선정해야 한다.
- **drop shadow 공유 여부는 명시적으로 결정해야 한다.** CPU drop shadow가 Gaussian helper 구조를 상속하고 GPU도 같은 blur shader를 사용하므로 내부 공통화를 잘못하면 공개 Gaussian blur만 바꾸려다 shadow 결과까지 달라질 수 있다.

## 구현 방향

1. 우선 benchmark corpus를 만든다. 작은/큰 bbox, sigma 1~128, quality 1/25/50/75/100, 1x·비균등 transform, 투명 가장자리와 wrap/duplicate border를 조합하고 세 backend에서 시간·메모리·이미지 오차를 기록한다.
2. `full`, `half`, `quarter`를 고르는 순수 policy 함수를 정의한다. 최소 조건으로 quality, transformed sigma, bbox 폭·높이, 예상 kernel work를 입력받고 작은 작업은 항상 full로 유지한다.
3. CPU에서는 prototype처럼 reduced ping-pong buffer를 사용하되 홀수 크기, 1-pixel 축, horizontal/vertical-only, scratch 용량 부족 시 원본 경로 fallback을 test로 고정한다. 기존 surface 내부를 분할한다면 offset·stride 겹침을 산술적으로 검증한다.
4. GL과 WebGPU에는 축소 크기의 render target을 pool에서 요청하는 API와 downsample/upsample pass를 추가한다. linear sampler의 좌표·edge 처리와 premultiplied alpha를 두 backend에서 같은 reference 결과로 맞춘다.
5. reduced sigma와 kernel radius를 uniform에 전달하고, 최종 `extend`/scissor는 full-resolution support를 유지한다. direction 한 축만 흐리게 할 때 다른 축의 resampling까지 화질을 떨어뜨릴지 또는 full path를 쓸지 정책으로 명시한다.
6. 기존 quality의 tap/level 의미와 resolution 의미를 한 번에 중첩해 지나치게 품질을 낮추지 않는다. 호환성을 위해 처음에는 높은 quality는 full, 낮은 quality의 큰 blur만 축소하도록 보수적으로 gate한다.
7. CPU prototype을 독립적인 검증 자료로 사용하되 그대로 cherry-pick하기보다 current main의 buffer 계약과 세 backend 공통 policy에 맞춰 나눈다.

첫 PR은 policy와 CPU half-resolution fast path, reference-image/benchmark 기반을 묶고, GPU target-pool 변경은 backend별 후속 PR로 분리하는 편이 검토 가능성이 높다.

## 위험/검증

- quality 100은 기존 full-resolution 결과와 같거나 합의된 매우 작은 오차 안인지 확인한다.
- quality 경계값 0, 1, 33, 34, 50, 66, 67, 100에서 축소율·tap 정책이 급격한 깜박임을 만들지 확인한다.
- sigma 0, subpixel sigma, 매우 큰 sigma와 transform scale 0.01~100에서 NaN, 0 크기 target, 과도한 allocation이 없는지 확인한다.
- 1×N, N×1, 홀수 폭·높이, viewport에 잘린 bbox와 화면 밖 effect에서 down/up sample 좌표를 검증한다.
- `direction` 0/1/2 및 `border` duplicate/wrap의 가장자리 pixel을 reference 구현과 비교한다.
- 반투명 색과 premultiplied/non-premultiplied surface에서 dark halo나 color bleed가 생기지 않는지 확인한다.
- clip, alpha/luma mask, nested scene, partial update와 blur가 겹칠 때 확장 영역이 잘리지 않는지 확인한다.
- GL/WebGPU target pool이 축소 texture를 크기별로 재사용하고 frame 간 누수·stale content가 없는지 GPU validation과 sanitizer로 확인한다.
- CPU는 reduced buffers 두 개가 scratch allocation을 넘지 않으며 source/destination과 겹쳐 읽기 전 데이터를 덮지 않는지 ASan/UBSan으로 검증한다.
- 대표 CPU와 discrete/integrated GPU에서 cold/warm frame, allocation 포함/제외 시간을 나누어 측정한다.
- SSIM/최대 채널 오차와 edge profile을 함께 기록해 성능 개선이 큰 blur의 허용 가능한 화질 저하인지 판단한다.
- adaptive path가 손해인 작은 작업은 full path로 돌아가는지 threshold 전후 benchmark로 확인한다.
